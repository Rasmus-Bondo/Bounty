Implementing the **RP (Rank Points)** design from `ranked_system_rp_design.md` — strictly additive, floored at 0, no punishment — chosen over the Elo alternative (archived 2026-07-26 to `depricated/superseded-md-2026-07-26/ranked_system_design.md`). Decided 2026-07-03: **numeric-only first (no tiers yet)**, **Redwater side first, then Bounty**.

**Redwater side — DONE & verified (compiles; RP math matches doc's worked examples):**
- `game.ServerScriptService.PlayerServices.RankedService` (new ModuleScript, 119 lines). `computeRoundRP(stats, placement, totalPlayers)` is pure/testable; `awardRound(player, stats, placement, totalPlayers)` adds RP to profile `RankPoints`, sets a `RankPoints` player attribute, returns `{gained, total}`, and mirrors the new total to a global OrderedDataStore **`RankPoints_v1`** (write skipped when 0 gained; pcall/task.spawn guarded).
- Weights (**trimmed ~33% on 2026-07-29** — players were climbing too fast; was kill 3 / placement {15,10,6} / top-half 3 / streakPer 2): kill 2 / assist 1 / headshot 1 / placement {1st 10, 2nd 7, 3rd 4, top-half 2} / streak `max(0,best-2)*1`. A strong round now pays ~62 RP, was ~93; round cycle is ~6.5 min (`Config.ROUND_TIME = 360`) so ~9.5 rounds/hr.
- **`MinPlayersForPlacement` was DELETED 2026-07-29** — placement now pays at every lobby size, by design. It was already dead code (`RoundController` passes `totalPlayers = #stats`, which **includes bot entries**, and `BotConfig.MinBots = 4` is a hard floor, so `#stats` never dropped below 5). Removing it was a runtime no-op *except* with `BotConfig.Enabled = false`, where a 1-2 player lobby now gets the bonus it used to be denied. Rationale: the bot floor means there is always a field to place against, so players should always earn. Don't reintroduce a minimum-player gate — it was removed deliberately, not overlooked.
- **Bot kills pay the same as player kills.** Nothing in the stats pipeline records whether a victim was a bot (no `isBot` outside `buildPostGameStats`'s sort), so devaluing them is a stats-pipeline change, not a weights edit. Also left alone 2026-07-29.
- `DataService` profile template gained `RankPoints = 0` (backfilled via existing `:Reconcile()`).
- `RoundController.buildPostGameStats()` awards once per player after its kill-sort (sorted index = placement), attaching `rankPointsEarned`/`rankPointsTotal` to each `VictoryShowcase` payload entry. Bots are excluded automatically (not `Players`).
- **Post-game display DONE:** the stat card's `StatFrame` is a name-sorted vertical `UIGridLayout` (full-width cells, 10% tall — really 8 stacked rows, not a 4×2 grid). Added a transparent `9GapSpacer` row + a `9RankPointsFrame` row (clone of `8AccuracyFrame`, label "RANK POINTS") in `StarterGui.VictoryShowcase.Canvas.MatchResultFrame.InnerFrame.StatFrame`. `VictoryShowcaseClient` sets it via `setExactStatFrameNumber(statFrame, "9RankPointsFrame", "+<earned>")`. Gap is one full row (~31px); to make it smaller the RP row would need to move out of the grid (grid `CellPadding` is uniform). All 8 tiles share one generic icon, so the clone matches. **Screenshot-verified 2026-08-01** (superseding the old "can't be screenshotted" note): clone the ScreenGui into `CoreGui` and `capture_screenshot` — see [[feedback_ui_screenshot_verify]]. The RANK POINTS row renders correctly and is not clipped on a small phone (Galaxy A06, landscape), despite being the 10th of exactly 10 grid cells (10 × 0.1 scale = 1.0, zero padding) flush against the bottom edge.

**Seasons / resets — BUILT 2026-07-31.** First reset **2026-07-31 19:00 CEST = 17:00 UTC = epoch `1785517200`** (season 2). Second reset scheduled 2026-08-13 for **2026-08-14 20:00 CEST = 18:00 UTC = epoch `1786730400`** (season 3 → `RankPoints_v3`); boundary rollover verified to the second by shimming `os.time` over the live source. **This one does NOT share the battle-pass boundary** — `BattlePassConfig.SEASON_START` stays on the Jul-31 instant and that pass season runs to Aug 21 17:00 UTC, so ranked and the pass are deliberately decoupled from season 3 onward (user's call, asked and answered).
- **RP cannot be bulk-zeroed, and this is the reason for the whole design.** ProfileService keys are not enumerable, so offline players are unreachable; an OrderedDataStore has no clear-all. So: the season number doubles as the store suffix, and each profile fixes itself lazily.
- `GameEnvironment` (mirrored, already on the 16-module gate list — deliberately reused instead of adding a 17th mirror) gained `RANK_SEASONS = {0, 1785517200, 1786730400}` + `getRankSeason()` + `getRankStoreName(season)`. Season 1 resolves to `RankPoints_v1`, the pre-existing store, so the scheme is backwards compatible and season 1 data never moves. Next reset = append one epoch + republish both places.
- Read live from `os.time()` per call, never cached at require time, so a server running across the boundary rolls over by itself. **No republish or restart is needed at the boundary** — publish early, then Shut Down All Servers so no pre-publish server survives.
- `RankedService.ensureSeason(player, data, season)` archives `RankPoints` into `LastSeasonRankPoints`, zeroes it, stamps `RankSeason`. Called from `awardRound` ONLY — `data.RankPoints` has exactly one reader across both places, so a stale value cannot leak, and this avoids a DataService→RankedService circular require. `awardRound` resolves the season once for both the reset and the store handle.
- **`RankSeason` defaults to 1 in the template and must stay 1.** `:Reconcile()` backfills the template value into existing profiles, so `0` would mismatch the live season at publish time and wipe everyone's RP hours early. This was the one real trap; a 5-case `ensureSeason` test covers it plus idempotence (must not re-wipe RP earned after the boundary).
- Not mirrored into Bounty's profile template — that place has never carried `RankPoints`. Harmless: `:Reconcile()` only ADDS, so a lobby-first profile picks the fields up on its first Redwater session.
- `RankLeaderboardService` flushes its row caches on rollover, checked on **every** request — a cache HIT is what would otherwise serve the old top 100 for 30s past the reset.
- **Reversible**, unusually for a data change: `RankPoints_v1` is never written to or deleted and each zeroed profile keeps its old total, so deleting the season row restores the old board. Note [[project_studio_live_datastore]] — a Studio playtest past the boundary zeroes the dev profile's RP for real.

**AUDITED & CLOSED 2026-08-01 — the system works; small totals are intended.** Launch issue #2 ("RP not awarded at match end") was investigated end-to-end and closed **WONTFIX, no code changed**. Don't re-open it or "fix" the numbers in a later pass.
- Verified live: `RoundController.buildPostGameStats` L1234-1236 awards once per entry in placement order, at the buzzer (L1464, same block as the Cash/XP flush, before `startVictoryShowcase`); both loops iterate `Players:GetPlayers()`; `safeAwardRank` L292 guards nil player / missing fn / pcall; bot ids are negative (`BotService.NextId = -100001`) so `GetPlayerByUserId` returns nil rather than throwing; `DataService.getPlayerData` returns live `profile.Data` so writes persist; `GameEnvironment` is byte-identical across both places (6134 bytes) and both resolve season 2 → `RankPoints_v2`.
- **The runtime round-trip is confirmed by the live board itself** — `writeLeaderboard` is skipped when `gained == 0`, so a player cannot appear at all unless awards and the OrderedDataStore write are landing. Entries exist. This retires the old "unverified" caveat; no playtest was needed.
- **A leaderboard total of exactly 1 is diagnostic, not a bug.** Brute-forced the reachable set: every way to score exactly 1 has `placement >= 6`, i.e. placement bonus 0. Since `kills*2` is even, a streak bonus needs >= 3 kills, and the minimum nonzero placement bonus is 2 — a total of 1 means 0 kills, bottom-half finish, one assist or one non-lethal headshot. It proves that player has **never** finished top-half.
- **Placement is scored against a bot-padded field, deliberately.** `totalPlayers = #stats` counts bots; bots fill `clamp(10 - humans, 4, 8)`, so the field is 9-14 and a human must finish <= ceil(n/2) (about <= 5) to get anything beyond kills/assists. At 1-2 humans vs 8 bots a weak player realistically earns ~0 placement RP. Four fixes were offered (smooth placement curve, humans-only ranking, participation floor, weight rebalance) and **all were declined** — RP is a skill score and a bad round paying ~0 is the intended shape. Consistent with the two earlier deliberate calls above (`MinPlayersForPlacement` deleted on purpose; bot kills pay full value).
- Season 2 began 2026-07-31 17:00 UTC, so around launch every profile zeroed on its first award and the board started empty on `RankPoints_v2` — expect genuinely small totals in the first days regardless.
- Leaderboard hides on non-Home tabs: `RankLeaderboardClient` hooks the bottom-menu tab buttons (`CanvasBottom.Frame.*.Button`) and toggles the ScreenGui `Enabled` (Home = on, others = off). The "RANK POINTS" subheader was removed at the user's request (header sits directly above the rows now).
