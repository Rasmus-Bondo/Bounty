Mobile auto-fire shipped into both places' data models on 2026-08-07 (unpublished; the release is marked data-affecting). `MOBILE_AUTOFIRE_GUIDE.md` in the project root is the full spec and was implemented end to end. Touch players fire by holding the crosshair on an enemy; the FIRE button is unchanged.

Key facts a later session needs:

- **Lock source:** `AimAssistController:GetLock()` — tolerance `clamp(atan(LockRadiusStuds/distance), MinLockAngleDeg, MaxLockAngleDeg)` measured from the target's **HumanoidRootPart**, computed against rendered geometry (bot visuals, not server rigs). NEVER re-derive the lock with a raycast (oversized `BotAssistHitbox` + `RewindHitboxes` phantoms).
- **THE SIZING RULE: match each hunter's own server hit registration, per hunter.** Reworked 2026-08-07 after the user reported auto-fire "only sometimes" firing when hovering an enemy. The original rule was the inverse — keep `LockRadiusStuds` *below* every hunter's forgiveness radius so a lock reliably became a hit — which forced one shared 1.6 at the smallest common denominator and made auto-fire **decline shots the server would have scored** (revolver forgives 3.5, lock demanded 1.6: roughly a fifth of the area where a shot actually lands). Values: Dust/Vesper 3.5 (`HitForgiveness.Radius`), Fortuna 2.4 (`CardsConfig.LagCompensation.PartRadii.HumanoidRootPart` — she has no `RevolverHitForgiveness`, so 3.5 would throw cards that cannot land), Bram 2.0 (`SpherecastRadius`) **floored at 7.6 deg** (`ConeHalfAngleDegrees`) because his body damage is a fixed cone, not a sphere — he was by far the worst served, auto-firing inside 1.5 deg while damaging everything inside 7.6. Do not restore a single global value. A 3.5 sphere at the root spans a whole R15 (head top +2.19, feet -3.00), which is why head/leg hovering locks with no body-shaped test.
- **The config knob was inert for 3 of 4 hunters.** `FPSRevolverClient`, `HunterFirstPersonClient`, `GrudgekeeperClient` and `CardsClient` never passed `LockRadiusStuds`/`MaxLockAngleDeg` into the constructor, so they ran module defaults that happened to equal the config values — editing `RevolverConfig.AimAssist` moved Vesper only, invisibly. Fixed 2026-08-07; if you add a hunter, pass the lock keys explicitly.
- **Eligibility split:** `_canAcquire` (touch + hunter gate) vs `_canRotate` (`+ Enabled`). `Enabled=false` kills magnetism only — acquisition and the lock report keep running. This is why [[mobile-aim-assist-design]]'s magnetism being disabled does not affect auto-fire, and why Vesper's `SunspikeClient` can run a second rotation-disabled instance as her lock source (her magnetism instance lives in `HunterFirstPersonClient`; the lock ticks in `BindToRenderStep("VesperAutoFire", Camera+2)`).
- **Per-hunter gates:** Dust `isUsingHighNoon` (calls `shoot()` directly, never the `FireRequested` bindable — HighNoonClient owns it); Vesper scoped shots wait for the Deadeye ramp (`S.ScopedSince`, stamped in the ScopeChanged handler); Bram `S.IsBreachCharging`; Fortuna `useBasic()` directly at a 0.05s poll — NEVER `startBasicHold()` (the hold state machine belongs to the FIRE button).
- **Range cap:** optional `MaxLockDistance` config (2026-08-07) — a lock farther than it reads as no lock. Bram: `GrudgekeeperConfig.Basic.AutoFireMaxDistance = 60` (= his blast's MaxRange, so only zero-damage shots are blocked; user raised it from 50 same day — don't lower it back without asking). Fortuna: `CardsConfig.Basic.Range` (card raycast hard-capped there; CardsClient gained a real require of CardsConfig for this one key — the cap tracks the config, 150 since the 2026-08-07 range buff; `Basic.Speed` must rescale with Range so Range/Speed stays under `Visual.MinFlyDuration` 0.08 — 2100 at 150). Dust and Vesper are deliberately uncapped — within the 200-stud lock ceiling Dust always deals his 20/40 falloff floor and Vesper's falloff starts at 240, so neither wastes ammo.
- **Settings:** `AutoFireEnabled` (default true) in both places' `PlayerSettingsService` whitelists + Redwater's profile template; UI row `AutoFireRow` under `INPUTHeader` in both `ReworkedSettingsGui`s, touch-only visible. Clients read the `AutoFireEnabled` player attribute; **absent must mean ON** (the attribute only exists after the settings payload lands).
- **No lock indicator:** the crosshair lock ring was built and removed the same day at the user's request. `OnLockChanged` still publishes an `AutoFireLocked` player attribute that nothing consumes — it is the hook if lock feedback returns (watch it from `HitMarkScript`, single-writer rule).
- **Reliability fixes shipped alongside the resizing (2026-08-07):** target-identity hysteresis is now built (`LockStickyScale = 1.25` — an already-locked model keeps a wider tolerance so a boundary hover stops chattering), and `_acquireTarget` walks the **three** nearest candidates on LOS failure instead of testing only the best. The old single-candidate test meant an enemy behind a post suppressed the lock on a second enemy standing in the clear — a large part of the "only sometimes" complaint, separate from the tolerance being too tight.
- **`MaxRange` is an ACQUISITION cut-off, not a preference.** It was 200 while Vesper's `Basic.Range` is 500 and her falloff only ends at 300 — so mobile Vespers had *no auto-fire whatsoever* past 200 studs, however well aimed, which is the band she is built to fight in. Found by playtest 2026-08-07 ("300+ studs it doesn't trigger at all"); raised to **350** = the server's `HitForgiveness.MaxDistance`. Per-hunter distance caps still ride on top via `MaxLockDistance`. Check this first whenever a hunter "never locks" at range.
- **Vesper's Deadeye scope gate is GONE** (2026-08-07). `CanAutoFire` used to block every scoped shot for the full `RampTime` (3s) so the passive's bonus could charge (`ResetOnFire`). Three seconds of dead trigger reads as auto-fire being broken, and the bonus is **headshot-only** while the lock measures from the ROOT — it was spending every scoped shot to protect a bonus that mostly did not apply. `CanAutoFire` is now `isCombatAllowed` alone; `S.ScopedSince` was removed with it (VesperHunterGuiClient keeps its own for the ramp bar).
- **Mobile-only gameplay advantages CANNOT be done server-side.** The only platform signal the server has is `player:GetAttribute("Platform")` from `Telemetry.setPlatform`, which is client-reported and spoofable *by design* — see [[project-mobile-telemetry]]. Wiring it to hit registration would let any PC player claim "Phone" for a double-size hitbox. The user was offered widening `HitForgiveness.Radius` for everyone and **declined** (2026-08-07), keeping the rule "auto-fire fires exactly when a shot would score, so nothing is wasted from a small magazine". Do not revive a mobile-only server buff without solving the spoofing first.
- **`LossGrace` preserved the dwell but ALSO authorised a blind shot** (fixed 2026-08-07, second playtest). The grace branch fell through to the fire call with `lock == nil`, so a cooldown maturing anywhere inside the 0.12s window fired at whatever the crosshair was on. Presented as auto-fire "firing for no reason and then missing", and it was overwhelmingly a **Vesper** symptom: her 1.8s `FireInterval` means the cooldown almost never matures on the frame she acquires, so maturing during a dropout was far likelier than for Dust's 0.4s — and her sub-degree tolerance at range flickers constantly. If a hunter fires at nothing, check this shape first: state that survives a dropout must gate *dwell*, never *permission to shoot*.
- **`FireQuality` (0-1, default 1) is the mobile-only, PC-safe buff lever.** Fraction of the lock tolerance the crosshair must be inside *before* the shot is taken — margin against client/server position divergence, which is roughly (ping x target speed) studs and eats the whole 3.5 at the tolerance edge. **Vesper alone sets it, 0.55**; the other three fire often enough that taking every chance is right. This is the answer to "buff mobile X without touching PC": everything in AimAssistController / MobileAutoFireController is behind the touch-only gate, so it cannot reach a PC player — unlike anything server-side ([[project-mobile-telemetry]]).
- **LOS must be tested at several body heights, not just the root.** Anchoring the ray to the root for server parity broke enemies on rooftops and platforms: viewed from below the parapet hides legs and root while head and chest are clear, so the candidate was rejected and the player saw enemies "go invisible when you look up". Now tests chest -> head -> root and passes on the first clear one; the server agrees, since its primary hit path strikes whichever part the ray actually meets. Chest is first so an unobstructed target still costs one ray.
- **Stealthed targets produce no lock at all** (2026-08-08). Aim assist had no notion of invisibility, so a Fortuna inside her ultimate stayed an ordinary acquire candidate and auto-fire tracked and shot her for the whole window — the one thing that ultimate exists to prevent. Gate is `HunterCharacterUtil.IsStealthed` (the same rule `BotBrain`/`BotCombat` have always obeyed) called in `AimAssistController:_evaluateCharacter`, **not** in `MobileAutoFireController`: putting it at the candidate stage removes the target from **magnetism** too, since a crosshair drifting toward someone nobody can see gives her away as loudly as the gunfire. Reads `character` (authoritative rig) not `geometry`, so it covers Fortuna **bots** — `BotFortunaInvisible` lives on the server rig even when the bot renders from its visual clone. She is deliberately still in the LOS ray (she absorbs a bullet aimed through her, so she must still suppress a lock on whoever is behind her). This is the **first client-side require of `HunterCharacterUtil`** — safe only because its workspace walk sits behind `RunService:IsServer()`; `loadstring`-ing that module in an edit-mode session runs that branch and hangs the plugin connection. **Not yet playtested.**
- **Remaining knobs** if it still feels weak: `AcquireDelay=0.08`; sprint suppression while a lock holds (fire entries cancel sprint before their cooldown check); and yaw-only magnetism, still `Enabled=false` (see [[mobile-aim-assist-design]]) — parity decides *when* to fire, so it cannot make a genuinely-off crosshair land, and long range stays hard by design.
