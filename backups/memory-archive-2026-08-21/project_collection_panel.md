The Bounty lobby's **Collection** menu (`3CollectionFrame` bottom tab): a user-designed `StarterGui.CollectionGui`. It is the wardrobe — browse and equip what you own. **Selling happens in the Trading Post, not here** ([[feedback_ask_placement_decisions]] is the memory about getting that call wrong).

> **SPLIT 2026-07-30.** `CollectionGuiController` went from **3872 lines to 144** — it now only requires, mirrors attributes into `State`, and runs startup. Behaviour lives in 15 child ModuleScripts: `Refs` (instances+constants) · `State` (session + ownership + the join prefetch) · `Catalog` · `Viewport` · `TileVisuals` · `Preview` · `PreviewMode` · `Shop` (the locked-item hand-off) · `EquipButton` · `HuntersTab` · `SkinsTab` · `TitlesTab` · `BoostsTab` · `EmotesTab` · `Panels` (view state + open/close). Verified working by the user clicking through Collection + Trading Post in Studio. **Two behaviour changes:** each tab now *registers* its own EQUIP label+action with `EquipButton` (was two parallel 100-line if-chains that had to agree), and `WEAPON_DISPLAY` moved to the shared Bounty-only `ReplicatedStorage.WeaponDisplayConfig`, also read by `HuntersBuyController`. `titleShop` and the `emoteState` payload no longer exist.

**Shape:** the LEFT canvas switches between three modes (`setLeftMode`) — **Hunters** (grid of hunter tiles with closeup viewports), **Boosts** (6 tiles from [[project_boost_potions]] `BoostConfig`, USE / IN USE / NONE button), **Emotes** (see [[project_emotes]]). The RIGHT canvas carries per-hunter tabs — **Skins**, **Weapon** (guns from `ReplicatedStorage.WeaponSkins.<Hunter>`), **Titles**. The middle is a live in-world preview: the model stands ~10 studs in front of `CameraPartActualCollection`, revealed after the 1.8s `CAMERA_MOVE_DURATION` camera flight. Ownership model is show-all-grey-out-unowned (viewport tint + label fade + LOCKED).

Equip goes through existing remotes — `CharacterSelectEvent`→PartyService, `EquipSkinEvent`/`EquipWeaponSkinEvent`→DataService (**not** "LobbyService", which older vault docs claimed). `CollectionPanelClient`, the original code-built text scaffold, was `Disabled = true` and is now DELETED.

**Locked items deep-link to the ITEM, not the tab** (2026-07-30). `Shop.navigate` takes a 4th `deepLink` argument and publishes six `Requested*` attributes on the buy-menu ScreenGui; `HuntersBuyController.consumeItemRequest`, `TitleBuyController.consumeModeRequest` and `EmoteBuyController.consumeEmoteRequest` walk them. Two things worth keeping: the hunter/gun grids are **two levels deep and the second level does not exist until the first hop runs** (drilling in rebuilds the shared entry slots), and each hop goes through `entryActivators[slot]` — the same body a real tile click runs, because an `RBXScriptSignal` cannot be fired from a script and a duplicate drill-in would drift. **A deep link cannot be consumed on one edge** — the first version did and shipped broken (right tab, wrong page: you landed on the plain `showHunterList` result). `TradingPostController.setSelectedTab` writes `huntersBuyFrame`'s `TradingPostMode` attribute and its `Visible` flag as **two separate statements and each rebuilds the grid**, so a drill-in done off the first was wiped by the second with the request already cleared. Fix: `scheduleItemRequest` retries ~45 frames and `tryConsumeItemRequest` returns true only once `selectedHunter`/`selectedWeaponHunter` **equals** the target — activating a slot is not proof it survived — clearing only then, which makes a later rebuild self-healing. Five edges feed it, including `GetAttributeChangedSignal` on the request attributes for the shop-already-open case. **A retry budget must count only frames where the target is actually open** — the second attempt still failed because the request is written *before* the navigation, so the attribute hook started the loop while the player was still in the Collection menu and the inter-menu camera flight outlasted the whole budget, which then cleared a request that never had a chance. **`huntersBuyFrame.Visible` is not a usable "shop is open" test** (never reset on close, reads true from the first visit on); `screenGui.Enabled` is.

**General rules this cost three attempts to learn: when driving another script's UI through an attribute, verify the END STATE and retry rather than trusting a single signal; and when a retry loop gives up, log what it wanted AND what it found — the third attempt was diagnosed instantly from one `guiEnabled=false` in the F9 log, after two rounds of guessing from the source got it wrong.**

> **⚠ The TITLES design here is SUPERSEDED by [[project_title_styles]] (2026-07-25).** Titles are **not** 5-per-hunter-all-unlocked any more: there are **31**, hunter-locked, bought in the Trading Post ACCESSORIES tab, and this tab became a wardrobe that lists them.
>
> **A locked row shows NO price badge and the button does NOT read LOCKED** — corrected 2026-07-30, after an earlier version of this memory said the opposite and put a wrong item on a test checklist. The badge was removed and the shared EQUIP button became the *only* marker that a row is locked: it names the destination (`PURCHASE` / `VIEW IN BOUNTY PASS`) and routes there. A row no longer states a price at all — the Trading Post card it lands on is where the price lives. **EMOTES is the one tab that still puts the word LOCKED on that button**, because it is the only one with a free slot for a separate shop button underneath (PREVIEW is hidden there). Read `Shop.md` / `EquipButton.md` in the vault before describing this tab's locked states. **Still true from the original design:** titles are per-**hunter** not per-player (`profile.EquippedTitles[hunter]`), `EquippedTitle_<Hunter>` attributes drive equip state, the display `EquippedTitle` label attribute follows the *currently equipped hunter* and refreshes on `EquippedCharacter` change, and `LobbySpawn`'s dummy nametag is the lobby display surface.

## Traps this panel taught (all still live)

- **`MenuHandlerScript.getFinalCameraCFrame` rotates every camera part 180°, so a part's real view direction is its NEGATIVE LookVector.** The first preview spawned behind the camera. Verify with an edit-mode screenshot at the flipped CFrame.
- **~~The 200-local ceiling~~ — RESOLVED by the split.** It was real and load-bearing (the file sat at 199/200, and a dozen design choices existed only to dodge it). All those workarounds are gone. **The lesson that outlives it:** a `local` is not in scope for a function declared *above* it, so a require sitting further down a file silently resolves to a nil global inside anything earlier — which compiles clean and only fails when a player clicks. Declare requires at the top, and static-check for use-before-declaration after any block move.
- **Weapon display tuning is shared with the Trading Post** — now `ReplicatedStorage.WeaponDisplayConfig` (Bounty-only, NOT one of the 16 mirrored modules), read by `Viewport`, `Preview` and `HuntersBuyController`. Without it Bram renders mis-angled, Vesper on its side, Dust's two revolvers upside down at different sizes. Every hunter now has its own gun folder, so the old "borrow Dust's revolver" fallback is dormant — it only fires for a hunter with no folder at all.
- **`UIStroke.Thickness` in this GUI is an authored fraction (~0.03), not pixels** — see [[project_uistroke_thickness_scale]]. Scale the authored value; never assign an absolute one.
- **Scale-sized children inside its ScrollingFrames resolve against the canvas, not the panel** — see [[project_scrollingframe_geometry]].
- **The UI is not proof the server agreed.** The controller writes `equippedWeaponSkins[hunter]` locally right after firing the equip remote, so the panel reads EQUIPPED even when the server rejected it for lack of ownership.
- **Join-time state needs a pull remote, not just a push.** `SkinDataEvent` was the one join push without a `Request*` companion and it lost the race against the old ~3500-line controller's handler, leaving every owned skin LOCKED on the live server. That connection now lives at the top of `State`, ahead of all grid construction, and **requiring `State` early is therefore load-bearing ordering, not just a dependency.** See [[project_join_state_handshake]].
- **`State` fields must be read THROUGH `State`, never aliased into a local.** Every session value is *reassigned* (`State.ownedSkins = payload`), so `local owned = State.ownedSkins` captures one value and then silently goes stale — and stale ownership renders owned skins LOCKED, with no error.
