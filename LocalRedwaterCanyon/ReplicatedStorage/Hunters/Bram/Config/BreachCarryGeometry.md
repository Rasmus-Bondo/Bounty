# BreachCarryGeometry

The geometry layer behind Bram's Breach Charge, shared by all four implementations of it — wall test, carry clear-space clamp, lane offsets, slam settle and the past-the-plane test.

## What it does
1. **Exists because the charge has four implementations and the geometry was hand-copied into every one.** The *decision* layer legitimately differs — a player charge is keypress-driven, camera-steered and multi-victim; a bot charge is server-driven, distance-scaled and carries one enemy — but the geometry does not. Every copy carried a comment saying it MUST match the others, which is the smell this module removes. The cost was measured before it was written: launch issue #5 had to be fixed in three implementations, #3 was missing on the player path while the bot had it right all along, #21 had no bot path at all, and the slam settle was written once for players and again for bots with the two disagreeing. Callers are BreachChargeService (player authority), GrudgekeeperClient (detects and reports), BramWorldFXClient (victim-side pin) and BotCombat (bots)
2. **Stateless by construction** — no `self`, no retained instances, and **no module-local tuning literals**. Every constant is resolved from [[GrudgekeeperConfig]] at *call* time, because duplicated literals are precisely the thing being deleted; the module does not get to keep any of its own. The one exception is `WallMaxNormalY` (`cos 55°`), exported so a parity harness can assert against it rather than retyping the expression a fourth time
3. **`findWall(origin, flatDir, distance, exclude) -> RaycastResult?`** — fires **both** a centre ray and a `WallCastRadius` (1.5) spherecast and accepts either, because neither alone is adequate and each covers the other's blind spot. Measured over 72 headings per site: at the wooden lattice the ray finds a wall on 43% against the sphere's 54% (the ray shoots the gaps between 1.4-stud beams and 0.6-stud panels), but at the CHARGEPOINT corner the ray finds 35% against the sphere's 28%, where the sphere clips the sloped floor first (`|normal.Y|` 0.65, rejected as a ramp) and never reaches the rock face behind it. OR-ing can only ever detect MORE wall than the original ray, never less, so it cannot regress an angle that used to slam. The **ray runs first and returns on a hit**, which is load-bearing at a corner: the ramp is rejected either way, but only the ray's result carries the position the slam should settle against. A hit qualifies when it exists, is not part of a character, and is steep (`|normal.Y| <= cos 55`). `IgnoreWater` and `RespectCanCollide` are set here rather than by the caller because they are part of the *test* — `RespectCanCollide` is what stops a HealthPack's invisible pickup hitbox reading as a wall
4. **`distance` is a parameter and never a config read, and that is the authority split, not an oversight.** The client detects at `ChargeWallCheckDistance` (5) and reports; the server re-verifies at `WallVerifyDistance` (18); the bot detects directly at `Pin.WallCheckDistance` (8). The module supplies the **test**, never the authority. Note the client's key is a *different* key one table away from the servers' — `ChargeWallCheckDistance` is not `Pin.WallCheckDistance` — which is exactly why deciding it here would be wrong
5. **The exclude list is caller-supplied**, and legitimately differs: GrudgekeeperClient excludes every player character plus the `ArenaBots` folder; BotCombat adds the `VesperHookSpotsBot` and `WallMap` folders (a bot must not slam a victim into its own navigation scaffolding, which a player Bram can); BreachChargeService excludes the caster and his own carried victims. In all cases the carried victim must be **excluded**, not merely rejected by the character test — they ride `CarryDistance` (6) ahead and a cast of `WallCastRadius` reaches `distance + radius`, so it lands on the carried body first and never sees the wall behind them, which would make a carrying Bram unable to slam at all
6. **`clampToClearSpace(fromPos, candidate, exclude) -> Vector3`** — never write a carried body into geometry. Spherecasts (`CarryCastRadius` 1.5, a body half-width) from a known-clear origin toward the intended point and stops `CarryCastEpsilon` (0.1) short of whatever is in the way. A single ray is not sufficient and was the original defect: over 216 directions at a lattice structure the ray reported "clear" on 6% of headings where a body-sized cast collided, and every one of those is a frame the carry writes the victim into a beam. The offset uses `result.Distance` — the sphere *centre's* travel, which already stands off the surface by the cast radius — so subtracting a clearance on top would double-count and yank victims backwards off every wall
7. **The clamp deliberately has NO character test on its result.** The bot copy had one; it was a vestige of a bug where the cast hit the victim sitting at the carry point and the guard returned the *unclamped* candidate every frame. That was fixed by excluding the victim from the filter, but the guard was left in, and its only remaining effect was that a **third-party** character standing between charger and carry point made the clamp a no-op for that frame. Both callers already exclude the caster and the victim, so a third character in the path should clamp, not be ignored
8. **`carryPoint(chargerCF, slot) -> Vector3`** and **`laneOffset(slot) -> number`** — where a carried victim rides: `CarryDistance` ahead, stepped into their own lane (centre, +1, -1, +2 … at `CarryLaneSpacing`). Neither clamps; the caller clamps, because it owns the exclude list. `slot` is optional and defaults to the centre lane precisely so a bot — which carries one victim and has no lanes — can ignore lanes entirely. `laneOffset` is exported separately because BreachChargeService also needs the lane as an **object-space** offset for the `"Pin"` FX message, which the victim's client multiplies by Bram's live root CFrame every frame
9. **`settlePoint(wallPos, faceFlat, victimY, slot) -> Vector3`** — where a slammed victim is left: back off the wall **face** by `SlamWallClearance` (2), step into their lane, keep their own Y so a slam never lifts or drops anyone. Measured back along the **charge direction**, not along the wall normal; the two disagree on any angled hit (1.53 studs apart at 45°) and the charge direction is the one that reads as being driven into the wall. Does **not** clamp, because the exclude list differs between the carry and the release — at the release, victims already settled must not block the ray for victims settled after them, so the caller clamps with a list it built once before releasing anyone
10. **`isPastPlane(victimPos, settlePos, faceFlat) -> boolean`** — push BACK only, never pull forward. `WallVerifyDistance` (18) is a generous tolerance for a laggy client wall report, so a slam can legitimately be granted with the victim still well short of the wall, and teleporting them onto it would be worse than the bug the settle exists to fix. Measured along the flat charge direction, so a height difference cannot flip the answer. **Sharing this test is what lets the bot path adopt the same rule without re-deriving it** — see the ownership note below
11. **The module computes; it never applies.** This matters most at the slam, where the two paths diverge for a real reason. The player path routes the settle through the victim's own client, because Bram's server HumanoidRootPart lags his client-owned one and the server therefore cannot judge the distance. A bot's root *is* the authoritative one, so the bot path evaluates the same test server-side and writes directly — while it still holds network ownership, i.e. **before** its release hands physics back. Same test, two appliers, on purpose
12. **The character test walks every ancestor to `workspace`**, rather than taking the nearest Model and asking whether *that* one has a Humanoid. The two forms differ when the nearest Model ancestor of the hit part is a nested non-character Model inside a character — a world-gun model parented into the rig, say — where the nearest-Model form reports "not a character" and grants a slam off a bystander's gun. Only reachable for a character the caster did not exclude, so it never bit the client and could bite both server copies; the walk-up is the strictly correct one and is what all four callers now get
13. **Placement is deliberate.** Not in `Hunters.Shared`, which `CLAUDE.md` scopes to hero-agnostic code — this is Bram-specific. In `ReplicatedStorage` because two of its four callers are LocalScripts. The clamp is arguably generic enough to promote (any displacement ability could want it) and was deliberately **not** generalised, since no second caller exists; revisit if Vesper's grapple or Fortuna's recall ever needs it
