# HunterSwitchClient

Controller for the authored `SwapHunterGui` (StarterGui) — the mid-match hunter switching UI. While the player is DOWN a **SWAP HUNTER** button appears; pressing it deals in a panel of hunter portrait cards, and clicking a card QUEUES that hunter on the server ([[HunterSwitchService]]) so it spawns in on the respawn that ends that same kill cam. Exactly one card is ever marked, and the mark means one thing — this is who you will spawn as. It sits on the hunter you're already playing when the panel opens and MOVES to whichever you click, leaving nothing behind marking the one you're switching away from. The line above the button also becomes "YOU WILL NOW SPAWN AS &lt;HUNTER&gt;". Re-clicking the marked card (or clicking the hunter you're already playing) cancels, which returns the mark to your current hunter. There is no in-match HUD toggle — the swap has always been death-gated server-side, so the kill cam is the only moment the choice is live. This script is hunter-agnostic and lives directly under `StarterPlayerScripts` (not a per-hunter folder) so it persists across switches and is never torn down by `HunterClientLoader`. It only drives UI + the request/state remotes; all validation is server-side.

The GUI itself is authored, not built in code, and was imported verbatim from the **"Bounty - UI Update"** design place on 2026-08-26, replacing the older icon-grid panel. `StarterGui.SwapHunterGui` holds `SwapHunterFrame` (Button + Title), three UI `Sound`s (`UIClick` / `UIDropDown` / `UIHover`), and `Hunters` (a Title plus `HuntersFrame` with one card per hunter — `1DustFrame`, `2VesperFrame`, `3BramFrame`, `4FortunaFrame`). Each card is a `Canvas` carrying a `ViewportFrame` with that hunter's rig **already inside it**, a `CharacterName`, a `WeaponName`, a `UIStrokeSelect` border, a green `UIShadow` glow and a rotated green `SELECTED` banner. It is `ResetOnSpawn=false` (the references taken here must survive every respawn) and `DisplayOrder=9600` so it sits above `KillCamGui`'s 9500 and receives the clicks. The panel it replaced is parked alongside it as `_LegacySwapHunterGui`, `Enabled=false`, pending deletion after a playtest.

**`Hunters` and `SwapHunterFrame` are both authored `Visible=false`**, the same as the panel they replaced; this script raises them. The design place authors them `true` — that is its canvas — so a re-import brings the `true` back and it must be set false again. It is not only Studio tidiness: `ScreenGui.Enabled` is never touched at runtime, so the panel is live in `PlayerGui` from the moment StarterGui is copied in, and the boot line that hides it is behind a `WaitForChild`. Authored `true`, a slow join flashes the whole swap panel on screen before the player has moved.

## What it does
1. Resolves the authored GUI out of `PlayerGui` and binds every card under `HuntersFrame`. The hunter name comes from the card's name with its leading sort digit and trailing `Frame` stripped (`1DustFrame` → `Dust`), so adding a hunter is an authoring change, not a code change. Captures the authored `UIStrokeSelect` colour and the portrait's `Ambient`/`LightColor` as the baselines every state is expressed relative to, and adds two instances per card: a full-canvas `SwapHunterHitbox` TextButton (the authored card has no button of its own, and a canvas-sized target is also what keeps it finger-sized on a phone) and a `SwapHunterScale` UIScale for the hover and press motion. Grid `SortOrder` moves to `LayoutOrder` so the server roster, not the authored names, decides card order; the name digit seeds `LayoutOrder` until the first push lands
2. **The portraits are authored into the cards, and their `ViewportFrame`s must stay camera-less.** Each card ships with its hunter's rig inside a `WorldModel`, all four posed at one shared spot. A `ViewportFrame` with `CurrentCamera` unset auto-frames its contents, and that is what makes the four bust shots match — the panel this replaced needed an explicit head-height camera per portrait only because it cloned the `ReplicatedStorage.Hunters.<Hunter>.ViewportFrame` templates, whose rigs sit at scattered map coordinates and framed inconsistently (Bram rendered empty). At bind time the rig's scripts are **disabled, never destroyed** (removing a rig's `Animate` LocalScript stops every skinned MeshPart in it from rendering inside a ViewportFrame — the parts stay in place and simply stop drawing) and its parts have collision/touch/query cleared. That walk runs off-thread so it cannot hold up the remote wiring; the card is bound and clickable immediately. A sanitised clone of the rig is kept nil-parented as the restore source for "wearing Default"
2a. **Dresses each portrait in the skin the player has equipped for that hunter** (launch issue #22 — the cards used to render everyone in their default skin, which is visibly a different character to the one that spawns). The rig inside the card's `WorldModel` is replaced with a clone of the model named by the server's per-hunter `models` entry, which is the already-RESOLVED `{category, subfolder, modelName}` from [[HunterSwitchService]]`.buildModelMap` — so the skin-name→model rule is never re-implemented here and the portrait cannot drift from what `applyPending` spawns. Deliberately **not** done at bind time: cards are bound before the state remote is connected and the priming query is fired, so the equipped skin is not known yet. The card renders in its authored default immediately and is re-dressed when the first push lands; `render` is called on every push, so the swap is keyed and idempotent (a repeat of the same skin must not rebuild the rig and flicker the portrait mid-kill-cam), generation-guarded so a later spec beats one still resolving, and off-thread because resolving a skin model yields on `WaitForChild`. A `subfolder` of `Default` maps to the card's **own authored rig** rather than re-resolving through `Characters/<Hunter>/Default`, which is a second rig that would then have to be kept identical. No camera is set on the replacement either — the viewport re-auto-frames; the new rig is pivoted onto where the outgoing one stood only so the portrait's scene doesn't jump to the skin model's own map coordinates. A model that fails to resolve leaves the default portrait standing and warns — a wrong picture beats an empty box, which reads as a broken menu. `Anchored` is deliberately untouched: no physics runs inside a viewport
2b. **The skin dressing is isolated from the visibility path, and that isolation is load-bearing.** `render` runs from the state handler **above** `refreshVisibility`, and its card loop is a shared `pairs` pass — so a throw while dressing a portrait would skip every later card *and* the visibility call, leaving the SWAP button hidden for the rest of that life with nothing scheduled to look again. That is launch issue #20's failure mode arriving by a new route. Two guards: `state.models` is **type-checked, not truthy-checked** (`state.models and state.models[hunter]` throws on a non-indexable value such as a number, which a truthy check happily passes), and the `applyPortraitModel` call is `pcall`ed so no future change inside it can reach the button. Which hunter you get to come back as must never depend on a cosmetic portrait resolving
3. Visibility: `SwapHunterFrame` (the button) is raised while the player is down; the cards stay closed until the button is pressed, and pressing it also fires a no-arg state query to refresh ownership. The button **stays on screen while the cards are up** — it is both the way back out and the only home for the status line. Respawning closes the panel, clears any transient message and restores the authored Title
4. Card states, all driven off the server-pushed state through `applyCardVisuals`, which is the **single writer** of card appearance — `render` sets the flags from a push, the hover handlers set `hovered`, and both then call it, so the ring, the glow, the banner and the portrait lighting can never disagree about which card is marked:
   - **selected** (`pendingHunter or current` — the hunter this kill cam will end with, so the mark is never absent on open and never on two cards at once) — the authored `UIStrokeSelect` takes the `UIShadow`'s green, the `UIShadow` glow is enabled, the `SELECTED` banner is shown, and the portrait uses its authored lighting
   - **current** — no marker of its own. It carries the mark only while nothing is queued; an `IN USE` badge on the hunter being left behind would be a second answer to the question the mark already answers, and the two disagree the moment a different hunter is picked
   - **owned, not selected** — white authored border, no glow, no banner, and on pointer devices a dimmed portrait that lights on hover. On touch it stays lit (see 12)
   - **unowned** — darkest and warmest portrait lighting, faded name and weapon lines, and a `LOCKED` badge. The badge is a **clone of the authored `SELECTED` banner** recoloured amber, so it inherits the design's font, rotation, placement and stroke and stays in step if the card is re-exported. Locked lighting deliberately sits *below* the un-hovered dim as well as below lit — the design prototype's dim was dark enough that a hunter you own looked less available than one you don't. The card still renders so the roster reads the same for everyone; clicking it is answered locally ("YOU HAVEN'T UNLOCKED X") rather than sent to the server for a rejection
   - Cards for hunters absent from the pushed `roster` (e.g. the unfinished Iris) are hidden; `LayoutOrder` is assigned from the roster index
5. The Title above the button is the single status line: the queued hunter's spawn text when something is queued, otherwise a server message (uppercased, `--` normalised) for `MESSAGE_HOLD` seconds, otherwise the authored ultimate-charge warning. It is widened past its frame at boot — authored at 1.0 × 0.541 of a frame that is only 0.2 of the screen wide, a 43-character sentence wrapped down to about 10px on a phone
6. Clicking a card fires `RequestHunterSwitch:FireServer(hunterName)`; queue / re-tap-to-cancel / tapping the current hunter are all the server's call. The click pulse is local and immediate, but the **mark** waits for the push, so the pulse never claims a swap landed
7. **Visibility needs BOTH authorities to agree the player is down**, and they guard opposite ends. `serverDown` (the `isDown` flag in the pushed state) sets the earliest the button may appear — driving it from the local `Humanoid.Died` instead let a player click before [[HunterSwitchService]]`.isPlayerDown` would accept it, since the two views of a death race (reproduced on mobile). `not isLocallyAlive()` sets the latest it may persist — `applyPending` pushes state from inside `loadCharacter` before the new character exists, so it reports `isDown = true`, and a push landing after `CharacterAdded` would otherwise strand the UI on screen for the whole next life. Full condition: `serverDown and not isLocallyAlive() and RoundActive`. **A push may only ever RAISE `serverDown`; `CharacterAdded` is the sole thing that lowers it** — two assignment sites in the file, one each. A push carries `isDown` as read when the SERVER processed the request, and replies are not ordered against the character's own replication: a query fired late in the kill cam, processed after the respawn timer had already run `loadCharacter`, came back `isDown = false` and beat this client's own `CharacterAdded`, hiding the button while the player was still watching the kill cam. Every tap that opens the panel fires such a query, which is why spam-tapping the button made a rare window a reliable one (reported on mobile, 2026-08-08). Ignoring the `false` costs nothing — a player who really is alive is retired by `isLocallyAlive()` anyway
7a. The death race has **three** recoveries, because one was never enough. `Humanoid.Died` and the replicated `Health` value do not arrive together on this client, so `refreshVisibility` called from either can still read a humanoid that says it is alive: the push lands, `serverDown` goes true, the check sees a live player and declines. (a) The local `Humanoid.Died` fires a state query and re-tests visibility — it never sets `serverDown` itself, so the server keeps owning the earliest moment the button may appear, and it cannot lead the server's own view either, since the client's health reaching 0 is a consequence of the server writing it. (b) A per-character `GetPropertyChangedSignal("Health")` listener re-tests on the write itself, so the moment the 0 actually lands here the button comes up; it is safe on every damage tick because `refreshVisibility` is three property reads and a no-op when the answer is unchanged. (c) The bounded recheck loop in 7c catches anything both of those miss. Before these, a single lost sample was permanent for that life — the button is only ever raised by a re-test, and pressing it was the only client-side thing that could trigger one, so a player who lost the sample had lost the control that would re-ask (launch issue #20, and the "button never appeared when I died" report of 2026-08-08). A `warn` still fires when a push reports down while the humanoid reads alive, so a live log export says whether the race is real and how often. Note the gating is deliberately not on the `KillCam` remote: zone and fall deaths never fire it (see `KillCamClient`) and those players would lose the swap window entirely. `watchCharacter` also queries and re-tests when it finds the humanoid already dead, covering the script starting up mid-death. `CharacterAdded` clears `serverDown` immediately rather than waiting for a push, since the server only re-pushes on respawn when it actually consumed a queued hunter
7b. `watchCharacter` is **generation-guarded** rather than disconnecting up front. Its `WaitForChild("Humanoid", 10)` yields, and two `loadCharacter` calls in quick succession (the death-respawn timer racing a round-start reload) put two invocations in flight; the old shape disconnected the `Died` hook first and could then bail at the identity check, leaving it nil for the whole life — back when that hook was the only recovery from the race above, that gap cost the player the entire swap window. Connections are dropped only once a replacement has actually resolved, and both per-character hooks (`Died` and the `Health` listener) are retired together for the same reason
7c. **The recheck loop is the backstop for the whole class of "a sample landed wrong and nothing looked again".** `refreshVisibility` kicks it whenever it finishes with the server calling us down and the button still not up — deliberately after the early-out, since the case worth covering is the one where nothing changed. It re-tests every `RECHECK_INTERVAL` (0.2s) for up to `RECHECK_DURATION` (12s, which outlasts `Config.RESPAWN_DELAY` of 6) and stands down as soon as the button is up, `serverDown` clears, or the round ends. A `recheckRunning` flag makes it idempotent, so the calls it provokes cannot spawn a second loop. Two deliberate details: it does **not** exit on `isLocallyAlive()`, because a humanoid still reading alive is the exact race it exists to outlast; and its body is `pcall`ed, because a throw would kill the thread with `recheckRunning` still true and silently disable the backstop for the rest of the session, precisely when it is needed
8. **Holds the card's aspect ratio on every device, and widens the panel rather than shrinking the cards.** The authored `UIGridLayout` cell is `{0.2,0},{1,0}` — scale on *both* axes, inside a frame that is itself 0.6 × 0.4 of the screen — so each card's shape tracked the SCREEN's aspect instead of staying a portrait: 0.73 wide on the ultrawide Studio viewport the design was drawn against, 0.53 on a 16:9 monitor, 0.40 on a 4:3 tablet. The cell is re-derived in pixels whenever the ScreenGui's `AbsoluteSize` changes, and on every roster change (the roster decides how many cards share the row). Card height comes from the panel, width follows from `CARD_ASPECT`, and if the row no longer fits across the authored 0.6-wide panel then the **panel** widens — to `PANEL_MAX_WIDTH_SCALE` 0.94 — before any card is allowed to shrink. Two details that were bugs: the cell is derived from the panel's actual *pixel* width and floored, because rounding the two independently left the row 2px wider than its frame, and a grid whose contents overflow by one pixel silently WRAPS the last card onto a second row (which then overflows vertically and pushes the panel off the top of the screen); and the width is `min`'d against the height-derived value, so a panel sitting at its authored width with room to spare doesn't grow the cell past the height it came from. `VerticalAlignment` moves to Center — the authored `Top` was only right while the cell filled the frame. It listens to the **ScreenGui's** size, not the frame's, because it writes `panel.Size` and a frame-level listener would re-enter on its own edit. Measured one row of correctly-proportioned cards at 317×431 (1080p), 231×314 (iPad 8th gen) and 107×146 (iPhone 13 landscape)
9. When the UI becomes visible it sets `MouseBehavior = Default` / `MouseIconEnabled = true` once. KillCamClient already leaves the cursor free for this panel, but a hunter client that failed to unlock on death shouldn't be able to strand it unclickable. On mouse-only devices a "HOLD RIGHT MOUSE BUTTON TO LOOK AROUND" hint is added under the button, since freeing the cursor is what moved kill-cam look-around onto a right-drag. A `UISizeConstraint` floors `SwapHunterFrame` at 210×42, its authored 0.2 × 0.086 landing at 150×29 on a phone
10. Fires a state query once at startup so the first death doesn't have to wait on a round trip
11. **Waits for the local character before it resolves the GUI.** Redwater runs `Players.CharacterAutoLoads = false` (set in `Main` and `SkinService`), and StarterGui is only copied into `PlayerGui` when the character FIRST spawns — a spawn that is itself deferred through `SkinService.loadCharacter`, which blocks on the profile-backed hunter selection before calling `LoadCharacter`. This script boots from `StarterPlayerScripts` the instant the client starts, so waiting on `SwapHunterGui` directly sat in an empty `PlayerGui` for that whole window and tripped Roblox's 5s *"Infinite yield possible"* warning on any slow join. A `player.CharacterAdded:Wait()` gate ahead of the lookup removes the false positive while leaving the `WaitForChild` after it as a real diagnostic. The deferral costs nothing here: the panel is death-gated so it cannot be needed before the player has ever spawned, the `CharacterAdded` handler would have missed that first character either way (which is precisely what the `if player.Character then watchCharacter(...)` fallback beneath it already covers), and the priming startup query in behaviour 10 re-pulls roster/ownership — so a state push landing during the wait is re-asked for rather than lost, per the general rule in 7
12. **Sound and motion, folded in from the design place's prototype.** The panel plays `UIHover` / `UIClick` / `UIDropDown`, cloned per play (so a hover cannot cut a click short) into `SoundService` with the `SFX` `SoundGroup` set on each clone — the authored templates carry none, and an ungrouped Sound escapes all four settings sliders. They are read off the **ScreenGui's own three Sound children**, not `ReplicatedStorage.SFX.UIButtonClick` as the prototype did. At the time that folder existed in Redwater and not in Frostbite, so the prototype's route would have shipped a silent panel on one of the two match places and warned on every hover; it is now absent from **both** (deleted from Redwater 2026-08-27 — nothing in either match place read it, and Bounty's ShopCore holds the real copy, which is also the only one whose Sounds carry a `SoundGroup`), so that route is gone rather than merely lopsided. Opening deals the cards in on an `OPEN_STAGGER` with a `Back` scale ease plus a transparency fade captured from each card's authored values, so no authored transparency is ever written into the script. Hovering lifts a card and lights its portrait; clicking pulses it. Every hover affordance is gated on `UserInputService.MouseEnabled` — on a phone `MouseEnter` never fires, so a hover-only reveal is a state the player can never reach. Touch therefore gets all owned portraits lit rather than three permanently dim ones, and the SWAP HUNTER button ships pre-filled rather than waiting for a hover that will not come
13. **The design place ships a `SwapHunterController` prototype inside the ScreenGui; it is deliberately NOT imported.** It owns a local `selectedCard`, which desyncs from the server queue the moment a pick is rejected — selection here is server state. Its presentation is folded into this script instead, so there is one writer of card visuals and one source of truth for which card is marked. It also hid `SwapHunterFrame` on open, which would have taken the way out of the panel, the pending-hunter confirmation, the LOCKED reply and every server rejection with it, since all four live on that frame's Title
