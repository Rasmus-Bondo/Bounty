# RoundClientController

Client-side hub for round transitions: black-screen fades, intermission blur/DOF/idle camera/countdown UI, and hiding/restoring gameplay HUD + viewmodel + crosshair between rounds.

## What it does
1. Creates a screen-covering black fade Frame plus an "INTERMISSION / [countdown] / Round starting soon..." overlay, and a Lighting `BlurEffect`/`DepthOfFieldEffect` pair used only during intermission
2. `ScreenFade` remote (`"FadeIn"`/`"FadeOut"`/`"InstantBlack"`/`"InstantClear"`) tweens or snaps the black frame's transparency
3. `IdleCamera` remote (`"Start"`/`"Stop"`) orbits the camera around `workspace.CameraSpawn.CameraIdlePart`, shows the intermission overlay + blur/DOF, and runs a live countdown text — **the sole owner of the intermission orbit camera** (the former duplicate `IdleCameraClient` was removed). On countdown expiry the orbit stops but **holds the last vista frame** (`stopOrbit()`) instead of snapping back to the player, so the holding box isn't flashed before the fade-to-black; the player camera is restored only on the explicit `"Stop"`. A `"Start"` is ignored while `RoundActive.Value` is true — a stale Start processed after round start (lag-burst reordering or a join sync racing the round start) must never re-latch intermission mid-round. The guard is checked **twice**: at handler entry and again inside `startIdleCamera` after `getIdlePart()` returns, because `getIdlePart` yields (`WaitForChild` on `workspace.CameraSpawn`, up to 10s on a still-loading client) and the round can go live during that yield — resuming without the re-check latched the INTERMISSION overlay/blur for the whole match
4. `GameplayVisibility` remote toggles: all other ScreenGuis enabled/disabled (except the `ALWAYS_ENABLED_GUIS` set — `VictoryShowcase`/`VictoryTop3Gui`, plus `VersionTagGui`, `VersionTagInsetProbe`, `PingFPSInsetProbeDevice` and `PingFPSInsetProbeNone` added 2026-07-30), the first-person viewmodel's local transparency, and a "hidden enforcer" RenderStepped loop that keeps everything hidden while gameplay is invisible. **Mobile combat buttons** are authored `Enabled=false` and handled by NAME on the gameplay-visible restore so the generic "unknown gui → visible" default never force-shows them on PC (the `MobileCombatButton` attribute alone is unreliable here — it is set only inside a button's touch-gated build, so it is absent on PC / before the build races in). Two categories: **universal** buttons every hunter gets (`UNIVERSAL_MOBILE_GUI_NAMES` = `HunterFireGui` / `HunterSprintGui`) are restored to `Enabled = UserInputService.TouchEnabled` (shown on touch, hidden on PC); **hunter-specific** buttons (`CONDITIONAL_MOBILE_GUI_NAMES` = `VesperScopeGui`) are shown only when their `MobileCombatButton` attribute is set **and** touch — that attribute is set solely by the owning controller (`VesperScopeController`, which early-returns for non-Vesper players and builds only on touch), so a non-Vesper player on mobile never sees the scope button. A third category, **owner-controlled transient overlays** (`OWNER_HIDDEN_GUI_NAMES` = `VesperDeadeyeGui`), is force-hidden (`Enabled = false`) on the gameplay-visible restore so the generic snapshot never resurrects it: the Deadeye ramp bar is enabled only while Vesper is actively scoped, and without this a player scoped at a round boundary would have "shown" captured and restored on the next round, leaving an empty bar stuck on-screen while not scoping. This name-based handling is load-bearing because the server re-fires `GameplayVisibility(true)` on every spawn into an active round and the ScreenGuis persist across respawns (`ResetOnSpawn=false`). They stay hidden during intermission like the rest of the HUD
4a. **`VersionTagGui` is in `ALWAYS_ENABLED_GUIS` as of 2026-07-30, and it is not cosmetic.** This sweep hides the HUD for intermission *and* the post-match summary, and the build tag was being swept with it — so the stamp was absent from exactly the scenes players screenshot most, which is the tag's whole reason for existing. A matching `VersionTagInsetProbe` entry sat here briefly on the same day and was removed with the probes it named — the tag no longer tries to reach the physical screen edge, because a ScreenGui clips its children to its own inset rect and the negative offset those probes fed simply cut the build string off. Note that these entries match **by name**, so renaming a GUI on the far side silently turns its entry into dead config rather than erroring
4b. **`SETTINGS_OWNED_GUI_ATTRIBUTES` — restore from the saved preference, not from the snapshot (added 2026-07-30, fixes a long-standing bug).** The generic path snapshots a ScreenGui's `Enabled` on the way into intermission and restores it on the way out, which is right for a HUD whose state has already settled and wrong for one whose true state is a setting that arrives a server round-trip later. `PingFPSGui` is built `Enabled = false` by SettingsController and only switched on when `PlayerSettingsResponse` lands. A player joining **during intermission** had that `false` snapshotted first — by the `playerGui.ChildAdded` handler or the RenderStepped hidden enforcer — and the `if storedGuiStates[child] == nil` guard meant the real setting arriving afterwards never corrected the snapshot, so round start restored the stale `false` and the ping/FPS chip stayed dark for the entire match. Joining mid-round worked, and toggling it by hand fixed it until the next join, which is why it presented as flaky rather than broken. The map now points `PingFPSGui` → the `ShowPingFPS` attribute that SettingsController stamps on the GUI in `applyShowPingFPS`, and the restore reads that attribute instead — the same shape as the `MobileCombatButton` attribute already honoured above, and independent of which of the two arrived first. A missing attribute restores to hidden, which is correct for an opt-in overlay. Matched **by name and by attribute key**, so renaming either silently breaks it
4c. `PingFPSInsetProbeDevice` / `PingFPSInsetProbeNone` are in `ALWAYS_ENABLED_GUIS` for the same reason as `VersionTagInsetProbe`: SettingsController decides whether the chip hugs the physical left edge or stays clear of a notch by measuring the delta between those two probe ScreenGuis, and a disabled ScreenGui stops laying out and reports `AbsolutePosition` 0. They are transparent full-bleed frames, so forcing them on shows the player nothing
4d. **`SWEEP_EXEMPT_GUI_NAMES` — the fourth category, and the only one the sweep does not get a vote on (added 2026-08-11).** `TutorialGui` is skipped in **all three** loops (the gameplay-visible restore, the hidden enforcer, and the `playerGui.ChildAdded` handler), in both directions. It is authored `Enabled = false` and ships in every Redwater server because the onboarding lesson and a real match are the same place, so only TutorialClient may ever show it and only on a tutorial server. Both halves of the sweep were wrong about it: the restore's generic "unknown gui → visible" default (there is no stored state for a GUI nobody ever hid, and `storedGuiStates` is cleared after every show) **force-showed the EXIT TRAINING button and the StepLabel's shadow plate on every respawn in a normal match** — found by playtest 2026-08-11, and note that an empty `StepLabel` is not a blank one, its `UIShadow` plates the whole box and ignores `TextTransparency`, so it read as a dark bar under a live button; while the hide half would have blanked the **lesson's own** banner the first time the player died during it, which the tutorial does often (`Config.TUTORIAL_RESPAWN_DELAY = 0` and step 11 is a live-fire fight). This is why it is not in `OWNER_HIDDEN_GUI_NAMES` — that set fixes only the first problem and *causes* the second. Matched by name, with the same rename fragility as the sets above. **`MapVoteGui` joined the set on 2026-08-14**, and **`DominationGui` on 2026-08-23**, for the same shape of reason: both are authored `Enabled = false` and are shown by their own controller alone — MapVoteClient for the one beat between the summary and the next round, DominationClient only while the `Gamemode` attribute reads `domination`. The restore's "unknown gui -> visible" default would otherwise put a live vote panel over ordinary gameplay on every respawn, and put the Domination score bars, capture dials and CAPTURING banner over Free-for-All and Team Deathmatch on every respawn — which is exactly what it did, found by owner playtest 2026-08-23. DominationClient additionally re-asserts its own gate every Heartbeat, because a name-matched exemption is only as good as the name and this is the one guard nothing else can race
5. While gameplay is visible, runs a short-lived (1.25-1.5s) "GunGui crosshair enforcer" that forces every GunGui element invisible except the `CrosshairDot`, restoring its original transparency — keeps the crosshair visible without flashing the rest of the weapon HUD during transitions
6. Re-applies the crosshair-only state whenever a new `GunGui` ScreenGui is added while gameplay is visible
7. Restores camera/visibility state appropriately on `CharacterAdded` based on current round state
8. Self-heals on `ReplicatedStorage.RoundActive.Changed → true`: restores the camera if it's still Scriptable/orbiting, unconditionally clears the intermission dressing (overlay frame, countdown loop, blur, DOF — needed because `startIdleCamera` can resume from its yield after visibility was already restored), and force-applies gameplay visibility (plus clears the black frame) if still hidden. RemoteEvents fired before this script connects are dropped and delivery order is only guaranteed per-remote, so a slow-loading client could miss/reorder the round-start burst and stay latched in intermission state for the whole match — the replicated Value is the reliable exit signal
