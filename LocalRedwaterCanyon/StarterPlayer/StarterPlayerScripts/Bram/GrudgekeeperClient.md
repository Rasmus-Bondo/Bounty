# GrudgekeeperClient

Bram's client combat controller: fire/reload/ability input, ammo state, the cosmetic single tracer, the client-owned Breach Charge dash, AND (since Bram got dedicated viewmodel art) his full first-person presentation — the Grudgekeeper arms viewmodel, camera/mouse lock, touch aim assist, procedural motion, and the Idle/Run/Charge/Reload/Shoot animation tracks. Exits early via [[HunterClientRuntime]] when the local player isn't Bram. Bram no longer uses the generic HunterFirstPersonClient fallback (which now skips him alongside Dust/Fortuna).

## What it does
1. **Fire** (LMB / mobile Fire button): client-side gates (round, alive, reload, ammo, cadence — 0.5s, or 0.25s during Last Call), cancels an active sprint (parity with Dust — the trigger pull drops you out of sprint), then `FireShotgun:FireServer(origin, direction, muzzle)`. Draws a single cosmetic tracer straight down the aim via [[laserBeamEffect]] (the server's thick raycast is authoritative). Both the tracer and shrapnel-shell tracer raycasts exclude each `HealthPack`'s green `Pickup` + invisible `TouchHitbox` (not the solid `Base`) so the beams pass through the pickup like the server does
2. **Reload** (R / auto): 1s (0.5s during Last Call), token-cancelled; [[HunterAutoReload]] triggers it on empty mag. A reload in progress restarts at the faster cadence when Last Call starts
3. **Breach Charge** (Q): a steerable forced charge. `tryBreachCharge` sends `BreachChargeRequest("Start", chargeDir)` then runs a client-owned Heartbeat loop that drives a forward `LinearVelocity` on the HumanoidRootPart for `BreachCharge.Time` seconds — speed ramps `ChargeStartSpeed`→`ChargePeakSpeed`, heading steers with **A/D (or the move pad)** at `ChargeTurnRateDegrees`, with ground-check + airborne-grace. Movement is unchanged from before; only the END behaviour changed for the pin rework: `detectBreachWall` casts forward each tick and, if it rams world geometry (after a 0.15s grace), calls `finishBreachCharge("WallHit")` → `BreachChargeRequest("WallHit")` so the server slams any carried victim. That test **is** [[BreachCarryGeometry]]`.findWall` as of 2026-08-05 — it fires both a centre ray and a `WallCastRadius` (1.5) spherecast, accepting either. It used to be a hand-copy that *had* to stay equivalent to the two server copies by comment alone, which was the highest-stakes duplicate in the ability: this client only *reports* the hit and the server re-verifies it, so detecting on a test the server does not share turns every reported slam into a rejected "no wall" and a 15-damage whiff. **Only the distance is this file's own** — `ChargeWallCheckDistance` (5) against the server's `WallVerifyDistance` (18) — and that gap is the authority split, not a divergence; note it is a *different config key* one table away from the servers' `Pin.WallCheckDistance`. **Moving to the module fixed a live defect in passing:** the old copy shared its cached `RaycastParams` object with `isGroundedForBreach` and set `RespectCanCollide` only inside the lazy initialiser — and the ground check runs first on every charge frame and builds that object *without* the flag, so the initialiser here never ran and the wall test spent its whole life collidable-blind, reporting slams off invisible pickup hitboxes the server then rejected. `findWall` always builds its own params, so the flag can no longer be lost to call order. A ray alone shoots the gaps in the map's wooden lattice (1.4-stud beams, 0.6-stud panels); a sphere alone clips sloped floors and rejects them as ramps before reaching the wall behind, so each covers the other's blind spot. It also excludes **every character**, not just the local one: the carried victim rides `CarryDistance` ahead and the sphere reaches `distance + radius`, so it would otherwise land on their body and never see the wall behind them. The ignore list also carries **`workspace.WallMap`** as of 2026-08-05 — the map boundary is 64 invisible 241-stud slabs whose vertical faces every wall test happily called a wall, so charging near the map edge ended in a stun against nothing visible; it must stay in step with `BreachChargeService._wallExcludeList` or this client reports slams the server rejects. **Stall release** was reinstated in the same pass: a charge blocked by something the wall test deliberately does not accept (that boundary, a shallow ledge, a prop wedged on a slope) used to grind in place for the rest of the 3s, and now ends via `finishBreachCharge("Stalled")` after `StallGrace` (0.15s) of continuous movement below `StallSpeed` (10 studs/s). It is measured on **full 3D displacement, not `AssemblyLinearVelocity`** — the LinearVelocity mover keeps asserting ~40 studs/s while the character is pressed against a surface — and it is ordered *after* the wall check so a genuine wall still slams. It exits as a **plain release, never a slam**, which is what makes it safe to bring back: stall detection was originally deleted for causing false slams, and `StallSpeed`/`StallGrace` sat unread in the config ever since. It measured **flat XZ** displacement for its first day and that was wrong: climbing is progress, and on a 55° face more than half the motion is vertical, so a flat reading called a charge riding cleanly up a slope *more* stalled the better it was climbing. **Climb assist** (added 2026-08-05 alongside that correction, the actual fix for charges dying on inclines): the charge moves on a **Plane-mode `LinearVelocity` that drives X/Z and leaves Y free**, so nothing lifts Bram at all — pressed into rising ground he fed the whole horizontal push into the contact normal and crawled, and a 40–55° lip stopped the charge dead short of the wall behind it, releasing the carried victim for `ReleaseDamage` instead of slamming. `breachClimbRate` probes the **ground** `ChargeClimbProbeDistance` (4) studs ahead — not the surface normal underfoot, which reads "level" right up until he is already against a riser — and holds the upward speed that clears the measured rise in the time it takes to reach it, capped at `ChargeMaxUpwardSpeed` (52, formerly 0 and read only by a dead `getBreachVelocity` that has been deleted). It only ever climbs: a nil rate, or one slower than the fall in progress, leaves velocity alone, so it is not a hover and does not cancel a drop off a ledge. Measured against ramps at known angles: 15–50° climb at exactly the needed rate (peaking at 50.1 studs/s, under `MovementChecker`'s `MAX_VERTICAL_SPEED` of 65), 54° climbs capped, and **56°+ is caught by the wall test first and still slams** — the handover lands exactly on the `cos(55°)` threshold with no gap. Bots never needed any of this: both `BotController:DashToward` paths move the **Humanoid** (`Pathing:RequestMove` / `MoveTo` plus a `HunterMovement` base) and the humanoid controller climbs slopes by itself, which is why the same incline stopped a player Bram and not a bot one. The wall test and the climb probe share one `breachChargeIgnoreList` helper, so the character/`WallMap` exclusions cannot drift apart between them — the probe needs the characters out for its own reason: it samples the ground 4 studs ahead, and a carried victim's legs sampled instead of the ground read as no rise at all, killing the assist in exactly the case it exists for. Every other end (timeout / Q again / airborne) sends `BreachChargeRequest("End")` for a plain release. **Firing during a charge no longer cancels it** (it commits, Reinhardt-style, so an accidental shot can't drop a carried victim into a release). **Q-again is therefore the only deliberate cancel, and it is locked out for the charge's first `BreachConfig.ChargeCancelLockoutTime` (1s)** — launch issue #6, since without it the ability could be thrown away on frame one. `tryBreachCharge` is the whole gate, so the mobile Q button inherits it through the `BreachChargeRequested` bindable. An early press is **dropped, not queued**: a queued cancel would end the charge up to a second after a panicked double-tap the player has already forgotten making. This is **client-only on purpose and the server cannot enforce it** — the Q cancel and the automatic airborne exit both send a bare `"End"`, indistinguishable server-side, and the airborne one can legitimately fire at `ChargeUngroundedGraceTime` (0.55s) off a ledge, so a server gate would keep carrying pinned victims after the client stopped driving, until `BreachChargeService`'s own `Time + 0.75` timeout. Nothing is lost by that: ending your own charge early only drops victims for the minor `ReleaseDamage` and still pays the full cooldown. It also **cannot strand a player mid-charge**, which is the risk the issue flagged — the gate is inside the `S.IsBreachCharging` branch, and every early end (WallHit, Airborne, Invalid, the server's `ChargeEnd`) clears that flag before the check is reached, after which the next Q is governed by `S.BreachReadyAt` like any other. `breachChargeStartedAt` is 0 once the movement loop is cleared, and the check falls *through* to the cancel in that case rather than blocking on a stale zero. The client also listens on `BreachChargeFX` for a `"ChargeEnd"` message and stops its local charge loop with reason `"Server"` (no request sent back) — this is how a server-initiated wall slam halts the charger instead of grinding the wall until timeout. The server owns all pinning/carrying/damage/stun — this client only drives Bram's own movement and reports the wall. **Jumping is locked for the whole charge** (`Humanoid.Jump = false` + `SetStateEnabled(Jumping, false)`, the same shape RevolverDash uses for its post-dash clamp): leaving the ground trips the airborne branch and cancels the charge, so a jump only threw the ability away. The lock is re-asserted every tick because a stun clearing mid-charge restores the jump settings HunterStatusEffects snapshotted, and `clearBreachChargeMovement` hands jumping back on every end path. **If `StatusStunned` is still set at teardown it defers rather than re-enabling** — a live stun owns the movement lock and handing the state back there would let a stunned Bram jump — but that deferral has to actually be *completed*, which is `restoreBreachJumpAfterStun`: it re-enables the state the moment the stun attribute clears, behind an 8s deadline backstop, a one-shot `done` flag, and a token so a newer charge supersedes a pending hand-off. **Before 2026-08-05 the teardown simply skipped the re-enable and nothing ever finished the hand-off, so the player could not jump again for the rest of that life.** The trap is that `HunterMovement`'s `LockJump` *does* call `SetStateEnabled(Jumping, true)` when it releases, which reads like the stun already covers this — but the stun is applied **server-side**, and `SetStateEnabled` is per-machine and does not replicate, so the server reopens only its own copy while the client's, the one `ManuelJumpClient.canJump()` actually reads, stays shut. What the stun *does* replicate — `JumpPower`/`JumpHeight` 0 and the `MovementJumpLocked` attribute — never reopens the state. In normal play this is only reachable when Bram is stunned as his own charge tears down: another Bram slamming him into a wall, or a charge clash (#23), which is why it surfaced alongside that fix. The hunter-switch cleanup force-enables the state as well, since a swapped-away Bram leaves nobody to complete the hand-off. **The cooldown starts in `finishBreachCharge`, at the end of the charge rather than on the keypress** (launch issue #5, fixed 2026-08-04), mirroring `_endCharge` in `BreachChargeService`; every exit reason funnels through that one function, which is what makes a single start point possible. `tryBreachCharge` still fires `BreachChargeCooldownStarted` at the press, but with `BreachCharge.Time` rather than `Cooldown` — a placeholder fill so the Q icon never reads READY mid-charge, where a press cancels rather than recasts, superseded by the real value on release because the HUD fill is token-guarded. The death path routes through `finishBreachCharge("Invalid")` for the same reason: the server restarts the cooldown from `_endCharge` whether or not the charger died, so a client that skipped it would come off cooldown seconds early and charge locally against a server that refuses. A `BreachCooldownEpoch` counter, bumped by Last Call activation and by each `AbilityCooldownsReduced` push and snapshotted when the charge starts, suppresses the restart when a refresh landed mid-charge — the client mirror of the server's `CooldownStamp` guard
4. **Shrapnel Shell** (E): local cooldown gate + `ShrapnelShellRequest:FireServer(origin, direction)`; draws an instant local shell tracer (other clients get theirs from `ShrapnelShellFX` via BramWorldFXClient, which skips the caster)
5. **Last Call** (F): requests at full charge; `UltimateState` Start/End flips the local cadence/reload multipliers and zeroes both local ability gates (cooldowns refresh on activation)
6. `AbilityCooldownsReduced` → adopts the server-authoritative remaining cooldowns after each landed-blast refund and re-fires the CooldownStarted bindables so the HUD restarts its fills
7. Renders other Bram players' single tracer from `ReplicateShot` (muzzle + one endpoint)
8. Runs the runtime-owned SprintController every RenderStepped and is the single owner of `camera.FieldOfView`: it `smoothDamp`s the FOV toward the sprint target (base 70 + `GetSprintAlpha()`×8) at speed 14, mirroring Dust's RevolverCameraEffects, so cancelling sprint mid-run (e.g. shooting) eases the widen back instead of snapping. Gated on alive (hands FieldOfView to KillCam/showcase when dead) and idles out once settled. Mobile buttons in [[BramHunterGuiClient]] reach this script through the request bindables
9. **First-person viewmodel** (a `BindToRenderStep` at `Camera + 1`): clones the viewmodel onto the camera as `ClientViewModel` — `runtime.Viewmodel.Template` (`Weapon.Viewmodel.Default.DefaultViewmodel`, from the manifest's `Client.ViewmodelTemplate`) unless `EquippedWeaponSkin_Bram` names a Model in the sibling `Weapon.Viewmodel.Skins` folder (`FrostbiteGrudgekeeper`), resolved **per call** and rebuilt on that attribute changing so a skin landing after boot still redraws the owner's own gun, normalizes it to an absolute `Model` scale (`VIEWMODEL_SCALE = 1` — the rig ships ~13.9x oversized in Studio), strips physics/anchors the `Root`, gates first-person camera/mouse lock + touch aim assist ([[AimAssistController]]) on round-active + alive, composes per-frame motion via [[HunterViewModelMotion]] (MouseDelta sway + jump/land, reusing [[RevolverConfig]]'s `ViewModel` tuning, plus a local `BramSprintBob` extra CFrame; there is **no procedural recoil**, so a shot moves the gun through the Shoot clip alone), and rebuilds the model if it's missing / reparents on camera swap
10. **Viewmodel animations**: loads six tracks off the rig's `AnimationController`/`Animator` — Idle (Core, looped, always-on base), Run (Movement, looped, played while sprinting and `MoveDirection` > 0.05), Charge (Action, looped, played for the length of a Breach Charge), Reload (Action, one-shot, speed-matched to `getReloadTime()` so it halves during Last Call), Shoot (Action2, one-shot restart each fire, played at authored speed but cut at `SHOOT_CLIP_CUTOFF` = 0.30s by a token-guarded `task.delay` + `Stop(0.12)`, keeping the clip's recoil beat and dropping its pump beat), ShrapnelShoot (Action3, one-shot). Shoot fires from `tryFire`, Reload from `startReload`, and `cancelReload` stops the reload track. **Charge outranks Run and is checked first**: before it was authored the charge borrowed the sprint cycle, and Run is still the fallback for a rig that ships no Charge clip. Charge sits below Shoot because firing *commits* a charge rather than cancelling it, so the blast has to read on top of the run. The rig clip named `ShrapnelShoot` is authored as `Ability` in `Hunters.Bram.ViewmodelAnimations`
11. Lifecycle: CharacterAdded/Died/round-end cancel the reload, invalidate the dash token, and reset ammo/ult state
12. **Auto-fire (touch only, 2026-08-07):** a [[MobileAutoFireController]] reads the aim assist's `GetLock()` report and calls `tryFire()` at `BasicConfig.Cooldown` intervals while the crosshair holds an enemy. Passes `MaxLockDistance = BasicConfig.AutoFireMaxDistance` (60 studs, added 2026-08-07 — set equal to the blast's `MaxRange`, so auto-fire only holds where a shell would deal literally zero damage; the FIRE button stays unrestricted). Ticked inside the `Camera + 1` render step directly after `aimAssist:Update` (and after the breach-charge camera alignment), plus in the not-first-person early-out where its gate fails so death or round-end resets the lock state the same frame. `CanAutoFire` is `isCombatAllowed() and not S.IsBreachCharging` — mirroring `tryFire`'s own charge-commit early-return so the lock state drops the moment a charge starts. `OnLockChanged` publishes the `AutoFireLocked` player attribute (currently unconsumed — the lock ring was removed 2026-08-07); the controller is destroyed pcall-guarded in the hunter-switch teardown

## Team modes

The local tracer sim skips allies exactly as the server's shot does, so the visual and the
authoritative raycast agree about what stopped the round.
