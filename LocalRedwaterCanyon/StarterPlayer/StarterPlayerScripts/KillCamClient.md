# KillCamClient

On death, desaturates the screen, cinematically pans to the killer — player or bot — then lets the player orbit-watch their killer until respawn.

## What it does
1. Listens to the `KillCam` RemoteEvent. The payload is either the killer `Player` (player kills) or the killer bot's server rig `Model` (bot kills); `getKillerParts` branches on the type and the rest of the camera pipeline is shared
2. First plays a death color-correction tween (desaturate + dark tint over 1.25s, recovering over 0.16s) via the scene's `ColorCorrection` effect, then starts the kill cam
3. If a valid killer with a living character exists: shows a "KILLED BY [Name]" GUI, tweens the camera from a cinematic start CFrame to an end CFrame behind the killer (1.05s), then switches into a mouse/touch-orbitable follow camera around the killer (smoothed via CFrame `:Lerp`). Bots present identically to players — the name comes from the rig's `BotDisplayName` attribute, with no bot marker
3a. **The killer card is an authored template** (`StarterGui.KillCamGuiTemplate.KillCamGui`), cloned by `createGui` at runtime; only its placement is computed in code. The template sits in a Folder wrapper (`KillCamGuiTemplate`) so RoundClientController's round sweep, which force-shows any top-level ScreenGui it has no stored state for, never sees it. The card's three rows — `Title` (28px "KILLED BY"/"YOU DIED"), `KillerName` (46px), `KillerTitle` (30px, reserved even while hidden so nothing shifts when TitleRenderer fills it) — are authored as `TextScaled` labels inside a 108px `Container` block
3b. Under the killer's name, the `KillerTitle` label shows the killer's equipped cosmetic title — read from the killer player's replicated `EquippedTitle` / `EquippedTitleId` attributes (published by the server's TitleDisplayService) and rendered through [[TitleRenderer]], which sets the text *and* its cosmetic style (gradient, halo, flames). Only players carry a title, so bot killers, suicides, and environmental deaths (the "YOU DIED" fallback with no killer) hide the label. `applyCosmeticTitle()` refreshes it whenever the killer name is set/re-set (including the freeze-on-killer-lost path); the renderer clears itself on empty text, so the single reused label never carries a previous killer's style
3c. **The killer card is bottom-anchored above the combat feed, not parked at a fixed screen fraction.** CombatFeedClient publishes the base-Y its rolling ELIMINATION/ASSIST feed is anchored to as a `FeedBaseYScale` attribute on its `CombatFeedGui`; that value differs per device profile and moves *up* on short/touch viewports, while the card used to sit at a hardcoded `0.55`. At 1080p the feed's first row occupied 610-654px against a killer title at 629-659px, so any reward earned on the trade that killed you landed straight on the killer's name (worse on phones, where the feed anchors as high as 0.49). `createGui` now reads that attribute — falling back to the desktop `0.565` if the feed GUI isn't up yet — and pins the card's bottom edge `FEED_CLEARANCE` (16px, scaled) above the first row. The container is a full `BLOCK_HEIGHT` 108px so its bottom edge is the block's true bottom: the cosmetic title's 30px slot stays reserved even while the label is hidden, so nothing shifts when TitleRenderer fills it a frame later. RoundStatusGui's timer stack is a fixed 58px box flush with the top edge (`ROUND_STATUS_HEIGHT`, was 110px at `y = 0.015` until the status line above the timers was deleted — the ceiling calculation dropped its `viewportSize.Y * 0.015` term at the same time — then 67px until the phase timer was pulled up under the match timer with -9px list padding), so when the gap between it and the feed is smaller than the card, the existing `MobileScale` shrinks the card to fit (floor `MIN_BLOCK_SCALE` 0.55) rather than sliding under the timer
4. **Bot killers** (`findBotVisual`): BotVisualClient hides the server rig locally and renders a smoothed clone in `workspace.ClientBotVisuals`, so orbiting the rig would frame an invisible bot. The rig is paired to its clone by the `BotId` attribute the clone inherits, resolved once per kill cam (not per frame) and cached. Geometry (the orbit root) is read from the clone; **liveness is read from the authoritative server rig**, because a clone's Humanoid is a spawn-time snapshot that never reports damage or death. Falls back to the rig itself when no clone exists (`ClientVisualSmoothing` disabled)
5. If the killer is invalid/missing (suicide, environmental death, or the killer already left): shows "YOU DIED" and opens a fallback cam framed on the local player's own corpse
5a. **The fallback cam orbits too** (`beginFallbackOrbit`, since 2026-08-13). It used to re-pin one frozen CFrame every frame with `isOrbiting = false`, so zone/firewall, fall and self-reset deaths gave a camera that could not be looked around at all — the one death cam where looking around is the only thing left to do, and on touch the only camera input that exists. It now shares the killer cam's yaw/pitch state, `setupTouchInput`, `updateMouseOrbit` and pitch clamps; only the pivot differs. That pivot is a **fixed world point** at the corpse rather than a tracked root part, because the body ragdolls after the death frame and a self-reset destroys the character outright — either would tumble the view or drop it mid-orbit. `getOrbitCFrameAround(pivot, distance, riseHeight)` and `setOrbitFromLookVector` are the extracted shared maths; the shot is authored as the offset `FALLBACK_OFFSET` (0, 7, 13) and its yaw/pitch solved back out of it, so the framing is the one that shipped. `FALLBACK_PITCH_MARGIN` (4°) then pulls the start angle off the stops: (0, 7, 13) solves to -28.3°, i.e. exactly `MIN_PITCH`, which would leave the first downward drag inert. When no character survives to be framed, the pivot is placed out in front of the last camera CFrame and yaw/pitch taken from it, so nothing snaps
5b. **The camera is claimed on the death FRAME** (`claimCameraOnDeath`, called from `watchLocalDeath`'s `Humanoid.Died`), separately from any presentation. This is purely about the cursor: PlayerModule pins the mouse to centre for as long as the camera is `Custom` in first person, and going `Scriptable` is what turns that off. Leaving it to the presentation left a visible lag between the swap cards appearing (raised by the server's death push) and the cursor actually moving — ~0.35s on a killer-less death, ~1.4s on a combat death, since the killer cam only starts once the death fade finishes. The claim holds the death-frame CFrame in a `RenderStepped` loop, so the view also stops tumbling with the ragdoll during the fade; both `startKillCam` and `startFallbackDeathCam` call `disconnectFollow()` and re-assert their own state, so they take over cleanly. The loop hands the camera back (via the forward-declared `restoreCameraSettings`) if the round ends while the player is still down, rather than holding it against RoundClientController's idle camera. `saveCameraSettings` is idempotent so the claim's snapshot of the pre-death camera survives — the kill cam re-snapshotting its own modified values would restore a Classic camera on respawn instead of the hunter's first-person setup
5c. **Killer-less deaths self-trigger the fallback** (`watchLocalDeath`). Zone/firewall, fall damage and suicide never fire the `KillCam` remote — only the combat modules and [[BotController]] do — so nothing used to take over the camera on those deaths. Because the character is still in first person, Roblox's PlayerModule re-pins the mouse to centre every frame, which left the HunterSwitchClient swap cards unclickable no matter what the hunter clients unlocked on death (their one-shot `setGameplayMouseLocked(false)` is simply overwritten). Making the camera `Scriptable` is what actually releases the cursor, so a local `Humanoid.Died` with no remote inside `KILL_CAM_REMOTE_GRACE` (0.35s) now starts the fallback cam. `killCamSequenceActive` is set the instant a remote arrives — not when `startKillCam` runs 1.4s later — so the fallback can tell "no killer" from "killer cam still fading in", and a late remote still upgrades the fallback into the real killer cam. Skipped when `RoundActive` is false so it never fights RoundClientController's intermission/idle camera. Unlike the killer cam the fallback engages immediately rather than after the fade — it has no cinematic pan to wait on, and the sooner it owns the camera the sooner the cursor frees
5d. **Both entry points sit the onboarding lesson out** (`workspace.TutorialMode`, added 2026-08-09): the remote handler returns and the killer-less fallback's `Died` handler returns before it claims the camera. Not a presentation choice — the lesson respawns instantly (`Config.TUTORIAL_RESPAWN_DELAY` 0), and this cam claims the camera on the death frame while only *opening* 1.4s later, so it would raise a death cam over a player who is already alive and hold it there: `restoreCamera` runs on `CharacterAdded`, which has long since fired. There is also nothing for it to present — one hunter, no swap cards, no killer worth studying.
6. If the orbited killer's character disappears mid-kill-cam — including a bot dying or despawning — freezes the camera at the last good CFrame rather than jump-cutting
7. **Cursor policy — the kill cam leaves the mouse FREE.** The hunter-swap card row (see the death-gated HunterSwitchClient) is on screen the whole time the player is down and has to be clickable, so `forceKillCamInputSettings` no longer pins `MouseBehavior` to `LockCenter` every frame. It still forces `CameraMode.Classic` and the zoom clamps, but sets `Default` + visible cursor unless a right-drag is in progress
8. **PC orbit is gated on holding the right mouse button.** `UserInputService:GetMouseDelta()` only reports movement while the mouse is locked, so `setupOrbitDragInput` tracks `MouseButton2` and flips the cursor to `LockCurrentPosition` (not `LockCenter`, so the cursor stays where the player left it) for the duration of the drag. `gameProcessedEvent` is respected on `InputBegan` — a right-click that landed on the swap UI belongs to the UI — but never on `InputEnded`, so the cursor can't get stuck locked. The first delta after a lock is dropped (`skipNextMouseDelta`) so the camera doesn't snap as the drag starts
9. Touch orbit needs no such gate (a finger drag reports `Delta` regardless of cursor state), so mobile keeps drag-to-orbit and tap-to-swap simultaneously. `setupTouchInput` binds orbit to the one touch `InputObject` that began on the world rather than to any touch delta, so a swipe starting on the swap cards belongs to the UI and a second finger can't double-apply yaw
10. Restores all camera/input settings, disconnects the orbit-drag connections, and destroys the GUI on respawn (`CharacterAdded`) and on `CharacterRemoving`
11. Orbit pitch is clamped to a -28°/+42° range on both input paths
12. **Publishes `KillCamActive`** on the local player so other client effects can stand down while the kill cam owns the screen. Set alongside `killCamSequenceActive` the instant the remote arrives (not when `startKillCam` runs, so the flag covers the death fade too), cleared in `restoreCamera` and on `CharacterRemoving`. Its one consumer today is ZoneAtmosphere's fire-wall tint: a player killed by a bot or another player while standing in the fire leaves a corpse lying past the wall, and the orange burn would otherwise stay layered over the kill cam's own death grade until respawn. Because only the combat modules and [[BotController]] fire the remote, killer-less deaths (the fire itself, falls, suicide) leave the flag unset and keep their zone tint
