# CardsClient

Fortuna's full first-person client: viewmodel rendering, all ability input, and combat request networking. The active replacement for the disabled FortunaCardsClient (HUD now lives separately in [[CardsHunterGuiClient]]). Phase 3 ported to consume [[HunterClientRuntime]] driven by the [[Manifest|Fortuna Manifest]] — replaces the inline `waitForSelectedHunter`, `getFortunaCardsFolder`, `getFortunaViewModelTemplate`, `getBindable`, and 7 RemoteEvent / 9 BindableEvent inline lookups with runtime references.

## What it does
1. Requires [[HunterClientRuntime]] + the [[Manifest|Fortuna Manifest]] and calls `HunterClientRuntime.Start(fortunaManifest)`; if not on Fortuna, the runtime returns nil and the script silently exits
2. Organizes itself into `CardsClient.C` (config/tuning constants), `.S` (mutable state), `.E` (BindableEvents — populated from `runtime.ClientEvents`), `.R` (RemoteEvents — populated from `runtime.Remotes`), `.ViewModelTemplate` (from `runtime.Viewmodel.Template`)
2. Builds and animates a first-person viewmodel every render step via a [[HunterViewModelMotion]] instance configured with `SwayMode = "CameraDelta"` (input-agnostic), `IdleShape = "VerticalOnly"`, `WalkBobXFactor = 0.55`, `SuppressIdleWhileMoving = true`; per-frame the viewmodel reads `S.BasicFlickCFrame` and `S.ReloadLeftArmCFrame` and pushes them into the motion's extra-CFrame slots so the card-flick / reload-arm animations compose into the final pivot. An airtime `VectorForce` that reduces effective gravity while airborne (floaty jump feel) is applied separately at the character level. Two looped viewmodel locomotion holds were added 2026-08-26 — `Walk` on the ground and `Run` once the sprint is actually engaged, both at Movement priority so an action clip reads over them, and both suppressed outright while a throw, reload, ultimate or Ability1 owns the arms, because a locomotion cycle blending underneath drags the cards out of frame. Airborne counts as not moving. The default `ArmsViewModel` was replaced 2026-08-29 with the same one-mesh-per-card rig the skins already used, and its `AnimationController` -- which had been left on the pre-rework 4-clip set -- was brought up to the full 10 the `ViewmodelAnimations` folder declares (`1`/`2`/`3CardThrow`, `Walk`, `Run`, `Recall`, plus the current `Ultimate` id). Before that the default skin fell back to `Basic` for every throw and had no locomotion holds at all, while both card skins looked correct. The tenth clip, `Idle`, was declared on all three rigs but **loaded by nothing** until 2026-08-29 — Fortuna was the only hunter with no base track. It now loads at Core, looped, and plays on build: a single-keyframe hold (0s) whose job is to be the pose the Action4 clips blend back down onto rather than releasing to the raw Motor6D transforms. It poses `Card1`-`3` as well as the arms, which is safe because card handling here is transparency-only (`applyCardVisibility`) and nothing writes card CFrames to fight it
3. **Basic throw** (left-click/tap): cycles through 3 pre-defined card slices with per-slice flick animation and throw delay, auto-triggers a reload when out of visible cards, and supports click-and-hold auto-repeat. Animation playback is sped up 2x (`BasicAnimationSpeed = 2`) and hold-repeat is halved (`BasicHoldRepeatDelay = 0.20`) — both roughly double basic throw rate. The BasicClicks init loop scales `ThrowDelay`/`FlickDelay` by `BasicAnimationSpeed` so throws stay synced with the sped-up animation. Since 2026-08-26 the clip is chosen by how many cards are still in the hand: `getCardThrowTrack()` indexes `1CardThrow`/`2CardThrow`/`3CardThrow` by `getVisibleCardCount()`, which still counts the card that is leaving because `playBasicSlice` runs before `hideCard`. The old single `Basic` clip stays loaded as the fallback for a rig that ships none of them, and is still what the Ability1 burst plays — that one throws the whole hand in a single clip. `stopBasicAnimation` stops all four, because the count moves mid-throw and the track that is playing is often no longer the current pick. Since 2026-08-28 those per-card clips are played from the top at a rate derived from each clip's own release frame (`CardThrowReleaseTimes`), rather than being seeked to the `Basic` combo's `PlayStart` offset — that offset fell past the end of `1CardThrow` and played nothing at all. `duration`, and so the fire cadence, is still computed from the combo's segment; `BasicClicks` retires `Card1`/`Card2`/`Card3` in the order the clips actually throw them; and per-card clips use a shorter `CardThrowFadeIn`.
4. **Reload** (R, or auto-triggered via [[HunterAutoReload]] when `AmmoChanged` fires with `newAmmo == 0`): plays a left-arm reload animation with staged visibility/position timings, then resets all 3 cards visible
5. **Ability1** (E): begins with a dash (fires `DashRequest` with move direction — falls back to camera forward if standing still — and attaches a `LinearVelocity` constraint to `S.CharacterRoot` (the character's HumanoidRootPart, NOT `S.RootPart` which is the anchored viewmodel root) in Plane mode so the ControlModule doesn't overwrite the push each frame, ramping speed via `computeAbility1DashSpeed` mirroring [[RevolverDashService]].GetDashSpeedAt, cleaned up after `Ability1DashTime = 0.5s`). Does not cancel sprint. After `Ability1DashThrowDelay = 0.15s`, fires `ThrowRequest("Ability1")`, plays a 2-burst rapid-fire animation sequence, continuously streams aim direction to the server via `Ability1AimUpdate` for re-aiming between bursts, and saves/restores card visibility state around the burst
6. **Recall** (Q): fires `RecallRequest`, starts the cooldown UI via the `RecallCooldownStarted` bindable, and since 2026-08-29 plays a `Recall` viewmodel clip. Like every clip, its id lives in the Fortuna manifest's `Animations` table (resolved via `loadAnimation` → HunterAnimations), so there is one id rather than one per skin to drift. `playRecallVisual` cancels the basic throw but **skips its own clip entirely** while a reload, ultimate or Ability1 owns the arms: `loadAnimation` puts all four on Action4, so two at once blend to an average instead of one winning. The cards fly back either way -- the skip only decides whether the hands re-animate. `RecallAnimationLength` is measured off the authored KeyframeSequence because `AnimationTrack.Length` is 0 until the asset finishes fetching, and it only decides when the track is released back to Idle -- the recall itself is instant server-side
7. **Ultimate** (F): requires full charge; fires `UltimateRequest` immediately (server handles windup), plays the ultimate animation, and on the `UltimateState` remote toggles invisibility-driven viewmodel hiding. Does **not** cancel sprint, and sprint is not gated during the cast or the invisibility window — the `SetCanSprintCheck` callback is `isCombatAllowed()` only
8. **Camera FOV** is composed per frame in `updateViewModel` as `DefaultFOV + ultEase * UltimateFOVBonus + sprintAlpha * SprintFOVIncrease`, with a single writer. The ultimate bonus rides on `S.UltimateFOVAlpha`, a hand-rolled 0..1 ramp (UltimateFOVInTime / UltimateFOVOutTime, Sine/Out eased) that replaced the old TweenService tween so the sprint widen can stack on top instead of being suppressed while invisible; `tweenFOV` survives only for the death/teardown restore, and the render step cancels any such tween before taking the camera back
9. Custom double-jump: disables `AutoJumpEnabled`, manually handles single jump on ground and one extra mid-air jump (cooldown-gated) with its own jump animation and `AssemblyLinearVelocity` impulse. `doJump()` is reached down **three** input lanes, all sharing one 0.08s guard: the `CardsDoubleJump` context action (Space/ButtonA, bound above ManuelJumpClient's priority so it sinks), `UserInputService.JumpRequest`, and — since 2026-08-08 — [[HunterMobileJumpButton]]'s `onPressed` fan-out. That third lane exists because the other two are both **dead on touch**: the mobile JUMP button is a plain `TextButton` (no context action fires) and it hides Roblox's built-in touch jump button, which was the only thing raising `JumpRequest` on a phone. Between that button shipping and this fix, a mobile press reached only ManuelJumpClient, whose `canJump()` requires the character to be grounded — so Fortuna's ground jump kept working and her air jump silently did not exist on mobile. The subscription is dropped in the hunter-switch teardown, since the button outlives every hunter and a stale listener would run her jump for the incoming one. The jump clip is loaded **once per life** via `getDoubleJumpTrack` ([[AnimationLoader]] `loadCached`), cached in `S.DoubleJumpTrack` against the animator it belongs to and replayed on each press; `stopCharacterState` releases it
10. Also listens to the `Ability1Requested`/`RecallRequested`/`UltimateRequested`/`ReloadRequested`/`FireRequested` BindableEvents (mobile buttons from [[CardsHunterGuiClient]]) and fires `Ability1CooldownStarted`/`RecallCooldownStarted`/`AmmoChanged`/`Reloaded` back for that GUI to display. `FireRequested` is the mobile FIRE button in **hold** style: a `true` payload presses (throws via `useBasic` + starts `startBasicHold` auto-repeat), `false` releases (`stopBasicHold`), a `nil` arg is treated as a press — mirroring the PC MouseButton1 path. The old delayed `UserInputService.TouchTap` mobile shoot handler was removed in favor of it
11. **Hand visibility replication**: every time `applyCardVisibility` runs, computes a 3-bit mask of which of Card1/Card2/Card3 are visible in hand and fires `CardsHandVisibilityUpdate` to the server (skipped when the mask hasn't changed). The server then writes a `VisibleCardMask` attribute on the character so `FortunaCardsWorldVisibilityClient` can mirror the hand state onto the world-cards prop other players see
12. **Auto-fire (touch only, 2026-08-07):** a [[MobileAutoFireController]] (forward-declared next to `autoReload`, constructed after the FireRequested wiring) reads the aim assist's `GetLock()` and calls **`useBasic()` directly — never `startBasicHold()`**: the hold state machine (`S.HoldingBasic` / `S.HoldToken`) belongs to the FIRE button's press/release pair, and hijacking it would let a real button release cancel an auto-fire the player never started. `FireInterval` is a fast 0.05s poll — `useBasic()`'s own `S.NextBasicTime` gates the real combo cadence, which varies per combo step with the animation's length. Passes `MaxLockDistance = CardsConfig.Basic.Range` (added 2026-08-07; 150 studs since the same-day range raise — the cap tracks the config by construction): the throw is hitscan hard-capped at that range, so a farther lock would only burn the 3-card hand into a reload for zero hits — the FIRE button stays unrestricted. `CanAutoFire` is `isCombatAllowed()` and not ultimate-invisible / ultimate-casting / Ability1-casting. Ticked in `updateViewModel` directly after `aimAssistController:Update(dt)`, plus in the not-alive early-out (gate fails there, resetting the lock state on death); `OnLockChanged` publishes the `AutoFireLocked` player attribute (currently unconsumed — the lock ring was removed 2026-08-07); destroyed pcall-guarded in the hunter-switch teardown
13. **Arm visibility** is owned by `applySpecialVisibility`, which `setViewModelVisible` defers to via `isSpecialPart` (claimed parts are skipped by the blanket transparency sweep). The left arm is hidden except during the ultimate cast and the staged reload fade; the right arm is visible except during the ultimate's invisible window, where it drops to `UltimateViewModelTransparency = 0.55`. Since 2026-08-12 each arm is a **pair**: the blocky original plus a `LeftArmSmooth` / `RightArmSmooth` mesh authored as its SIBLING at the viewmodel root, driven by a Motor6D of the same name parented inside the blocky part. `findArmSmoothPart` resolves the root-level BasePart for each (the name is ambiguous — a recursive lookup can return the Motor6D), and both members of a pair are claimed and given the same transparency. Before that, hiding only the blocky part left a floating smooth left arm on screen, and the right smooth arm stayed solid through the ultimate

## Dependencies
- **Requires:** [[HunterClientRuntime]], [[HunterActionLock]], [[HunterViewModelMotion]], [[HunterAutoReload]], [[AimAssistController]], [[MobileAutoFireController]], [[HunterMobileSprintButton]], [[HunterMobileReloadButton]], [[HunterMobileJumpButton]], [[HunterViewmodelContract]] (`Normalize`, on every fresh viewmodel clone — weapon-model rename only; its clip back-fill is gone), [[HunterAnimations]] (every viewmodel clip id, in `loadAnimation` — the clone's Animation instances are unread) (all from `ReplicatedStorage.Hunters.Shared`); [[Manifest|Fortuna Manifest]] (from `ReplicatedStorage.Hunters.Fortuna.Config`); [[RevolverConfig]] (for `AimAssist` tuning table); [[CardsConfig]] (`.Basic.Range` only — the auto-fire lock cap, added 2026-08-07); [[AnimationLoader]] (from `ReplicatedStorage.Modules`, for the double-jump clip and `loadCached` in `loadAnimation`). [[HunterClientState]]. The rest of the client's tuning stays hand-authored in its own inline `CardsClient.C` table rather than being read from CardsConfig.
- **Required by:** Nobody
