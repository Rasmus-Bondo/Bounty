# BreachChargeService

Bram's Ability 1 (Q): a **Reinhardt-style pinning charge**. Dash validation/cooldown reuses the hunter-agnostic [[RevolverDashService]] instance; the charge *movement* is CLIENT-owned ([[GrudgekeeperClient]] drives a steerable forward LinearVelocity for `BreachCharge.Time` seconds, A/D steering intact). This server module owns everything that must be authoritative: pinning, carrying, wall-slam damage + stun, and release.

## What it does
1. `TryStartCharge(player, moveDirection)` — delegates to [[RevolverDashService]]:DoDash (cooldown/alive/round validation, animation), sets a full-charge `KnockbackGraceUntil`, and registers the charge in `ActiveCharges` (token, start time, Bram character, empty `Pinned` set). A single shared `RunService.Heartbeat` loop (built in `.new()`, mirrors [[HunterStatusEffects]]) ticks every live charge
2. **Pin** — each tick, a frontal box in front of Bram (`BoxDepth`/`BoxHalfWidth`/`BoxHalfHeight`, measured in Bram's LIVE `HumanoidRootPart` object-space so it tracks his steering) grabs any enemy caught in it ([[HunterCharacterUtil]].GetHumanoidModels + IsEnemy). Pins are **sticky**: once grabbed a victim is carried just ahead of Bram (`CarryDistance`) until the charge ends. Pinning also claims the `StatusPinnedUntil` deadline that [[HunterActionLock]] reads — for players and bots alike — which is what locks a carried victim out of firing, abilities and reload. Before that existed only the wall-slam stun set a status flag, so the whole ram was ungated and the three displacement abilities (Dust's Quick Draw, Fortuna's Surge, Vesper's Grapple Hook) could break the carry and let `ReleaseDistance` below finish the escape. The claim goes through `HunterActionLock.AcquirePin(victim, pinKey(player), deadline)` and is dropped by the matching `ReleasePin` in `_unpin`, keyed per Bram (`"BramPin<UserId>"`). **The refcount lives in the shared module rather than here** because a victim can be held by more than one charger and the lock is a single attribute — and critically because the bot Bram's charge is a *separate implementation* in `BotCombat` that this service cannot see. A local `_isPinnedByAnyCharge` scan used to serve that role, but it only ever walked `ActiveCharges`, i.e. player Brams; with bots now claiming the same attribute it would have let a player Bram's release lift a bot's lock and vice versa. A deadline rather than a flag, so no skipped cleanup path can lock a player out for the rest of the round
3. **Charge clash** — a Bram whose grab box catches another Bram **who is himself mid-charge** does not pin him; both charges cancel and both Brams are stunned for `ClashStunDuration` (1.5s) via [[HunterStatusEffects]]:ApplyStun (launch issue #23, fixed 2026-08-05). Before this, nothing in the pin scan excluded a charging victim — it excluded only self, already-pinned, dead and same-team — so two charging Brams **pinned each other**. Player victims are carried by their own client, so A's client wrote A to `CarryDistance` in front of B while B's client wrote B in front of A, each position defined by the other's one frame stale: a stable two-frame oscillation snapping ~8 studs per frame. It never self-released, because the gap peaked at 10 studs, under `ReleaseDistance` (16), so the desync check never fired and both players rode out the full `Time + PinGraceBuffer` (~3.8s) locked out of fire, reload and abilities by `StatusPinnedUntil` with no way to cancel. The test lives **inside** the pin geometry rather than in its own sweep so the two can never disagree — whatever would have been pinned is exactly what clashes — and it reads `ActiveCharges`, the authoritative charge set, so it needs no attribute and cannot be spoofed. Resolution reuses `_releaseCharge` rather than a bespoke teardown: it is already the "ended without a slam" path, so each Bram's own carried victims drop for `ReleaseDamage`, `IsDashing`/AutoRotate reset, each cooldown restarts from now, and the `"ChargeEnd"` FX stops each client's local charge loop — which is why this needed **no client change at all**, a server-initiated end being the same message the wall slam already sent. **There is deliberately no knockback, no clash damage and no impact FX**; the stun is the entire read, and a bounce would have been a new mechanic to tune. `ClashStunDuration` is deliberately shorter than `SlamStunDuration` (2.5) — a slam is a play the victim lost and pays 50 damage on top, while a clash is symmetrical and both Brams already forfeit the charge and a full cooldown, and in a free-for-all two Brams stunned together in the open are a free double-kill for any third player. Two guards make it safe inside the shared Heartbeat loop: `_scanForPins` returns `true` so the caller stops touching a charge that no longer exists, and `_updateCharge` bails when `ActiveCharges[player] ~= charge`, because one tick ends **two** charges and clearing a key mid-`pairs()` does not un-schedule the other Bram's entry — without it that stale table would re-pin the victims just dropped and restamp a cooldown the clash had already restarted. **Player Brams only:** a bot Bram's charge is a separate implementation in `BotCombat` that never enters `ActiveCharges`, and it is not this bug — a bot is server-owned, so a player pinning a charging bot is one-directional with none of the client-vs-client oscillation
4. **Carry** — every carried victim gets a **lane** (`Slot`, assigned in `_pin`, converted to a lateral offset by `BreachCarryGeometry.laneOffset`: centre, +1, -1, +2 … at `CarryLaneSpacing`). Before lanes existed all victims were written to the *same* carry point and later the same settle point, i.e. several interpenetrating character assemblies; the grab box is 12 studs wide so 2-3 victims per charge is routine. The carry point is also **clamped to clear space** every tick by `BreachCarryGeometry.clampToClearSpace`, which **spherecasts** (`CarryCastRadius` 1.5, a body half-width) from Bram's own position — known-clear, he is standing in it — toward the intended point and stops just short of anything solid. **A single ray is not sufficient and was the original defect:** Redwater's cover is a wooden lattice of 1.4-stud beams and 0.6-stud panels with gaps, and measured over 216 headings a centre ray reported "clear" on 6% of directions where a body-radius cast collides. The offset uses `result.Distance` — the sphere *centre's* travel, which already stands off the surface by the cast radius — so subtracting `SlamWallClearance` on top would double-count and yank victims backwards off every wall. That clamp is what stops a victim being force-written *inside* geometry: the carry sits `CarryDistance` (6) ahead of Bram, but the wall test only counts a face as a wall at `|normal.Y| <= cos 55`, so a **steep slope stops Bram without ending the charge** and he bulldozes the victim into it for the full 3 s while this loop re-teleports them and zeroes their velocity each frame. A zero-velocity assembly repeatedly forced inside terrain is ejected unpredictably, and on sloped ground that ejection goes *down* — the observed failure was a bot sent through the floor into the void and another left inside a rock, from a **single** victim, at a corner where a 0.65-normal terrain face meets a 0.05-normal rock face. Bots are server-owned, so the loop writes their `CFrame`/velocity directly each tick; a bot's brain + humanoid fight that, so pinning it (a) sets the bot AI's own `BotUltimateMovementLocked` attribute (BotBrain honours it, skipping strafe/combat movement) AND (b) registers a per-Bram zero **override** on [[HunterMovement]] (`BramPin<userId>`, with `LockJump` and a TTL covering the pin plus the slam stun), cleared on unpin. The zero speed is load-bearing: BotBrain runs `Pathing:Update()` *before* it honours the lock, so an in-progress path keeps issuing `Humanoid:MoveTo` and walks the victim out of the carry spot — a zero override makes that residual MoveTo a no-op so the CFrame carry write wins and the victim locks in front. This used to snapshot the bot's live WalkSpeed and write it back on unpin, so pinning an already-slowed bot locked the slowed speed in for the rest of the round; an override needs no "before" value at all. **Player victims are network-owned by the SERVER for the duration of the carry** (`SetNetworkOwner(nil)` in `_pin`, re-asserted every tick by `ensureCarryOwnership`, handed back explicitly in `_unpin` with a `task.delay` watchdog as backstop). Without it the clamp below is computed correctly and then thrown away: a player owns their own character, so the server's CFrame write loses to their client's pin loop — measured mid-carry, the victim sat 2.9 studs from the *unclamped* carry point and 6.8 from the clamped one. Ownership is also what closes the `StreamingEnabled` hole, since a client cannot clamp against lattice geometry it has not loaded. Consequently `_maintainPins` now **writes player victims server-side too**; that branch previously had no server write at all, so taking ownership without adding one would leave nobody driving them. The `BreachChargeFX` "Pin" message still goes out and [[BramWorldFXClient]] still follows Bram locally, but it is now client-side *prediction* against the server's write rather than the source of truth. **The restore must name the player** — `SetNetworkOwnershipAuto()` was tried first and measured not reassigning at all, leaving test players server-simulated (visibly floaty, no on-screen cause) until they next died. `KnockbackGraceUntil` is kept fresh on dragged victims so MovementChecker ignores them. Victims that die / vanish / desync past `ReleaseDistance` are dropped
5. **Wall slam** — while carrying ≥1 victim, two triggers end the charge as a slam: (a) the per-tick server forward raycast (`WallCheckDistance`); (b) the client-reported `OnWallHit`, re-verified within `WallVerifyDistance`. Both use `BreachCarryGeometry.findWall`, which counts a hit as a wall ONLY if it is **collidable** (`RaycastParams.RespectCanCollide = true`, so non-collidable triggers/cosmetics like the HealthPack's invisible pickup hitbox are skipped) **and steep** (`|normal.Y| ≤ cos 55°` = the module's `WallMaxNormalY`, so floors/ramps the flat torso-height cast skims don't count) **and not a character**. **Only the distance differs between the two call sites** — `WallCheckDistance` on the tick, `WallVerifyDistance` on the re-verify — which is why the module takes it as a parameter and never reads it: the test is shared, the authority is not. Both pass `_wallExcludeList`, which is `_carryExcludeList` **plus `workspace.WallMap`**: the map boundary is 64 invisible slabs (Transparency 1) up to 241 studs tall with vertical faces, so every one read as a slammable wall and a charge near the map edge paid 50 damage and a 2.5s stun against something the player cannot see. Measured 2026-08-05 over 3,000 charge starts, that was **55 of 298 stops (16%)**, now 0. Bots always excluded it (`BotCombat._rayParams`), which is why one boundary produced two symptoms — a bot ground to its timeout while a player was stunned by thin air. The boundary is deliberately **still respected by the clear-space clamp**, which keeps using `_carryExcludeList`: the slabs are solid, and writing a carried victim inside one is the void-death failure the clamp exists to prevent. It fires **two casts — a centre ray AND a `WallCastRadius` spherecast — and accepts either**, because neither alone is adequate and each covers the other's blind spot. Measured over 72 headings per site: at the wooden lattice the ray finds a wall on 43% against the sphere's 54% (the ray shoots the gaps between 1.4-stud beams and 0.6-stud panels), but at the CHARGEPOINT corner the ray finds 35% against the sphere's 28% — there the **sphere** clips the sloped floor first (`|normal.Y|` 0.65, rejected as a ramp) and never reaches the rock face behind it. Swapping ray for sphere therefore trades one blind spot for another; OR-ing them measured **0 regressions** at every site (39/28/0 vs the ray's 31/25/0), so no angle that used to slam has stopped slamming. The client's own `detectBreachWall` applies the same collidable+steep rule so the charge plows past props instead of stopping short. Each carried victim takes `SlamDamage` (via the injected `ApplyAbilityDamage`) **and is stunned** for `SlamStunDuration` ([[HunterStatusEffects]]:ApplyStun); a slammed **bot** is settled against the wall at the **raycast hit point** (`wallPosition`, backed off `SlamWallClearance`) — NOT a fixed offset from Bram, whose client-owned HRP lags the server and can be well short of the wall at slam time — and keeps BOTH its brain-freeze AND the zero movement override for the stun (both released via `task.delay` when the stun ends; the stun's own override from [[HunterStatusEffects]] holds independently, so releasing the pin's key early cannot free the victim) so it stays pinned to the wall rather than stunned in open ground. **Player victims get the same settle, and as of 2026-08-05 it is applied SERVER-SIDE by the same call, so both victim types land on the identical point.** It used to be shipped to the victim's own client as args 2-3 of the `"Unpin"` FX message and applied there behind a push-back-only guard — which failed routinely and skipped the whole reseat, the reported symptom being a slammed player left short of the wall while bots landed flush. The guard measured against the *client's* root position, which is the **lagging** copy ever since the server took ownership of carried players (2026-08-01); the premise it was written under had inverted and its comment was never revisited. `_unpin` also releases ownership *before* firing the remote, so it ran mid-flip. The settle never depended on Bram's lagging root anyway — it comes off the raycast hit on the wall, which is absolute. The write now sits **above** the `_unpin` call, which is what makes it stick: after that line the victim's own client owns them again and a server write loses. `"Unpin"` is now bare and [[BramWorldFXClient]] only stops its follow loop. Position is identical to a bot's; **orientation deliberately is not** — a bot is turned to face back out of the wall, while a player keeps their own yaw, because they are about to spend `SlamStunDuration` unable to move and an imposed facing would simply stick. Without it the victim is left *inside* the wall — the carry writes them `CarryDistance` (6) ahead of Bram every Heartbeat while the client reports a wall at `ChargeWallCheckDistance` (5), so at slam time they are a stud or more past the wall **face**, and the stun's WalkSpeed-zero then holds them in the surface for the full 2.5 s. Two properties matter and are easy to break: the settle is **small on purpose** (`SlamWallClearance` 2, just past the deepest skin's 1.73-stud forward geometry) so the victim reads as slammed INTO the wall rather than bounced off it, and it is a **push back only** — the client applies it only when it is genuinely past the safe plane (`(pos - safePos):Dot(forward) > 0`), because `WallVerifyDistance` (18) is a deliberately generous tolerance for a laggy client wall report and an unconditional teleport would *drag a victim who was safely short of the wall onto it*. Only the victim's client knows their true position; the server's copy lags, which is why the decision lives there. The client also reports its own wall hit (`OnWallHit`) — the server re-verifies a wall within `WallVerifyDistance` AND that pins exist before awarding the stun, so a spoofed WallHit in open field just releases
6. **Release** — `EndCharge` (client reports a natural end: timeout / Q again / airborne; firing no longer cancels) drops victims with only the minor `ReleaseDamage`, no stun. `_endCharge` clears the charge, resets `IsDashing`/AutoRotate, and fires `BreachChargeFX` "ChargeEnd" to the charger so a server-initiated slam stops the client's local charge loop (instead of grinding the wall to timeout). FX: a "Grab" flash per pin + a "Slam" flash at the wall, both via `BreachChargeFX`
7. **Cooldown runs from the END of the charge, not from the keypress** (launch issue #5, fixed 2026-08-04). [[RevolverDashService]]`:DoDash` still stamps at activation and has to — that stamp is what refuses a second Q mid-charge — so `_endCharge` restarts the clock from the charge's end instead. The **duration is untouched** (`BreachCharge.Cooldown` is still 6): moving the start point lengthens the effective gap on its own, from 3s after a full 3s charge to a flat 6s, and a charge that ends early on a wall now waits the same 6s instead of resuming a clock that had been ticking since the press. The restart is **skipped when the stamp is no longer the one `TryStartCharge` recorded** in `charge.CooldownStamp`, because Last Call refreshes the cooldown mid-charge on purpose (`ResetCooldown` → nil) and every landed blast shaves it (`ReduceCooldown`) — restamping would silently undo both. `GrudgekeeperClient` mirrors the same rule and the same guard client-side, since the HUD fill and the local input gate are its own. `GetRemainingCooldown` / `ReduceCooldown` / `ResetCooldown` expose the [[RevolverDashService]] cooldown table for Last Call's refund/refresh mechanics. `CleanupPlayer` unpins + clears on disconnect; `Destroy` disconnects the loop

**`ResetAll()` clears the charge cooldown at round start** (2026-08-06), called by GrudgekeeperModule on `ReplicatedStorage.RoundActive`. It delegates to the wrapped dash service, which is where the cooldown actually lives — the same place `ResetCooldown(player)` reaches for Last Call. Active charges are deliberately left alone: a round start rebuilds every character, and `_unpin` only has meaning against the character that was pinned.

## Team modes

An ally cannot be pinned, carried or clashed with -- the scan that finds pin targets skips them,
so the charge passes a teammate rather than picking them up.
