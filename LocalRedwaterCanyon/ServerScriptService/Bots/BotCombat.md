# BotCombat

Server-authoritative weapon and ability adapter for bots; reuses the authored damage calculators and shared status-effect primitive without treating NPCs as Players.

## What it does
1. OOP module (`BotCombat.new`); one instance per bot, configured with the controller, difficulty, and a seeded `Random`.
2. Maintains per-hunter weapon profiles (range, cooldown, magazine, reload time, tracer colour) for Dust (Revolver), Fortuna (Cards), Vesper (Sunspike Carbine), and Bram (Grudgekeeper). Each profile's `WeaponName` is the kill-feed icon key, so it must match that hunter's `Manifest.KillFeedWeaponName` or bot kills resolve a different icon than player kills. The bot-only ability keys (`Fan the Hammer`, `Card Burst`, `Card Recall`, `Fortuna's Hand`, `High Noon`, `Shrapnel Shell`, `Breach Charge`) are icon keys too and need their own templates.
3. Delegates damage calculation to the matching `DamageService` module (`RevolverDamageService`, `SunspikeDamageService`, `GrudgekeeperDamageService`), applying distance falloff and `DamageReductionPercent` attribute reductions. `_applyUltimateHit` takes an opt-in `ignoreDamageReduction` flag for true executes — only Dust's High Noon passes it, so that shot stays lethal through Bram's Last Call; every other caller leaves it nil and goes through `applyReduction` as before.
4. Tracks ammo and reload state; fires the weapon at the current target according to difficulty `FireRateMultiplier`, broadcasting muzzle/tracer FX via `BotShotFX` remote. `ThinkAbility` dispatches per hunter: Dust dash/Fan, Fortuna dash/burst/recall, Vesper grapple/pinning, and Bram charge-then-shell (the charge takes priority once the target is past `DesiredRange` but still within `Basic.MaxRange`, so the run never crosses the whole canyon). **A charging Bram bot cannot fire**: the fire guard rejects the shot while the bot's `IsDashing` is set, matching a real Bram, whose `tryFire` in GrudgekeeperClient returns early during a Breach Charge. Without it the bot landed a blast players are denied, and the Action4 shoot beat overrode the Action3 charge pose so the stowed shotgun snapped back out to the hip. The check is **Bram-only, not a blanket `IsDashing` test** — Dust's and Fortuna's roll is deliberately built to let a shot read mid-dash. Shrapnel Shell (E) is *not* blocked, because a real Bram's `tryShrapnelShell` has no charge guard either; only its world animation beat is suppressed, over in BotController.
4b. **`HoldFire` — the peaceful-bot flag** (added 2026-08-08). Both `FireAt` and `ThinkAbility` early-return at the **top** when the bot's model carries `BotHoldFire = true`: the bot keeps walking, pathing, choosing targets, taking damage and accruing ultimate charge, but never fires and never uses an ability. One flag disarms all four hunters because bot AI is not per-hunter code — aggression leaves BotBrain through exactly two calls (`FireAt` and `ThinkAbility`) and every hunter difference is a branch inside them. `TryUltimate` is called from *inside* `ThinkAbility`, so the veto has to sit **above** that line or bot ultimates escape it; Vesper's grapple is cast from inside `ThinkAbility` too (`_bestVesperHookSpot` → `GrappleToSpot`), and BotBrain's perch lifecycle early-returns unless `BotSniperPerchUntil` is set — written only once she has actually hooked — so blocking the cast leaves the whole perch state machine inert rather than half-running. `FireAt` checks the flag **itself** rather than relying on the brain's call site, because the ability branches re-enter it from `task.spawn`ed loops (Dust's Fan empties the cylinder, Fortuna's burst), so a burst already in flight stops shot by shot instead of running to completion. It deliberately does **not** touch movement: a stationary dummy teaches nothing about leading a target, and confinement is a separate mechanism. For the same reason it is not `BotBrain:SetActive(false)`, which stops the step loop, calls `Pathing:Stop()`, clears `FacePosition`/`IsStrafing` and drops `SetWorldScoped` — that is a frozen bot, not a peaceful one. Named `HoldFire` and not `Passive` because BotController already uses `"Passive"` as the HunterMovement base-speed layer key that owns every bot's WalkSpeed. Absent or false is a no-op, so the flag changes nothing in production; BotService owns setting it, stamping the attribute at spawn from either `BotConfig.HoldFire` (the blanket testing switch) or a per-bot `record.HoldFire` (`SetHoldFire`, what the tutorial uses). Both vetoes go through a module-local `isDisarmed(model)` that reads **`BotStandDown` as well** — the stronger inert state BotBrain implements, which returns out of the brain before any combat call. That would seem to make the second read redundant, and it is not: a bot stood down mid-fight can have a Fan or card burst already in flight, and those loops re-enter `FireAt` from their own `task.spawn` answering to nothing else. Either flag can also be hand-toggled on a live rig in the Explorer, so neither can be inferred from the other. Neither call is per-frame — one is per shot, the other runs on `AbilityThinkInterval` — so the attribute read is free at this frequency. **`TryFortunaDash` and `TryFortunaJump` carry their own `isDisarmed` veto as well** (added 2026-08-09): not every trigger passes through `ThinkAbility` — the health-seek defensive dash, the evasive hop and the vertical chase all call these directly from BotBrain, and BotPathing's traversal jumps arrive through the `JumpRequest` callback — so a HoldFire Fortuna in the tutorial dashed the moment the player shot her below the health-seek threshold. The mobility bursts are her abilities, and a disarmed bot uses none; ordinary walking is untouched.
4c. **Difficulty damage scaling** (`_damageScale`, added 2026-08-08): multiplies every damage path by the active tier's `DamageMultiplier`, which is `1` for `Easy`/`Normal`/`Hard` and `0.35` for the tutorial's `Training` tier — so this is a no-op outside the tutorial. Each of the three damage services **already accepted a multiplier**, so the basic-shot paths just pass it (Vesper's call was passing `1` for `headshotBonusMultiplier` and nothing for the separate sixth `damageMultiplier` argument); Bram's is applied between `GetTotalDamageForDistance` and `ApplyAccumulatedDamage`, and Fortuna's inline branch scales before `applyReduction`. It also covers the `overrideDamage` path and `_applyUltimateHit`, deliberately: a bot that cannot kill with its gun but still slams for full has not been made gentler. In `_applyUltimateHit` it is applied **before** the `ignoreDamageReduction` branch, because Dust's High Noon passes a percentage of the victim's MaxHealth as a true execute and would otherwise ignore every other lever.
5. Manages ultimate charge using each hunter's real passive/hit/headshot/kill values from config; charge persists across deaths for the current round. Bram reads his source-keyed table straight from `Bram.Config.Manifest.UltimateCharge.Sources` rather than a flattened copy. Broadcasts `BotUltimateFX` (`Start`/`End`) when the ultimate fires; the Dust and Bram `End` are broadcast **before any token check**, because `Destroy()` bumps `UltimateToken` — gating the broadcast on the token would skip it whenever the caster dies mid-window and leave [[BotVisualClient]]'s highlight, looping sound, and dust ring running forever on every client.
6. Implements hunter-specific ultimates: Dust's High Noon scan (each fire-time target takes the same true execute a player's locked shot deals — `HighNoonServerConfig.GetLockedShotDamage`, a percentage of the victim's MaxHealth, passed with `ignoreDamageReduction` — rather than the old flat `HeadshotDamage`, which left a full-HP Bram alive), Fortuna's card volley (`BotFortunaCardFX`), Vesper's scope shot with a grapple-perch trigger (`GrappleFX`), and Bram's Last Call. **Fortuna's ult publishes `UltimateUntargetable` alongside `BotFortunaInvisible`** when the invisible window opens (both cleared in `_finishBotUltimate`): `BotFortunaInvisible` is read only by [[BotVisualClient]] and HealthBarController, so without the second attribute an invisible Fortuna bot went on being lockable by a Dust player's High Noon — the player-vs-player escape did not hold for bots. A bot that dies mid-ult never runs `_finishBotUltimate` and leaks both attributes, which is harmless because BotService destroys the model on death and clones a fresh rig on respawn. All three ultimates register their speed change as a keyed [[HunterMovement]] modifier with a TTL (`BotUltimate` base for Dust's crawl and Fortuna's 31, `BotUltimateBuff` for Bram's +25%), which `_finishBotUltimate` clears unconditionally — clearing a key that was never set is a no-op, so it does not need to know which ultimate ran. All three used to snapshot the live WalkSpeed on cast and write it back on finish, so a bot that ulted while slowed kept the slowed speed for the rest of the round.
6a. **A Bram cancels a bot Dust's High Noon wind-up** (2026-08-31). `_tryDustUltimate` polls `HunterActionLock.IsLocked` on the bot's model every `BOT_ULTIMATE_CANCEL_POLL` (0.08s, matching the player's cone-scan interval) instead of waiting out a single `task.delay(LockInTime)`: a carry (`StatusPinnedUntil`) or wall-slam stun (`StatusStunned`) from either Bram implementation ends the cast with no shot, releases the public `Start` FX and runs `_finishBotUltimate`. Polled rather than checked once at fire time because a one-shot check would deny the damage but leave the highlight, looping sound and dust ring running for the rest of the lock-in; the final wait is clamped to the exact remainder so an uncancelled cast still fires on `LockInTime`, the duration the `Start` FX told every client to expect. Same counter a player Dust gets in HighNoonModule's scan loop (a parallel implementation, not a require).
7. **Bram Last Call** (`_tryBramUltimate`): a 10s buff window, not a cast — it deliberately never sets `BotUltimateMovementLocked`, and Bram keeps walking, shooting, and using abilities throughout. Publishes `UltimateActive` (MovementChecker speed-check headroom) and `DamageReductionPercent = 0.5`, applies +25% move speed as a proportional [[HunterMovement]] buff (so it composes with an enemy slow instead of replacing it, exactly like LastCallModule's player-side version), drops fire cadence 0.5s→0.25s and reload 1.76s→0.88s, refreshes both ability cooldowns on cast, and adds 25% lifesteal plus a −1s ability-cooldown refund per landed shot. Cadence changes go in per-instance `FireCooldownOverride`/`ReloadTimeOverride` fields — `HUNTER_PROFILES` entries are shared by every bot of that hunter and must never be mutated. `FireAt` and `ThinkAbility` both special-case Bram past their `BotUltimateActive` early-returns for this reason.
8. **Bram Shrapnel Shell** (`_tryShrapnelShell`): raycasts to `Range` (100), excluding `HealthPack`-tagged parts so only the solid `Base` stops a shell, then after the travel window applies the authored two-tier blast by root distance with no line-of-sight test — inner 5.4 studs for 50 damage + 30% slow, outer 12.2 for 25 + 15%. Fires the authored `ShrapnelShellFX`, whose client handler ignores its shooter argument, so the bot Model stands in for a Player, and plays the world shoot beat via BotController`:PlayWorldShootAnimation` — the same animation GrudgekeeperWorldVisualServer gives a real Bram's E.
9. **Bram Breach Charge** (`_tryBreachCharge`): the authored player charge is client-driven, steerable, and carries multiple victims; a bot has no client, so this is a simplified server-driven gap-closer that carries only the **first** enemy it catches and slams it into the first wall ahead (`SlamDamage` + `SlamStunDuration` stun), or releases for `ReleaseDamage` without a stun on timeout. Wall detection is [[BreachCarryGeometry]]`.findWall`, the same call the player service and the reporting client make (it *mirrored* a private `_isWallAhead` here until 2026-08-05): collidable **and** steep (`|normal.Y| ≤ cos 55°`) **and** not a character, tested by a centre ray **and** a `WallCastRadius` spherecast with either accepted (the ray shoots the gaps in the map's wooden lattice; the sphere clips sloped floors and rejects them as ramps before reaching the wall behind). The carried victim must be **excluded** from that cast, not merely rejected by the character test — they ride `CarryDistance` ahead and the sphere reaches `distance + radius`, so it lands on their body first and the wall behind them is never seen, leaving a carrying bot unable to slam at all. **Every victim, player or bot, is claimed on the [[HunterActionLock]] pin deadline** (`AcquirePin` in `_pinVictim`, `ReleasePin` at the top of `_releasePin` — above the player/bot branch, because the player branch returns early). Being rammed is identical from the victim's side: they cannot tell whether the Bram hauling them has a client, and all 12 gates that read the lock are indifferent to who did the pinning. This was **missing** while the player-Bram path had it, so a player carried by a bot Bram could keep shooting and dash straight out of the grab, after which the carry loop's own `ReleaseDistance` check dropped the pin and completed the escape — the ungated-ram hole [[HunterActionLock]] exists to close, left open on the half of the feature that has no client. The holder key is **this bot's model**, not the shared `BOT_PIN_KEY` string: the refcount is per holder, and one string shared by every bot would let two bot Brams on one victim release each other. On the slam path `_slamPin` applies the stun *before* releasing, so `StatusStunned` carries the lock on and the victim never sees an unlocked frame. **`_slamPin` seats PLAYER victims as well as bots as of 2026-08-05**, which closes a standing defect: the settle was gated behind `not pin.Player`, and `_releasePin` then fired an argument-less `"Unpin"` that [[BramWorldFXClient]] skips because it type-checks its arguments for Vector3s — so a player slammed by a bot Bram got no seat at all and was left floating short of the wall while the stun's WalkSpeed-zero held them there. It is written **directly** rather than routed through the victim's client, and that is the one place this legitimately differs from the player-Bram path: that path must ask the client because Bram's server HumanoidRootPart lags his client-owned one, whereas a bot's root *is* authoritative. It must therefore happen **before** `_releasePin` hands network ownership back, or the write loses to the victim's own client. It is deliberately **not** also passed through `"Unpin"` as a second application, since a redundant client write risks a visible double correction. The same pass replaced a hardcoded `3` — the exact value `GrudgekeeperConfig` warns reads as a rebound off the wall — with the config's `SlamWallClearance` (2) via [[BreachCarryGeometry]]`.settlePoint`, which also backs the victim off along the **charge direction** rather than the wall normal (1.53 studs apart on a 45° hit, and the charge direction is what the player path uses); guarded by `.isPastPlane` so a slam granted at long range can never *pull* a victim onto a wall they were clear of; and it now preserves the victim's own yaw instead of writing a bare `CFrame.new()`, which had been snapping slammed victims to face world +Z. A **bot** victim additionally needs both `BotUltimateMovementLocked` and a zero-speed [[HunterMovement]] override — BotBrain runs `Pathing:Update()` before honouring the lock, so a residual `MoveTo` would otherwise walk the victim out of the carry spot. The override replaces a snapshot-and-restore of the victim's live WalkSpeed, which permanently locked in a slow if the bot was already slowed when pinned; a **player** victim gets a `BreachChargeFX` `Pin`/`Unpin` `FireClient` and follows locally — **but the carry loop also writes the victim's `CFrame` server-side every iteration regardless of type**, so a player rammed by a bot Bram has two writers and the client-side clamp alone cannot protect them. [[BreachCarryGeometry]]`.clampToClearSpace` therefore guards that write (a private `_clampCarryToClearSpace` mirroring the player service's copy until 2026-08-05): it **spherecasts** (`CarryCastRadius` 1.5) from the bot's own position — known-clear, it is standing there — toward the intended carry point and stops just short of anything solid. Two things about it are load-bearing and were each a bug first. It must **spherecast, not ray**: the map's cover is a lattice of 1.4-stud beams and 0.6-stud panels with gaps, and a centre ray reports "clear" on ~6% of headings where a body collides. And the call must pass **an exclude list containing the victim** rather than `_rayParams()`'s — that builder is for line-of-sight and excludes only the bot, so the cast hit the victim (who is *standing at the carry point*), the old copy's character guard fired, and the function returned the **unclamped** candidate on every single frame. It was a no-op from the moment it was written, which is why adding the spherecast and server ownership both appeared to change nothing. **That character guard is now gone**: excluding the victim was the actual fix, and the guard's only surviving effect was that a *third-party* character standing between bot and carry point made the clamp a no-op for that frame. Player victims are additionally **server-network-owned for the carry** (`takeBreachOwnership` / `ensureBreachOwnership` each tick / explicit `SetNetworkOwner(player)` restore in `_releasePin`, plus a watchdog), because a server CFrame write on a player-owned character is silently discarded in favour of their own client. Without it the bot pushes its victim straight through geometry, because the wall test above only ends the charge on a face steeper than `cos 55°`, so a **slope** stops the bot without stopping the charge and it bulldozes the victim into the surface for the rest of the duration while this loop re-teleports them and zeroes their velocity each pass. A player forced through a wall by a bot Bram was the reported symptom; the equivalent defect on the player-Bram path voided a bot into the map's underside. `KnockbackGraceUntil` uses `tick()`, not `os.clock()`, because that is what MovementChecker compares against. **A stalled bot charge now releases instead of grinding** (2026-08-05): blocked by something the wall test does not accept — most often the invisible `WallMap` boundary, which `_rayParams` already excludes from that test — the bot used to press against it for the rest of its duration. The loop now breaks after `StallGrace` of continuous movement below `StallSpeed`, landing on the ordinary timeout path (`ReleaseDamage`, no stun, because nothing was rammed). Measured on **displacement, not `AssemblyLinearVelocity`**, since `DashToward` drives a WalkSpeed override that keeps asserting speed against a surface. Its 0.3s startup floor is larger than the player path's 0.15 **on purpose**: a player charge is a client-driven LinearVelocity at full speed on frame one, while `DashToward` must resolve a path and spin the humanoid up, and without the floor a bot would abort its own charge during startup every time. The active pin is tracked on `ActiveBreachPin` so `Destroy()` can hand the victim back — a Bram killed mid-charge would otherwise leave its victim frozen for the rest of the round. **The cooldown restarts when the charge loop exits, not when `_ready` stamped it** (launch issue #5, fixed 2026-08-04, matching the player path in `BreachChargeService:_endCharge`). `_ready("BreachCharge", …)` both checks and stamps at activation, which is what stops the brain re-entering mid-charge, so the restart is a single write to `AbilityCooldowns.BreachCharge` on the line every `break` and the loop condition land on. Bot charges are distance-scaled (`0.45s` to `Time`) so the shift is smaller than the player's, but without it a bot Bram re-rams sooner than a player Bram can. The two early-return paths that refund the cooldown to `nil` when the charge never starts are unaffected.
10. **Fortuna jump** (`TryFortunaJump`): the single choke point for all four jump triggers, so the cooldowns stay in one place — called from BotBrain (vertical chase, evasive hop), from `ThinkAbility`'s own Fortuna branch (high ground), and from BotPathing's blocked-route recovery through the `JumpRequest` callback BotController installs. Each mode has its own cooldown. **Evasive** is the one mode with no destination: it skips the pad search entirely, passes `KeepMovement` so she keeps her strafe, and spends only the first jump — the second would just hang her in the open. The other modes peek the cooldown **non-destructively** before paying for the pad sweep, since `_ready` arms the cooldown the moment it passes and the raycasts are not free. `DesiredRange` is read off the controller's behavior table and handed to `ChooseJumpLanding`, which cannot reach it otherwise. The high-ground branch sits **last** in the Fortuna `ThinkAbility` chain on purpose: height is a positioning choice, not a substitute for damage, so she only takes the crate or shelf between her and the target while the card burst and recall are both still cooling. Nothing pins her up there — `_combatMovement` walks her back off on its own next cadence, so it needs no lease and no eviction rules, unlike Vesper's perch.
11. **Vesper perch selection** (`_bestVesperHookSpot`): the authored `VesperHookSpots` markers sit on the sloped **lip** of a rock or tower, not on ground a Humanoid can stand on — 13 of the 33 markers have a surface steeper than 43° directly beneath the old `marker + PullTargetHeightOffset` landing point, up to 80°, so bots slid straight back off. `resolvePerchPad` instead searches a ±6-stud grid around each marker for a pad with slope ≤ 35°, headroom, and most of a 3-stud ring at the same height, scoring for flat/wide/close/level; every Redwater marker resolves to one 2–6 studs away. Results are cached per marker (markers are static), including misses, and a marker with no pad warns once and is excluded. `resolveGrappleAim` then picks the pull target and doubles as the reachability test: it capsule-sweeps a **single straight line** (bots grapple like players, they do not route around rock) and returns the first clear one, so an unreachable perch is never chosen rather than attempted and failed. The aim must sit **above** the pad — the pad is inset a few studs from the marker on top of the rock, so a line drawn straight at it clips the lip: aiming at the pad is clear for 6% of marker/approach pairs versus 39% at +8. It tries `AIM_CLEARANCES = {4, 6, 8}` in order so the arc stays as flat as possible; the player's own `PullTargetHeightOffset` of 4 suffices about 62% of the time. Returns marker, landing pad, and aim point as three distinct values. Passing `escapeFrom` (a threat position published by BotBrain when it evicts her under pressure) switches the search to disengagement: the upward-only rule relaxes to `heightGain >= -14` so she can rappel sideways or down off her own rock, candidates must gain at least 25 studs of separation from the threat so she cannot "flee" to a perch the attacker is standing under, and scoring is by separation rather than height. That relaxation roughly doubles her options — median 5 escape perches versus 3 upward-only, with only 6% of rushed situations having none. `HasEscapePerch` exposes this as a public probe for BotBrain's fight-or-flight decision, so "can I flee?" is answered against real geometry rather than assumed. An `escapeFrom` query also **bypasses the perch-hold and commit early-outs** — an escape deliberately abandons the perch she is standing on, so the guards that stop her re-hooking mid-camp must not block it. `BotFightBackUntil` suppresses grappling entirely while she has chosen to stand and fight. The grapple cooldown is peeked non-destructively before any of this, since `_ready` arms the cooldown when it passes and the scan is not free.
12. Validates line-of-sight for both basic shots and ultimate candidates via `workspace:Raycast`, excluding the shooter model and scene furniture folders (`VesperHookSpotsBot`, `WallMap`). `_ultimateCandidates` takes an opt-in `skipUntargetable` flag that drops anyone carrying `UltimateUntargetable` — an invisible Fortuna, player or bot — **or `SpawnProtected`**, the shield attribute SpawnProtectionService writes for the 3s window after a spawn. Only Dust's two High Noon scans pass it (the initial gate and the fire-time rescan), mirroring HighNoonTargeting for the player: a bot Dust must not spend its ultimate locking someone the ForceField makes immune, and the flag is checked at both scans so a player who spawns during the lock-in window drops off before the shot. Fortuna's own outgoing ring and Bram's proximity gate deliberately leave it off, because their player-side equivalents are plain raycasts that still hit an invisible Fortuna, and their damage against a shield is simply absorbed rather than mis-aimed. `CanSee` takes an optional `maxDistance`; it defaults to the weapon's attack range, and abilities that reach further than the gun (Bram's charge closes distance he cannot yet shoot across) must pass their own or the range clamp rejects every valid use. It also takes an optional third
`ignoreCone` (2026-08-22): a bare line-of-sight answer for BotBrain's Domination threat test, where a
bot milling on a pad faces its walk rather than the enemy walking up to it.
13. **Vesper Pinning Round line of sight** (`_resolvePinningShot`): the round flies in a perfectly straight line, and the only gate used to be `IsInFireCone`, which is **yaw-only** — so a perched Vesper aiming down at someone below fired into the lip of her own rock. Measured against the 33 resolved perch pads, half of all pinning shots (49.6%) landed more than 12.5 studs from the target, and **two thirds of those died within 15 studs of the shooter** (mode 6–9 studs — her own platform), which is exactly the wasted-cooldown complaint. The resolver now raycasts the full flight (`ThrowSpeed * MaxFlightTime`, the same line the launch loop steps) and accepts only when the round would land within half the zone radius of the target root, so the test is *where the zone lands*, not whether a ray is clear. It tries aim points at the target and at 6 and 12 studs **past** them: pushing the aim out flattens the line, which is what clears a lip, and the 25-stud zone still covers the target — but each candidate is validated by its landing point, so a flat long-range shot that would sail over the target and come down elsewhere is rejected rather than assumed good. `ThinkAbility` **peeks** `AbilityCooldowns.Pinning` instead of calling `_ready`, and only consumes the cooldown once a line resolves; without that the fix would be a downgrade, holding the shot *and* burning 12s. `_launchPinningRound` now takes the resolved origin/direction rather than recomputing them, so the validated line and the fired line cannot diverge. Net effect from a perch: 55% of opportunities fire (5 points of that recovered by the aim-push) and 45% hold the ability until the angle opens.
12b. **Stealth gating** (2026-08-06). `ThinkAbility` returns early when the target satisfies [[HunterCharacterUtil]]`.IsStealthed`, which is one gate covering every ability that aims at `targetCharacter` — Dust's dash and Fan, Fortuna's burst and recall, Vesper's perch choice and pinning resolver, Bram's charge and shell — rather than four that drift apart. It sits **below** `TryUltimate` on purpose: ultimates run their own candidate scans and never consult the brain's target, and Dust's High Noon already drops her through `_ultimateCandidates`' `skipUntargetable`, so gating them here would let her stealth suppress an ultimate aimed at somebody else entirely. `_ultimateCandidates` itself is **unchanged** — Fortuna's own outgoing ring and Bram's proximity gate still see her, because their player-side equivalents are plain raycasts and untargetable never meant unhittable.

12c. **Position-based perception** (2026-08-06), the half of the stealth model that lets a bot shoot at a memory. `GetFireConeDot` and `CanSee` both resolved a character to `getAimPart(...).Position` and then worked on a point, so each grew a point-taking twin and the character version now delegates: `GetFireConeDotToPosition` / `IsPositionInFireCone` / `CanSeePosition`. `CanSeePosition` cannot use `CanSee`'s "or the ray hit the target" clause — the aim point is a spot in space with no character attached — so it accepts a clear ray **or** a ray that stops within `STEALTH_AIM_HIT_TOLERANCE` (4 studs) of the point. That tolerance is load-bearing, not slack: a ray stopping essentially *at* the aim point is a body standing where the bot last looked, and rejecting it would delete the counterplay the whole path exists for, namely that a Fortuna who vanishes and does not move should still be shot. 4 studs because `getAimPart` returns the torso centre, so the ray stops ~1 stud short on a player and up to ~2.25 on a bot, whose `BotAssistHitbox` reaches past the visible rig. `FireAt` gains an `AimPoint` option that overrides where the shot is *aimed* and nothing else — the raycast is untouched and still resolves whoever is actually on that line, and the fire-cone test and `LastBotFireConeDot` switch to the position variants when it is set.

14. Fires `DamageDirection` to the victim client on every successful hit; records stats (shots fired/hit, headshots, damage) on the controller record. Multi-victim ability damage books one `ShotsFired` per victim so blast hits do not inflate bot accuracy. **It does not fire `KillFeed` itself** — both damage paths (`_applyUltimateHit` and `_damageTarget`'s caller) hand kills to BotController`:RecordKill`, which is the sole bot emitter and the only place the one-row-per-death gate is applied. An unused `killFeedRemote` handle sat at the top of this module until 2026-08-04 and was removed for that reason: a second emitter here would bypass the gate.
15. Creates `BotShotFX`, `BotUltimateFX`, and `BotFortunaCardFX` RemoteEvents in `ReplicatedStorage.Hunters.Shared.Remotes` at module load if they do not exist. Vesper's and Bram's own remote folders are created at runtime by `HunterServerRuntime`, so `getVesperRemote`/`getBramRemote` resolve those at use-time instead of aborting the server bootstrap.

## Team modes

Bots ask the same gate players do, at every site: target consideration, the ultimate hit, the
direct damage call and the pinning victim sweep. A bot will not fire on, or damage, its own side.
