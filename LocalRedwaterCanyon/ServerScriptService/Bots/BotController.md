# BotController

Owns and drives a single NPC character; composes [[BotPathing]], [[BotCombat]], and [[BotBrain]] into a unified per-bot lifecycle including rig assembly, weapon attachment, locomotion, facing, hitboxes, death, and ragdoll.

## What it does
1. OOP module (`BotController.new`): accepts a record, character model, config, and a death callback; wires up all sub-systems and starts the heartbeat tick loop. **Difficulty is per-bot as of 2026-08-08** — `record.Difficulty` names a tier and falls back to the global `BotDifficulty` via `config.GetDifficulty()`. Resolved once here and handed to both the brain and combat, so `BotService.SetDifficulty` applies on the bot's next spawn rather than immediately. The tutorial is what needs it: two tiers have to be alive in one round, gentler bots for the step that finally shoots back than for the ability steps, which one global cannot express.
2. **R15 rig assembly** (`buildR15BodyRig`): programmatically creates `Motor6D` joints for all 15 R15 body connections using `RigAttachment` CFrames, enabling standard animations on cloned hunter characters.
3. **Assist hitboxes** (`createAssistHitboxes`): attaches transparent `BotBodyHitbox` and `BotHeadHitbox` parts welded to `UpperTorso` and `Head` with sizes from `BotConfig`; tagged `BotAssistHitbox = true` so the raycast hit-detection path can find and classify them.
4. **Weapon attachment** (`attachDefaultWeapon`): clones the hunter's world-model from `ReplicatedStorage`, strips scripts, makes all parts non-collidable/massless, and connects it to the `RightHand` via `Motor6D` (Dust, Vesper) or `WeldConstraint` (Fortuna).
5. **Locomotion** (`setupLocomotion`): loads a directional animation set from `ReplicatedStorage.BotAnimate.Animate`, blending movement tracks by velocity using a two-nearest-neighbour weighted blend; also loads hunter-specific world-model idle/shooting animations via `getWorldAnimationId`, which since 2026-08-29 is a one-line resolve through HunterAnimations — bots fire the SAME manifest-declared clips the player-path visual servers resolve, so Dust's old hardcoded ids are gone with the rest of the folder reads. The Action-priority world idle is what holds each hunter's long gun; the world shoot track is Action4 for Dust/Vesper/Bram and Action2 for Fortuna.
6. **Dash animations**: `DashRollTrack` is the shared roll `RevolverDashService` plays for real players — neither `RevolverConfig.Dash` nor Fortuna's dash config sets an `AnimationId`, so both fall through to its default, and one track at Action3 serves the Dust and Fortuna bots alike. Action3 is what clears the world idle's arm grip while staying under the Action4 shoot beat, so a shot fired mid-roll still reads. **Both branches of `DashToward` play it** — Fortuna's open-lane burst scales it to the dash duration, Dust's terrain-following branch leaves it at natural speed because `RevolverDashService` does not scale it either (its 0.53s clip already outruns the player's 0.46s dash). Dust had no dash clip at all until this was added: the burst branch owned every animation call, and Dust never enters it.
7. **`IsDashing` on the Dust branch**: the terrain-following branch also publishes the attribute, which only the burst branch used to set. That is what makes the dash *commit* — [[BotBrain]]'s `_step` guard stops re-steering the bot mid-dash, where before `_combatMovement` ran again ~0.28s in and overrode the dash's own forced move. Suppressing fire for the window matches the player, whose shoot handler returns early while `RevolverDash` reports dashing. Two consequences have to be paid for: it is cleared on the **token alone, never on aliveness**, because it also suppresses BotPathing's launch/tumble recovery and must not stay latched on a corpse that lives another `RagdollDuration`; and because `BotPathing:Update` skips its velocity clamp while set, the release sheds any upward pop off a terrain seam before the clamp and launch suppressor re-arm. Only the vertical component — `MaxGroundHorizontalVelocity` (62) already exceeds the 58 dash speed, and damping horizontal the way the burst branch does would stop a walk-speed dash dead. Note the burst branch still clears the flag behind its aliveness check, so a Fortuna or Bram that dies mid-dash leaves it latched until the model is destroyed. **Dash speed itself is an Ultimate-priority [[HunterMovement]] base (`BotDash`) with a TTL**, not a snapshot-and-restore of the live WalkSpeed — the old version captured whatever the bot happened to be moving at, so dashing while slowed wrote the slowed speed back afterwards. The burst branch sizes its dash off `HunterMovement.Get` (the resolved speed with every modifier folded in) rather than the raw humanoid value.
8. **Bram bot Breach Charge animation**: Bram bots additionally load the looped `WorldAnimations.Charge` at Action3, and opt out of the shared roll (`AnimationId = ""`) because its legs fight the charge run. `DashToward`'s burst branch plays it immediately and stops it when the dash duration elapses — including when the bot died mid-dash, since the looped track would otherwise keep running on the corpse. Same clip real Brams get. **`PlayWorldShootAnimation` refuses to play while a Bram bot is charging**: that clip is Action4 and outranks the Action3 charge pose, so for its full 0.167s it threw the stowed shotgun back out to the hip. Basic fire is already blocked outright by [[BotCombat]]'s guard, but Shrapnel Shell (E) stays castable mid-charge — a real Bram's `tryShrapnelShell` has no charge guard, so blocking the cast would leave bots weaker than players. Only the beat is suppressed, never the ability.
9. **Facing** (`FacePosition`): rotates `HumanoidRootPart` toward a world position each tick during combat; suppressed while strafing.
10. **CollectionService tagging**: adds the `AimAssistTarget` tag to the bot character model so mobile aim assist can lock onto it.
11. **Heartbeat tick loop**: runs at `BrainTickInterval`; calls `BotBrain:Tick`, `BotCombat:UpdateUltimateCharge`, and locomotion blending each frame; calls `BotBrain:ThinkAbilities` on `AbilityThinkInterval`.
12. **Death and ragdoll**: on `Humanoid.Died`, calls the death callback, fires `SetActive(false)`, disables joints, and schedules destruction after `RagdollDuration`.
13. **Vesper grapple** (`GrappleToSpot`): fires `GrappleFX` to all clients, then flies the bot along **one straight line**, the same shape and pacing as the authored player pull — `pullSpeed = distance / TravelTime`, abort deadline at `TravelTime * 2`. It deliberately does not path around geometry; what keeps that honest is [[BotCombat]] only ever handing over a perch whose straight pull it has already swept clear, which is the bot's stand-in for a player aiming at something they can see. Takes three points from BotCombat: the marker (rope visual), the aim point above the platform (pull target), and the pad (landing). Arrival tests **overshoot as well as proximity** — a long pull covers several studs per frame at this pacing and can step clean over the `ArrivalRadius` sphere without landing inside it.
14. **Fortuna jump** (`JumpTo`): `Humanoid.Jump` is a dead end for bots — `Jumping` is state-disabled at build *and* force-reverted to `Running` by the `StateChanged` handler — so this is a pure velocity impulse, which is what CardsClient does for a real Fortuna's second jump anyway. The Humanoid drops into `Freefall` on its own, which is one of the states bots are allowed to be in. Horizontal travel is deliberately **not** scripted: the bot keeps its own `MoveTo` and steers itself through the air at walk speed, the same air control a player has. It recreates the client's airtime `VectorForce` (28% of gravity cancelled) because without it the arc is a third shorter than the pads were validated against. The second impulse fires only when the pad needs it, which is what makes the double jump read as a decision rather than a tic. **Jump animations are loaded here and nowhere else**: `setupLocomotion` only loads BotAnimate sets carrying a `LinearVelocity` attribute (the directional quadrants), and `jump`/`fall` have none — so before this, an airborne bot kept playing the Movement-priority run blend and visibly slid upward in a running pose, which is why early jumps did not read as jumps even when they fired. The full-body `jump` (1.08s) and looped `fall` (0.79s) clips sit at Action3, the dash roll's slot, which clears the world idle's arm grip and is never contested since she cannot dash and jump at once; the settle loop hands off from jump to fall once vertical velocity goes negative. Fortuna's authored 11-joint double-jump clip layers over the top at Action4 — a slot her Action2 shoot beat leaves free — so it reads as a flourish on the second kick rather than replacing the body pose. `IsJumping` is armed **before anything yields** (the `IsDashing` lesson) and held until the humanoid is genuinely grounded or `SettleTimeout` elapses — releasing it mid-descent re-arms the `MaxUnexpectedAirRise` watchdog while `LastSafeCFrame` is still the takeoff below, which is exactly what used to teleport grappling Vespers back to the canyon floor. It is cleared **on the token alone, never on aliveness**, or a bot killed mid-air lives another `RagdollDuration` with BotPathing's recovery passes switched off. A ledge she gains height on is registered via `MarkSafe`. `Destroy()` bumps the jump token, which strands the settle pass, so it also tears down the airtime force explicitly — otherwise a ragdolled corpse keeps falling at 72% gravity — and stops all three clips, since the looped fall track would otherwise keep running on the corpse the way Bram's charge loop once did. Passing `KeepMovement` (the evasive hop) skips the `Stop`/face/`MoveTo` takeover so the brain's existing strafe carries her sideways through the air.
15. **`Pathing.JumpRequest` wiring**: installed for Fortuna only, and after `BotCombat` exists because that is where the jump cooldowns live. Lets BotPathing's blocked-route recovery ask for a jump without holding a back-reference to the controller.
16. **Perch settling** (`_settleOnPerch`): the pull ends above the pad, so arrival zeroes horizontal velocity and lets the bot drop the last few studs (median 4, about 0.2s). The authored player arrival damps to 0.25 and adds a hop, which suits someone who can course-correct on landing; at this pull speed 0.25 still carries a bot off the far edge. `IsGrappling` and `AutoRotate` are held until the humanoid is actually grounded — releasing them mid-descent re-arms [[BotPathing]]'s `MaxUnexpectedAirRise` recovery while `LastSafeCFrame` is still the launch point far below, which teleported the bot back to the canyon floor. If still airborne after 1.2s the bot is placed on the pad directly (it was validated as standable before the pull), then the perch is registered via `BotPathing:MarkSafe` so a later stumble recovers to the rock rather than the floor. A token guards the pass; `Destroy` bumps it, since this runs on `task.spawn` rather than a connection.
17. **Kill reporting** (`RecordKill`): the single choke point for every bot kill — both [[BotCombat]] paths (basic shots and ultimates) call it, and it is the only place a bot kill-feed row is fired from. Resolves the victim's display name (real player, or another bot's `BotDisplayName`), claims the death via [[KillFeedGate]], then increments the bot's kill stat, fires `KillFeed` to all clients, and — when the victim is a real player — fires `KillCam` to that player with the bot's server rig so [[KillCamClient]] can play a kill cam of the bot that killed them.
    - **It is also where a bot's bounty streak is counted** (launch issue #21): `RecordKill` calls [[BountyService]] `registerBotKill(self.Record, self.Model)`, which marks the bot at the same 3-kill threshold players use. This has to hang off the emitter rather than off `Record.Stats.Kills`, because that counter is cumulative across lives and can never express "kills since the last death" — BountyService keeps the streak itself. Sitting inside the KillFeedGate claim is what stops a repeated call advancing the streak twice, the same reason the stat sits here. Required at use time rather than at the top of the file, matching BotService's own bounty calls.
    - **The claim is taken before the stat, not merely before the row** (launch issue #10). This is the one kill-feed emitter that also *books* the kill: player kills are credited once per death on the universal `Humanoid.Died` handlers via `LastDamager`, so a double call on the player path costs only a duplicate row, while a double call here would also double the bot's scoreboard kill. Returning early on a refused claim keeps stat, row and kill cam consistent with each other.
18. **Server physics ownership lock**: every bot BasePart is set to `SetNetworkOwner(nil)` at build so the server AI (`Humanoid:MoveTo`) authoritatively drives movement. A `DescendantAdded` handler re-locks ownership (deferred, after the joint lands) for any part welded onto the bot at runtime — notably Fortuna's stuck cards, which join the Humanoid's physics assembly. Without the re-lock, auto-ownership would hand the whole assembly to a nearby player and the server-driven bot would freeze in place.

## Team modes

A bot's kill feed broadcast carries its own team and the victim's, matching the player path.
