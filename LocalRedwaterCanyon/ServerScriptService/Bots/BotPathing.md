# BotPathing

Throttled `PathfindingService` wrapper with patrol/tactical destination sampling, alternate-lane detour selection, direct-escape fallback, airborne detection, and stuck recovery.

## What it does
1. OOP module (`BotPathing.new`); one instance per bot, holding path state, waypoints, stuck counters, and a request token for cancelling stale async computations.
2. Computes async paths via `PathfindingService:CreatePath` with the agent params from `BotConfig.PathAgent`; tokens prevent stale callbacks from overwriting a newer path.

2c. **"Am I computing?" is derived from the request token, never a boolean** (`ComputingToken` / `_isComputing`, 2026-08-19). Five sites cancel an in-flight computation and all five bump `RequestToken`, so comparing the two answers the question for free. It used to be a `Computing` boolean that each site had to clear by hand, and `_recoverFromInvalidState` did not — it bumped the token, the in-flight computation then returned at the stale-token guard one line *above* the clear, and the flag latched true for the rest of that bot's life. That silently disabled both the re-request guard in `RequestMove` and the stuck detector in `Update`, which reads the same flag and so could never rescue the bot it exists for. Do not reintroduce a boolean.

2d. **The navigation mesh is warmed on demand, after the map is dressed** (`WarmNavigation` / `warmNavigationMesh`; warm added 2026-08-19, ordering fixed 2026-08-23). Roblox builds the mesh **lazily**, on the first `ComputeAsync` of a server's life, and the calling thread waits out the whole build — measured **11.0s**, later **15.2s**, on Redwater. The entire bot fleet asks for a route in the same instant a round starts, so a round beginning mid-build opens with every bot standing still until it lands. One throwaway computation between the two furthest-apart spawn points pays for it while the round loop is still waiting for players. `IsNavigationReady()` reports completion, and as of 2026-08-23 **nothing waits on it** — RoundController gated the round on it for four days and stopped, so the flag is now purely observational (RoundController 0a2). A separate mesh exists **per distinct `AgentRadius`/`AgentHeight`**, so the warm-up walks `BotConfig.HunterBehavior` and builds every capsule it finds — `AgentCanJump`/`AgentCanClimb` are free (117 ms on a first-ever jump-enabled request against a built capsule).

2d-i. **The build must not run while the map is being dressed.** It measures the workspace as it stands, and RoundController's boot swaps the dressing right after the modules load — TeamBaseService parks the props a team mode replaces, CapturePointService un-parks the capture pads — with 36 of Redwater's parked props sitting *inside* `RedTeamBase`'s bounding box. Warming at module load put the bake in a race with that swap, and roughly one cold server in two came out with the red house's region **unbaked**: `ComputeAsync` from all twelve of its spawn markers returned `NoPath` for the server's whole life, so red's bots cycled the alternate-destination lane inside their own house while blue played the match. The warm is therefore no longer self-starting: `BotPathing.WarmNavigation()` is called by RoundController after the last `Apply` of a mode's geometry, at boot, on the tutorial path, and again on a mode ballot (which re-closes `IsNavigationReady()`, because that bake measures different geometry). A 20-second fallback warms unasked if nothing ever calls it, so the module still **fails open** in both directions — an unordered late warm is survivable, never warming is not.
2a. **Three tiers of path acceptance** (third added 2026-08-15). The ordinary path uses `PathAgent.AgentCanJump`, which is `false` for every hunter. If it fails, **one** jump-enabled path is computed and accepted only if its jump links satisfy one of two rules: `isSafeDropRoute` (every link a downward ledge of `SafeDropMinimumHeight`..`SafeDropMaximumHeight`) or `isSteppedRoute` (every link a small step within `SteppedRouteMaxStepUp` / `MaxStepDown` / `MaxHorizontalGap`, with **no** drop required). Either route is walked with `Humanoid.Jump` suppressed — the `WalkJumpLinks` flag, read by `_advanceWaypoint` — so the bot never enters the unstable `Jumping` state. The stepped tier is what stops a bot stranding on high ground: rock and crate tops are navmesh **islands**, and 48% of the 469 pads Fortuna's jump can reach have no `AgentCanJump = false` route back to the floor at all. Every one of those is solved by a jump-enabled path whose links are seams rather than jumps (worst measured step-up 2.3 studs, step-down 4.2), which the older safe-drop rule rejected because it demands a real drop. Before it, a Fortuna who jumped onto a rock never got another usable path and stood there shooting until she died.

3. Throttles re-computation with `PathRecalculateInterval`; consecutive requests to the same destination within a small radius are silently dropped.
4. On `MoveToFinished` (not reached): attempts an alternate-destination sample by casting rays around the blocked point across `AlternatePathSampleRadii`; falls back to a direct-escape `Humanoid:MoveTo` if sampling fails.
5. Blacklists unreachable destinations for `UnreachableDestinationCooldown` seconds after `PathFailureAbandonCount` consecutive failures; subsequent calls detour automatically.
6. Detects stuck state on a `StuckCheckInterval` heartbeat (position delta vs `StuckRecoveryDistance`) and triggers direct lateral escape.
7. Clamps all destinations to the safe zone via `ZoneService.clampPositionToSafeZone` using `FirewallAvoidanceMargin`.
7a. `GetFirewallEscapePosition` asks `ZoneService.getSafeClearance` how deep in the fire the bot is and escapes only when that is worse than `margin - FirewallEscapeCompletionTolerance`, then clamps to the margin for the destination. The hysteresis is the point: an exact boundary comparison stayed true for tiny path/terrain offsets and suppressed combat movement for the rest of the phase after the bot had visibly reached safety. Rewritten 2026-08-13 off the Z-bounds pair it used to read, so the escape runs inward along the radius on a radial map instead of along one axis.

7b. **Leash** (`_clampToLeash` / `_leashDirection`, added 2026-08-08): an optional flat (XZ) radius around an authored anchor, read from the `BotLeashAnchor` / `BotLeashRadius` model attributes that BotService stamps. The destination is **clamped to the edge, not rejected**, so a leashed bot walks to the boundary and stops rather than freezing whenever its own logic wants something outside. It sits in `RequestMove` immediately after the safe-zone clamp, for the same reason that one does: `RequestMove` is the single door every destination goes through — patrol, combat repositioning, the health-pack run — so no caller needs to know a leash exists. Measured flat so a hillside never eats into the radius, and the destination's own Y is preserved. **`DirectMove` needs its own check and this is not redundant:** Dust's combat strafe never calls `RequestMove`, and `DirectMove`'s `MoveTo` aims 100 studs out and persists between brain ticks, so an unchecked strafe walks a leashed bot clean out of its area. That check only turns an *outward* strafe from outside the radius; anything heading back in is left alone, and it sits below the near-zero magnitude guard so the unit vector is always safe. An absent anchor means unleashed, which is every production bot.
8. Exposes `FindNearestActiveHealthPack`, `IsPositionSafe`, `DirectMove` (immediate `Humanoid:Move` for Dust strafing), and `Stop`. **`IsPositionSafe` is a firewall/safe-zone containment test, not a standability test** — the name reads like a ground check and it was the only "validation" Vesper perch selection had, which is how bots ended up being pulled onto rock faces they could not stand on.
9. **Fortuna jump landing search** (`ChooseJumpLanding`, `_resolveJumpPad`, `_jumpArcClear`): returns pad, rise, and whether the second jump is needed, or nil when there is nothing worth jumping onto. Mirrors `ChooseOpenDashPosition` in shape. A body-sized `Blockcast` forward finds what is actually in the way, and a candidate qualifies two ways: **onto** (rise at or above `MinRise`) or **over** (past the obstruction, at any height). Without an obstruction a same-height pad is just walkable ground and jumping to it would be pure noise. `_resolveJumpPad` applies the rules the Vesper perch search already had to learn — slope, headroom, and most of a flat ring at the same height, because a lip reads as flat to a single downward ray. `_jumpArcClear` casts straight up to the apex and then across: an endpoint-only check happily picks a pad on the far side of a solid ceiling, and the map has bridge pillars and walkway undersides she fights beneath. `desiredRange` is passed **in** rather than read from config — `pathingConfigForHunter` only merges `PathAgent` overrides, so per-hunter behaviour values never reach this table. **Cost ordering is deliberate**: `_resolveJumpPad` takes an `accept(candidate, rise)` callback that is consulted after its single ground ray and *before* the seven validation rays (headroom + a six-sample ring). Most samples in open canyon are ordinary flat ground the jump has no reason to target, so rejecting them on rise alone rather than fully validating them first takes a 20-sample sweep from 123 raycasts to 35 — measured 0.474 ms to 0.204 ms per call, with pad selection verified identical across 500 cases. For reference the already-shipped dash-lane sampler costs 0.672 ms per call, so the jump search is the cheaper of the two.
10. **Jump-aware guards**: `IsJumping` is exempted alongside `IsGrappling`/`IsDashing` in the launch suppressor, the unexpected-rise clause of the fall watchdog, the velocity clamp, and the tumble stabiliser. The clamp one is load-bearing — `MaxUpwardVelocity` (42) is below both of Fortuna's impulses and would otherwise eat the takeoff on the frame it happened.
11. **`_tryProactiveJump`** (called from `Update`, throttled by `ProactiveJumpInterval`): the trigger that actually makes Fortuna jump. Hanging the traversal jump off `_recoverBlockedDestination` alone measured at **zero firings** — over 35 cross-canyon routes the pathfinder never failed once, it simply walked the long way around, so she was never asked. Probing forward on a timer finds a jumpable obstacle on ~21% of waypoint steps, which works out to a jump every ~5s of walking. It deliberately aims at the **destination, not the next waypoint**: the waypoints are already routed *around* the fence, so the straight line to the destination is the one that runs *through* it, which is the shortcut a player would take. Sits after the velocity clamp (so a takeoff impulse is never clipped on the frame it happens) and before stuck detection (so a hop resolves the obstacle rather than waiting to be classified as stuck against it). `LastProactiveJumpAt` is seeded with a **random phase**, not zero: the brain loop is a per-bot `task.wait(BrainTickInterval)`, so bots activated on the same frame at round start stay in lockstep indefinitely, and a shared start would put every Fortuna's pad sweep on the very same frame — turning a cost that should be spread into one visible hitch. `TryFortunaJump` also peeks the cooldown **before** the sweep, so ~71% of probes cost nothing at all; the measured total is 1.4 ms per second of server time for twelve Fortuna bots, about 0.2 ms in any single frame. Non-Fortuna bots exit on `not self.JumpRequest` — one nil check, zero casts.
12. **`JumpRequest`**: an optional callback BotController installs for Fortuna alone, used by both `_tryProactiveJump` and `_recoverBlockedDestination`; the latter still tries it before the alternate-lane detour for the genuinely-blocked case. Every other hunter has no callback and falls straight through to the existing behaviour. Note that a jump calls `Stop()` first, which nils `Destination` — that is what makes both branches of the `MoveToFinished` handler no-op instead of booking the jump's own `MoveTo` as a path failure.

12b. **Both jump triggers are vetoed during an authored walk** (added 2026-08-09): when the model carries `BotAuthoredWalk` (set by BotBrain's `SetRoute`/`SetApproach`, cleared when the route ends or the approach is cancelled), `_tryProactiveJump` returns immediately and `_recoverBlockedDestination` skips the `JumpRequest` lane. The proactive probe aims at the raw `Destination`, which during a scripted walk is the route waypoint — the tutorial's walk-in Fortuna hopped onto the scenery on that straight line and the waypoint re-path could not always recover. A transiently blocked authored route self-heals through the route's 1s re-path cadence instead.
13. `MarkSafe(cframe)` lets a caller register an already-validated standing position as the fall-recovery point. `LastSafeCFrame` otherwise only updates while grounded in the safe zone, so a bot that grappled to a perch kept the canyon floor it launched from as its recovery point and the first stumble teleported it all the way back down.
