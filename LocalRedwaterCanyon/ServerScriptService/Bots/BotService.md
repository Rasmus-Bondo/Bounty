# BotService

Round-slot ownership, hunter/name selection, live player-count reconciliation, bot respawning, kill crediting, and arena folder management for all bots in a Redwater Canyon round.

## What it does
1. Singleton service (table, not OOP class); called by the main server entry point at round lifecycle events: `Start`, `PrepareRound`, `ActivateRound`, `EndRound`.
2. **Reconcile** (`Reconcile`): computes desired bot count (`DesiredRoundParticipants - realPlayers`, clamped between `MinBots` and `MaxBots`, so at least 4 bots exist at every player count and `BotConfig.Enabled` is the only way to reach zero); then reconciles in three ordered passes. **Over target it flags, it does not delete** — the oldest records get `Retiring = true` and keep fighting, leaving on their next death in `_onBotDied`, because destroying a controller took its character with it and made an opponent vanish mid-fight. The surplus pass is a *bounded* `for`, not the old `while`: retiring records stay in `Records`, so a count-based loop could never see the count fall and would spin forever. **Under target it un-retires before it creates**, newest flag first, so a leaving player hands the slot back to the bot about to lose it rather than spawning a stranger — and because `_chooseHunter` counts a retiring record as live, draining the flags first is also what keeps `HunterCaps` honest for any record genuinely created after. The trailing "every record has a controller" pass skips retiring records, or one that just died would be resurrected inside its ragdoll window. Population counting is `countActiveRecords`, which ignores retiring records entirely. Called again when any player joins or leaves.
3. **Hunter selection** (`_chooseHunter`): weighted random draw from `BotConfig.HunterWeights` over the `EnabledHunters` list, minus any hunter that has hit its `BotConfig.HunterCaps` ceiling. The cap counts hunters across the live `Records` — which outlive death, since a respawn reuses its record — so it is a per-round population limit, not a per-spawn one. The all-weights-zero fallback also skips capped hunters before defaulting to Dust, so a cap can never be breached by the fallback.
4. **Character spawning** (`_spawnController`): clones the hunter's default character from `ReplicatedStorage`, destroys any `LocalScript` descendants, parents it to `workspace.ArenaBots`, pivots it to a safe spawn CFrame, then constructs a `BotController`.
5. **Spawn position** (`_spawnPosition`): samples `SpawnService.getSpawnParts()`, then picks randomly from [[SpawnService]] `getSafeSpawnPool` — the same fire-wall clearance rule players get, so a bot is never dropped on the wall's inner face or (via the old `or spawnParts` fallback) hundreds of studs behind it for BotPathing to escape from.
6. **Kill crediting** (`_creditPlayerKill`): on bot death, reads `LastDamager` userId from the model attribute and calls `ProgressionService.awardKill` for the killer, then — since bots carry bounties too — `BountyService.claimBounty(killer, record)` before `BountyService.registerKill(killer)`. That order matches RoundController's player-victim path: the victim's bounty is read before the killer's own streak can place a new one. Takes the dying bot's record as a second argument for exactly that reason. Skips entirely when the bot's `KilledByZone` attribute is set (written by ZoneService) — a firewall death credits no kill — and returns before the claim when no *player* landed the blow, which is what stops a bot-on-bot kill paying anyone (the bounty is still cleared, by `registerBotDeath`).
7. **Assist + stat-kill resolution** (`_resolveDeath`): also on bot death, calls [[RoundStatsService]] `ResolveDeath(model, killerPlayer, killerBotId)` — resolving `killerPlayer` from `LastDamager` and passing `LastDamagerBotId` — then awards assist XP/Cash via [[ProgressionService]] `awardAssist` for each returned UserId. Universal: credits contributors whether a player, a bot, or the zone/firewall finished the bot (the old `_creditPlayerAssistsFromBotKill` only fired when a *bot* landed the final blow, dropping assists on zone/player finishes). When `KilledByZone` is set it passes no killer, so a firewall death still awards assists but no kill.
8. **Respawn loop** (`_onBotDied`): resolves the record first (both the claim inside `_creditPlayerKill` and the clear below need it), calls `_creditPlayerKill` + `_resolveDeath`, then `BountyService.registerBotDeath` so the bot's bounty ends with its life exactly as a player's does — and only after the claim above has read it. After `RagdollDuration` destroys the controller, waits `RespawnDelay` and re-spawns the same record if the round is still active and no controller exists. **A record flagged `Retiring` exits here instead of respawning** — this is the whole reason retirement hangs off the death path rather than off `Reconcile`: credit, assists and `BotCombat`'s pin release have all already run by this point, so a retiring bot's last kill still pays out and any victim it was carrying is handed back. Its `_removeRecord` waits out `RagdollDuration` so the corpse behaves like any other, and re-checks the flag inside the delay, since a player leaving in that window un-retires the record rather than spawning a replacement. Retirement state never crosses a round boundary: `PrepareRound` calls `Cleanup(true)`, which clears `Records` outright.
9. **Arena folder**: creates `workspace.ArenaBots` on `Start`, storing client-smoothing config as folder attributes; `EndRound` clears all children for clean round reset. `EndRound` also calls `BountyService.clearBotBounty` for every record, and `_removeRecord` does the same for a single retiring bot: records outlive `EndRound` (only the next `PrepareRound`'s `Cleanup` clears them), so a bot still marked at the buzzer would otherwise hold a bounty-list row through the whole victory showcase pointing at a rig this function just destroyed. No payout either way — a bot that survives to the buzzer gets nothing, the same as one that dies holding it.
10. **Post-game stats** (`GetPostGameStats`): returns a list of stat tables (kills, deaths, damage, accuracy, etc.) in the same shape as player stat tables, used by the scoreboard/post-game UI. Every entry is tagged `isBot = true` — RoundController merges these into the player stats and relies on that flag to keep a bot below any real player on equal kills, so it must stay set.
11. **Best bot** (`GetBestBot`): returns the highest-kill bot record (tagged `IsBot = true`) plus its kill count, for RoundController's winner check.
12. **Transform broadcast**: resolves `Hunters.Shared.Remotes.BotTransformUpdate`, destroying and recreating it as an `UnreliableRemoteEvent` if an older reliable `RemoteEvent` is found, then fires a flat batch of `botId, pivot, velocity, isGrappling` on an accumulator tick — 10Hz for ordinary transforms, 20Hz while any bot is grappling. Unreliable is deliberate — stale pivots are worthless, so dropping them beats resending — but it also means the remote discards rather than queues when a still-loading client has no handler yet.
13. **The broadcast is per-player, not `FireAllClients`** (changed 2026-08-07): each tick it loops `Players:GetPlayers()` and sends only to those [[BotFXAudience]] reports ready. `FireAllClients` sent to every player from the instant they entered the player list, which on the server is `PlayerAdded` — seconds before that client has replicated the 7,000-descendant `ReplicatedStorage` and attached a handler. At 10-20Hz that produced dozens of discarded events per join, logged as "Remote event invocation discarded event". [[EarlyShotRemoteDrain]] attaches handlers as early as a client can but cannot close the window on its own, because a client cannot attach a handler to an instance it has not received yet — so the fix is on the send side. Bots still render correctly for a gated player: [[BotVisualClient]] builds its visuals from the `ArenaBot` tag, and the next batch lands within 100ms of the client going ready.
14. **Peaceful bots** (`SetHoldFire` / `SetStandDown`, both `(recordOrId, enabled)`, added 2026-08-08): two states of increasing strength, both owned here as flags and implemented elsewhere. **HoldFire** keeps a bot walking, pathing, choosing targets, taking damage and accruing ultimate charge but never firing and never using an ability — BotCombat vetoes `FireAt` and `ThinkAbility` on the `BotHoldFire` model attribute, and since 2026-08-09 `TryFortunaDash`/`TryFortunaJump` directly as well, because Fortuna's mobility bursts have callers outside `ThinkAbility` (health-seek dash, evasive hop, vertical chase, BotPathing's traversal jumps). **StandDown** additionally roots it where it spawned and stops it acquiring or facing a target, making it a live damageable training dummy — BotBrain returns out of `_step` on the `BotStandDown` attribute before it paths or fights, so it implies HoldFire. Both share one `setBotFlag` helper. They live on the **record**, not only on the rig, because `_spawnController` clones a brand-new character on every respawn — a rig-only flag would come back armed the first time a player killed the bot. `_spawnController` therefore re-stamps `BotHoldFire` and `BotStandDown` on each spawn from **either** source — the per-bot `record.HoldFire` / `record.StandDown` or the matching `BotConfig` key, the blanket testing switch — and writes them unconditionally (as `false` for an ordinary bot) so they are visible and hand-togglable in the Explorer on any live bot. The setters write both halves, so a bot toggled mid-round stays toggled through its next death. Neither flag leashes a bot: `StandDown` roots one completely, but confining a bot that is *allowed* to walk is a separate concern this service does not yet implement.
15. **Authored bot control** (added 2026-08-08), the set of levers a scripted sequence such as the onboarding tutorial needs. All of them store on the **record** and re-apply on spawn, because a respawn clones a fresh rig and builds a fresh brain.
    - **`SpawnBot(spec)`** — spawns one bot to an authored spec instead of letting `Reconcile` choose it, returning the record. `TargetPlayersOnly = true` (added 2026-08-09) stamps `BotTargetPlayersOnly`, which BotBrain reads to drop other bots from the target pool — for scripted bots whose whole job is menacing the one human. It **names** the hunter, which deliberately bypasses the `HunterWeights` draw and the `HunterCaps` ceiling — both sample a roster a scripted sequence does not want — and places the rig on an authored `Position` (Vector3, CFrame or BasePart), stored as `record.SpawnCFrame` and re-used on every respawn rather than scattering the bot back into the pool. The peaceful-bot flags are applied to the record **before** `_spawnController` builds the controller, so a bot meant to stand still never gets a tick of ordinary behaviour on the way there. **`Route` and `Approach` are in the spec for that same reason, and an authored walk should always be declared here rather than set afterwards** (added for `Approach` 2026-08-09): `SetActive` runs a brain tick *synchronously*, so a bot spawned bare and handed an approach on the next line has already had one tick of ordinary combat behaviour — for a Vesper that is an 18-28 stud sideways strafe to open her 150-stud `DesiredRange`, plus the scoped world pose, and `PathRecalculateInterval` then holds that path for up to a second before the approach can displace it. The tutorial's bounty bot walked out of cover *away* from the player for a second that way. `Approach` takes a Player, a character Model, or `{ Subject, StopDistance }`, and clears `Route` the same way `SetApproach` does. Positions are lifted 4 studs by default, the same offset `_spawnPosition` applies above a spawn part, because a rig pivoted exactly onto an authored floor part stands buried to the ankles and the offset differs per hunter; `HeightOffset = 0` places a CFrame exactly. Pair it with `SetPopulationLocked(true)` — `Reconcile` counts these bots toward its target and will retire them to hit it otherwise.
    - **`SetLeash(target, anchor, radius)`** — confines a bot to a flat radius around an anchor; it still walks, chases and fights normally inside it. Stamped as the `BotLeashAnchor` / `BotLeashRadius` attributes and enforced by BotPathing. Pass no anchor to unleash. This is confinement, not choreography.
    - **`SetRoute(target, waypoints, options)`** — hands the bot an authored walk (BotBrain does the following). Waypoints may be Vector3s, BaseParts, or **a folder of BaseParts**, which is the point: a route is dropped into the workspace and eyeballed rather than typed as coordinates. Folder order is the part **name**, with a trailing number compared numerically so `Point10` follows `Point9` rather than `Point1`; Explorer child order is not stable and a route that reorders itself on rejoin is unusable.
    - **`SetApproach(target, subject, stopDistance)`** — sends a bot to a Player (or character Model) and keeps it there, stopping ~12 studs short by default. Unlike `SetRoute` it tracks the subject, so it walks to where they *are*; and it overrides the hunter's `DesiredRange`, without which a Vesper told to approach walks away to open the 150 studs she prefers. Mutually exclusive with `SetRoute`; BotBrain does the following. **Prefer `SpawnBot { Approach = … }` when the bot is being spawned to approach** — see below; this setter is for changing a live bot's mind.
    - **`SetDifficulty(target, tierName)`** — per-bot difficulty, nil restoring the global `BotDifficulty`. Applies on the bot's next spawn, since BotController resolves the tier table once at construction. The tutorial needs two tiers alive in one round, which a single global cannot express.
    - **`Despawn(target, reason)`** — removes a bot outright: no kill credited, no death recorded, no ragdoll. `Retiring` is set **before** `_removeRecord` because the death path re-checks that flag inside its respawn delay, so a bot dying in the same instant cannot race a replacement into the slot. `DespawnAfter(target, seconds)` is the "the player never killed it, move on" case; its delayed check compares **record identity**, not the id, because ids are reused and despawning whoever holds one later would retire a bystander.
    - **`SetPopulationLocked(locked)`** — makes `Reconcile` return immediately. Required alongside `Despawn` for any caller that owns its roster: `MinBots` is a floor, so an ordinary round refills a despawned slot within a second.
    - **`PrepareScripted()`** (added 2026-08-09) — arms the service for a scripted session in one call: locks the population, runs `Cleanup(true)`, and sets `Prepared`/`Active` **ignoring `BotConfig.Enabled` on purpose**. That switch turns off the *ambient* arena population (`_desiredBotCount`'s fill), not the authored `SpawnBot` door — with it off, `PrepareRound` returns before setting `Prepared` and every authored `SpawnBot` is silently ignored with only a warn, which is exactly how the tutorial's choreography failed its first playtest. Wind down with `EndRound` as usual (no `Enabled` gate there).

## Team modes

Bots carry a team like players do. The record holds `Team`, the value is stamped onto the rig as an
attribute before it is parented (so the shared ally test answers for a bot the instant it exists),
and `GetBotTeam(botId)` hands it back for the mode's scoring hook -- a dying victim's rig carries
only the killer's bot id, and that rig may already be a ragdoll.

Fill is per team when the mode asks for it. `_desiredBotCount` consults the rules module's
`DesiredBots`: a nil answer keeps the FFA maths (`DesiredRoundParticipants` minus humans, clamped
between `MinBots` and `MaxBots`), while a table routes `Reconcile` through one `_reconcileBucket`
call per side with team-filtered spawn and retire passes. Retirement therefore takes the bot from
the side the joining player landed on.

Hunter choice is **coverage-first inside a team bucket**: the picker counts only records on that
team, and while any eligible hunter is missing from the side it rolls among the missing ones, so a
team of five fields five different hunters before it repeats any. `HunterCaps` follows the same
rule -- judged against the team's own count in a team mode and against the whole arena in FFA, so
the two-Vesper cap is two per side in TDM rather than two in the match.

Spawning defers to the mode: when a record has a team and the rules module exposes
`resolveSpawnForTeam`, the bot is placed at its team's pad keyed by bot id; otherwise it falls
through to the FFA pool unchanged.
