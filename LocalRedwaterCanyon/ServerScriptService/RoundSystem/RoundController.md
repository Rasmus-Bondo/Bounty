# RoundController

Core round lifecycle manager for Redwater Canyon FFA deathmatch.

## What it does

0. **Rounds LOOP. The server no longer dies after one match** (2026-08-06). `RoundController.Start`'s `task.spawn` body is wrapped in `while true do`, and the only exits are the end-of-round move at 0i and the two server exits at 0b. Everything a round needs reset already happened inside that body — `State.playerKills/playerDeaths/botKills/botDeaths`, `RoundStatsService.Reset()`, `QuestEvents.reset()`, `BountyService.resetAll()`, `ZoneService.resetZone()`, `DestructibleService.resetDestructibles()`, `BotService.PrepareRound/ActivateRound/EndRound`, and (since 2026-08-07, see 0g) [[DataService]] `resetAllSessionStats()` — so an iteration is self-contained. Two things had to move for the loop to work at all:
   - **`unfreezeAllPlayers()` moved into the loop tail.** It only ever ran inside `closeServer`, because closing the server *was* how a round ended. Without it there, every player carries the `VictoryFreeze` movement override, an anchored root, `ACImmune` and their `VictoryImmunityField` straight into the next round — unable to move and unable to be damaged. This is the single most load-bearing line in the change
   - **The `"Not enough players!"` branch `continue`s instead of closing.** Everyone leaving during the countdown falls back to waiting for players; only the exits at 0b end a server now
   The tail also fires `VictoryShowcase "Clear"` and hides the finish pillars / victory box before looping
0a. **`State.roundPhase = "Summary"` at the buzzer, and `"Ended"` is reserved for `closeServer`.** This is what lets Bounty handle the loop with **no code change at all**: Bounty's FriendJoinService refuses on `entry.phase == "Ended"` with *"your friend's match has already ended"*, which is right for a retiring server and exactly wrong for a podium ~17s from the next round, while its MatchmakingService governs `"Summary"` purely by the entry's `open` flag — and [[MatchDirectoryService]] now lists `Summary` alongside `Waiting`/`Countdown`/`Starting` as open. `hookCharacter`'s post-buzzer branch and the `setupPlayer` arrival flag both moved to `"Summary"`; the 1s late-join sync accepts either
0a2. **The round does NOT wait for the navigation mesh** (gate added 2026-08-19, removed 2026-08-23). Roblox builds the pathfinding navmesh lazily, on the first route request, and the calling thread waits out the whole build — 11.0s on Redwater, later 15.2s. For four days the loop gated on `BotService.IsNavigationReady()` at the tail of the intermission, bounded by a `Config` timeout. **The gate was removed because the cure was worse than the symptom**: the countdown reached zero and the intermission screen then sat frozen on "Preparing map…" for whatever was left of the build — 4.5s measured — which reads as a hang rather than as loading. Starting on an unfinished mesh is safe for the **bots**, and that is the whole justification: a bot's opening `ComputeAsync` *yields* until the build lands instead of failing, and BotPathing's stuck detector explicitly skips any bot that is `_isComputing()`, so nothing records a destination failure, blacklists a goal via `AvoidDestination` or drops into `DirectEscape`. The bots stand on their spawns for what is left of the build and then all set off within a second of each other; do not "fix" that stillness by making them move before they have a route. What survives at that point in the loop is a **non-blocking observer** that prints how far into the round the mesh landed — keep it, because the build cost is otherwise invisible. `Config.NAVIGATION_READY_TIMEOUT` was deleted with the gate. One piece of the old placement rationale still binds anything else put here: the idle camera's duration stays `COUNTDOWN_TIME` and must not be padded, because RoundClientController feeds that value straight into its on-screen countdown and padding it printed "35" on the intermission.

0a3. **The controller decides *when* the mesh is built, not just when to wait for it** (2026-08-23). The bake measures the workspace as it stands, and this module's boot dresses the map for the resolved mode — TeamBaseService parks the props a team mode replaces, CapturePointService un-parks the capture pads. BotPathing used to start the build itself at module load, which put a 15-second bake in a race with that swap; on Redwater, where 36 parked props sit inside `RedTeamBase`, roughly one cold server in two came out with the red spawn house unroutable for its whole life. So `BotService.WarmNavigation()` is now called **after** the last `Apply`, from three places: the boot path, the tutorial path (which returns before the boot one), and `switchGamemode`, whose re-dress makes the previous bake describe the wrong map. The mode-ballot call re-closes `IsNavigationReady()`, so the round after a mode change also opens on an unfinished mesh — which nothing waits on either way, see 0a2.

0b. **How a server ends, evaluated after the buzzer so a round in progress always plays out.** Module-level `roundsPlayed`, `serverStartClock` and `everHadPlayers`. Two exits: **empty** (`everHadPlayers and #Players == 0`) and the `Config.SERVER_MAX_LIFETIME` (1 hour) wall clock, so the worst case is ~66 minutes. **Both are re-checked inside the `MIN_PLAYERS` wait as well as at the tail** — that wait is the one place a looping server can sit indefinitely, and a server that emptied out while waiting there would otherwise never close at all. `everHadPlayers` is set once in `setupPlayer` and gates the empty test against the **boot window**: that same wait is where a fresh server sits while the party that caused it to exist is still joining, and closing on a bare "nobody is here" would bounce them off a server that had not started yet. `ServerScriptService.SoftShutdown` cannot serve this purpose: it is a `BindToClose` handler and is not callable
0b-i. **Server retirement was deleted on 2026-08-27** (SERVER_CONSOLIDATION_SPEC §1). `SERVER_RETIRE_AFTER_ROUNDS`, the `matchmakingRetired` latch and MatchDirectoryService `setMatchmakingClosed()` are all gone. Retirement existed for code freshness — publishing does not update servers that are already running — and the end-of-round decision at 0i now rotates to the sibling place at **every** round end that did not merge, which is a fresh boot on fresh code and does the same job for free. It was also the last rule in the system that deliberately made a full, healthy server unjoinable, which is the opposite of what consolidation wants. `SERVER_MAX_LIFETIME` stays as the backstop for a server that somehow never rotates
0c. **Late joiners are held for the next round rather than bounced.** `setupPlayer` still flags an arrival during `"Summary"` in `lateArrivals`, and `hookCharacter`'s summary branch now uses that flag to skip `freezePlayerForVictory` and **return** — the surviving `GameplayVisibility(false)` + `sendPlayerToJailSpawn` *is* "held for the next round". Freezing them would be actively wrong, not merely redundant: the freeze anchors the root, and the loop's unfreeze runs once, at the moment such a player is still mid-settle. `forwardLateJoiner` remains, but is now only reachable via the `serverClosing` path. Two supporting guards: the freeze re-checks `State.roundPhase == "Summary"` after its 0.1s settle (a freeze applied after the loop's single unfreeze has nothing left to release it), and `lateArrivals` is cleared at the top of every round — it describes **one summary, not a session**, and a stale flag would skip that player's victory freeze at the *next* buzzer and leave them free to walk out of the cage while everyone else is anchored
0d. **The loop top writes `State.roundPhase = "Waiting"`, and that is load-bearing rather than tidy** (2026-08-06). `"Summary"` has to outlive the whole showcase — see 0a — but leaving it set into the next iteration meant the round-start respawn at 0e fired `hookCharacter` while the phase still read `"Summary"`, whose branch freezes everyone it cannot identify as a late arrival. The loop's single unfreeze has already run by then, so every survivor would have been anchored in the cage for the following round. Writing the phase here also stops the directory advertising a full `ROUND_TIME` of `"Summary"` while the server is actually idle waiting for players
0e. **Everyone gets a NEW character at round start, survivors included** — [[SpawnService]] `respawnAllPlayers()` in place of `ensureAllPlayersAlive()`, which only rebuilds the dead. This is the single chokepoint that resets health, ammo and the client-side ability state between rounds: all three are rebuilt on `CharacterAdded`, and a player who lived to the buzzer never fires one, so they used to walk into the next round on whatever health they finished on holding a half-empty cylinder. Skipped on the server's **first** round (`roundsPlayed > 0`), where there is nothing to reset and everyone present has just arrived — rebuilding a character seconds old would make a party of eight pay for two `LoadCharacter`s each at the busiest moment in the server's life. Server-side **ability cooldowns** are not covered by this and are cleared separately, by each hunter's server module on `RoundActive` — see RevolverModule / CardsServer / SunspikeModule / GrudgekeeperModule. Ultimate charge already reset itself on the same signal (UltimateChargeService), and bots need nothing at all: `BotService.PrepareRound` destroys every controller and clears the records, so a bot's health, ammo, cooldowns and charge are fresh by construction
0f. **The summary hands over to the intermission behind a black screen.** The loop tail calls `fadeInForAll()` *before* `VictoryShowcase "Clear"`, and the curtain stays down through the respawn, the jail teleport and the camera hand-off; `fadeOutForAll()` lifts it only once `startIdleCameraForAll` owns the view. Clearing the showcase hands the camera straight back to the player's own character, which is standing in the jail, so without this the cage flashed on screen between the podium and the intermission. One extra guard: if the loop is about to *wait* for players, the curtain is lifted first — otherwise anyone still here would stare at black for however long the wait lasts
0g. **The TAB / Stats menu's own tallies were the one set of per-match numbers the loop never reset** (fixed 2026-08-07). Kills, deaths, K/D, time alive and time dead in that panel — and the `SessionKills` / `SessionDeaths` attributes its round leaderboard reads — live in [[DataService]]'s `sessionTracker`, not in `State`, and that table was built once on join and only torn down on `PlayerRemoving`. Correct while a server played one match and closed; under the loop the panel showed every round the server had played added together. The round-start block now calls [[DataService]] `resetAllSessionStats()` alongside `State.playerKills = {}`. **The match summary was never affected** — it reads `State.playerKills` — which is why the drift surfaced only in this one panel and looked like a display bug. Two couplings the fix had to respect: [[ProgressionService]] `snapshotRoundStart` must clear its `timeRewardTracker` in the same round (a stale high-water mark against a zeroed `TimeAlive` kills the alive-time reward outright), and the panel pulls its data on open and never again, so `sendStatsToAll()` is pushed at round start for anyone holding it open across the boundary
0h. **The end-of-match ballot**, which **rides the match summary as of 2026-08-16** instead of following it as its own beat. `runBallotsDuringSummary()` has replaced the loop tail's bare `task.wait(POST_GAME_VICTORY_TIME)` — it yields the whole summary window on **every** path, the no-vote one included, so returning early would tear the podium off mid-cinematic. Inside that window it waits `SUMMARY_CINEMATIC_TIME + SUMMARY_REVEAL_TIME` (the client's step 1 + step 2, so the ballot appears exactly as the stats card, podium and counter land together — a vote castable before the scoreboard is seen is a vote cast blind), fires `MapVote "Start"`, collects ballots for `Config.MODE_VOTE_TIME`, broadcasts a running `"Tally"`, then `"Result"`, then waits out whatever remains of the window — derived from the window rather than reading `MODE_VOTE_RESULT_TIME` directly, so a retune of any one term cannot leave this returning late and stalling the loop. `ballotOpen` is raised beside the `"Start"` rather than at the top of the function, so the open window is the window the tiles are actually on screen for. `"Clear"` is NOT fired here: the loop tail sends it alongside `VictoryShowcase "Clear"`, after `fadeInForAll`, which is what gives the winning tile ~0.7s legible against the curtain. The tally counts only players still present, so a leaver stops deciding for everyone else, and the vote moves only on an unambiguous mandate — one leader, not the incumbent; a tie, a shared lead or no ballots all stay. The tutorial never reaches it — `runTutorialSession` replaces the round loop entirely
0h-i. **The MAP ballot was deleted on 2026-08-27** (SERVER_CONSOLIDATION_SPEC §2), leaving the mode ballot as the only one. The map is a routing consequence now rather than a player choice — it is whatever server the roster is packed into, or whatever place it rotates to, decided at 0i after this returns. With two live maps a map vote was a coin flip rather than agency, and spending that beat on consolidation buys a real thing; hand it back at five or six maps. Consequences: the mode options are now just `MapConfig.Gamemodes` filtered through [[GamemodeConfig]] (there is no remote destination to validate against at ballot time, so the old intersection with the winning map's `MapCatalog.gamemodes` has nothing left to intersect), which is **three tiles on both live maps**; `MODE_VOTE_TIME` inherited the whole window at 7s; and the summary dropped 20.0s → 14.0s. **All three modes are offered every round with no population gating** — a menu that shrinks reads as a broken game, and the population signal belongs in routing, not the UI. The `#modeOptions >= 2` guard survives as a safety for a future one-mode map. `runBallot` stays `kind`-driven although `"mode"` is the only kind, so bringing a second ballot back is a one-caller change

0h-ii. **The map came back as ART on the mode tiles** (2026-08-28), which is what stops "the map is a routing consequence" reading to a player as "nobody will tell me where I am going". At ballot open, `runBallotsDuringSummary` resolves a destination map per mode and sends its [[MapCatalog]] thumbnail as that option's `thumbnail`: [[MatchDirectoryService]] `previewMergeMaps(roster, modeIds)` names the map each mode would MERGE into, and a mode with no candidate gets one from `rollRotationMap(modeId, true)`. So a tile reads "this mode, over there", and three tiles can show three different maps. **The roll includes the map we are standing on**, unlike the rotation's own roll — excluding it left every no-merge tile showing the same other map, which is not a choice of anything; a home roll still reserves a *fresh* server, never a stay, so code turnover survives but a map can now repeat back to back. `rollRotationMap` / `rotationMapEligible` / `mapRunsMode` are shared with `reserveRotationDestination` precisely so the tile and the reservation cannot disagree, and `livePlayersByMap` stopped counting our own entry, which would otherwise weight every no-merge tile back onto the map everyone just played. **The winning tile's map rides back as the function's second return value** and pins the decision at 0i. One extra `GetRangeAsync` per round buys it; in Studio there is no directory, so every tile rolls
0i. **The end-of-round destination** (2026-08-27, SERVER_CONSOLIDATION_SPEC §3). One decision point, three outcomes, in order: **MERGE** — ask [[MatchDirectoryService]] `chooseMergeTarget(roster, nextModeId, plannedMapId)` for a live server this whole roster fits into and dissolve into it; **ROTATE** — otherwise `reserveRotationDestination(nextModeId, plannedMapId)` reserves a fresh server on the planned map, or, with no plan, on a *different* live map that runs the mode, weighted by that mode's live headcount per map off the read the merge already paid for; **STAY** — nil from both (no eligible map for this mode, or `ReserveServer` failed) plays another round here. **Both calls are pinned to the map the winning ballot tile showed** (2026-08-28): the vote decides the mode *and* the map, so a server on another map running the elected mode is not a worse candidate, it is not a candidate. That costs merges — a roster that would have consolidated onto the other map now rotates into a fresh server instead — and it was taken deliberately, because a ballot whose photograph can be overruled by whatever server appears during the seven seconds of voting is not a ballot. `plannedMapId` is nil only when no ballot ran (a one-mode map), which restores the old any-map merge. An empty server skips the decision and falls to the 0b exit. A mode change never forces a move — both live maps run all three modes and `switchGamemode` changes mode in place — so consolidation and rotation are the **only** reasons this server ever teleports
0i-i. **Rotation has no round-count gate**: it happens at every round end that did not merge, so no server plays the same map twice in a row, every round boundary becomes a repack point, and code is never more than one round old (which is what let retirement go at 0b-i). The cost to watch in a soak is that **every round now ends in a teleport**, so any per-teleport failure rate compounds per round rather than per map vote; the existing machinery covers it (group-call valve → per-member fan-out, `TeleportInitFailed` regrouping, 12s drain, then kicks) but a rise in *"Teleport failed. Please try again."* is the signal
0i-ii. **The move itself** via `moveToMap(destination)`, where `destination` is `{ accessCode, privateServerId, placeId, mapId, modeId, isFresh }` and always evacuates. Ordering: [[MatchDirectoryService]] `setClosing()` **first** (the lobby must stop routing joiners into a server that is evacuating), then — **only on the fresh/rotation path** — `registerAccessCode`, `registerRegion` and `publishProvisionalFor`; a merge target already has all three. **The reserve moved AHEAD of `moveToMap` entirely** (was after `setClosing`, inside it): that old ordering is what forced a failed reserve to degrade into `closeServer`, because the entry was already withdrawn and playing on would have left a healthy server invisible for life. With the reserve first, a failed reserve is simply a STAY and that branch is gone; the trade is a join race of roughly one web call, and a joiner landing in it drains to the lobby exactly as one racing a shutdown does. Then one `TeleportAsync` per surviving group plus one per solo (the same split as `teleportAllToLobby`, for the same reasons), with each group payload's `redwaterAccessCode` overridden to the NEW code so the destination server cannot adopt the abandoned server's code as its own at boot. Every traveller's `characterSelections` entry is rewritten from their LIVE hunter via `getPlayerHunterSelection` (2026-08-14) — group members stamped one at a time into a deep-copied selections table (one `TeleportData` covers the whole group, and the shallow `table.clone` would otherwise write through into the arrival payload), solos handed a one-entry map instead of a payload carrying no selection at all. **`weaponSkinSelections` is stamped the same way and for the same reason** (2026-08-28): it was missing from the move entirely, so a solo rotating maps arrived with only `characterSelections` — enough to read as a lobby arrival rather than a direct joiner, so nothing deferred the publish and [[HunterSelectionService]] published `DEFAULT_WEAPON_SKINS` before the profile landed. A combat client samples `EquippedWeaponSkin_<Hunter>` once at boot and Dust's viewmodel cannot rebuild, so every solo spent the next match holding the default gun while everyone else saw their real skin on the world model. Group payloads carried the join-time snapshot instead, which is stale after a mid-match hunter switch; both now carry the LIVE table from `HunterSelectionService.GetWeaponSkins`, which the profile refresh keeps current on every spawn. Without it a mid-match hunter swap did not survive the move: the group payload was the join-time snapshot and the solo payload had nothing, so the destination respawned switchers as their lobby hunter (solos via HunterSelectionService's direct-joiner profile path, which also held their first spawn on a profile read). **`friendUserId` is carried on the solo payload too** (2026-08-29), and it is the third field to fall into the same trap: the solo payload is BUILT rather than cloned, so anything a party keeps for free has to be restated. Both commonest friend joins land in the solo bucket — a follow-join from the Roblox app carries no `groupId` at all, and a SOLO pressing Join on the banner has `members = { self }`, so the `#members >= 2` partition test is false — which meant a friend join survived every round on one map and was re-split from that friend the moment the roster rotated or merged. It is carried, never rebuilt, and a solo still does NOT get its `groupId` or `members` back (Bounty would rebuild a party of one around them); a friend link is not a party marker. Then the same 12s drain re-aimed at the new server, then kicks. Nothing about this server's age travels — the destination starts fresh, exactly as if the party had come from the lobby, and `SERVER_MAX_LIFETIME` binds per server
0i-iii. **The provisional entry on the rotation path** (`publishProvisionalFor`) is what stops each rotation opening a ~10s hole in the directory where a lobby Play press finds nothing open and reserves its own server. It states **`players = the travelling roster`, not 0** — the one field that differs from Bounty's `publishProvisionalEntry`, which writes 0 because a Play-press reservation genuinely has nobody in it yet. A rotation knows exactly who is arriving, and stating it is what makes the new server a usable merge target immediately: a 4-player server rotating advertises 4, and a 2-player server ending its round right after merges straight in and makes 6. Because `players` already counts the travellers, slots are deliberately **not** also claimed for them — the lobby adds `players` and pending together, so doing both double-books the seats; `claimSlots` runs on the merge path only
1. Initializes ProgressionService, ZoneService, and hooks all player CharacterAdded events
2. On PlayerAdded, reads `player:GetJoinData().TeleportData` and stores group/party data for return teleport
3. Waits for minimum player count, then runs a countdown phase
4. Teleports all players to round spawns, sets round to active, starts zone shrink. The bulk `SpawnService.teleportAllToRoundSpawns()` returns any players it couldn't place (slow-loading clients whose character wasn't fully replicated during the pass); once the round is active a background reconciliation loop retries `sendPlayerToRoundSpawn` for each until it succeeds (or they leave / the round ends), also firing `GameplayVisibility`/`IdleCamera "Stop"`/`ScreenFade "InstantClear"` on rescue. This enforces the invariant "no alive player is left in the jail cage during a live round" — previously a slow device jailed during Countdown and missed by the single teleport pass stayed trapped in the cage the whole match
4a. **`hookCharacter` places the character on a round spawn synchronously, at the top, before anything yields.** Redwater has **no SpawnLocation anywhere in workspace**, so `player:LoadCharacter()` drops every fresh character on the terrain at the world origin `(0, 14, 0)` — the far north of the canyon. From mid-Event phase onward that is *behind* the north fire wall (the Final-phase safe band is roughly Z −362..−137), and the SpawnProtectionService ForceField is only granted as part of a [[SpawnService]] teleport. The deferred pass further down waits on `AncestryChanged`, two `WaitForChild`s and a 0.1s settle before it moves anyone, so **every late-round respawn used to stand unprotected in the burn for that whole window** — and because the burn ramp survived death, a player who died in the fire resumed at the `ZONE_DAMAGE_MAX` cap. The deferred pass re-teleports when the early placement returned false, *or* the root has ended up outside [[ZoneService]] `isPositionInSafeZone` (checked with no margin — the question there is "are they in the fire", not "is the spawn comfortable"), *or* — added 2026-08-13 — the root is further than [[SpawnService]] `PLACEMENT_TOLERANCE` (30 studs) from the spawn the placement actually aimed at. The safe-zone test alone could not cover the engine repositioning the character as it is parented into workspace, which was the whole point of it: a discarded write leaves the character at the world origin, and clearance is infinite until the walls start closing, so the safe-zone test *accepts* a character sitting 30–660 studs from its spawn. Those respawns fell through to SpawnService's 0.35 s verify instead — a correct repair, but a visible yank later and a warning every time. `teleportPlayerToSpawn` returns the target CFrame as a second value to make the comparison possible; the distance test is skipped when the settle took over a second (a slow `WaitForChild`), by which point the player may simply have walked
5. Tracks kills via `LastDamager` attribute on victim characters (set by RevolverModule) and awards kill rewards via ProgressionService
6. On kill, checks if victim had a bounty and calls BountyService.claimBounty, then registers the kill streak via BountyService.registerKill
7. Tracks deaths, awards death tracking via ProgressionService, resets kill streaks via BountyService.registerDeath, and **on every player death calls [[RoundStatsService]] `ResolveDeath(character, killerPlayer, killerBotId)` — resolving `killerPlayer` from `LastDamager` and passing `LastDamagerBotId` — to credit the killer's stat kill/streak and grant an assist to every recent contributor, then awards assist XP/Cash via [[ProgressionService]] `awardAssist` for each returned UserId. This is the universal per-death assist + stat-kill crediting point (mirrored for bots in [[BotService]]), so finishers that bypass the hunter pipelines — zone/firewall, fall damage, a bot's killing blow — still resolve assists that the old in-pipeline `RegisterKill` path silently dropped.** **Zone exception:** when the victim's `KilledByZone` attribute is set (see [[ZoneService]]), the kill block is skipped entirely (no `State.playerKills`, no `awardKill`, no bounty) and `ResolveDeath` is called with no killer, so a firewall death awards assists to recent contributors but credits a kill to nobody. Respawns players after a configurable delay via `SkinService.loadCharacter` (preserving their selected skin)
8. Resets all bounties at round start via BountyService.resetAll
9. Awards bounty survivor bonuses at round end via BountyService.awardSurvivorBonuses
10. When the round timer expires, runs the round-end payout loop over every player still on the server: first [[ProgressionService]] `flushPendingRewards`, then `awardRoundCompletion` for the flat end-of-round bonus, then [[DailyRewardService]] `registerPlay` (the "finished a round" trigger; the reward itself is claimed later in the Bounty lobby). **Since 2026-09-06 the flush normally finds an empty bucket** — round earnings are credited the moment they are earned so the level-up card can fire mid-match, and leaving early no longer forfeits them; the call stays as the safety net for an earnings hold that was never lifted. It runs before `buildPostGameStats()` so the stat card's `roundXPEarned`/`roundCashEarned` and the showcase XP bar animate over the whole round's earnings. Guarded by a `typeof` check plus a per-player `pcall` so a stale/broken ProgressionService warns instead of aborting the round-end sequence
11. Determines the winner by highest kill count (`getWinner`). Players are scanned first and the best bot only takes over on *strictly* more kills, so a bot tied with a player never claims the "X wins with N kills!" status line
12. Builds combined combat+progression stats per player (`buildPostGameStats`, blending [[RoundStatsService]] combat stats with kill/death counts and ProgressionService's XP/Cash summary) and fires it to all clients via the `VictoryShowcase` RemoteEvent (`"Start"` action) — the older `PostGameStats` remote/GUI is dead, see [[PostGameScript]]. Bot entries from [[BotService]] `GetPostGameStats()` (each tagged `isBot = true`) are appended to the same table before sorting, and the sort is **kills descending → real player before bot → deaths ascending**: on equal kills a human always outranks a bot, ahead of the deaths tiebreak, so a bot can never take a placement off a player. No client re-sorts — [[VictoryShowcaseClient]] and StatMenuGui both render the server's order — so this comparator alone decides the podium, the stat screen and the RP placement. The sorted placement order also drives [[RankedService]]`.awardRound()` once per player, attaching `rankPointsEarned`/`rankPointsTotal` to each entry in the payload. Each stats entry also carries an `emote = { name, animationId }` resolved by `getPlayerEmoteAnimationData` — the player's equipped emote from `profile.EquippedEmote` (validated valid + owned via [[EmoteConfig]]), else the default emote (`EmoteConfig.DEFAULT_ID` = `electro_swing`) — never a random pick — which [[VictoryShowcaseClient]] plays on that player's showcase dummy. This replaces the old random `EndScreenEmote` folder pick (still sent as `victoryAnimationsByRank` for a per-rank fallback). Each entry also carries a `character` selection (`getPlayerHunterSelection`) — the hunter + skin [[VictoryShowcaseClient]] builds both summary scenes from (the podium dummy AND the local player's stats-card viewport portrait). It reads the **live** [[SkinService]] `.getSelection`, the same call `loadCharacter` builds the character from, so the summary shows the hunter the player FINISHED as — a mid-match swap (HunterSwitchService, applied on respawn) is reflected by construction rather than by two paths agreeing. The arrival `TeleportData` (`playerGroupData`) is only a fallback for an invalid live selection: it is frozen at join, so reading it first meant a player who swapped was shown on the podium as their lobby hunter. Timing is safe because `buildPostGameStats` runs *before* `SpawnService.ensureAllPlayersAlive()`, so a player who dies on the buzzer with a swap still queued is captured as the hunter they actually played. At round end (`freezePlayerForVictory`) each player is teleported to the jail spawn and frozen (root velocity zeroed, then root anchored, plus a `VictoryFreeze` zero **override** with `LockJump` on [[HunterMovement]]) for the summary; `freezeAllPlayersForVictory`/`unfreezeAllPlayers` bracket this. **The freeze also grants anti-cheat immunity** (`player.ACImmune`, read by MovementChecker), cleared again in `unfreezePlayer` — set *here* and not in `closeServer`, because the freeze pins the character for the whole `POST_GAME_VICTORY_TIME` (30s) showcase while the only cover reaching this point was the 8 s `ACImmuneUntil` from SpawnService's jail teleport one line earlier. That left ~22 s in which MovementChecker judged a body the server itself had anchored: a player frozen with no ground inside its 25-stud probe (under the terrain, over a gap, mid-void) flagged "airborne with no ground" every 2 s and "airborne for Ns" every 3 s, could not move off the flag, and could not decay (decay requires `grounded`) — a guaranteed kick ~14 s into the showcase, observed live 2026-08-04. It is an attribute rather than a "skip anchored characters" rule inside MovementChecker because clients can set `Anchored` on their own character parts and have it replicate. `closeServer` re-grants `ACImmune` for the lobby teleport **after** `unfreezeAllPlayers()` — it used to set it before, where the unfreeze immediately cleared it. The velocity zero matters for diagnosis, not behaviour: anchoring stops simulation without clearing `AssemblyLinearVelocity`, so a frozen body kept reporting the speed it carried into the buzzer on every anti-cheat sample. Unfreezing drops the override so the character's real speed is re-resolved — the old hardcoded `WalkSpeed = 16` / `JumpPower = 50` restore left every Fortuna (passive 24) a third slower for the rest of her life and stomped any live scope, ult or slow. **Post-round damage immunity:** the instant the round ends (`grantVictoryImmunityForAll`, before the ~1s teleport wind-down) and again in the `"Summary"` late-join freeze branch, every player's character gets an invisible `ForceField` (`VictoryImmunityField`) so lingering ability damage (e.g. a Fortuna ultimate recall thrown pre-buzzer) can't kill a locked-away player during the showcase — a ForceField blocks every `Humanoid:TakeDamage` path. It is cleared in `unfreezePlayer` (and auto-destroys with the character on respawn). **Freeze is guarded against shutdown _and_ against the loop boundary:** `freezePlayerForVictory` early-returns when `serverClosing` is true, and `hookCharacter`'s `"Summary"` late-join branch gates on `not serverClosing`, then after its settle wait re-checks **both** `serverClosing` and `State.roundPhase == "Summary"` — the round loop runs `unfreezeAllPlayers` exactly once per round, just as `closeServer` does, so a freeze landing after either has passed has nothing left to release it. `closeServer` runs `unfreezeAllPlayers` exactly once, so a freeze applied after that (a player joining right as the match/showcase ends, whose `hookCharacter` resolves during the drain) would otherwise anchor them in the cage with nothing left to release them — the drain loop teleports these joiners to the lobby instead
12b. **Awards the team-mode win quests** (2026-08-27), in the buzzer branch right after mode hook #5 resolves the outcome. When `outcome.kind == "team"` every player whose [[TeamService]] `teamOf` matches `outcome.team` gets `teamWin` and `teamWin:<mode>` through [[QuestEvents]]. A draw yields `kind == "draw"` and awards nobody; an FFA round yields `kind == "player"` and never enters the branch. This is deliberately **not** the same objective as the `win` that `buildPostGameStats` fires: that one is individual 1st place off the kill-sorted standings and fires in team modes too — just as readily for the top fragger on the **losing** side — which is exactly why "your team won" needed an event of its own rather than a reinterpretation of an existing one. Sitting inside the buzzer branch, alongside the win/podium awards, is what stops an abandoned round banking a team win
13. Drives the intermission idle camera (`IdleCamera` remote) and black-screen fades (`ScreenFade` remote) around the countdown/spawn/fight transitions, and toggles HUD/viewmodel visibility for all clients via `GameplayVisibility` during intermission. Sets a transitional `"Starting"` round phase the instant the countdown loop exits (before any yield) — the 1-second late-join sync in `setupPlayer` and the character-spawn sync in `hookCharacter` both treat `"Starting"` like an active round, so they can no longer act on a stale `"Countdown"` phase during the ~2s round-start window (previously this race could re-start the intermission blur/DOF for a late joiner and leave it stuck on for the whole match, or jail-spawn a character into a starting round)
14. Teleports players back to the Bounty lobby via TeleportService, attaching group data via `TeleportOptions:SetTeleportData()` so groups survive the return trip. The original arrival TeleportData is passed through **untouched** — members are NOT filtered by who is still on the server (that filter used to strand players whose partymates left early, because the last leaver's payload dropped below 2 members and lost the group). Players whose arrival data had `#members >= 2` teleport together with the full original payload (including `weaponSkinSelections`); direct joiners teleport with no data. **Everyone else travels in FRIEND BUCKETS** (2026-08-29): the ungrouped list is unioned over `friendUserId` and each bucket goes out as ONE `TeleportAsync`, which is the only thing that can guarantee a shared destination — Bounty is a public place, so there is no jobId or access code to aim a second call at, and Roblox routes every separate call on its own. Before this, two friends who had played a whole match on the same team landed in different Bounty servers, and the party frame's invite list is built from `Players:GetPlayers()` of that server — so they could not even see each other to party up afterwards. **A bucket is not a party:** the payload carries no `groupId` and no `members`, so `tryReconstructGroup` ignores it exactly as it ignores a lone solo. A bucket of one keeps the old payload verbatim; a bucket of several merges `characterSelections` (keyed by user id, read back per arriving player, so no hunter crosses over) and carries nothing else. **Tutorial returns never merge** — `tutorialComplete` and the two paid amounts are stamped for ONE player and a shared payload would promise that reward card to the whole bucket. A failed bucket teleport fans out per player, as the group path does. **Still split:** a friend-joiner whose friend travels with a REAL party, since riding along would hand them that party's `groupId` and Bounty would add them to it

The value is still maintained for the disabled PostGameGui and any future reader. That is what actually stops the Bounty lobby routing new players here the instant shutdown begins — the short drain below only limits how long the dying server lingers, it cannot stop arrivals on its own

The drain is deliberately short. Its original reason — the dying server stayed a public-matchmaking candidate — no longer applies now Redwater is reserved and Roblox cannot route anyone anywhere; what still applies is that [[MatchDirectoryService]] withdraws the entry at 15a, so the only remaining arrival risk is a teleport already in flight, and a joiner landing mid-shutdown still surfaces as "Connection Failed"

It replaced **the cage**: a late arrival used to be sent to the jail spawn and frozen there until `closeServer` ran, which with `POST_GAME_VICTORY_TIME` = 30 is the 5-10 second freeze-then-bounce reported at launch (launch issue #13, `changelog/OPEN-ITEMS.md`). It should now be unreachable — Redwater runs on reserved servers, so Roblox's matchmaker cannot place anyone here and Bounty refuses to route into a match that is `Ended` or closing — which is exactly why it is a backstop and not the fix. Deliberately does **not** requeue: they land in Bounty and press Play again, where a requeue flag would risk a bounce loop on a path that should never run

That distinction used to decide who got *forwarded to the lobby*; under the round loop it decides who gets **frozen** (see 0c). Either way a flagged arrival is parked at the jail spawn, so they are not standing in the fire, and is **not** frozen
17a. **Leaving forfeits the round.** The `PlayerRemoving` handler nils the leaver's `State.playerKills`/`State.playerDeaths` (instance-keyed, so a rejoin already reads zero — this just stops the dead instance's entries lingering in the scoreboard tables) and calls [[RoundStatsService]] `ClearPlayer`, which is the one that matters: that table is **UserId**-keyed, so without it a player who left and rejoined the same live round resumed their old kills/assists/deaths/streaks/damage/accuracy on the post-game stat card while the live scoreboard showed them at zero. Bounty + kill streak are cleared by [[BountyService]]'s own `PlayerRemoving` handler and session stats by [[DataService]]'s — so a rejoiner starts the round completely fresh. **XP/Cash are no longer among the things leaving costs them** (2026-09-06): earnings are credited live, so there is no bank to drop

16a. **`teleportAllToLobby`'s solo branch rebuilds the payload rather than passing it through, and that is deliberate** — a solo return must not carry a `groupId` or a `members` list back to Bounty, or the lobby tries to reconstruct a party of one around them. `tutorialComplete` / `tutorialCash` were added to what it carries on 2026-08-11, `tutorialTokens` on 2026-08-17 and `tutorialChest` on 2026-09-07, and they are the exception that had to be made: this function is `closeServer`'s drain, re-run every 3 seconds for 12, which makes it the **last retry of a tutorial player's return**, and TutorialDirector stamps those onto the arrival table (see its item 10a) so its own ladder and this one promise the player the same thing. Dropping them here meant a retried return landed in Bounty with the reward already paid and no card to say so.

## Round length

The clock is the **mode's**, not `Config.ROUND_TIME` -- the fight phase reads
`GamemodeConfig.get(State.gamemode).roundTime`. `Config.ROUND_TIME` survives only as the figure
MatchDirectoryService advertises for pre-round phases and as ZoneService's final-phase
number, which is why editing it alone does not shorten a round. `Config.FORCE_ROUND_TIME`
(2026-08-23) overrides the mode's value for testing; Config nils it out on a live server, so
there is no environment check here. `roundLength` has exactly two readers -- the Heartbeat that
publishes `RoundTime` / `RoundTimeLeft`, and the loop's exit condition.

## Team modes

Gamemode is resolved once at boot -- `resolveGamemodeRules` errors unless the id has a
`GamemodeConfig` row, is listed in `MapConfig.Gamemodes`, and matches the `.Id` of exactly one
ModuleScript under `RoundSystem.Gamemodes`. The resolved module is published as
`State.gamemodeRules` and consulted at nine points (`Init`, `PrepareRound`, `ResolveSpawn`,
`OnDeath`, `GetOutcome`, `DecorateVictoryPayload`, `CanDamage`, `DesiredBots`, `EndRound`); the
round loop, payouts, analytics, routing and teleports stay mode-agnostic.

`switchGamemode(modeId)` reconfigures the running server in place after the end-of-match mode
ballot -- never a teleport, because the map has not changed. It tears teams down when leaving a
team mode, re-points the active rules, restores or parks the capture pads through
`CapturePointService.Apply(newRules.UsesCapturePoints == true)`, calls the new mode's `Init` (after the
pads, because Domination's `Init` resolves their geometry out of the workspace), then swaps the spawn
houses through `TeamBaseService.Apply`. The boot path and the tutorial path make the same calls. When
the map DOES change,
`moveToMap` carries the mode in both payload shapes: the access-code record and `TeleportData`.

## Domination (2026-08-22)

**Mode hook #10, `ShouldEndRound`.** The fight loop's `repeat task.wait(0.25) until …` now also exits
when `activeRules.ShouldEndRound` exists and returns true (Domination at its score limit); the wait
tightened from 1s to 0.25s so the winning point does not linger. Deathmatch and TeamDeathmatch leave
the hook nil and still run to the clock. That is the only RoundController change for Domination —
the capture/accrual loop lives in the rules module, started in its `PrepareRound` and stopped in its
`EndRound`.

20. **Owns the per-match analytics emit block**, feeding [[Telemetry]]. `logMatchStart` fires `MatchStart` (the denominator for first-match completion rate) and advances the persisted `MatchesPlayed` / `LastMatchAt` / `SittingMatchIndex` counters in [[DataService]]. **The counters advance inline, but the `MatchStart` event itself is emitted from a spawned `emitMatchStart` that first polls (0.5s, up to 10s) for `SelectedHunter` and a non-`Unknown` platform to resolve.** Both halves of the `Platform|Hunter` composite are join-timing dependent, and on the late-join path `logMatchStart` runs inside `setupPlayer` — before the deferred `SkinService.loadCharacter` has set `SelectedHunter`, and before TelemetryClient's platform report (~2s after the client boots) lands.
