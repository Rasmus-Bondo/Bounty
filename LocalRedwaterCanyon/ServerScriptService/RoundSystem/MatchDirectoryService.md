# MatchDirectoryService

Publishes this Redwater server's live state into a MemoryStore sorted map so the Bounty lobby can decide who is allowed to join it.

## What it does

1. **Why it exists:** a Roblox server cannot refuse matchmaking. `Players.MaxPlayers` is not scriptable ("can only be set through place settings" per the API docs) and there is no engine signal for "stop sending me players". Every join rule — the lock, both caps, the friend slots — therefore has to be enforced by the **sender**, in Bounty. This module is the only thing that tells the lobby what is happening in here
2. **Redwater servers are reserved** (2026-08-03). Bounty calls `TeleportService:ReserveServer`, teleports the party in with `TeleportOptions.ReservedServerAccessCode`, and Roblox's own matchmaker cannot place anyone here at all. Before that, a blank `ServerInstanceId` — the "nothing is open" case, which at launch population was the *common* case — handed the decision to Roblox, which has never read this directory: players landed in matches seconds from shutdown, ate the reserved friend slots, and sailed past the join lock
3. Writes one entry keyed on **`game.PrivateServerId`** into the sorted map `RedwaterMatchDirectory_v1`, with a 30s TTL refreshed by an 8s heartbeat — a crashed server drops out of the directory on its own, with no cleanup path to get wrong. The key was `game.JobId` before reserved servers
4. **Three identifiers are published and they are not interchangeable.** `privateServerId` is the key, stable for the server's life and the id Bounty reserved it under. `accessCode` is what a teleport actually needs. `jobId` is what `GetPlayerPlaceInstanceAsync` returns when the lobby looks up a friend someone tapped Join on in the Roblox app — not the key, so the lobby has to scan for it, and it can only scan for something that is published
5. **A reserved server cannot read its own access code.** There is no API for it (`game.PrivateServerId` is available; the code is not), so it has to arrive from outside. Two independent sources: the first arriving player's `TeleportData.redwaterAccessCode`, and the `RedwaterAccessCodes_v1` hash map that Bounty writes before it issues the teleport. A server that misses **both** is an orphan — advertised, full of players, and unjoinable for its whole life — so failing to resolve one after five lookups warns loudly
6. The entry carries `{ privateServerId, map, accessCode, jobId, players, members, phase, secondsLeft, open, cap, soloCap, lockSeconds, hardCap, closing, updatedAt }`. `members` is the roster of UserIds, which is what lets the lobby show "your friend is in a match" (FriendJoinService (Bounty)) without a second lookup — it rides along in the read the matchmaker already does
6a. **`map` is the field that makes one shared directory work across several match places** (2026-08-14). Every match place carries this module byte-identical, so Frostbite publishes into the same sorted map Bounty queries for Redwater servers, and before this nothing in an entry said which map it was. Readers must treat an **absent** `map` as `"redwater"`: publishing does not update servers that are already running, so for one server generation the map holds entries written by code that predates the field, and dropping them as "unknown" empties the lobby's candidate list until they drain. The four MemoryStore names keep their misleading `Redwater` prefix on purpose — a rename is a coordinated three-place cutover for zero behaviour change, so it waits for a `_v2` bump
6b. **`region` is what lets the lobby refuse a player an unplayable ping** (2026-08-15). The entry carries this server's latency bucket (`NA`/`SA`/`EU`/`AS`/`OC`), and Bounty's matchmaker will not send a player to a server outside their own — the call being that a bot-padded local match beats a full one at 300ms. Roblox tells a reserved server nothing about where it lives, so the value arrives from outside exactly as the access code does: `resolveRegionFromStore` reads `RedwaterServerRegions_v1` (privateServerId → bucket), written by Bounty's MatchmakingService the moment it reserved. A **separate map** from `RedwaterAccessCodes_v1` on purpose — that map's value shape is load-bearing across place versions, and widening it breaks access-code resolution on any lobby still running the previous build
6c. **One source, unlike the access code's two, and the asymmetry is deliberate.** A server with no access code is an orphan: advertised, full, unjoinable for its whole life — worth a backup path through the arriving party's TeleportData. A server with no region merely publishes none, which the lobby reads as "no opinion" and routes freely: the pre-feature behaviour, and survivable. Taking it off an arrival instead would be actively **wrong** — the only arrivals carrying a trustworthy region are the reserving party, and by the time a later one shows up their region says where *they* are, not where this datacenter is. For the same reason the value is resolved **once and never recomputed** from the current roster: a friend join can bring in a player from another continent, and letting that shift the published region would advertise the server to their region and pack the wrong people into it for the rest of its life
6d. `getRegion()` exposes it to RoundController — for the `MatchPing` telemetry, and for `registerRegion(privateServerId, region)`, the region half of `registerAccessCode` below: the end-of-round move path carries this server's region across to the sibling it just reserved, since the players being moved are the ones who will boot it and therefore fix its datacenter
7. `open` is true when the server is not closing, holds fewer than `Config.SOLO_PLAYER_CAP` players, and is either in `Waiting`/`Countdown`/`Starting`/`Summary` or in `Fight` — the last of those unconditionally as of 2026-08-12, since `Config.JOIN_LOCK_SECONDS` is 0 and `isOpen` checks `<= 0` explicitly so a fight on its last second is still open. **It deliberately uses the most permissive of the two matchmaking ceilings** so an entry never reads closed to a solo just because it is closed to parties; Bounty narrows it per party size against the published `cap`/`soloCap` pair. `Ended` and anything unrecognised are closed
7a. **`Summary` sits with the pre-round phases, not with `Ended`** (2026-08-06, the infinite match loop). A server showing its match summary is ~17s from starting another round, so a player matchmade into one gets the same deal as a player matchmade into `Countdown` — and a better one than seeding an empty server. `secondsLeftFor` returns the full `ROUND_TIME` for it for the same reason. `Ended` is now published by exactly one thing, RoundController `closeServer`, and means "this server is going away"; that split is what lets Bounty handle the round loop with **no code change**, since FriendJoinService (Bounty) refuses on `Ended` with *"your friend's match has already ended"* — correct for a retiring server, and precisely wrong for a podium
7b. **`setMatchmakingClosed()` was deleted on 2026-08-27** (SERVER_CONSOLIDATION_SPEC §1) along with its `matchmakingClosed` flag and its term in `isOpen`. It was the soft half of server retirement — force `open` false, keep the entry published so friend joins still worked — and it was the last rule in the system that deliberately made a full, healthy server unjoinable. Retirement existed for code freshness, and a server now rotates to a sibling place at every round end that did not merge, which is a fresh boot on fresh code. Nothing in Bounty changed: `acceptsMatchmaking` reads `entry.open`, which simply stopped being forced false
8. `cap`, `soloCap`, `lockSeconds` and `hardCap` are published rather than duplicated in Bounty, so [[Config]] stays the single source of truth for the numbers. `hardCap` is `SOLO_PLAYER_CAP + FRIEND_SLOTS` — the friend slots sit on top of the *solo* ceiling, not the party one. `lockSeconds` is still published with the lock disabled, which is what lets re-enabling it be a one-number change in [[Config]]: the lobby only re-applies the time rule when the entry's `lockSeconds` is above 0
9. Reads its inputs from state that already exists: `State.roundPhase` and the `RoundTimeLeft` workspace attribute maintained by RoundController's round timer
10. Publishes immediately on `PlayerAdded`/`PlayerRemoving` as well, coalesced to at most one write per second so a party of four arriving does not fire four writes. `PlayerRemoving` excludes the leaver, who is still in `Players:GetPlayers()` when it fires. `PlayerAdded` also checks that arrival's teleport data for the access code
11. `setClosing()` withdraws the entry outright and deletes the access-code key. RoundController `closeServer` calls it before anything else — and `moveToMap` likewise calls it first — so the lobby stops routing players here the instant shutdown or evacuation begins. Also bound to `game:BindToClose`. It is now the **only** way an entry leaves the directory before its TTL; the softer `setMatchmakingClosed` is gone (7b)
11a. **`registerAccessCode(privateServerId, newAccessCode)`** (2026-08-14, spec §9.4) writes the `privateServerId → accessCode` pair for the **sibling server the end-of-round rotation has just reserved** — a different key from this server's own, which is why it can run after `setClosing` has deleted ours. This is Bounty's job done from inside a match: MatchmakingService (Bounty) writes the same pair the moment it reserves, but a rotation reserves with no cross-place RPC to hand the write back, so the logic is duplicated and noted at both copies (same key, bare-string value, 3600s TTL). Losing the write is survivable — every move payload carries the code as the arriving server's backup source — so a failure warns rather than aborting the move
12. **A session with no `PrivateServerId` does not advertise at all.** It is empty in Studio, and empty in any server that was not reserved — either way there is no reserved server for anyone to be sent into, and a key nobody can teleport to is worse than no entry because the lobby would route a real party at it and fail them. Publishing is skipped with one warn. The map names additionally carry a `_studio` suffix under `RunService:IsStudio()` (Studio talks to the **production** MemoryStore), and MatchmakingService (Bounty) applies the same suffix rule
13. Every write is wrapped in `pcall` and failures are counted, warning on the first and then every tenth. A failed write is retried rather than fatal and nothing in the round flow depends on one — but note there is **no** "falls back to plain Roblox matchmaking" any more. A server that never manages to publish simply never receives anyone beyond the party that created it
14. **Resolves tutorial mode at boot and fails closed on it** (onboarding tutorial, design 5.2). `State.tutorialMode` is tri-state (nil until resolved) and `writeEntry` refuses to publish unless it has resolved to **false** — so a tutorial server never writes a directory entry at all, and a normal server delays its first publish by one MemoryStore read. Three resolution sources: `Config.TUTORIAL_FORCE_MODE` (the Studio/non-live testing switch — ignored with a warn on a live server), the `RedwaterAccessCodes_v1` entry for this `PrivateServerId` (a plain string is a normal reservation; a `{ code, tutorial = true }` table is a tutorial reservation, written by MatchmakingService (Bounty) `reserveTutorialServer`), and any first arrival's `TeleportData.tutorial` as backup — an arrival *without* the flag resolves normal. The resolved value is mirrored onto the `workspace.TutorialMode` attribute for clients. `resolveAccessCodeFromStore` accepts both value shapes
14a. **A tutorial server publishes exactly one thing: a marker saying so** (2026-08-13). Its entire footprint is `jobId → true` in the hash map `RedwaterTutorialServers_v1`, on the same 30s TTL and the same 8s heartbeat, written the instant `setTutorialMode` resolves TUTORIAL rather than waiting for the next beat — a friend can tap Join within seconds of the lesson starting. It exists because Bounty's follow-join path holds a **jobId and nothing else**, so a server with no directory entry gave it nothing to map that onto: a friend in the training run and a friend whose match had died produced the identical empty lookup, and both were told the match had ended. That was reported live on 2026-08-11. The marker carries no roster, no phase and no capacity — nothing may ever be routed here, and the only question it answers is "is my friend in the training run?", read back by MatchmakingService (Bounty) `isTutorialServer`. It is deliberately a **separate map** from the directory, because every destination decision reads that one. `publishHeartbeat` is what picks between the two writers per beat: tutorial writes the marker, normal writes the entry, unresolved writes neither. `setClosing` removes the marker unconditionally (free on a normal server, where the key was never written)
15. **It READS the directory now, not only writes it** (2026-08-27, SERVER_CONSOLIDATION_SPEC §5). This module was a pure writer for its whole life — it published what was happening in here and Bounty decided where anyone went. The end of a round is now a routing decision taken from inside the match (dissolve this roster into a fuller server, or rotate to a sibling place), and there is no cross-place RPC to hand that decision back to the lobby, so six functions were added: `readDirectory()`, `chooseMergeTarget(roster, modeId, requiredMapId)`, `resolveAccessCodeFor(entry)`, `claimSlots(privateServerId, count)`, `publishProvisionalFor(...)` and `livePlayersByMap(modeId)` — plus `previewMergeMaps(roster, modeIds)` on 2026-08-28, making seven. `readDirectory` is a `GetRangeAsync` over the same sorted map, descending by player count, normalising absent `map`/`mode` to the legacy values exactly as Bounty's `readServers` does; its result is cached in `lastDirectoryServers` purely so the rotation weighting reuses the read the merge already paid for
15a. **`chooseMergeTarget` is the whole consolidation mechanism, and it has no threshold.** A candidate qualifies when it is not us, runs the winning mode, sits on a map this build can route to, matches our region, is fresh, accepts matchmaking, and has `ceilingFor(entry, roster) - players >= roster`. Survivors sort by `players` **descending**, then at most `PENDING_PROBE_LIMIT` (5) are probed for pending claims and the first that still fits is taken. Every merge that fits is worth making, because the alternative is never "stay put" — it is rotating to an empty server. A roster of 2 into a 5 makes a 7; a roster of 4 into a 3 makes a 7; a roster of 6 needs 6 free seats against a cap of 7 and so can only land on a server holding 1, which makes a 7 as well and rescues a lone seeder. The descending sort is what keeps that honest: a downward merge only happens when nothing fuller had room. **The roster travels whole** — it is never partitioned to squeeze out more packing, because keeping the people you just played with together is the point

15a-i. **`requiredMapId` pins the map, and it is the one thing here that outranks packing** (2026-08-28). The end-of-match tiles show the map each mode would send you to, so the vote is a mode *and* a map; RoundController passes the winning tile's map back in, and a server on any other map stops being a candidate at all rather than a worse one. When nothing on the promised map fits, the caller rotates onto a fresh server there instead of merging elsewhere — so expect somewhat more rotations and slightly thinner packing. That cost was accepted deliberately: a merge that quietly landed the room on a different map would make the panel lie about the thing it had just asked them to choose. Nil restores the old any-map behaviour, which is what a caller with nothing to promise gets (a one-mode map skips the ballot)

15a-ii. **`previewMergeMaps(roster, modeIds)` is that vote's forecast, and it is read-only by construction** (2026-08-28). It runs `chooseMergeTarget`'s own filter and comparator over one `readDirectory()` and then stops: no pending probe, no access-code read, and above all **no `claimSlots`** — a forecast that reserved would hold seats on three servers for a vote that picks one, and the two nobody chose would keep them until the TTL expired. It returns `{ [modeId] = mapId }`, absent meaning "this mode has nowhere to merge, so it will rotate". One `GetRangeAsync` covers the whole ballot and refreshes the `lastDirectoryServers` cache the roll's weighting then reads — and `livePlayersByMap` stopped counting **our own entry** on the same date, harmless while the only caller excluded the map we are standing on, but the ballot's roll may land at home and our own headcount would otherwise drag every no-merge tile straight back onto it. What it returns is **binding on the map axis**, since the caller feeds it straight back as `requiredMapId`; staleness therefore costs a *merge* rather than a wrong photograph — if the named server fills while people are voting, the roster rotates onto a fresh server on that same map. `canPublish` false (Studio, or a server that was never reserved) returns empty, so every tile rolls
15b. **Size does NOT decide who merges into whom — phase does.** 2 joining 5 and 5 joining 2 both produce a server of 7, and under rotate-every-round the server that just ended its round is teleporting regardless, so refusing to let a bigger roster join a smaller one saves nobody a loading screen and just sends more people to an emptier room. What a direction rule *is* needed for is the **simultaneous-move race**, where two servers each merge into the other and both land in a room the other has just abandoned. That race only exists between two servers both at their decision point, which is readable off the entry: `Fight`/`Waiting`/`Countdown`/`Starting` is not deciding anything and imposes no size constraint at all; a candidate also in `Summary` may be moving too, so `directionAllows` breaks the tie on `privateServerId` and exactly one side travels. **Do not "fix" this by excluding `Summary` candidates outright** — two servers whose round timers are in sync hit `Summary` together every round, so an exclusion would leave that pair missing each other forever, where the tie-break resolves them on the first attempt
15c. **`publishProvisionalFor` differs from Bounty's `publishProvisionalEntry` in exactly one field, and it matters:** `players` is the travelling roster, not 0. Bounty writes 0 because a Play-press reservation genuinely has nobody in it yet and reserves its seats through `claimSlots` instead; a rotation knows exactly who is arriving, and stating it is what makes the new server a usable merge target the moment it exists rather than 20 seconds later. Publishing 0 would fail the capacity test against every possible roster and waste the window. Because `players` already counts the travellers, slots are deliberately **not** also claimed for them — the lobby adds `players` and pending together, so doing both double-books the seats. If the teleport then fails and nobody arrives, the entry advertises phantom players for up to its 30s TTL, which fails in the safe direction (others read it as full and decline to merge) and expires on its own
15d. **These predicates are duplicated from Bounty's MatchmakingService on purpose** — `isRoutableMap`, `isFresh`, `isRegionMatch`, `acceptsMatchmaking`, `ceilingFor` and the pending / access-code readers, plus `ENTRY_MAX_AGE`, `PENDING_TTL`, `RANGE_COUNT`, `PENDING_PROBE_LIMIT` and `PROVISIONAL_TTL`. It follows the precedent `registerAccessCode` already set, and **both copies carry a comment naming the other**; change one, change the other. Extracting a shared `MatchRouting` module is the right shape if a third caller ever appears, but it means refactoring the most safety-critical path in the project — four launch complaints came out of it — to ship a behaviour change that does not need it. The **ceilings** are the one thing not duplicated: they ride on the published entry, so a merge reads the destination's own numbers and they cannot drift from its Config. `RedwaterPendingJoins_v1` is new to the match place; the other map names already existed here

## Team modes

Owns the resolved mode. It picks it from the access-code record's `mode` field, else the first
arrival's `TeleportData.gamemode`, else the default -- absent always means the default, because
records written before the field existed outlive a publish. It writes `State.gamemode` and
mirrors it onto the workspace `Gamemode` attribute (which is what clients read), publishes the
mode on the directory entry so the lobby can filter, and stamps it into the access-code record
for the next map so a party carries its mode across the teleport. `switchGamemode(modeId)` is the
same write for a mid-server mode change, followed by a publish nudge.
