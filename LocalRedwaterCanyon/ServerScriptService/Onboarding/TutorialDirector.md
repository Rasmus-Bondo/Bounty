# TutorialDirector

Owns the onboarding tutorial lesson on a tutorial Redwater server: the eight-step state machine, the bot choreography, the payout, and the return teleport.

## What it does

1. `Init(dustRuntime)` — called unconditionally from Main; stores the Dust runtime so step 7 can call `ChargeService:Set(player, MaxCharge)` (there is no runtime registry). The `Set` fires from **inside** step 7's `afterBeat` callback, last, after the firing line has spawned — not on the step boundary; see item 4a.
2. `Run(player)` — blocking; called by RoundController's tutorial session once `State.tutorialMode` resolves true and the round state is live. Returns an outcome: `Completed | Exited | Ceiling | Left`.
3. Drives the 8 lesson steps — the design's eleven with Look merged into Move on 2026-08-09 and the two panel steps cut on 2026-09-09 (the look sweep passed before a player could register the banner existed). **The merged step became the opening WALK on 2026-08-16** (`arriveAt`, item 4e): the look sweep and the sprint observation are both gone, sprint survives as copy rather than as a gate, and the first thing the lesson asks for is the thing a new player was going to do anyway — which also lands them where the range is. Each step has a timeout that auto-advances so a confused player is never trapped, and every deadline adds `STEP_BEAT` (2s) on top: the client holds the *completed* step on screen for that long, fades it, and only then pops the next line in, so the instruction is not readable for the first two seconds after this module fires it. **`STEP_BEAT` is duplicated in TutorialClient and the two must move together** — the client owns the pause, this module owns the budget and the choreography timing. A `Welcome` payload goes out before step 1 and the session holds `WELCOME_HOLD` (**6s**, up from 4 on 2026-08-12) while the client plays its card. **That constant is what gates step 1, so it has to stay ahead of the client's own hold**: firing early does not fade the welcome card, it *cuts* it — `presentStep` calls `hideWelcome` first thing. It covers the client's pop (0.45), its hold (4.4, raised in the same pass when the card became a logo, a rule and a full sentence rather than three words) and its fade (0.6), leaving the same ~0.55s of clear screen before the first instruction that the old 2.4/4 pairing had. **The two panel steps — `FreeMouse` (open the settings panel) and `Stats` (open the scoreboard) — were CUT on 2026-09-09**, taking the lesson from 10 runtime steps to 8. Between them they shed 12.6% of everyone who started the lesson (1087 players a day) to teach two menus that nothing in a round needs. The funnel is what settled it: `LiveFire`, a step that **cannot be failed**, churned 7.58% on its own, so per-step churn was a function of elapsed time rather than of any step's content and cutting steps was the only lever there was. `LiveFire` inherited `FreeMouse`'s `stop = 4`, so the walk to the last pad survives and now leads straight into the fight. The `pcOnly` skip mechanism is still intact and still unused (`step.pcOnly` tested against `isTouchPlayer`, platform via `Telemetry.getPlatform`), and nothing left in the list is platform-specific. The bounty step carries a 3s lead-in before its 30s budget starts, and that number is load-bearing on the client side as well as here (see item 5). **Step numbers in this file and in the code's table names (`STEP6_BOTS`, `STEP7_HUNTERS`, `STEP11_HUNTERS`) keep the design doc's original 11-step vocabulary and no longer track the runtime list at all** — read the step *ids*, never the constants or the numbers. The runtime order is Move, Shoot, Dash, Fan, FirstBlood, Ult, Bounty, LiveFire; where this file says "step 11" it means `LiveFire`, which is runtime index 8.
4. Server-observed gates ride Dust's existing combat remotes — `FireBullet` (3 shots), `DashRequest`, `Skill2Request`, `HighNoonShootRequest` — never the input path that requested them. The ult gate is **"lock, then fire" — both halves**, which is what the step's own line asks for. Not `HighNoonRequest`: that fires on the F press before any lock-on, and gating there advanced the step the moment the ult merely opened. But `HighNoonShootRequest` alone was not enough either (fixed 2026-08-11): HighNoonClient sends it once `MinShootTime` (1.5s) has passed **whether or not anything was ever locked**, so a trigger pull at empty air passed a step whose entire subject is locking on. `gate()` therefore takes an optional `predicate` read at the instant the remote lands — for this step, the `HighNoonHasLock` character attribute HighNoonModule publishes from its live scan, so the gate reads the same skull the player is looking at. A failed reading is **dropped, not counted**, exactly like an unarmed gate: the player keeps the step, the spent ult is refilled (item 4c), and they try again. The strict gate and the refill are a pair — the gate alone would stall the lesson, the refill alone would not teach the ability. **The live remotes are under `ReplicatedStorage.Hunters.Dust.Remotes`** — authored there, and the runtime re-uses that folder rather than replacing it. Looked up with NO blocking waits: waiting on a folder that turned out to be empty once cost a playtest a 2-minute blank screen (4 × 30s `WaitForChild`), so a miss is one warn and a step that rides its timeout. Client-observed gates arrive over the `TutorialProgress` RemoteEvent as `(stepId)`, validated only against the current step — and `CLIENT_GATED` is **empty** since 2026-09-09: Alt and the stats panel were its only two entries and both steps are gone, so every gate left is a server-side poll or a combat remote. The table and its handler stay standing — an empty gate set refuses every report on its own, and a future client-observed step needs both halves back rather than rebuilt. The look sweep and the sprint observation left with step 1's rewrite (item 4e): the walk is polled server-side against the pad, so the one step whose gate was purely a client report is now the one step the server watches directly. Step 6 polls `State.playerKills` for 2 bot kills, and **step 11 polls nothing at all** — it is a plain **20-second** stopwatch (`timerOnly`, restored 2026-08-12; cut from 30s on 2026-09-09, when it also gained a visible countdown under EXIT TRAINING and moved into area 2). It was gated on 1 kill for a day, with the timeout as a backstop and a two-minute free-roam window behind it; the gate and the window are both gone, so there is nothing left for a gate to bring the player to sooner — the lesson ends when the clock does and the player is teleported back to Bounty (item 9b). `timerOnly` is what keeps that ending counted as a real advance rather than a timeout in the funnel: riding the clock **is** the step, so a player who never lands a hit has not failed anything. The kills baseline `enterStep` used to read before the five bots spawn went with the gate. (Worth knowing if it is ever retuned: the five bots spawn 100–125 studs out and take 6–9s to walk in, and the Training tier's `AttackRange` is 90, so **20s of budget is ~15–17s of actual engagement** since the spawns moved to the area-2 firing line (44–78 studs, 3–5s to walk in) from the area-3 free-roam ring (100–125 studs, 6–9s). That is what stopped the walk-in eating a third of the step, and it is why the countdown can start at the instruction rather than at the bots' arrival — which remains the lever if this ever has to be more generous without making the run longer.)
4b. **A gate does not exist until its instruction does** (`armGates` / `gatesArmed`, 2026-08-09). The combat remotes are live the moment a step is entered — a full `STEP_BEAT` before its line is on screen — so a player who dashed straight off the back of the shooting step cleared the dash step without ever seeing it. `s.gateArmedAt` is set to `math.huge` as the step id changes (`enterStep` can yield, so the window has to be *shut*, not merely short) and opened by `armGates` immediately after the push, at `STEP_BEAT + GATE_ARM_GRACE` (0.3, covering the client's 0.14 pop fade and a leg of latency) — or at the grace alone when `advancedBy` is nil, mirroring the client's own branch, which only sits on the beat for a real transition and presents step 1 and any `"__sync"` resend at once. An action inside the window is **dropped, not banked**: banking would pop the line and complete the step in the same breath, which is the same bug with an extra frame. Dust's cooldowns make a dropped input cheap — dash 4s and fan 8s against 15s budgets that already exclude the beat. `pollStep` is held to the same rule and loses nothing by it (a poll reads state, so it just advances a tick later). The **client-observed** gates are deliberately exempt: the client arms those inside `presentStep`, so they already start with the line, and re-checking them here would drop a legitimate report from a low-latency client that satisfied the gate instantly — each is reported once, so a dropped report is a step that rides its full timeout.
4a. **Nothing spawns on a step boundary.** Every dummy and bot in `enterStep` goes through `afterBeat(s, id, extra, fn)`, which waits `STEP_BEAT` plus the previous step's `holdAfter` (still unconsumed in `s.pendingHold` at `enterStep` time, so the wait tracks the LINE rather than the payload) plus a per-step extra, and then checks the step is still current before running — otherwise the choreography walks in over the line the player just finished reading, five bots appearing on top of the ult sentence being the tell. The extras: step 6's pair starts on the step BOUNDARY (`-STEP_BEAT`, the floor — the id guard needs the step to be current) because it has 110+ studs to walk and would otherwise still be specks behind the lumber when the line says to take them down, the ult firing line waits one further second — and **the ultimate charge is granted inside that same callback, after the line spawns**, rather than on the step boundary three seconds earlier: a full charge ring is the loudest thing on the HUD, so a player who read it as the cue fired Dead Eye into an empty canyon and had nothing left when the targets arrived (playtest 2026-08-09) — and the bounty bot waits the **whole lead-in**, which is not a tuned number: the client pops the lead-in line at `STEP_BEAT` and swaps to "claim it" `leadIn` later, so `afterBeat(leadIn)` is that swap's instant *by construction* — the second line and the bot walking out of cover are one event, and shortening the reading time moves the bot with it rather than letting the two drift (they were 4s apart before 2026-08-09). Step 6's was walked back across the same playtests — the beat that stops a spawn landing on the previous line is also that much of a long walk not happening. There are four calls and no more: the step 6 pair, the ult line, the bounty bot and step 11's five. **The one timed despawn is gone with the dummies** — step 6 used to retire the cloned range targets a second in (`1 - STEP_BEAT`) so that deleting them did not read as the player's last shots deleting the range, and there is nothing to delete now that the targets are authored map rigs (item 5). Deadlines already include `STEP_BEAT`, so the wait costs a step nothing, and a step that ends during the wait spawns nothing at all.
4c. **The ult step refills the charge if the attempt is wasted** (`watchUltCharge`, 2026-08-11). It is the only step a player can lock themselves out of: High Noon spends the entire charge on the F press (`HighNoonModule` does `chargeService:Set(player, 0)` at activation) and then ends on its own after `MaxHoldTime` (5s) whether or not a shot was taken — but the gate is `HighNoonShootRequest`, the shot. Two ways to strand: never pressing fire, or only pressing it inside the 1.5s `MinShootTime`, which HighNoonClient drops before it reaches the remote. Either way the ultimate is gone, a lesson with no combat pressure offers no way to earn another, and the step rides out its 20s timeout with nothing the player can do. **Firing without a lock is a third way in as of the same day**, now that item 4's gate checks `HighNoonHasLock` — which is the whole reason the two changes ship together: tightening the gate without the refill would have turned the commonest ult mistake into a hard stall. A watcher polls every 0.5s for the life of the step and tops the bar back to `MaxCharge` whenever the charge is short and High Noon is not running, reading the `IsUsingHighNoon` character attribute (set at activation, cleared in `endHighNoon`) so a refill can never land mid-ultimate and hand out a second free cast; a respawned character has no such attribute, which reads as "not active" and is correct, since the ult does not survive a death. Armed from **inside** step 7's `afterBeat` callback immediately after the first grant — started any earlier it would fill the ring before the line lands and undo the ordering in item 4a. Capped at 2 refills, and each one also sets `restartStepTimer` so a late attempt gets a full window rather than the remains of the first: without the cap that pair could hold the step open until the lesson's hard ceiling.
4d. **The ult step plants, faces and FREEZES the player** (2026-08-16). The ult is the one step that cannot tolerate the player standing wherever the last fight left them: High Noon's cone is a 45° half-angle and the six-marker firing line only fits inside it from the area-2 pad — worst marker 30.1° off-axis, 14.9° of margin, against `CheckPointTutorial2.Stand`'s authored facing (the centroid of the six markers from eye height). `enterStep` teleports them onto that Stand via `SpawnService.teleportPlayerToSpawn` **at the step boundary, before the beat**, and ships the Stand's LookVector on the step payload as `face`: the server can place a player but cannot turn one (under LockFirstPerson the client camera owns the yaw), so TutorialClient points the camera, **pitch included** — the line sits ~16 studs above the pad and a levelled look puts all six above the crosshair. The ordering is the design: player planted looking at empty ground, then the line pops into exactly their view (`afterBeat` 1s), then the charge fills last (item 4a). The `"__sync"` resend carries `face` too, so a reconnecting client on the pad still gets pointed. **The plant is also a hold**: `applyUltFreeze` takes a `HunterMovement.SetOverride(character, "TutorialUltStep", 0, { LockJump = true })` — the documented victory-freeze shape, and an override is the layer that short-circuits every other one, so High Noon's own `SetBase(6, ...)` crawl cannot lift it — and the payload's new `pin` flag tells the client to hold the camera on `face` every frame rather than pointing it once. Released in `exitStep` and again, `pcall`ed, at the top of `finishSession`, and re-applied on `CharacterAdded` for the length of the step so a death cannot escape it. The step is a demonstration: the player is placed, pointed at six targets and asked to press two buttons, and every input that is not those two buttons is a way to end up aiming at rock.
4f. **The firing line rebuilds itself** (`spawnUltLineBot`, 2026-08-16). The step's whole subject is holding a full set of six in the cone until they lock, so a player who shoots one down with the revolver first would otherwise spend the rest of the step aiming at a gap. A death respawns the same hunter on the same marker facing the same pad after `ULT_LINE_RESPAWN_DELAY` (1.5s — longer than `retireOnDeath`'s own 1s despawn, so the replacement lands after the corpse leaves rather than inside it), capped at `ULT_LINE_MAX_RESPAWNS` (12). **The ultimate's own kills are not replaced and nothing tests for that**: the gate fires on the shot *request*, so `stepDone` is already true by the time the executes land, and the `s.stepId == "Ult" and not s.stepDone` guard the callback shares with the spawner is what makes the distinction for free.
4e. **The lesson's four STOPS** (`awaitStopArrival` / `STOP_PADS`, 2026-08-16). **Stops are not areas.** The bowl has three wall-separated areas and four stops, because stop 2 (`CheckPointTutorial1`) is a walk *inside* the opening area with no wall in front of it. There are two shapes, and the difference is which side of the step the walk sits on:
   - **`arriveAt` — the walk IS the step.** Only step 1 (`arriveAt = 2`). It opens on the spawn pad, its line names the destination, and it passes when the player stands on checkpoint 1, polled by `pollStep` through the same `playerIsOnPad` test as everything below. Its 30s timeout is therefore a travel window rather than a lesson's, and it ends in the same backstop teleport. Its payload carries `pad`/`via` like a Travel push, because the client's rule is simply "a payload with a pad has a route".
   - **`stop` — an arrival gate standing in FRONT of a step.** Stops 3 and 4 (`FirstBlood` carries `stop = 3`, and that is now the ONLY one — `LiveFire` briefly inherited `FreeMouse`'s `stop = 4` when the panel steps were cut on 2026-09-09 and lost it the same day. **Stop 4 is no longer visited by the lesson at all**: a 122-stud walk to a third pad is exactly the elapsed time the cut was made to remove, so the closing fight is staged where the bounty step leaves the player). The whole block — line, bots, choreography — is held until the player stands on the destination pad (7-stud radius, 8 vertical, against the pad's `Stand`). Deliberately **not a step**: the funnel's indices must stay comparable across the change, so the gate lives inside the existing step's lead-in.

   The gate pushes a banner line of its own (`id = "Travel"`) carrying `pad` — the destination pad's NAME, which the client draws its guide beam to — and `via`, the optional corner the route bends around (`STOP_VIA[3] = "middlepoint"`; names, never positions, because the map owns where its geometry is). `TRAVEL_WINDOW` is 20s and sits **on top of `STEP_BEAT`** like every other deadline; the walks are 7-10s, so the backstop teleport onto the Stand (`SpawnService.teleportPlayerToSpawn`, counted into `s.travelTeleports`) fires on a player who is genuinely lost, never one who is merely slow. It restarts when the character changes mid-walk — a death respawns on the *previous* stop's Stand, since the anchor only advances on arrival — and retries a teleport the character was not ready for. On arrival either way, `State.tutorialRespawnStand` advances; RoundController's `sendPlayerToLessonSpawn` reads it, which is what makes every respawn land where the player currently is (cleared in `finishSession`). The gate walls fall in `exitStep`, timeout included — `TutorialWallStep1` + its "FINISH THE PREVIOUS TASK" sign when `Fan` ends, `TutorialWallStep2` + its sign when `Bounty` ends; wall and sign are destroyed together so the sign never outlives the barrier it explains.

   **`lastAdvance` is demoted for the walk and promoted back on arrival**, and both halves matter. The Travel push carries the finished step's own `advancedBy` so that step still gets its cue, its fade and its beat; `lastAdvance` is then set to `"travel"`, which the client fades and beats on but does not chime, so the real instruction replaces the walk line without announcing a completion that never happened. Reaching the pad **is** a completion, so it is promoted back to `"action"` (2026-08-16) and the next step's push carries the chime and the green flash — the same cue checkpoint 1 has always had, since `arriveAt` is an ordinary step and ends the ordinary way. The promotion is gated on `walked and s.lastAdvance == "travel"`: the backstop teleport stays silent (it completed nothing, exactly as step 1's own timeout does when it teleports), and the `== "travel"` half stops a stop the player was already standing on from upgrading a previous step's `"timeout"` into a chime.

5. Bot choreography through BotService's control layer, with **every position resolved from the map's authored Tutorial folder since 2026-08-16** (`MapConfig.Instances.Tutorial` → `BotSpawns/` markers and `Areas/` pads — this module is mirrored into Frostbite, which has no folder, so no coordinate may live in the code): `PrepareScripted()` at start (locks the population and arms `SpawnBot` even while `BotConfig.Enabled` is off — the ordinary `PrepareRound`/`ActivateRound` pair honours that switch and left every lesson bot silently ignored); **step 3 spawns nothing at all since 2026-08-16** — the shooting targets are the `Dummy` rigs AUTHORED in the map, standing 52-60 studs down the course from the spawn pad and in view of its facing, so this module no longer clones `ServerStorage.TutorialDummies` onto the `TutorialDummySpawn` markers, no longer re-seats them on raycast ground, and no longer destroys them a second into step 6. The step cost nothing by it: its gate is 3 shots FIRED, never a hit on a dummy, so a map whose builder moves or re-poses the rigs still passes. (`ServerStorage.TutorialDummies` is now referenced by no script. It is dead but harmless, and the tag it carries is a trap: the templates are tagged `AimAssistTarget` and the authored rigs were not, which is what silently cost touch players auto-fire on the range until the rigs were tagged directly.); step 6 spawns Dust+Fortuna `Easy`/HoldFire/`TargetPlayersOnly` on the two `PassiveBotSpawn` markers ~70 studs out (paired to the markers sorted by X, so a builder nudging one cannot reshuffle who stops where), each stamped with a `TutorialOutline` attribute that BotVisualClient reads to draw the red enemy outline on its clone — the ordinary TDM/Domination `Occluded` outline, deliberately not the see-through bounty style, and set on the server rig because a Highlight parented there never renders — and they **pathfind to the player** — `Approach = { Subject = player }`, the same mechanism as the step 8 bounty bot, since 2026-08-10. They used to walk a fixed `Route` to where the middle target dummy stood, which is a mark chosen before anyone knew where the player would be: a route arrives where the player no longer is, and the pair read as two men marching to a spot rather than coming for the person shooting at them. "Walk in, then stand down and wait to be shot" survives the change, which matters because it is what `HoldAtEnd` used to buy — `SetApproach` owns the brain tick for the rest of their lives, stopping and facing the player on arrival and resuming if the player moves off, and it never hands them back to ordinary behaviour (the 2026-08-09 playtest that did had them wandering off mid-aim, which is worse than statues for a shooting lesson). Their `StopDistance` is staggered 12 / 20 because both walk at the same target from entries 7 studs apart, so a shared radius stands them shoulder to shoulder on one side of the player. **They carry no `Leash`, and that is required rather than incidental**: `BotPathing` clamps every destination inside `RequestMove`, which is the same door the approach issues through, so a leash on the tutorial spawn would cap the walk at the leash edge and leave the pair pressing into an invisible boundary, re-asking every 0.5s, whenever the player stood further out — the approach is its own confinement, since the only destination it ever issues is the player; step 7 spawns the six-bot StandDown firing line — one bot per `UltimateBotSpawn` marker, six because High Noon's `MaxTargets` is 6, roster cycling Dust/Fortuna/Vesper/Bram/Dust/Fortuna — faced at the area-2 pad at spawn (the markers carry only accidental tilt from being dragged onto terrain, so the facing is computed, not read), **retired one second into the bounty step** (2026-08-09; it was 12s, which left up to five idle bots standing behind the bounty target the player is being told to pick out of the canyon — one second rather than zero only because an execute still resolving needs a bot that exists, or the kill is lost); step 8 spawns a Vesper on the `BountyBotSpawn` marker (`Easy`/HoldFire/`TargetPlayersOnly`; a missing marker means a warn and a step that rides its timeout) with **`Approach = { Subject = player }` in the spawn spec**, and marks it with three `BountyService.registerBotKill` calls (the production path) — **spawned on a `STEP_BEAT + leadIn` (5s) delay, not on the step boundary**, so it walks out exactly as the "claim it" line lands rather than while the player is still being told what a bounty is. The approach rides the **spec** rather than a `SetApproach` call after `SpawnBot` returns, because `SetActive` runs a brain tick synchronously and one bare tick of a Vesper is an 18-28 stud sideways strafe to open her 150-stud `DesiredRange`, held for up to a second afterwards by `PathRecalculateInterval`: the first thing the player saw of the bounty was it walking out of cover *sideways, away from them*, which is what "the bounty bot pathfinds strangely" turned out to be (2026-08-09); step 11 spawns five bots (Bram, Dust, Dust, Fortuna, **Vesper** — she replaced the second Fortuna on 2026-08-16; she had been out since 2026-08-09 because on the canyon floor she grappled to a ledge and pot-shotted the player, and **that was a canyon fact rather than a Vesper fact**: a Vesper bot only leaves the ground by hooking an authored `workspace.VesperHookSpotsBot` marker, the nearest one to this bowl is 1445 studs away against a `GrappleHook.Range` of 125, and a 20-stud sweep of the whole bowl footprint never gets within 1339 — so `_bestVesperHookSpot` has no candidate anywhere in here and she fights on foot. **Author a hook marker inside the bowl and she goes back to sniping from a rock.** Her ultimate cannot fire either: passive charge is 0.4/s against a 20s step. Nothing about the tier needed changing — Training's `DamageMultiplier` 0.35 was sized against *her* 125 headshot in the first place, three hits to kill) at `Training` with normal targeting, **leashed 60 studs to the AREA-2 pad since 2026-09-09** — on the five **FURTHEST** `UltimateBotSpawn` markers from that pad (42–78 studs, measured horizontally, re-picked at runtime so the rule survives a builder moving a marker). **The marker set changed with the pad, and `FreeRoamBotSpawn` is now unused by the lesson entirely.** That ring is authored around the area-3 pad and splits badly from area 2: five of its eight markers are 21–73 studs away on every bearing — 21 studs being precisely the "jumped by five bots out of nothing" spawn the distance rule exists to prevent — and the other three are 103–159 studs away *behind the area-3 wall*, which only opens as this step begins. The ultimate line is authored for this pad and in view of it, and sits in a ~60-degree arc, so the five walk in from one side as a squad rather than closing from all round. It is free by then: the six-bot firing line that used it is retired a second into the bounty step. **If area-2 free-roam markers are ever authored, this is the choice to revisit.** **The distance is the warning**: nothing in this game tells a player a bot is about to exist, so the only thing standing between a spawn and an ambush is enough ground to watch it walk — two earlier passes got this wrong by being too close (a 35–45 stud ring, then 60–90), and both read as *being jumped by five bots that appeared out of nothing*. The Training tier's `AttackRange` is 90, so the far spawns cannot fire until the walk has mostly closed, and blocked line of sight at spawn is fine — a bot walking out from behind cover is the intent. All five spawn *outside* the 60-stud leash on purpose: `BotPathing._clampToLeash` trims their destinations to the leash edge, so the tether is what turns a far spawn into a walk toward the player rather than five bots milling where they landed. Every marker was path-verified back to the pad in edit mode with the gate walls open (Success, no jump waypoints), and each bot is faced at the pad at spawn like the step 7 line. `TargetPlayersOnly` keeps the scripted bots off each other, and the `BotAuthoredWalk` attribute their routes/approaches carry holsters Fortuna's jumps mid-choreography.
6. Every tutorial bot's record is despawned ~1s after it dies (after BotService's own death path has credited the kill), so the ordinary 6s respawn never fires for a lesson bot.
7. Fires `TutorialStep` to the client on every transition (`index`, `total`, `id`, `timeout`, `leadIn`, `advancedBy`, `extraBeat`, plus `face` / `pin` for the ult plant and `pad` / `via` for a step whose gate is a pad) — plus the step-less `{ id = "Welcome" }` before step 1, `{ id = "Travel", stop, pad, via }` during an arrival gate (item 4e), `{ id = "Outro", key }` and `{ id = "Complete" }` at the end — and keeps the last payload on the session: a client `"__sync"` pull over `TutorialProgress` re-sends the current step (minus `advancedBy`, so no spurious advance flash, but **with** `face`, `pin`, `pad` and `via`, so a reconnecting client is still pointed and still has its route). The pull exists because the step-1 push fires within a second of the session starting — before a booting client has connected its listener — and a RemoteEvent with no listener is simply dropped, which read as "the tutorial never started".
8. Telemetry: fires `Telemetry.logTutorialFunnelStep` for each step on any advance against the funnel session id carried in TeleportData (`tutorialFunnelId`, minted by Bounty's dispatch; a Studio test mints its own); the completion step (`#STEPS + 1`, currently 11) fires only on genuine completion; one `TutorialRun` aggregate event per run (outcome, with a `T<timeouts>|S<exitStep>|W<travelTeleports>` detail — W added 2026-08-16 to report whether the arrival gate's backstop ever fires, without touching the funnel indices).
8a. **Also fires the middle of the `NewPlayer` journey funnel** (2026-08-15): step 2 "Tutorial Started" in `Run`, once the session is built and the carried funnel id resolved — the lesson being genuinely under way here is a different fact from Bounty having dispatched them, and everything between the two (reserve, teleport, the retry ladder, a quit at the loading screen) shows up as that funnel's 1 -> 2 drop. Step 3 "Tutorial Completed" fires in `runOutro`, plus the rare `finishSession` fallback guarded on `outcome == "Completed"`. It shared that signal with the Tutorial funnel's own step 11 until 2026-09-09, when that row was cut — it read 100% off Live Fire every single day, because finishing the stopwatch **is** finishing the lesson. `s.funnelStepSent` outlived it, because what it still guards is this NewPlayer step double-firing on the way out. It is hooked to that signal rather than to `Tutorial.Completed`, which `finishEarly` also sets on the `Exited` outcome — that flag means "never dispatch this account again", not "finished the lesson", and reading it would count everyone who pressed EXIT TRAINING as a completion. `Ceiling` is excluded for the same reason the Tutorial funnel excludes it. These take no session id: that funnel's id lives on the profile.
8b. **A REPLAY is kept out of the Tutorial funnel entirely** (2026-08-17). A player arriving from Bounty's CHANGE MODE picker carries `tutorialReplay = true` in TeleportData; `Run` reads it into `s.isReplay` in the same block that resolves `funnelId`, and every funnel write goes through one `logFunnelStep(s, player, stepIndex)` writer that returns early on it. Suppressing at the **writer** rather than at each of the three call sites is the point — a future step cannot reintroduce the leak by calling `Telemetry.logTutorialFunnelStep` directly and forgetting the flag. Without it a veteran re-run enters as a near-100%-completion session and dilutes the first-time drop-off the funnel exists to measure. **Deliberately NOT applied to the `NewPlayer` journey funnel** (item 8a): that one is per-account for life and enforces step order, so its step 2 is refused anyway on a run with no step 1 behind it. The flag reaches this module only as telemetry — it gates nothing about the lesson and nothing about the payout, which stays governed by `Tutorial.BonusPaid` (item 9e) so a replay is paid 0 by the ordinary rule. **This change is in the mirrored copy too** — Frostbite's TutorialDirector is byte-identical (79311 bytes / checksum 123774826).
9. The payout is **paid a step at a time as of 2026-08-17**, not as one lump at the end. `TUTORIAL_COMPLETE_CASH` (250) and `TUTORIAL_COMPLETE_TOKENS` (50) are run TOTALS; `payStepReward` pays `stepShare` = `floor(total / #STEPS)` — 25 Cash and 5 Tokens on the stock 10-step run — on **every advance**, and `payOut` pays whatever is left. The split is derived rather than a hand-written per-step table, so it cannot drift from the step list, and the remainder covers both a pot that does not divide evenly and a `pcOnly` step the platform skipped (the same fact, "a step that never paid", settled in one place). Both currencies go through `Wallet.award(..., "tutorial_complete")` — a reason maps to a transaction TYPE and the currency rides its own argument, so the instalments land under Onboarding in analytics without a new reason in both copies of Wallet. `payOut` still does `ProgressionService.clearPendingRewards` and the `Tutorial.Completed/CompletedAt` writes.
9e. **A step that rides its TIMEOUT still pays**, for the same reason nothing else in the lesson punishes one — the flat award this replaced ignored timeouts too, and paying only clean steps would land a confused player at the end of the whole lesson holding less than Bounty's completion card promises. Two consequences of the split are worth knowing. The **first** instalment burns `Tutorial.BonusPaid`, not the last: a run abandoned three steps in has been paid part of the pot, so the account has to read as paid from that moment or a replay would earn a second full pot on top of it — which is why `finishEarly`'s `Exited` branch no longer says "no Cash, BonusPaid stays false". And `paysBonus` is resolved **once and cached** on the session, because that first instalment sets `BonusPaid` itself; re-reading it per step would answer "already paid" from step 2 on and leave the run holding a single 25. A missing profile answers false *without* caching — that is "not readable yet", not "already paid".
9f. **Each instalment fires a combat feed row** via `ProgressionService.notifyTutorialReward(player, cash, tokens)`, `pcall`ed because a missing reward row is never a reason to stall the step machine. It is the one row that survives CombatFeedClient's blanket tutorial silence, and it lands on the same instant as the step-complete chime and the green vignette. The end-of-run remainder deliberately fires **no** row: it is 0 on every ordinary run, and on a run where it is not it would arrive as the outro card lands and read as a second award. Then a return teleport to Bounty carrying `{ tutorialComplete = true, tutorialCash = N, tutorialTokens = N, tutorialChest = bool }`; in Studio the teleport is skipped and the session stays open. The 330s hard ceiling reaches the same payout by a different door (260 → 300 when the beats, the longer lead-in and the welcome card pushed a full-timeout run to ~230s; 300 → 330 on 2026-08-16 when the two 20s+beat travel windows pushed the worst case up; re-derived at the end of that day's changes to **300s exactly** once step 1 became a 30s walk, which is 30s of headroom under the ceiling — either way a slow run still ends as `Completed` rather than `Ceiling`); the ceiling is checked inside the step loop only, so it cannot fire during the outro.
9g. **Tutorial super chest** (2026-09-03, LOOTBOX_SPEC.md 7a / 7b). `bankTutorialChest(s)` banks one super chest into `profile.Lootboxes.SuperUnopened` — once per account, guarded by its own `Lootboxes.TutorialChestPaid` flag. Not `Tutorial.Completed` (true for skippers and every grandfathered veteran) and not `Tutorial.BonusPaid` (burned by the first step's instalment, so a run abandoned at step 2 carries it). Ceiling counts. Written here for the same reason the Cash award is — this server holds the session lock, so a failed return teleport cannot eat it — and as `SuperUnopened`, never `Unopened`: the super chest is a fixed outcome outside the pity system, and Bounty's LootboxStateEvent reports it on the next profile load, so no remote is needed. **It moved out of `finishSession` and gained a second caller on 2026-09-07**, so Bounty's completion card can name it. `runOutro` banks it immediately after `payOut` and **before** `stampReturnTeleportData` — a chest granted after the stamp is one the card cannot mention — and `finishSession` still calls it for the Ceiling path, which never reaches an outro. The profile flag makes the second call a no-op rather than a second chest, and `s.paidChest` (set only by the call that actually banked) is what both return paths stamp as `tutorialChest`. A replay finds the flag burned, so the card shows the two currency chips alone. A plain profile write through `DataService.getPlayerData`, so no new connection
9d. **`payOut` runs at the end of the LESSON, not the end of the session** (2026-08-11), and is guarded so `finishSession` calling it again on the way out is a no-op rather than a second 250. Those two moments used to be the same instant; the outro window separates them — 7.4s now, two minutes while free roam existed — and EXIT TRAINING is a legitimate way to leave inside it, so a payout that hung off the session's end would pay nothing to a player who finished every step and pressed the button. It is also why the funnel's completion step and the `TutorialRun` aggregate moved with it: the aggregate measures how long the LESSON took, not how long the player sat on the closing card. The Ceiling path is the one that still pays from `finishSession`, since it never reaches the outro.
9a. **Listed test accounts re-earn the award on every run** (`repaysBonusEveryRun`), and `TEST_ACCOUNT_BONUS_REPLAY` is **on as of 2026-08-17, FOR TESTING — it must go back to `false` before the next publish** (open item 119), because it is a repeat live payout keyed to a hardcoded UserId. It was off from 2026-08-11, retired alongside Bounty's `TEST_ACCOUNTS_ONLY` on the reasoning that the two only worked as a pair: with dispatch on the stock rules a listed account was no longer exempt from `Completed` either, so the only route to a second run was a wiped profile — and a wiped profile has `BonusPaid = false` and is paid by the ordinary rule anyway. **That reasoning stopped holding on two counts.** Bounty's replay exemption became its own switch (`TEST_ACCOUNTS_REPLAY`, on since 2026-08-16), so a listed account replays the lesson with no wipe — and with this switch off every one of those replays ran **unpaid**. That used to cost one reward line on the completion card at the very end; since the award became a per-step instalment it costs *every step's feedback*, because an unpaid step pays nothing and a step that pays nothing fires no feed row. A whole lesson with no reward text reads as a broken feature rather than as a replay, and that is exactly how it was reported on 2026-08-17. What it does while on: `BonusPaid` is once per account, so a replaying account was paid nothing from its second run on — which also blanked the reward line on Bounty's completion card, since that card will not claim a payout that did not happen, and the accounts that replay the lesson are exactly the ones that need to see what a first-timer sees. The check is against the **UserId, server-side, here** — not a flag in TeleportData, which arrives with the joining client and would make this a repeatable 250 Cash farm. `BonusPaid` is written for a test account either way, which is what let the switch be cleared with no profile surgery. The `TEST_ACCOUNTS` table here is a **second copy** of the one in Bounty's TutorialDispatchService, which stays the authority on who is dispatched at all; drift costs only that an account listed there but not here sees no reward line on its replays, which is why it is not worth mirroring a frequently-edited list into a shared module. Real players are untouched: `paid` is 250 on a genuine first completion and 0 on any replay.
9b. **The outro — one card, then home** (`runOutro`, 2026-08-12). This was `runFreeRoam` until 2026-08-12: two minutes of canyon after the lesson, the Training bots still respawning into it, and a second card naming how long it lasted. The run now ends with the live-fire fight, so the window and the card that promised it are both gone. What is left: `payOut`, one centre card, and the return teleport. The card goes out as `{ id = "Outro", key = "Thanks" }` — not a step, nothing gated on it — `delay`ed a `STEP_BEAT` on the client so the completion cue and the fading instruction line get the screen first. **`OUTRO_HOLD` (3.0) is deliberately SHORTER than the card's own life, and that inversion is the design**: the client holds the card 10s (pop 0.3 + its own `OUTRO_HOLD` 9.1 + fade 0.6) while this module waits only `STEP_BEAT + OUTRO_HOLD` = 5.0s before `finishSession` fires `Complete` and teleports, so the thank-you is always still on screen when the player leaves and is **never seen to fade** — the teleport takes it away. The old two-card version had the opposite rule, where the gap had to *cover* the client's animation so the second card landed on an empty screen, so anyone reading across the two versions has to notice the constants swapped roles. `holdOutro` polls `s.running`, so it is not left waiting out a window the player has already left. **5.4 → 3.0 on 2026-09-09** (owner, from a playtest): the card pops at `STEP_BEAT` + 0.3 and the teleport landed 5.1s after that, which is five seconds of a finished lesson holding the player on a thank-you they read in two — and the teleport's own load still to come on top of it. 3.0 leaves ~2.7s of card. It also widens the margin against the client's 9.1 rather than narrowing it, which is the safe direction: that margin only does anything if the teleport stalls, and what it buys is the card never fading to an empty canyon.
10. EXIT TRAINING: listens on the existing `LeaveToLobbyRequest` remote; there is still no second exit path. What it writes depends on **when** it is pressed, and the `postLesson` flag is the whole distinction. During the lesson it is an abandoned run: `Completed = true` so they are never re-dispatched, but **no** Cash and `BonusPaid` stays false, so a future replay can still earn it once. While the outro card is up the run is already finished and already paid, so the button ends the window and nothing else — outcome stays `Completed`, and `returnTeleportElsewhere` hands the return teleport to LeaveToLobbyService, because a second `TeleportAsync` at the same player would only race it over whose payload lands. A player who simply leaves gets no writes in either case — `Attempts` was already counted at dispatch.
10a. **Which is why the return data is stamped** (`stampReturnTeleportData`). LeaveToLobbyService sends whatever TeleportData the player ARRIVED with, so Bounty's completion card — which reads `tutorialComplete` off the join payload — never appeared on the button's path. The stamp writes `tutorialComplete` / `tutorialCash` / `tutorialTokens` / `tutorialChest` onto the very table `RoundController.getReturnTeleportData` is about to hand that service, which is what makes leaving while the outro card is up identical to riding it out: same payout, same card. **All four keys have to appear in TWO places** — here and in `sendHome`'s own `SetTeleportData` — because the stamp is only read on the EXIT TRAINING path. `tutorialTokens` was added to the stamp and missing from the teleport for part of 2026-08-17, which showed the completion card a cash-only reward on every ordinary run. This is the module's one require of [[RoundController]], and it is deliberately **lazy** — inside the function, once, long after both modules are loaded. The two modules already require each other (RoundController pcall-requires this one to run the session), so the graph can only draw one direction of a dependency that genuinely runs both ways; that is a property of the code, not an error to correct.

10b. **The return teleport owns a retry ladder** (`sendHome` / `scheduleReturn`, 2026-08-11). It used to be one `TeleportAsync` and a warn, leaning on `closeServer`'s drain — which does re-teleport whoever is still here every 3s for 12s, but rebuilds a solo player's payload from the arrival data and kept only `characterSelections`, so **every retry of a tutorial return arrived in Bounty with no completion flag and no card**, on a run that had already been paid for. Now: 3 attempts on a growing delay, a fresh `TeleportOptions` each (one handed to `TeleportAsync` must not be reused), and `TeleportInitFailed` handled — the failure shape a clean `TeleportAsync` return cannot report, and the one that reaches nothing at all when nobody listens. `Unauthorized` is terminal; `Flooded` / `IsTeleporting` / `GameFull` take the 6s backoff instead of the fast retry. The listener is gated on this player and `LOBBY_PLACE_ID` so it cannot steal LeaveToLobbyService's or RoundController's teleports, and it is stored **outside** `s.connections`, which `finishSession` disconnects before it teleports. Constants match LeaveToLobbyService and Bounty's dispatch. `closeServer`'s drain is still the last resort, and RoundController's solo branch now carries the three tutorial keys through so that resort promises the player the same thing this ladder does. **One failed attempt buys exactly one retry** (`scheduleReturn(..., forAttempt)` / `s.returnScheduledFor`, 2026-08-15): both the `pcall` path and the `TeleportInitFailed` listener schedule from the same function, and a `TeleportAsync` that throws synchronously *and* raises the signal used to take two of the three attempts on one failure and put two teleport requests in flight for the same player — the give-up line reporting 4 attempts against a maximum of 3 is the tell it happened live.
