# MovementChecker

Server-side movement validation that detects and kicks players using fly, speed, teleport, and jump exploits.

## What it does
1. Tracks per-player state: violation count, last position, last check time, airborne start time, last decrement time
2. Waits 3 seconds after `CharacterAdded` before starting checks — covers initial spawn and round-start teleports
3. Skips all checks when `humanoid.Health <= 0` (dead characters), when the player has `ACImmune` (boolean, set by RoundController's `freezePlayerForVictory` for the duration of the victory freeze and re-granted around the closing lobby teleport — **until 2026-08-04 it was only set in `closeServer`, after the 30 s showcase had already run**, so an anchored, `WalkSpeed = 0` player who happened to be frozen with no ground inside the 25-stud probe accrued flags they could neither move off nor decay, and was kicked ~14 s into the showcase) or `ACImmuneUntil` (tick() timestamp, set by SpawnService teleports — replaced the old 1s boolean window that false-kicked loading clients whose physics replayed a round-start teleport seconds late), when the character has `IsDashing`, or while a time-based grace attribute holds: `FortunaDashGraceUntil` (set by Fortuna's dash flow), `GrappleGraceUntil` (set server-side by Vesper's GrappleHookService — the grapple pull peaks far above the speed ceilings, and that script now extends the window every poll until the caster lands rather than expiring on a fixed timer), or `KnockbackGraceUntil` (set by Bram's BreachChargeService and by BotCombat for a player pinned by a Bram bot — both now hold the window open until the character lands via the shared MovementGrace helper, rather than expiring on a fixed 0.8 s buffer). `ChargePeakSpeed` (42) sat **above** this script's horizontal ceiling while that ceiling was 40, so Bram's charge was only legal while the grace held; combined with decay being unavailable while airborne, a window that lapsed mid-flight reached the kick threshold in 2.5 s. The ceiling is 50 as of 2026-08-01, so the peak now fits under it. Every graced check also sets a `gracedLastCheck` flag consumed by the position-delta check below
4. Every 0.5 seconds runs four checks per player:
   - **Horizontal speed** — flags if `HumanoidRootPart` XZ velocity magnitude exceeds **50** studs/s (weight 1). The ceiling is set above the fastest **legitimate** speed in the game, not merely above walking: Fortuna's passive WalkSpeed 24 × sprint multiplier 1.25 = 30, and Bram's `ChargePeakSpeed` is 42. It was 40 until 2026-08-01 — *below* Bram's charge peak — which meant detection depended entirely on grace coverage being perfect, and any gap was an instant false kick rather than a near miss. That is exactly how a Bram charge whose grace lapsed mid-flight kicked its own caster at 42.5. Skipped when the character has the `UltimateActive` attribute (Fortuna's ult sets `WalkSpeed = 31`, → 38.75 sprinting — fits under the ceiling, but the skip protects against transient physics spikes)
   - **Position delta** — flags if XZ displacement since last check exceeds 70 studs/s effective speed. **Weight is conditional on corroboration**: `DELTA_WEIGHT_CORROBORATED` (3) when the horizontal-speed check fired on the same sample, `DELTA_WEIGHT_UNCORROBORATED` (1) when it did not, in which case the reason string appends `(uncorroborated)`. A jump with no velocity behind it is equally the signature of a CFrame teleport and of a stalled client snapping in, and at a flat weight 3 two of those in one life were a silent kick. Skipped on the **first sample after any grace window closes** (`gracedLastCheck`): the graced check refreshes `lastPosition`, but up to a full `CHECK_INTERVAL` of graced travel happens between then and the next sample, so the delta measures movement the grace was granted for. A Vesper grapple or a Fortuna dash clears 70 studs/s in that gap easily, and at weight 3 it is most of the kick threshold for an ability the server itself authorised. The speed checks still run on that sample
   - **Vertical speed** — flags if upward Y velocity exceeds 65 studs/s, catching jump power hacks (weight 3)
   - **Flight/airborne** — grounded state comes from `findGround`, a footprint probe of 5 rays 25 studs downward: one from the `HumanoidRootPart` centre plus four offset 2 studs along the root's flattened right/look vectors, any hit counting as ground. The single centre ray it replaced false-kicked players standing on ledge lips, gapped plank bridges, and narrow beams, where the root hangs over open air while the character is still legitimately standing. When no ray finds ground: flags "airborne with no ground" if not in a legitimate airborne state (weight 1, after a 2s grace), and separately flags sustained airborne time (weight 2, after 3s). Both timers restart after flagging, so one episode costs one violation per grace window rather than one per 0.5s check. The airborne timer does not accumulate while descending faster than 15 studs/s (`FALLING_VELOCITY`) — a canyon fall is not flight. Both timers reset (no flag) when the character has the `UltimateActive` attribute
5. Listens to `Humanoid.StateChanged`; flags immediately on `Flying` or `PlatformStanding` states (weight 1)
6. Violations decay by 1 every 2 seconds, but only on checks where the player is verifiably grounded (or has `UltimateActive`) — decaying on any non-flagging check would let a hoverer sit below the threshold indefinitely now that the flight checks rate-limit themselves
7. **Every flag carries a context string** built by `describeContext`: the player's `SelectedHunter`, humanoid state, `FloorMaterial`, resolved `WalkSpeed`, the `grounded` probe result, the measured horizontal speed, the round-trip **`ping`** in ms (`Player:GetNetworkPing()`, `pcall`'d — it runs on the kick path), the **vertical velocity and root position** (`vY` / `pos`), and each ability grace attribute rendered **relative to the moment of the flag**. `ping` was added 2026-08-13: a large position delta at `hSpeed` ~0 reads identically for a CFrame teleport and for a client whose packets stopped, and the connection state is the only field that separates them after the fact. A negative grace value (`KnockbackGraceUntil-0.42s`) means the window had already closed when the flag fired — the signature of a grace sized to an ability's duration rather than held until the player lands. `vY` / `pos` were added 2026-08-03 for open item #25: the existing set could not distinguish a player falling off the map from one hovering in place (the airborne checks suppress themselves while descending, so both read identically), and could not say **where** the character ended up. They are per-entry on purpose — they change between samples, and the trajectory across the history is the point

   **`describeMovement` is separate and deliberately not part of the context string.** It returns a flattened [[HunterMovement]]`.Explain` dump (`move{...}`) explaining which modifier set produced the character's `WalkSpeed`, and is appended **once per `warn()`** — to the 3-violation line and to the kick detail header — rather than to every history entry. Added for the same open item, where the context reported `walkSpeed=0.0` with no way to ask what had put it there: [[HunterMovement]] owns `WalkSpeed` outright and its rogue-writer warning is gated to `RunService:IsStudio()`, so a stuck modifier is silent on a live server. Emitting it per-entry instead was measured at **2,190 bytes** for a worst-case kick line against **1,432** for once-per-warn — the modifier set does not meaningfully change across flags 0.5 s apart, so six copies bought nothing and spent the headroom `FLAG_HISTORY_LIMIT` exists to protect. A truncated line would lose the field it was added for. The call is `pcall`'d because it runs on the kick path — a throw in the logger would take the kick record with it — and its newlines are flattened to `; ` so the warn stays one dashboard row Ground state is resolved before the speed checks rather than alongside the flight check so the context is available to all of them; the raycast count is unchanged
8. `print()` logs every flag with its context for Studio visibility, but **only `warn()` reaches the Creator Hub error dashboard** — it captures warnings and errors, never prints. That is why per-flag detail is buffered rather than warned: promoting every weight-1 blip would flood the page. `warn()` fires when violations reach 3 (carrying the context), and **twice** at kick:
   - a **stable** line, `"[AntiCheat] <name> kicked for movement violations."`, deliberately left in its original form so the dashboard keeps aggregating it into one countable row per player. Folding the detail into this line made every kick a unique row and destroyed the tally
   - a **detail** line carrying the violation total, the triggering reason and the whole flag history — up to `FLAG_HISTORY_LIMIT` entries, each stamped with seconds since the character spawned, the weight, the running total, the reason and the context. Expected to be one row per incident
   
   `FLAG_HISTORY_LIMIT` is **6**, which is the entire run: the threshold is 5 and the lightest flag is weight 1, so at most five flags can precede a kick. A worst-case detail line measures ~1,120 characters; the earlier limit of 12 reached ~2.5 KB and risked dashboard truncation
9. Kicks player with `"Movement anomaly detected."` after 5 accumulated violations — the only script in Redwater that kicks. A sustained flyer reaches the threshold in ~11s (~7.5s if their humanoid state is spoofed to a grounded one); tune via `AIRBORNE_WEIGHT` / `MAX_AIRBORNE_TIME`
