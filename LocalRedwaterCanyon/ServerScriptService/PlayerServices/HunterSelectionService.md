# HunterSelectionService

Tracks which hunter (Dust, Fortuna, Vesper, or Bram) each player is playing and is the shared gate every hunter-specific server system checks before acting.

## What it does
1. Stores each player's hunter selection (`category`, `subfolder`, `modelName`) in memory by UserId. `HUNTER_ASSET_NAMES` maps the hunter key to the Studio asset folder under `ReplicatedStorage.Hunters.<Hunter>.Character` — an identity map for all four hunters, since each character folder matches its manifest `HunterName` (Bram's folder was renamed from the old codename `Brakk` to `Bram`). `buildDefaultSelection` derives `category`/`subfolder`/`modelName` from the resolved asset name, and `category` doubles as the `SelectedHunter` gate value, so it MUST equal the manifest `HunterName`
2. `DEFAULT_HUNTER` is the last-resort fallback and is pinned to **`"Dust"`** — the one hunter every account owns, so it is the only value that is always safe for a player whose loadout can't be resolved. It is deliberately **not** a testing knob any more: it used to be, and a value left on `"Vesper"` meant every direct joiner (see 4) spawned as a hunter they might not even own
3. `STUDIO_TEST_HUNTER` is the replacement testing knob — set it to `"Dust"` / `"Fortuna"` / `"Vesper"` / `"Bram"` to force every player to spawn as that hunter, `nil` for normal resolution. Gated on `RunService:IsStudio()`, so a value accidentally left in it can never reach a live server. **It still has to be put back to `nil`, though, because this file is match-tier mirrored:** on 2026-08-17 it was found holding `"Vesper"` in Redwater and `"Dust"` in Frostbite, which was the only drift in the whole match tier and would have stopped `/preflight` at its first gate. A knob that cannot reach production can still fail the mirror check — reset it when the test is over, in both places
4. `InitPlayer(player)` resolves the loadout on join, from one of two sources:
   - **Teleport data** (arrived from the Bounty lobby) — reads either an explicit `characterSelections[userId]` table or a flat `selectedHero`/`hero`/`hunter`/`character` field (kept as-is; this is Bounty's external teleport-payload contract, not renamed), normalized to "Dust"/"Fortuna"/"Vesper"/"Bram" via `normalizeHunterName`, plus `weaponSkinSelections`. **The `characterSelections` entry is re-resolved through `resolveSelection` (6), never trusted as sent** — Bounty stores skins under `ReplicatedStorage.Characters.<Hunter>.Skin` (singular) and stamps that folder name into the payload, while the match places use `Hunters.<Hunter>.Character.Skins` (plural), so the `subfolder` field does not survive the teleport. `isValidSelection` only type-checks the three strings, so before 2026-08-24 "Skin" passed straight through and every lobby arrival wearing a skin spawned in their default look. Model names are identical across places, so the model name is the only field carried over. Fully synchronous — nothing ever waits
   - **The persisted profile** (direct joiner) — a player who joins a Redwater server straight from the Roblox friends list never passes through Bounty, so there is no teleport payload at all. `DEFAULT_SELECTION` is seeded immediately so nothing can read a nil selection, then an async task waits up to `PROFILE_WAIT_SECONDS` (8s) for ProfileService and applies `EquippedCharacter` + `EquippedSkins[hunter]` from the shared profile via [[DataService]], plus `RefreshWeaponSkinsFromProfile` for the guns — the only record of what that player had equipped in the lobby. Ownership is re-checked against `OwnedCharacters` / `OwnedWeaponSkins` rather than trusted, because Bounty's normalization only runs in the lobby and a hunter can stop being owned between equip and join
4a. **The direct joiner's seed is held in memory and never published to attributes** (`deferPublish[userId]`, armed in `InitPlayer` *before* the first `Set*` call and cleared by `publishAttributes` when the resolve settles). `applyAttributes` / `applyWeaponSkinAttributes` early-return while it is armed, so `SetSelection` and `SetWeaponSkinSelections` still update the in-memory tables — server reads (`GetSelection` / `IsHunter`, and therefore `HunterServerRuntime`'s gate and every `*WorldVisualServer`) are unaffected — but nothing reaches the client until the loadout is final. **Attributes are the client's boot signal**: HunterGate unblocks the instant `SelectedHunter` appears and a hunter client then samples `EquippedWeaponSkin_<Hunter>` **once** to build its first-person viewmodel. Publishing the placeholder let clients boot on it seconds before the profile resolved, and nothing re-read it afterwards — a direct joiner whose profile hunter matched the seed held the **default gun in first person for the whole session** while everyone else saw their real skin (the server-side world model self-heals off its own `EquippedWeaponSkin_<Hunter>` changed listener in HunterWorldModel). The arming has to precede `SetWeaponSkinSelections`, which publishes immediately; `studioOverrideSelection` is hoisted above it so a Studio override still counts as a known loadout
4b. `publishAttributes` flushes hunter + all four gun skins in one shot, and runs **before** `resolving[userId]` is cleared — so the character SkinService is about to build and every client waiting on `SelectedHunter` both see final values, first time, with nothing to correct. On the profile-timeout path it lands at `PROFILE_WAIT_SECONDS` (8s), inside the 10s HunterGate window, so a profile that never arrives degrades to the default loadout rather than to a client that never boots — **`PROFILE_WAIT_SECONDS` must stay comfortably under HunterGate's timeout**. Known narrow consequence: a direct joiner who lands *mid-round* gets their RoundController `MatchStart` telemetry logged on PlayerAdded, inside the deferral window, so its hunter field reads `Unknown` instead of the seed's previous (and often wrong) `Dust` guess
4c. **A tutorial server always spawns Dust, and that override outranks `STUDIO_TEST_HUNTER`** (added 2026-08-11). `isTutorialServer()` is applied in `InitPlayer` immediately *after* `studioOverrideSelection`, so it wins: a Studio force-mode run with `STUDIO_TEST_HUNTER = "Vesper"` silently spawned Vesper into the lesson, and the tutorial is not what that knob is for (it still governs every normal Studio round). The lesson is authored entirely around Dust — every ability gate rides Dust's combat remotes (`FireBullet` / `DashRequest` / `Skill2Request` / `HighNoonShootRequest`) — so a non-Dust player cannot pass a single ability step and nothing is logged to say why. **This is a backstop, not the primary path:** Bounty's TutorialDispatchService already puts Dust in the TeleportData, but that is the only thing carrying it, and a rejoin into the reserved tutorial server (or any Studio force-mode run, which has no teleport at all) arrives without it and would otherwise resolve the player's *profile* hunter. Resolving to a valid selection here also keeps a tutorial player off the direct-joiner path in 4, so their spawn never waits on a profile read. `State` and `Config` are required **lazily inside the function, via `pcall`** — the same shape [[DataService]] uses to read round state — because this module is required from Main well before RoundSystem is touched. The **unresolved** tri-state is the case that matters: Main starts `HunterSelectionService` before MatchDirectoryService, so `State.tutorialMode` is still `nil` when `InitPlayer` runs for a player already present at boot, which is precisely the Studio force-mode case; it therefore falls back to [[Config]]`.TUTORIAL_FORCE_MODE` honoured on exactly MatchDirectoryService's terms (Studio or non-live only, read from [[GameEnvironment]]) so the two can never disagree
4a. `RefreshWeaponSkinsFromProfile(player)` re-publishes **every** hunter's equipped gun skin from the shared profile's `EquippedWeaponSkins` (ownership-checked against `OwnedWeaponSkins`). SkinService`.loadCharacter` calls it at the top of **every** spawn, not just on join, so no spawn depends on the teleport snapshot being complete: a friends-list / follow join carries no `TeleportData` at all, and a mid-match swap needs the swapped-**to** hunter's gun, which the join snapshot may never have covered. Deliberately a no-op while the profile is still loading, so it can never downgrade a good snapshot to defaults on a lobby arrival's first spawn. The profile is session-locked to this server while the player is here, so this corrects a missing/partial snapshot rather than tracking live edits
4b. `DEFAULT_WEAPON_SKINS` lists **all four** hunters (`DefaultRevolver`/`DefaultCard`/`DefaultSniper`/`Grudgekeeper`, mirroring Bounty's profile template). `applyWeaponSkinAttributes` iterates that table, so a hunter missing from it would never get an `EquippedWeaponSkin_<Hunter>` attribute at all and its client would silently fall back to the default gun — which is exactly what used to happen to Vesper and Bram
5. `WaitForSelection(player, timeout)` — the spawn gate. Blocks **only** while a direct joiner's profile resolve is still in flight (`resolving[userId]`); it is a no-op both for lobby arrivals and for a player whose `InitPlayer` has not run yet, so it can never stall a spawn path that reaches `loadCharacter` first. SkinService`.loadCharacter` calls it at the very top, which is what stops a direct joiner's first character being built off the seeded default
6. `resolveSelection(hunterName, skinName)` — turns a hunter plus an equipped skin NAME into the `{category, subfolder, modelName}` selection SkinService expects: `"Default"` (or a skin that no longer resolves) → `Hunters.<Hunter>.Character.Default`, any other name → `Hunters.<Hunter>.Character.Skins.<name>`. Exported and shared with HunterSwitchService, which delegates to it, so the direct-joiner first spawn and the mid-match swap can never disagree about how a skin name maps to a model
7. `SetSelection(player, selection)` stores the selection and mirrors it onto player Attributes: `SelectedHunter`, `SelectedHunterCategory`, `SelectedHunterSubfolder`, `SelectedHunterModelName`
8. `GetSelection()` / `GetHunter()` / `IsHunter(player, hunterName)` are the read API other server modules use to gate hunter-specific behavior (e.g. revolver/dash-dust logic only applies `IsHunter(player, "Dust")`)
8a. `GetWeaponSkin(player, hunterName)` reads one hunter's equipped gun skin; `GetWeaponSkins(player)` returns a **copy** of all four at once, which is what RoundController stamps into the end-of-round map-move `TeleportData` as `weaponSkinSelections` — the field `readWeaponSkinSelections` reads back on the other side. Copied so a caller cannot write through into the live table, and deliberately the live table rather than the join-time snapshot: `RefreshWeaponSkinsFromProfile` rewrites it from the profile on every spawn, so it is already corrected even on a server whose own arrival payload was stale, partial or absent
9. `Start()` wires `PlayerAdded`/`PlayerRemoving` to call `InitPlayer`/clear stored state, and initializes any players already in-game

## Dependencies
- **Requires:** [[DataService]], [[State]], [[Config]], [[GameEnvironment]] (the last three lazily inside `isTutorialServer`, via `pcall`)
- **Required by:** Main, HunterServerRuntime (consumes `IsHunter` for both hunters' hunter gate), DashDustVFXServer, RevolverWorldModelServer, SkinService, CardsWorldVisualServer, HunterSwitchService, BountyService (`GetSelection` per bounty-card portrait), RoundController (`GetWeaponSkins` for the map-move teleport payload). (RevolverModule, HighNoonModule, CardsServer used to require this directly; after Phase 2 they go through the runtime's `IsHunter`.)
