# DataService

Manages player data persistence using ProfileService and tracks in-memory session statistics.

## What it does
1. Creates leaderstats (Cash, Level) and PlayerStats (XP) folders on each player
2. Loads player profiles from DataStore via ProfileService with session locking
3. Kicks players whose profile fails to load or whose session is stolen
4. Tracks per-match stats in memory (kills, deaths, assists, time alive/dead) in `sessionTracker`, keyed by UserId. `incrementSessionStat` is the only writer, and it mirrors each value onto a `Session<Stat>` player attribute so clients can read the tallies without a round trip
4a. **`resetSessionStats(player)` / `resetAllSessionStats()` zero those tallies at the start of every round** (added 2026-08-07), rewriting the `SessionKills` / `SessionDeaths` / `SessionAssists` attributes as well as the table — the round leaderboard of StatMenuGui reads the attributes directly, so the table alone is not enough. Called from RoundController's round-start reset block (plain text: this module does not name it). **This is per-match state despite the "session" name**, and the distinction only started mattering when Redwater servers began looping rounds instead of closing after one match — before that a "session" was a match, nothing reset it, and the TAB / Stats menu quietly showed every round the server had played added together. **`JoinTime` is deliberately excluded**: `onPlayerRemoving` banks `TotalPlaytime` off it, so resetting it per round would discard the playtime earned in every earlier round. `IsAlive` is excluded too — the `setupTimeTracking` heartbeat owns it. **Zeroing `TimeAlive` has one non-obvious consumer**, ProgressionService's alive-time reward, which compares it against a high-water mark that must be cleared in the same beat or the reward stops paying for the rest of the server's life
5. Provides API for other modules to read/write player data and session stats
6. Updates TotalPlaytime on player disconnect before releasing profile
7. Syncs cached data to leaderstats ValueObjects via updateLeaderstats()
8. Profile template includes `RedeemedCodes` (table of code -> true), backfilled onto existing profiles via `:Reconcile()`, used by CodeRedemptionService to block re-redeeming the same code
9. Profile template includes `MouseSensitivity` (default 0.45), read/written by MouseSensitivityService to persist the player's sensitivity slider across sessions
10. Profile template includes a `Settings` sub-table (crosshair color index, crosshair size, show-ping/fps, auto-fire enabled — default true, added 2026-08-07 — shadows, master/SFX/music/hit-sound volumes) backfilled via `:Reconcile()`, read/written by PlayerSettingsService to persist the rest of the settings-panel controls
11. Profile template includes the ranked fields, all backfilled via `:Reconcile()` and written by RankedService at round end: `RankPoints` (default 0, the running skill/performance score), `RankSeason` (**default 1** — which season that total belongs to), and `LastSeasonRankPoints` (default 0, the previous season's total, kept purely as a safety net so that zeroing a profile stays recoverable; nothing reads it today). The `RankSeason` default **must stay 1**: `:Reconcile()` backfills the template value into every existing profile, so a 0 there would read as "season 0", mismatch the live season the moment the place is published, and wipe everyone's RP at publish time instead of at the season boundary. Not mirrored into Bounty's template — that place has never carried `RankPoints` and neither reads nor writes it, and since `:Reconcile()` only ADDS keys, a profile created lobby-first simply picks the fields up on its first Redwater session
12. Profile template includes battle-pass fields backfilled via `:Reconcile()`: `Tokens` (wallet, shared with Bounty), `BattlePass` (seasonId/xp/level/ownsFullPass/claimed/quests — season-scoped, managed by BattlePassService), `Cosmetics` (persistent inventory), and `Boosts` (`{ Inventory = {[boostId]=count}, Active = {xp=…, cash=…} }` — boost consumables + the currently-running boost per kind; catalog in BoostConfig, activated/ticked by BoostService)
13. Profile template includes `EquippedTitles` (equipped cosmetic title id per hunter — `{ Dust, Vesper, Bram, Fortuna }`, `""` = none) and `OwnedTitles` (`{[titleId]=true}`, purchased titles), both backfilled via `:Reconcile()`. `OwnedTitles` is mirrored here only to keep the shared `PlayerData_v2` template in sync — Redwater never reads it, because Bounty's CollectionService is the only writer of `EquippedTitles` and so nothing unowned can arrive here. **Bounty-owned** (CollectionService writes it; the lobby dummy shows it) but **read here** by TitleDisplayService, which resolves the match hunter's equipped id to a label (via TitlesConfig, which that service requires -- not this one) and publishes it as the replicated `EquippedTitle` player attribute for the Redwater title surfaces (match summary, overhead health bar, kill cam)
13a. Profile template includes `EquippedEmote` (single account-wide emote id, defaults to `electro_swing`; legacy `""` migrated to the default on join by Bounty's CollectionService) + `OwnedEmotes` (`{[emoteId]=true}`), backfilled via `:Reconcile()`. **Equipped in Bounty** (CollectionService) but **read here** by RoundController to play the player's emote on their end-of-match showcase dummy (catalog in EmoteConfig)
13b. Profile template mirrors the hunter-loadout fields Bounty owns, all backfilled via `:Reconcile()`: `OwnedCharacters` / `EquippedCharacter` / `EquippedSkin` / `EquippedSkins` (hunter + character skin) and `OwnedWeaponSkins` / `EquippedWeaponSkins` (gun skins). **Written only in Bounty** (on purchase and on equip); mirrored here to keep the shared `PlayerData_v2` template in sync. Read here by HunterSwitchService (ownership gate + the skin a mid-match swap spawns) and by HunterSelectionService, which needs them for a player who joined this server **directly** from the Roblox friends list — that player never passed through Bounty, so no TeleportData carries a selection and the profile is the only record of what they had equipped
14. Store name is `PlayerData_` .. `DATA_VERSION` (currently "v2"); **bumping `DATA_VERSION` wipes ALL player data universe-wide** — the release-reset lever. Must match Bounty's DataService
15. Profile template includes `OnboardingFunnel` (`{ [tostring(step)] = true }`, lazily created if missing), the persisted onboarding-funnel de-dup set shared with Bounty. `tryLogFunnelStep(player, step, name)` is the **onboarding funnel chokepoint**: it fires `AnalyticsService:LogOnboardingFunnelStepEvent` only the first time a player reaches each step (recording it in `OnboardingFunnel`), so a step never re-fires across rejoins/teleports/places. Redwater's steps 4-7 (RoundController step 4, RoundStatsService steps 5-7) route through this — previously step 5 "Shot the Gun" fired on every shot and tripped AnalyticsService's per-server event cap
15a. Profile template carries `Settings.AbilityDescriptions` (`"On"` / `"Default"` / `"Off"`, default `"Default"`) — how Redwater's hunter ability tags behave, read by HunterAbilityIntroClient and written from either place's settings panel via PlayerSettingsService (plain text — this module names neither in code). Present in Bounty's template too (same `PlayerData_v2` key) so both templates stay aligned. This **replaced** a `SeenHunterIntro` set that recorded which hunters a player had already had explained: a setting the player can see and change is a better answer than invisible state. `:Reconcile()` only ever ADDS keys, so profiles written before the change keep a dead `SeenHunterIntro` table that nothing reads
16. Profile template includes the daily play-streak fields backfilled via `:Reconcile()`: `DailyStreak`, `DailyLastPlayDay`, `DailyPending` (unclaimed reward queue), `DailyPermaBoost` — advanced by DailyRewardService on round finish; `DailyPermaBoost` (the passive +10%) is read by BoostService. Shared with Bounty (same `PlayerData_v2` key), where the rewards are claimed
17. Profile template includes the onboarding `Tutorial` sub-table (`Completed`, `Skipped`, `BonusPaid`, `Attempts`, `StartedAt`, `CompletedAt`, `Screened`, `JourneyId`, `JourneyStep`), backfilled via `:Reconcile()` and shared with Bounty. `onPlayerAdded` applies the **grandfather rule** right after Reconcile: a not-Completed profile with `Attempts == 0` and any veteran signal (`MatchesPlayed`, `TotalPlaytime`, `Level > 1`, or `XP`) is silently marked Completed so the live player base is never dispatched into a tutorial; profiles with `Attempts > 0` are already in the tutorial flow and are governed by the dispatch's `Attempts < 2` rule instead
17a. **The grandfather rule is a one-time migration decision, not a standing rule** (`Screened`, 2026-08-11). It used to re-run on every profile load, so the four veteran signals kept growing under a player who simply had not been dispatched yet, reclassifying them as a veteran the moment they played anything. The case that forced it: a brand-new player who arrives by **following a friend** is deliberately not dispatched in Bounty and plays the match they were invited to — which happens **here**, so this place's copy is the one that seals their screen, and it must agree with Bounty's exactly. `Screened` is stamped on the first load a profile ever gets, whichever way the screen decides, and the block is skipped entirely afterwards. The `Attempts == 0` guard stays alongside it: a profile mid-lesson when this shipped has `Screened` false and playtime from the lesson itself
17b. **The screen's un-grandfathered branch mints `Tutorial.JourneyId`** (2026-08-15), a GUID that is the session id for Telemetry's `NewPlayer` journey funnel, alongside `JourneyStep = 0`. That branch is the only moment in the codebase that knows an account is genuinely new, and Telemetry treats an empty id as "not in the cohort" and drops every step — which is what keeps the entire existing player base out of a funnel they could never finish. It is deliberately **not** a `tryLogFunnelStep`-style call: the data layer carries no dependency on analytics, so this writes a profile field and Telemetry reads it. Present in **this** copy for exactly the reason the screen itself is, per 17a — a follow-joiner's first load happens here, and minting in Bounty alone left that player permanently invisible to the funnel while still being dispatched into the lesson on their next ordinary join. One-way, like `Screened`: an account gets at most one journey
18. **Tutorial guard on the onboarding funnel:** `tryLogFunnelStep` early-returns while `State.tutorialMode` (pcall-required from `RoundSystem.State`) — the funnel's steps fire at most once per player EVER, so a tutorial consuming them would silently stop every player's first real match from registering (design section 7)

17. Profile template includes the analytics counters backfilled via `:Reconcile()`, all written by RoundController and read by Telemetry: `MatchesPlayed` (matches STARTED, not finished — a player who quits mid-match still consumed an attempt, and counting only finishers would compute completion rate against a denominator that drops the very people it measures), `LastMatchAt` + `SittingMatchIndex` (the same-sitting replay counter — a Redwater server hosts exactly one match then closes, and the lobby a player returns to may be a different server instance, so "did they immediately play again" can be held neither in-server nor in memory; RoundController compares `os.time()` against `LastMatchAt` at round start and a gap under 30 minutes continues the sitting), and `LastPlatform` (written by Telemetry `setPlatform`, persisted so a server can attribute a player's events before their client has booted — notably a friends-list joiner who lands straight here without passing through the lobby). Shared with Bounty (same `PlayerData_v2` key); the template block is byte-identical across both places
