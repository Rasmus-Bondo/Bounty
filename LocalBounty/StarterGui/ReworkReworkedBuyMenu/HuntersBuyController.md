# HuntersBuyController

> **SUPERSEDED 2026-08-23.** The Trading Post is now `StarterGui.Shop` (ShopController + Shop.Modules.*). This ScreenGui is kept `Enabled = false` for one release as the rollback, and its LocalScripts are `Disabled = true` (they played purchase SFX and pulled state even while hidden). Nothing enables it; MenuHandlerScript, CurrencyHudController, BattlePassClient, ReworkedUIPlay and the Collection Shop module all point at `Shop` now. The text below describes the retired script as it still exists in Studio.

Controls the Hunters tab of the reworked buy menu — hunter/skin browsing, equip, and the Fortuna cinematic.

## What it does
1. Populates the hunters scrolling list (Dust, Fortuna, Vesper, Bram) with title, class, description, and pricing from hardcoded `HUNTERS` table (cross-references [[StoreConfig]] for ProductId/CashPrice). Bram, Vesper, and Dust are free; Fortuna is the only paid hunter
   - **Ownership routing:** selecting a hunter you do NOT own opens her **skin page**, the same as an owned hunter — her looks are worth browsing before the purchase. Ownership (`ownsHunter()`: `StoreConfig.FreeCharacters` + the `Owns<Hunter>` attribute) no longer decides *which page* you land on, only what each tile offers on the right. `applySelectedSkinPanel` is the single place that decides, so the ownership listeners can redraw the page in place:
     - **The Default tile shows the hunter BUY panel** (Robux + Cash via `refreshPurchaseState`) rather than a skin card, because a locked hunter's default look *is* the hunter — `showsHunterBuyPanel` is the test. This is load-bearing, not cosmetic: the BUY panel used to be the only thing an unowned hunter could open, so sending her to the skin page without this would have deleted the sole route to buying Fortuna.
     - **Every other tile shows the skin card priced but not for sale** — **UNLOCK &lt;HUNTER&gt;** in place of BUY NOW, which jumps the page back to the Default tile. This is not decoration: [[DataService]] refuses both `PurchaseSkinWithTokensEvent` and `EquipSkinEvent` for a hunter the player does not own (`isCharacterOwnedData`), so a BUY NOW here would fire a remote the server drops in silence. The pass-skin branch stays **ahead** of this check, because buying Fortuna would *not* grant SummerFortuna — VIEW IN BOUNTY PASS is the only true instruction on that card.
     - **`isSkinOwned` returns false for every skin of an unowned hunter, `"Default"` included.** That is what actually prevents the false EQUIP the old blanket gate was written to avoid, and it is why the routing above is safe to relax.
     - Only a hunter with **no `SKINS` entry at all** still lands straight on the BUY panel — there is nothing to browse. Since 2026-08-14 no hunter is in that state (Bram was the last, until DirewolfBram gave him a SKINS entry), but the branch stays for the next skinless hunter. Buying the hunter while her page is open redraws it in place (`refreshHunterOwnershipState` → `refreshSelectedSkinPanel`) instead of stranding the player on a stale BUY. **`showingSkins` no longer implies `buyHunterSkinFrame` is the visible panel** — `revealHuntersPage` animates whichever frame is actually up.
1b. **Battle-pass skins are listed but never sold.** `SummerDust`, `SummerVesper`, `SummerFortuna` (hunter skins) and `HellFire` (Dust's gun skin) are all Bounty Pass exclusives. They now appear in the shop with **no price at all** — `BOUNTY PASS` in the price slot and a **VIEW IN BOUNTY PASS** button that fires `MenuNavigateRequested("4BattlePassFrame")` on [[MenuHandlerScript]], the same hand-off the Collection menu's locked tiles use. This follows the existing `GroupUnlock` (Wraith) precedent for a "not for sale, button routes elsewhere" skin; HellFire previously carried `Locked = true` and rendered a dead **LOCKED** label with no way forward. **Which skins those are is asked of [[BattlePassConfig]]** (`isExclusiveSkin`) rather than flagged by hand on the `SKINS` entries — the pass builds that set from its own reward tracks, so a skin moving on or off the pass cannot leave the shop advertising the wrong thing, and [[DataService]] already refuses a shop purchase of one, so a stale hand-kept flag would offer a buy the server rejects
1c. **DEEP LINKS from the Collection menu land on the ITEM, not just the tab.** That menu's Shop module publishes `RequestedHunter` / `RequestedHunterSkin` / `RequestedWeaponHunter` / `RequestedWeaponSkin` on the buy-menu ScreenGui (attributes, not a code link), and `consumeItemRequest` walks them — so `UNLOCK FORTUNA` over there now opens **Fortuna's own page** rather than the grid she is somewhere in. **Every hop goes through `entryActivators[slot]`, the same body a real tile click runs.** That table is the reason the click body no longer lives only inside its own connection: an `RBXScriptSignal` cannot be fired from a script, and a second copy of the drill-in logic is how the two paths would drift apart. It is assigned inside the existing `HunterShopBound` guard, so it is written once per slot even though `configureEntry` re-runs on every drill-in, and it captures only `entry` — a slot later reconfigured as a different hunter or skin still activates correctly.
   - **Both grids are two levels deep, and the second level does not exist until the first hop has run.** Drilling into a hunter *rebuilds the shared entry slots* as her skins (or his guns), so the skin lookup can only resolve after the hunter lookup has fired. The hops are walked in order for that reason, not for tidiness.
   - ⚠ **ONE EDGE IS NOT ENOUGH, and betting on one is how the first version of this failed.** The symptom was landing on the hunter **list** with the equipped hunter on the stand — the plain `showHunterList` result — with the right tab and the wrong page. Any single hook bets on one moment being both *after* the grid is built and *before* anything rebuilds it, and **neither half holds**: `TradingPostController.setSelectedTab` writes `huntersBuyFrame`'s `TradingPostMode` attribute and its `Visible` flag as **two separate statements**, and each one rebuilds the list — so a drill-in performed off the first was wiped by the second, and the request had already been cleared, so nothing redid it.
   - **So `scheduleItemRequest` retries for `ITEM_REQUEST_ATTEMPT_FRAMES` (45) and stops the instant the drill-in VERIFIES.** `tryConsumeItemRequest` returns true only when `selectedHunter` / `selectedWeaponHunter` actually equals the target — activating a slot is *not* proof the drill-in survived — and the request is cleared only then. That makes a later rebuild self-healing instead of fatal, and removes any dependence on which hook fires first. Five edges feed it: `TradingPostMode`, `huntersBuyFrame.Visible`, `screenGui.Enabled`, and `GetAttributeChangedSignal` on `RequestedHunter` / `RequestedWeaponHunter` (the last two are the only edge that fires when the request lands while the shop is **already** open). The `Enabled` edge is needed because **`huntersBuyFrame.Visible` is never reset on close** (see the ⚠ under 3), so an open landing back on HUNTERS can fire no `Visible` change at all. Closing the shop clears the request, so an abandoned navigation cannot steer a later visit.
   - ⚠ **ONLY FRAMES WITH `screenGui.Enabled` TRUE COUNT AGAINST THE 45-FRAME BUDGET.** Getting this wrong broke the *second* attempt at the fix, and its log line named the cause outright — `guiEnabled=false`. The request is written **before** the navigation that opens the shop, so the `RequestedHunter` attribute hook starts the retry loop while the player is still in the Collection menu, and the camera flight between the two menus is far longer than 45 frames. The whole allowance was spent before the shop existed, and the loop then *cleared* a request that had never had a chance. There is also a wall-clock cap (`ITEM_REQUEST_WAIT_SECONDS = 25`) so a navigation the player abandoned mid-flight cannot leave the loop spinning forever.
   - **`huntersBuyFrame.Visible` cannot stand in for "the shop is up"** — it is never reset on close (the ⚠ under 3), so it reads `true` from the first visit onward. That is exactly why the failing log showed `frameVisible=true guiEnabled=false`. `screenGui.Enabled` is the only flag that means open.
   - **Giving up quietly vs. warning is a real distinction.** Falling out with the shop closed means the player simply never arrived — the request drops silently. The `warn` fires only when the shop **was** open and 45 of its frames still could not resolve, which is the genuine anomaly.
   - **Giving up `warn`s with the full picture** — what was wanted, the current mode, frame/GUI visibility, `selectedHunter`, and every slot's `EntryMode`/`HunterName`/`SkinName`/`WeaponHunterName`/`WeaponSkinName` plus whether it has an activator. A player who asked for one card and got a list is a real anomaly, and this is what makes a single reproduction name the failing stage instead of narrowing it.
   - An **unowned hunter arrives with no skin named** — her own page is the destination and the buy panel is on it. A locked skin on a hunter the player already owns names the skin too.
2. Handles skin selection panel (hunter skins per hunter — every hunter has a `SKINS` list, Bram's newest with DirewolfBram; weapon skins for Dust, Fortuna, Vesper, Bram) with token prices. The 2026-08-14 winter drop added BluefrostDust (300), FrostveilVesper (600), DirewolfBram (600) and Vesper's Frostpiercer gun skin (400) — prices live here for display and in DataService's `TOKEN_SKIN_PRICES` / `TOKEN_WEAPON_SKIN_PRICES` for authorization. The 2026-08-21 gun-skin drop added four more at 600 each — Dust's `Icefang`, Fortuna's `FrozenHand` and Bram's `FrostbiteGrudgekeeper` are the ice set; Dust's `BetaRevolver` is a cardboard prop revolver and ships alongside them. **Append them, never prepend:** `isWeaponSkinOwned` treats `WEAPON_SKINS[hunter][1].Name` as the hunter's free gun, so index 1 has to stay the default.
   - **The Token price is a COIN + number, not the word `TOKENS`** — `BuyHunterSkinFrame.PriceLabel` gained a `CurrencyLabel` ImageLabel child (`rbxassetid://138855504574427`, the Token half of the same set the Cash pill uses). It is a **child of the price label** so the two travel as one, and every write now goes through `setSkinPriceAmount` / `setSkinPriceWord` rather than assigning `.Text` directly. **The pair exists because that one label serves four states that are not prices** — `OWNED`, `GROUP PERK`, `BOUNTY PASS`, `LOCKED` — and each must hide the coin and put the label back on the panel's TRUE centre — which is the authored position **minus** the coin's allowance, not the authored position itself (see the next bullet). Both writers use them: `setSkinPurchaseState` (hunter skins) and `refreshWeaponSkinPurchaseState` (gun skins), so neither can leave the other's coin on screen.
   - **A price that gains a digit moves the COIN only — the label does not move at all.** The figure is centre-aligned in a full-width label, so its left edge, where the coin sits, travels with its width; sliding the label right by half of (coin + gap) is what re-centres the *pair*, by an amount **independent of the price's width**. ⚠️ **That allowance is already in the AUTHORED x, so the code must not add it again** — measured, the authored `0.5562761` is the panel's centre plus a computed shift of `0.0562690`, and the authored coin x is this file's own formula for a three-digit price to six decimals. It is the same idiom as the hunter's Cash pill below, whose authored x is nudged for its coin and never touched in code.
   - ⚠️ **It DID add it again, until 2026-08-05.** `setSkinPriceAmount` captured the authored position and added the shift on top, landing every skin price **10.2px right of centre in a 180.8px panel**; `setSkinPriceWord` restored that same authored position, so `OWNED` / `GROUP PERK` / `BOUNTY PASS` / `LOCKED` each sat on an allowance for a coin that was hidden. Both states now derive from one captured pair: an amount takes the authored position **unchanged** (so Studio's preview is exactly what ships), a word takes `authored − shift`. The earlier "verified dead-centre" note measured the arithmetic in isolation and never caught it, because the authored preview it was checked against is the one state the runtime never rendered. Re-measured after the fix: `+0.25px` at "500", `+0.13px` at "1000" and "250", and `0.00px` on all four word states.
   - **The width comes from the digit count, never from `TextBounds`** — TextBounds over-reports under TextScaled on a real phone, which neither Studio nor the device simulator shows. But the 6px advance against the label's authored 164.6px is an **average, not a tabular one**: measured per 100 of text size, Oswald's `0` is 35 and its `1` is 27. That is worth a quarter-pixel on the prices actually in use and would matter on a price of all `1`s. `AccessoryBuyPanel` measures the string with `TextService` instead — exact, and it handles a thousands separator; this panel stays on the digit count because its prices carry neither.
   - The grid tiles carry no price text at all, so this panel is the shop's only skin-price surface — nothing else needed the same swap.
   - **The shared `PurchaseFrameTokens` button is a two-row template** — `PriceLabel` on top (the action: `BUY NOW` / `EQUIP` / `EQUIPPED` / `JOIN GROUP TO UNLOCK` / `VIEW IN BOUNTY PASS` / `UNLOCK <HUNTER>` / `LOCKED`; `TextWrapped` is **false** so the longest of these scales down rather than breaking to two lines in a 22px pill) over a static `InfoLabel` subtitle (`BUY SKIN`). **The subtitle and the action label's vertical position are one decision, not two,** and `setSkinActionRows(subtitleVisible)` writes both: a priced BUY NOW keeps the subtitle and the authored y `0.346` top-row slot, and **every** other state hides the subtitle and drops the surviving single line to y `0.5`, the pill's true centre. Before this it hid the subtitle and left the lone line in the top row, reading as floating high. **Every branch of `setSkinPurchaseState` (hunter skins) and `refreshWeaponSkinPurchaseState` (gun skins) calls it** — that is what stops the two panels leaving a stale offset on each other's selection, and it is why a new branch cannot centre one without the other. The authored position is captured at load (`skinActionPriceOriginalPosition`), and only Y is overwritten — the sibling Robux button's label carries an X nudge to clear the icon in its price string. The pill drawn behind the text is `SelectedBackgroundGlow`, which fills the frame 1:1, so the frame's y 0.5 is the true visual centre. **The hunter's own `PurchaseFrameRobux` gets the same treatment inline** in `refreshPurchaseState` — owning the hunter drops that label to `UDim2.new(0.5, 0, 0.5, 0)`, which is also where its long-standing X re-centre lives (the authored x `0.4551` allowed for the icon that ships with the price string, and an owned hunter shows no price). It is written directly rather than through the helper because that frame's unowned path already restores `robuxPriceOriginalPosition` wholesale one branch below
   - **The hunter's Cash price is drawn as a COIN + number, not a `$`.** `PurchaseFrameCash` gained a `CurrencyLabel` ImageLabel carrying the same cash art the lobby currency bar, the emote cards and the Bounty Pass rewards use (`rbxassetid://73057941480631`), so the currency is read off the icon rather than a glyph — and `refreshPurchaseState` no longer prefixes the string. It is a clone of the emote card's coin, so the drop shadow and its `SizeConstraint = RelativeYY` square sizing come along verbatim; the pill sits under the aspect-locked shop canvas, so a scale-only square holds on every device. **The coin's position and the price label's X are one decision:** the label is full-width and centre-aligned, so it is nudged right of centre (x `0.5608`) and the coin parked at x `0.4051` to make the pair read as one group centred in the pill — the same idiom as the Robux label's authored `0.4551` nudge. Both were derived from the measured text width, not eyeballed; a price wider than 4 digits would need them re-derived, and Fortuna is the only hunter with a `CashPrice`
   - **Group-perk skins:** membership is declared in [[GroupPerkConfig]], not on the `SKINS` entry — currently only Dust's `Wraith`, which simply carries no `TokenPrice`. Unowned, it shows **GROUP PERK** as the price and a glowing **JOIN GROUP TO UNLOCK** button that opens `GroupService:PromptJoinAsync` in place rather than firing `PurchaseSkinWithTokensEvent`. ⚠ It called `GuiService:OpenBrowserWindow` until 2026-08-12 and did nothing at all in the live client — that method is RobloxScriptSecurity and the `pcall` ate the rejection, while edit-mode probes pass because plugin code runs at PluginSecurity. The `PurchaseFrameTokens` InfoLabel (a static "BUY SKIN" subtitle authored into the template) is hidden because it would misdescribe the action. The skin description carries the "free for members" line. The grant is server-side and lands on the **next** lobby join ([[DataService]] `grantGroupSkins`), and [[DataService]]'s purchase handlers reject group-perk skins outright, so this branch is presentation only — not the gate. Once owned it takes the normal EQUIP / EQUIPPED path
 Weapon-skin models come from `ReplicatedStorage.WeaponSkins.<Hunter>` — Vesper's `DefaultSniper` and Bram's `Grudgekeeper` are single default guns. `WEAPON_DISPLAY` is now a require of the shared [[WeaponDisplayConfig]] (it used to be a table copied byte-for-byte into the Collection menu as well, with a rule that every shared key stay identical); it tunes stand/icon presentation per hunter (rotation, `displayScale` in studs — multiplied by `Model:GetScale()` since the sniper/Grudgekeeper carry a baked-in scale baseline — `iconDistanceScale`, and one of two vertical placements: `standRaise` = extra world-Y studs on top of a **bottom-aligned** gun, or `standCenterOffset` = pin the bounding-box **center** to `standTop.Y + offset`). **All four guns now lie level with the muzzle to screen-left**, so the shop reads as one set.
   - **`standCenterOffset` exists because bottom alignment cannot hold two skins of different heights at the same line** — a taller model's center lands higher even at a matched length. Dust uses `-2.837` (world Y 9.21, exactly where the old union revolver's center sat) and Vesper `-1.63` (world Y 10.42, the camera's view axis). Bram still uses `standRaise = 2.68`, which arrives at that same 10.42 by the other route; it is verified and left alone.
   - **Dust's `DefaultRevolver` is the NEW MeshPart revolver**, swapped from the old `UnionOperation` model — the same Base/Hammer/Reel/Trigger build HellFire uses, copied from Redwater's `RevolverDefaultViewmodel.ArmsViewModelRevolverNew.Default` (what the player sees down the sights). Note Redwater's **third-person** world gun, `Revolver.Objects.WorldRevolver`, is still the old union model, so the shop now matches first person rather than third. Both Dust guns therefore share one pivot convention — muzzle toward **+X**, receiver top toward **-Y** — so the 180° roll that used to be a HellFire-only special case in `getWeaponSkinDisplayRotationOffset` is now the hunter's base `rotationOffset` and that function is an empty hook. `displayScale = 6` reproduces the old union revolver's on-screen length (6.07 studs) **and** drags HellFire up to match: unnormalized, HellFire's raw model is only 56% of the default's size, which is why it read as a small gun sitting low.
   - **Vesper's sniper lies HORIZONTALLY, muzzle to screen-left**, via `explicitOrient`/`explicitIconOrient` — it used to hang off the shared lookAt path with a 90° roll, which pitched it and pointed it the *opposite* way to its own icon (muzzle right on the stand, muzzle left in the icon). In its own pivot space the sniper is axis-clean: length along **X with the muzzle at -X** (scope, magazine and bolt all sit toward +X), top of the gun at **-Z** (the scope sits at pivot z = -0.74), thin axis **Y**. `explicitOrient` = `fromMatrix((0,0,-1),(1,0,0))` puts the muzzle at world +Z and the top at world +Y; `CameraPartHunterCloseup` sits at world +X looking -X, so its screen-right is world -Z and muzzle→+Z reads as pointing left. `explicitIconOrient` is Bram's icon recipe on these axes — `fromMatrix((1,0,0),(0,0,1))` then the same 38° yaw. Measured against yaw 0 and -38: 0 leaves it tilted, -38 stands it on a steep diagonal.
   - **Bram lays the Grudgekeeper HORIZONTALLY with the muzzle to screen-left**, an upright side profile like Vesper's sniper. The displayed model is the MeshPart shotgun copied from Redwater's `ReplicatedStorage.Grudgekeeper.WorldShotgun` (the old UnionOperation gun it replaced is gone). It is axis-clean: in the model's own pivot space the muzzle points **-Z**, the top of the receiver points **+X**, and the thin side-to-side axis is **+Y** — so no droop correction is needed and both orientations are exact `fromMatrix` rotations. `explicitOrient` = `fromMatrix((0,1,0),(1,0,0))` sends the muzzle to **world +Z** and the receiver top to **world +Y**; `CameraPartHunterCloseup` sits at world +X of the stand looking -X, so its screen-right is world **-Z** and muzzle→+Z reads as pointing left. `displayScale` is **8** (just under Vesper's 9 — a shotgun should read shorter than a sniper) and `standRaise = 2.68` puts the gun's world-Y center on the camera's view axis (~Y 10.42, eye-level center). `explicitIconOrient` = `Angles(0, rad38, 0) * fromMatrix((0,1,0),(0,0,1))` lays the gun flat with the muzzle to the left and yaws it 38° so the barrel runs along the icon camera's screen-right axis, filling the round icon edge to edge. The stand drag-to-spin for weapons rotates around **world-vertical through the model's bounding-box center** (translation-only centered pivot), not the model's local Y, so no per-hunter drag axis is ever needed — for Bram's horizontal gun this is a level turntable (verified: muzzle direction keeps Y = 0 and the world-Y span is identical at 0/45/90/135°); for Vesper's pitched sniper it keeps it from tumbling. This generalizes the old Dust-only centering to all weapons
3. Displays 3D hunter models on a rotatable stand in `workspace.FeaturedItems.Stand`; supports drag-to-spin on both PC and mobile
   - **With nothing picked, the stand shows the player's own loadout.** HUNTERS opens on the equipped hunter + skin (`showHunterList`), and **SKINS opens on the gun that hunter currently has equipped** (`showWeaponHunterList` → `showEquippedWeaponOnStand`) — it used to open on a bare stand. The gun resolves `equippedWeaponSkins[equippedHunterName]`, falling back to that hunter's first `WEAPON_SKINS` entry when the equipped one has no model under `ReplicatedStorage.WeaponSkins`, and to Dust when the equipped hunter has no gun list; every hunter's default gun does exist, so it always lands on something. Drilling into a hunter hands the stand to `selectWeaponSkin`, and GO BACK restores the equipped gun. Neither page marks a grid tile selected to match — the stand is the only thing that reflects the equipped item, on both tabs.
   - **⚠ Nothing may touch the stand while the shop is CLOSED, and `huntersBuyFrame.Visible` alone does not tell you that.** That flag is never reset on close, so it stays true for the rest of the session after any visit that ended on HUNTERS or SKINS — which is why `screenGui.Enabled` is part of the `skinDataEvent` handler's gate rather than decoration. The Collection menu fires `EquipSkinEvent` as well, and this push is [[DataService]]'s reply to it, so on the stale flag alone equipping a hunter over there dropped one onto the shop stand with the shop shut. `showHunterOnStand` calls `FeaturedSequence.Cleanup()`, so a reply landing during the Trading Post's featured cinematic (equip, then switch straight to the shop) killed the reveal and left the newly equipped hunter standing there through the whole opening. `FeaturedSequence.Play()` and `placeFortunaOnStand` only clear their **own** tracked instances, so a foreign `LocalHunterShopDisplay` survives both — the gate is the only thing keeping the stand clear between visits

   - **The gutters are `0.012` on both sides of the card** — between it and the buy panel, and between it and the canvas edge. That outer margin is why the card's right edge is `0.988` rather than the SKINS card's `0.975`: growing rightward into the margin is the only direction that does *not* push the buy panel further onto the hunter, and it is now fully spent. **The four numbers are one budget** — panel width + card width + both gutters have to fit between the podium hunter and the canvas edge.    - **Every card-drawing function takes a card table** built by `makeLimitedCard(frame)` (`titleLabel`/`editionLabel`/`stockLabel`/`priceLabel`/`viewport`/`purchaseFrame`/`purchaseButton`/`infoLabel`/`actionPriceOriginalPosition`) instead of reading upvalues — `renderLimitedCardViewport`, `setLimitedActionRows`, `refreshLimitedStockLabel` and `refreshLimitedPurchaseState` all gained a leading `card` parameter. `limitedItemFrame` / `limitedPurchaseFrame` / `limitedPurchaseButton` survive as aliases onto the SKINS card so the older call sites read unchanged.
   - **It lives in this script rather than TradingPostController** (which owns the rest of the featured page) because stock, ownership and the resolved Robux price are all state this script already keeps for the SKINS card. A second copy over there would be free to drift, and the `RequestSkinData` / `LimitedStockEvent` plumbing would have to be duplicated wholesale.
   - **The `GetProductInfoAsync` result is memoized per item, so the resolved price repaints EVERY card, not just the one that asked.** Both cards show the same item; whichever refreshed first is the only one that spawns the lookup, so a single-card repaint would leave the other stuck on `R$ ...` until something unrelated refreshed it. Each card carries a `stillShowing(itemId)` predicate for this — the SKINS one re-checks the grid selection, the featured one only that it is still on screen.
   - **This script never writes the featured card's `Visible`.** TradingPostController's staggered featured reveal owns that flag (the frame is in its `FEATURED_REVEAL_ORDER`, last, after the buy panel), and a stock push landing mid-reveal would pop the card in ahead of its turn. The sole exception is startup: the frame is hidden outright if `FEATURED_LIMITED_ITEM` is absent from [[LimitedStockConfig]], since every label would otherwise keep its authored placeholder text forever.
   - **The shop's `Enabled` handler now pulls stock on open.** The existing pull hangs off `huntersBuyFrame.Visible`, which never fires for a player who opens the Trading Post and never leaves FEATURED — they would read the count from whenever they joined. `refreshFeaturedLimitedCard()` is also called from the `LimitedStockEvent` and `SkinDataEvent` handlers (both ungated — the featured tab is not one this script tracks) and from `refreshEquippedWeaponSkinFromAttribute`.
   - **Its buy button is a 44px-touch-target exception.** At 70% the pill measures ~`0.142 × 0.0310` of the featured canvas width — 265 × 58 px on a 1080p desktop but only ~104 × 23 px on a landscape phone. The full-size SKINS card is 1.43× that and already misses the minimum on phones; this is the same trade at a smaller scale, not a new pattern
6. Fires `CharacterSelectEvent` / `EquipSkinEvent` / `EquipWeaponSkinEvent` on equip
7. Listens to `SkinDataEvent` from server to populate owned skin state, and fires `RequestSkinData` once at startup to **pull** that state rather than relying on [[DataService]]'s one-shot join push having landed after this handler was connected — a RemoteEvent fire with no listener yet attached is dropped for good, which would leave owned skins reading as purchasable for the whole session. The handler also re-stands the equipped hunter (or, on SKINS, the equipped gun) when nothing is picked, **only while `screenGui.Enabled`** — see the stand rules in 3, which that gate exists for
8. **SFX volume routing:** its hover/click sound helper clones sounds from `ReplicatedStorage.SFX.ShopMenuSFX` and assigns `SoundGroup = SoundService.SFX` before playing, so they obey the player's SFX + Master volume settings (SettingsController drives `SoundService.SFX.Volume`)

9. **It owns a second copy of `getStandTopPosition` (line 503), and that copy fails SILENTLY.** It reads `standModel.PrimaryPart` exactly as the FeaturedSequence version does, but returns nil with **no warning**, and both call sites (583 and 1149) respond with `model:Destroy()` — so a single `Stand model needs a PrimaryPart set.` line in the log can correspond to two blank stands, only one of which announced itself. `workspace.FeaturedItems.Stand` was made `ModelStreamingMode = Persistent` on 2026-08-03 to fix this; see the FeaturedSequence entry for why the `WaitForChild` pair at lines 120-121 does not protect against it. If a blank display stand is ever reported again, check that property before reading any code
