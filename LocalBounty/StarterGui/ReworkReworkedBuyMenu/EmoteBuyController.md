# EmoteBuyController

> **SUPERSEDED 2026-08-23.** The Trading Post is now `StarterGui.Shop` (ShopController + Shop.Modules.*). This ScreenGui is kept `Enabled = false` for one release as the rollback, and its LocalScripts are `Disabled = true` (they played purchase SFX and pulled state even while hidden). Nothing enables it; MenuHandlerScript, CurrencyHudController, BattlePassClient, ReworkedUIPlay and the Collection Shop module all point at `Shop` now. The text below describes the retired script as it still exists in Studio.

The EMOTES half of the Trading Post **ACCESSORIES** tab — builds the emote shop cards from the authored card frames and the shared catalog.

## What it does
1. Pairs the 17 authored `NEmote` card frames in `EmoteBuyFrame.Canvas.ScrollingFrame.1Side` with the 17 `IntValue`s in the sibling `Emotes` folder, matching each IntValue's name to an [[EmoteConfig]] entry by normalised display name (lowercased, non-alphanumerics stripped). A mismatch warns rather than failing silently, and the IntValue's animation id is cross-checked against the config's
1a. **The two lists are sorted differently, so a card frame is not tied to an emote.** Cards sort by their numeric name prefix, the IntValues sort ALPHABETICALLY, and the two are then paired by index — so inserting a value re-seats every card after it. `Take The L` (added when the L28 pass reward finally reached the shop) lands between `Small Wave` and `Tip Toe`, which pushed `Wild Celebration` onto the new 17th card. Nothing is hard-coded to a card, so this only changes which dummy dances which emote; the name, price and animation all come from the pairing
1b. **The shop lists every emote except `electro_swing`, not just the buyable ones.** `wild_celebration` became default-owned when `take_the_l` moved onto the pass, and its card is deliberately kept — it reads OWNED for every player. So the count is 17 cards = 11 purchasable + 5 BOUNTY PASS + 1 permanently owned
2. Renders a **full-body animated preview** per card: strips scripts from the authored `Rig`, frames it with a per-card `Camera` (FOV 36, distance derived from the rig's bounding box) and loops that emote's animation
2b. Those authored `Rig` models are **shared showcase art, not private to this shop.** BattlePassClient clones the first usable one for its own emote reward cards so the two menus can never show different dummies — deleting or renaming them (or the `1Side` / `ViewportFrame` / `WorldModel` path above them) silently drops the pass back to flat icons. No code connection: it reads the instances, it does not require this script. Note the pass does **not** copy the framing, because by then these rigs are mid-animation and their bounding boxes are pose-dependent
3. Preview playback is gated on the shop being open **and** the tab showing emotes — the tab now hosts titles too (see TitleBuyController), and in TITLES mode the emote cards are detached from the scroll but still alive, so without the `AccessoryMode` attribute check their rigs would keep animating off-screen
4. **A card SELECTS; the panel BUYS.** Each card gets a full-size transparent `SelectButton` at `ZIndex = 10` — the player reaches for the dancing figure, and the price strip is only a fifth of the card's height; it was the click target purely because it happened to be the authored button. Clicking fills [[AccessoryBuyPanel]] with the emote's name, `"EMOTE"`, its price and a live **BUY NOW**. The price goes over as the **amount** (`priceAmount`), not a formatted string: the panel draws the Cash coin beside it — the same art as the card behind it — and has to know the number's width to place the icon. No currency is passed, since [[EmoteConfig]] has no currency field and emotes are Cash-only, so the panel's default stands. Selection shows as a `1.04` UIScale plus a **doubled** stroke — ⚠️ the authored thickness (`0.0125`) is **multiplied, never assigned**; a plain `2` renders a border hundreds of pixels thick. The `AccessoryMode` handler drops the selection on the way out to TITLES so an emote's BUY button cannot survive the switch (TitleBuyController clears the panel offer itself, in `setMode` — doing it here too would race it)
4a. The card's bottom strip shows the price (thousands-separated, e.g. "2.000") or **OWNED**, and is inert in **every** state now that it is a label rather than the purchase; owned cards hide their `CurrencyLabel`
4b. An emote with **no `price` in [[EmoteConfig]] is not for sale** (the five battle-pass exclusives). Its card shows that entry's `unlockText` — `"BOUNTY PASS"` — instead of a price and hides the Cash `CurrencyLabel`, since there is no Cash cost to sit beside. The card is deliberately left **visible**: it advertises the pass, and hiding it would leave a hole in the authored grid. The price is no longer defaulted to 2000 when absent (that would print a fake price on an unbuyable card), and the buy path re-checks `isPurchasable`. Selecting one arms the panel with **VIEW IN BOUNTY PASS** rather than a purchase, which fires `MenuNavigateRequested("4BattlePassFrame")` on [[MenuHandlerScript]] — the same hand-off the Collection menu's locked tiles use, so the camera flight and tab highlight run the real path rather than reaching into another panel's internals
5. **This script does not own the scroll canvas.** TitleBuyController sizes it for whichever mode is showing — a page is 9/`VISIBLE_CARD_COLUMNS` windows wide, so six cards fill the frame and the other three columns are read by scrolling — and attaches only the pages that hold cards, so the authored empty `2Side` spare is detached and the emote side no longer scrolls a blank page past the last card. Only `1Side` is looked up here, so that filtering is invisible to this script. Its `UIGridLayout.CellSize.X.Scale` is what tells that script how many columns a page holds, and the title pages clone the same grid — so re-authoring it resizes **both** halves of the tab
6. **The shared `ScrollingFrame`'s authored size is pure scale.** Its height used to carry a `+100px` offset, which is a fixed share of a big screen but a huge share of a small one: at 1080p the scroll was 0.93 of the panel, at 720p 1.01, and on a phone **1.20** — so on mobile it burst out of the panel at both ends, the tab row printed over the card headers and the bottom row of prices ran under the main-menu nav diamonds. It is now `0.965` scale tall at `y = 0.496` and `0.9767` wide at `x = 0.5009` — the full width of its parent panel — which sits inside the panel and clears the nav's topmost art at every landscape size, and `HorizontalScrollBarInset = ScrollBar` gives the horizontal slider its own lane instead of drawing it across the bottom row's price buttons
7. Hover/press feedback via a per-button `UIScale` (grow on hover, dip on press, Back-eased settle on release)
8. A staggered **ripple reveal** (`playShopRipple`) pops each card's background and name label in sequence when the tab opens; reset when it closes. **Its start state is applied SYNCHRONOUSLY by `primeShopRipple`**, called in the same frame the panel becomes visible. `playShopRipple` runs through `task.defer`, so setting the start state inside it meant the tab drew one frame with every card at full size before they all snapped small and grew back — a visible flash of cards landing ahead of the rest of the tab. Priming first means the cards are only ever seen growing in. `playShopRipple` still primes as well, harmlessly, for any caller that plays the ripple without priming
9. Purchases are server-authoritative: fires `PurchaseEmoteEvent` with only the emote id and lets [[CollectionService]] resolve the price from [[EmoteConfig]] and charge through Wallet. A `PurchasePending` attribute blocks double-clicks
10. Ownership comes from `EmoteStateEvent`, re-requested whenever the shop or the tab becomes visible; the handler re-runs `selectEmote` for the current selection so the card just bought flips its BUY button to OWNED rather than offering the purchase again
    - ⚠ **That re-arm makes `selectedEmoteId` outlive the shop unless the close handler drops it, and it did not.** Closing and reopening ACCESSORIES came back up on the previous visit's card, armed, because the state reply re-selected whatever the variable still held. `clearEmoteSelection()` on the shop's `Enabled` → false edge is the missing half. **TitleBuyController carries the identical re-arm and never showed the bug** — its close handler calls `setMode("Emotes")`, which runs `clearTitleSelection()` on the way through. Fixed 2026-07-30; surfaced as a deep-link bug because a deep link is what put a surprising card there, but a manual click left exactly the same residue.
    - The shared buy panel is deliberately **not** cleared from here — `setMode` owns the offer, and clearing it from both scripts would race (same reasoning as the `AccessoryMode` handler).
11. **Deep-link target (`consumeEmoteRequest`).** A locked emote in the Collection menu arms **its own card** here and scrolls the canvas to the page holding it, rather than dropping the player among 18 emotes across several pages. The id arrives as a `RequestedEmote` attribute on the buy-menu ScreenGui, written by the Collection menu's Shop module (an attribute, not a code link) alongside the `AccessoryModeRequest` that picks this half of the tab. An id with no card is left in place rather than cleared, since the request can land before this tab has ever been shown; the shop's close handler clears an abandoned one.
    - ⚠ **Every caller defers it, and that is load-bearing.** TitleBuyController's `setMode` publishes `AccessoryMode` at its top and clears the shared buy panel at its bottom, so anything arming that panel *synchronously* off the attribute change is wiped a few lines later. Deferring lands after `setMode` has finished, whichever of the two scripts' handlers ran first. Honoured on three edges — the shop's `Enabled`, the tab's `Visible`, and a switch **into** the emote half — so it resolves whether the request arrives before or after the shop opens.
    - `scrollCardIntoView` derives the offset from absolute positions rather than a page index times a width (the page is several windows wide), and bails on the NaN that position reads before the first layout

## Dependencies
- **Requires:** [[EmoteConfig]], [[AccessoryBuyPanel]], [[AnimationLoader]]
- **Required by:** Nobody (top-level LocalScript)

## Connections
### RemoteEvents
| Remote | Direction | Other script |
|--------|-----------|-------------|
| `PurchaseEmoteEvent` | → Server | [[CollectionService]] buys an emote with Cash (`emoteId`) |
| `RequestEmoteState` | → Server | [[CollectionService]] asks for a fresh owned/equipped emote state |
| `EmoteStateEvent` | ← Server | [[CollectionService]] pushes `{ owned, equipped }`; flips bought cards to OWNED |

### BindableEvents
| Bindable | Direction | Other script |
|----------|-----------|-------------|
| `MenuNavigateRequested` | → | [[MenuHandlerScript]] a selected pass-exclusive emote's VIEW IN BOUNTY PASS button fires `"4BattlePassFrame"` |

### Direct require()
| Target | Function | Purpose |
|--------|----------|---------|
| [[EmoteConfig]] | `list()`, `get()`, `isDefaultOwned()`, `isPurchasable()`, `unlockTextOf()` | Emote catalog: display name → id matching, price, animation id, default-owned check, and whether a card offers a purchase or a BOUNTY PASS badge |
| [[AccessoryBuyPanel]] | `get()`, `setCopy()`, `setOffer()` | The shared info panel + BUY button for the selected emote |
| [[AnimationLoader]] | `AnimationLoader.load()` | Load a card's preview clip only once it is confirmed fetched, so a failed fetch warns instead of leaving a frozen dummy on the card. `loadPreview` wraps it in `task.spawn` — the build loop must not stall per tile, but the script strip and camera framing stay synchronous so a rig's own scripts die before they can start an idle of their own |
| [[AnimationLoader]] | `AnimationLoader.prewarm()` | Warm every card's clip in one pass before the build loop, read from the authored `Emotes` values folder (the exact ids `loadPreview` will ask for), so the grid costs one fetch round-trip rather than one per card |
