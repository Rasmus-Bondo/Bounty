# TitleBuyController

> **SUPERSEDED 2026-08-23.** The Trading Post is now `StarterGui.Shop` (ShopController + Shop.Modules.*). This ScreenGui is kept `Enabled = false` for one release as the rollback, and its LocalScripts are `Disabled = true` (they played purchase SFX and pulled state even while hidden). Nothing enables it; MenuHandlerScript, CurrencyHudController, BattlePassClient, ReworkedUIPlay and the Collection Shop module all point at `Shop` now. The text below describes the retired script as it still exists in Studio.

The TITLES half of the Trading Post **ACCESSORIES** tab — the only place cosmetic titles are sold.

## What it does
1. The tab formerly called EMOTES is now **ACCESSORIES** (the authored instances keep their old names — tab `4Emotes`, frame `EmoteBuyFrame`) and hosts two modes. This script adds a segmented **EMOTES | TITLES** toggle to the tab's right-hand info panel (`BuyHunterFrame`), at `y = 0.655` — **above** the price line, not in the lower band. That band belongs to `PriceLabel` (0.768) and `PurchaseFrameCash` (0.896), which this tab finally uses (see 13)
1b. **The toggle is built from the shop's own button art.** Each half is a clone of the authored `PurchaseFrameCash` (`PriceLabel` + `SelectedBackgroundGlow` + `TextButton`), so it inherits the gradient, stroke and corner exactly; selection lights the authored glow via [[AccessoryBuyPanel]]`.setGlow` and tints the label gold. It was previously two hand-rolled `TextButton`s with a flat fill, a 6px `UICorner` and a 1.5px `UIStroke` — the one control on the tab that looked nothing like the shop around it. Cloning is also the only *safe* way to get that look: authored `UIStroke.Thickness` in this GUI is a scale, so hand-building one means guessing a number that is not pixels
2. **Only PURCHASABLE titles get a card** (16 of the 26). A hunter's free title needs no shop entry and a battle-pass title cannot be bought at any price, so neither belongs in a shop — the list comes from `TitlesConfig.Purchasable()`, which returns them in hunter order (Dust → Vesper → Bram → Fortuna) then price-ladder order
3. **Each card is headed with its HUNTER's name** — "DUST", "VESPER". Every title belongs to one hunter and this grid mixes all four, so the hunter is part of what you are buying. It is only the hunter: the card body renders the title itself directly below, so a qualified "DUST: HIGH NOON" over HIGH NOON said it twice
4. The card body shows the title **rendered in its real cosmetic style** through [[TitleRenderer]] — the gradient/aura/flames are the product shot. The authored rig `ViewportFrame` is stripped from the card template once at startup (a title has nothing 3D to show), so cloning a card never clones a rig
4b. **The preview label is sized explicitly (`fitPreview`), NOT with `TextScaled`.** TextScaled wrapped the two-word titles ("WRECKING RAM", "THE BUTCHER") onto a second line in a card built for one. Disabling `TextWrapped` is not the fix and is actively worse: with `TextScaled` still on, Roblox collapses the text to **8px** rather than shrinking it to fit — measured, DEADEYE went 22px → 8px. So the label picks the largest size ≤22 whose single-line width fits, via `TextService:GetTextSize`, re-run on `AbsoluteSize` changes. Titles land between 17 and 22px. This also keeps the aura ghosts exact, since [[TitleRenderer]] reads a non-scaled label's `TextSize` directly
5. **Price uses the currency ICON**, not the word: the card's authored `CurrencyLabel` is pointed at the Cash icon (`rbxassetid://73057941480631`) or the Token icon (`rbxassetid://138855504574427`) — the same art as the lobby currency bar. The amount is formatted with the emote cards' thousands separator so `1500` reads "1.500" exactly as an emote's 2000 reads "2.000". **Alignment is left exactly as authored (centred) in both states**, which is what keeps the number sitting against its coin the way an emote's does. A title card *is* an emote card (the template is a clone of `1Emote`) at the same cell width, and the widest title price — "1.500" — is exactly as wide as every emote's "2.000", so the centred text clears the icon at x=0.225 by the same margin. Right-aligning it instead parked the number on the button's far edge with half a button of dead space between it and the coin. Owned titles read "OWNED", centred, with the icon hidden
6. **Mode switching REPARENTS the page frames** rather than toggling `Visible`: the ScrollingFrame's `UIGridLayout` still reserves a cell for an invisible child, which would leave a blank page. Detached pages are held in Lua tables so they survive
6b. **The scroll WINDOW is AUTHORED, not computed — the card width is derived from it.** This is the inverse of what the script used to do: `applyScrollWindow` forced the ScrollingFrame to 5 authored cards wide (`0.625` of the panel) and re-centred it on **every** show, which silently threw away any resize done in Studio and left a wide dead margin either side of the grid. `applyScrollWindow` is gone; `Size`/`Position` are taken as given and a card comes out at 1/`VISIBLE_CARD_COLUMNS` of whatever window it finds, so resizing the frame in Studio now moves the cards with it
6b-i. **`VISIBLE_CARD_COLUMNS` is the one knob for card size**, currently **6**. The authored page is 9 columns, so anything below 9 makes a page wider than the window and the remainder is read by scrolling — at 6 the frame holds six cards and scrolls two. Measured at a 767px window: 6 → 128×168 cards, 5 → 153, 8 → 96 with no scroll at all. 8 was tried first and read as squished, which is what the scroll is buying back
6b-ii. **On a narrow window the TITLE cards get bigger rather than the text smaller** (`cardShape`, mode-aware). A title card is a *word* — there is no art to fall back on — and `fitPreview` shrinks the title until it fits, bottoming out at 8px. Measured on a phone the shop window is ~529px, which at 6 columns is an 88px card, a ~74px text slot, and `WRECKING RAM` (164px at the full 22px) collapsing to about 10px; desktop's 225px card keeps it at 22px, which is why this only ever showed on a handset. So the visible count becomes `clamp(floor(window / 176), 3, 6)`, **and** the page is re-shaped from 9×2 to 18×1 in the same step: widening the cards alone would letterbox them (176×120 against desktop's 225×306), while a single row spends the freed height on the card and yields 176×240 — twice the area, the desktop card's aspect, and the title back around 20px. Pagination is untouched (`CARDS_PER_PAGE` cards a page either way, so the page count is unchanged); only the arrangement moves. **Emote pages get the same 18×1 treatment** on the same trigger, so the tab does not change shape when you flip halves. Measured on a phone: 17 emotes in one row of 18 cells, ~176px wide, one card-width of trailing blank.
6b-ii-a. ⚠️ **The single row is gated on `UserInputService.TouchEnabled`, NOT on window width — desktop always gets the authored two rows.** The row count originally keyed off `visible >= VISIBLE_CARD_COLUMNS`, which needs a **1056px** scroll window (6 × 176). That window is only ever that wide on a *fullscreen* desktop: measured, it is 1351px at 1920×1080 but **900px at 1280×720 and 773px in a 1100×650 window**, so every windowed PC silently rendered the handset's single row. The width test survives for `visible` (card width, and so title legibility); only the row count moved to touch. Rows trade card **height** only — card width is `window/visible` and `visible` is capped at `window/176`, so any window ≥ 528px keeps cards ≥176px wide at either row count, which is why two rows on a small desktop window does not bring the unreadable-title case back. Verified: 3840×2160 → 1100×650 desktop all give 2 rows (9+8); phones at 844/896/932 wide all give 1 row of 17; a small tablet (1180×820) gets 1 row and a 2048×1536 iPad reaches `visible = 6` and so 2 rows Recomputed inside `applyCanvas`, so a rotation or window resize re-shapes without a rebuild
6b-iii. **The two page types do not fill the same way, and the reshape has to respect that.** The title pages this script builds fill **vertically** (so `FillDirectionMaxCells` means rows); the authored emote page fills horizontally (where the same field would mean columns). `shapeTitlePages` sets rows; `shapeEmotePages` pins Horizontal with no cap at one row deep — the one arrangement that preserves the authored left-to-right card order — and restores the captured authored grid *field-for-field* above the threshold. Getting that wrong reorders the emote cards rather than just resizing them. `AUTHORED_PAGE_COLUMNS` and the emote grid are both captured **once at load**, before any reshape: the column count used to be re-read off `emotePages[1]` every call, which was safe only while the emote pages were never touched — now it would measure the reshape and walk on every resize

6c. ⚠️ **THE GEOMETRY MUST BE SETTLED BEFORE THE TAB IS DRAWN, NOT AFTER — this is the actual "ACCESSORIES loads glitched" bug.** The symptom is that part of the emote grid appears when you click the tab and is removed again almost instantly, and the part that vanishes is the strip sitting behind the right-hand info panel. Cause: `applyCanvas` originally hung off `scrollingFrame:GetPropertyChangedSignal("AbsoluteSize")` **only**, and AbsoluteSize is computed *during* layout — so the handler necessarily runs a frame **after** the tab has already been drawn at whatever geometry the instances carried, reaching right underneath the info panel. The correction then clipped that strip away in full view. Two things fix it together, and both are needed:
   - `applyCanvas` is now also called from the `Visible` and `Enabled` handlers. **`Visible` fires synchronously on assignment** (inside TradingPostController's `setSelectedTab`), so it lands ahead of the first draw, which the AbsoluteSize signal structurally cannot.
   - **The authored instance values are baked to exactly what the code computes**, all scale-based so they hold at any resolution: `ScrollingFrame.Size = (0.9767, 0.965)`, `Position = (0.5009, 0.496)`, `CanvasSize = (1.4650, 0)` and the outer `UIGridLayout.CellSize = (1.5, 0.9655)`. This is what covers the very *first* open, where the ScreenGui has only just been enabled, `AbsoluteSize` still reads 0 and `applyCanvas` correctly bails. Verified by rendering the ScreenGui with every script stripped. **If you re-author any of those four values, re-derive the others** — a mismatch between authored and computed is exactly what puts the flash back. A page is `COLUMNS_PER_PAGE / VISIBLE_CARD_COLUMNS` windows wide, so the two canvas numbers are `Size.X.Scale` times that ratio (9/6 = 1.5); the outer cell's Y carries a first-frame allowance for the scroll bar's lane, which is a fixed 12px and so only approximable in scale
7. **Canvas sizing (`applyCanvas`) is in OFFSET, and drives the grid's cell width with it.** Neither scale means what it looks like: `CanvasSize`'s scale resolves against the ScrollingFrame's **parent**, and the outer grid's `CellSize` scale resolves against the ScrollingFrame's **`AbsoluteSize`** — *not* the canvas this function just set, which is the measured correction to the older note here. Offset sidesteps both — the canvas is n page-widths and a page is `COLUMNS_PER_PAGE / VISIBLE_CARD_COLUMNS` windows, so the scroll stops dead on the last page. The columns-per-page figure is **derived** from the page's own `UIGridLayout` (`1 / CellSize.X.Scale`), read off `emotePages[1]` rather than whatever is attached — in Titles mode the emote page is detached and held in a Lua table, and the title pages clone that same grid anyway. Re-derived on `AbsoluteSize` changes, since an offset canvas cannot track a resize on its own
7a. **The page width is ROUNDED, not floored.** The inner cell is `1/9` *scale* of the page, so a column is exactly `pageWidth/9` whatever the outer number is; rounding keeps `VISIBLE_CARD_COLUMNS` of those within half a pixel of the window, which is what stops a sliver of the next card showing against the right edge. Measured at a 767px window: exactly 6.00 columns visible and a max scroll of exactly 2.00 columns on one page, 10.00 on two
7b. **The scroll bar's lane is DERIVED, never measured.** `AbsoluteWindowSize` reports the lane that the *current* canvas produces, and `applyCanvas` is what sets that canvas — reading it there chases its own tail by a frame: sizing the page to a 336px window releases the lane, the window becomes 348px, and the page is left 12px short with a gap under the bottom row. The bar's presence is knowable up front instead — the canvas simply has to be wider than the window. The page height is `AbsoluteSize.Y` minus `ScrollBarThickness` whenever that holds. Get this wrong the other way and the bottom row's card border is clipped off by the bar's own lane
8. **Only pages that actually hold cards are attached** (`pageHasCards`). The authored `2Side` is an empty spare, and an empty Frame still claims a grid cell — that plus the authored `(2, 0)` canvas is what let both modes scroll a whole empty page past the last card
9. **Title pages sort by `LayoutOrder`, not Name.** The authored page grid sorts by Name, which the emote side gets away with because its cards are hand-placed; generated names sort lexicographically ("10Title" before "1Title"), which scrambled hunter order
10. Pages hold `CARDS_PER_PAGE` cards — **derived** as `AUTHORED_PAGE_COLUMNS × AUTHORED_PAGE_ROWS`, currently 18 from the authored 9×2 grid. It was a hardcoded `16` until the emote grid widened to 9 columns to fit a 17th emote; a literal there would have gone on paginating titles to the old shape and left two dead cells on every full page. More titles automatically spill onto additional pages that scroll horizontally, exactly like the emote side — and the canvas grows with them
11. **Title pages fill VERTICALLY (`FillDirection = Vertical`, `FillDirectionMaxCells = 2`), unlike the authored horizontal grid.** The emote side gets away with horizontal fill because its one page is near enough full — 17 cards in 18 cells, so its single hole falls at the END of the bottom row; the title catalog does not divide by a page, so the last page dumped every card into the top row and left the bottom row empty — with 20 titles, 4 across and 0 beneath. Filling down each column balances the rows instead (4 cards become two columns of two), and a **full** page is visually unchanged since 9 columns × 2 covers the same grid. It also groups better: each hunter's titles run down a column rather than wrapping mid-hunter across the row
11. Sets an `AccessoryMode` attribute ("Emotes"/"Titles") on the tab frame. EmoteBuyController reads it to stop animating its rigs while the titles half is showing
12. Swaps the info panel's Title/Class/Description per mode. The emote copy is **captured at load** rather than hard-coded, so a designer editing that blurb in Studio keeps their wording when the tab switches back
13. **A card SELECTS; the panel BUYS.** Each card gets a full-size transparent `SelectButton` at `ZIndex = 10` — the player reaches for the artwork, and the price strip is only a fifth of the card's height; it was the click target purely because it happened to be the authored button. Clicking fills [[AccessoryBuyPanel]] with the title's label, `"<HUNTER> TITLE"`, its price and a live **BUY NOW**, or an inert **OWNED**. The price crosses as the **amount plus the currency** (`priceAmount` / `priceCurrency`), not a formatted string: the panel draws the coin beside the number — the same Cash/Token art this card uses — and has to know the number's width to place it, so a title reads `600` where it used to read "600 CASH". The bottom strip is now a price tag in *both* states (`Active = false`), since leaving it active would give it a competing hit area and its own hover highlight under the button that actually does something. Selection shows as a `1.04` UIScale plus a **doubled** stroke — ⚠️ the authored thickness (`0.0125`) is **multiplied, never assigned**; a plain `2` renders a border hundreds of pixels thick. `setMode` clears the selection and the panel offer, so a title's BUY button cannot survive the switch to EMOTES
13b. Purchases are server-authoritative: this sends only a title id on `PurchaseTitleEvent` and [[CollectionService]] resolves price/currency from [[TitlesConfig]] and charges through Wallet. A `pending` guard blocks double-clicks; ownership arrives back on `TitleStateEvent`, which re-runs `selectTitle` for the current selection so the card just bought flips its BUY button to OWNED rather than offering the purchase again
14. Resets to EMOTES when the shop closes, and re-requests ownership whenever the shop or the tab is shown
15. **Deep-link target (`consumeModeRequest`).** The Collection menu's locked title rows and locked emote tiles hand the player off to whichever half of this tab the item lives on, rather than dead-ending on the word LOCKED. That is two attributes: TradingPostController's `TradingPostRequestedTab` gets the shop onto the ACCESSORIES tab, and an `AccessoryModeRequest` attribute on the tab frame set by the Collection menu's Shop module — set by CollectionGuiController, read here — picks EMOTES vs TITLES. **Cleared on read**, because a leftover value would hijack the next ordinary visit, which always starts on EMOTES. Honoured both when the shop's `Enabled` flips true and live via `GetAttributeChangedSignal`, so it works whether the request lands before or after the shop opens. Note this is a *separate* attribute from `AccessoryMode` (item 11), which is this script's own published state — writing the request into that one would make EmoteBuyController act on a mode that had not been applied yet
15b. **The deep link now names the TITLE, not just the half.** A third attribute, `RequestedTitle` on the buy-menu ScreenGui, arms that title's own card and scrolls the canvas to the page holding it — landing the player among 31 titles across several pages and leaving them to find the one they clicked was most of the way to a dead end. Three details it depends on:
   - **Read AFTER the `setMode` above, never before.** Every mode switch drops the selection and clears the shared buy panel, so selecting first would arm a panel that switch then wiped.
   - **An unknown id is left in place rather than cleared.** The cards are built at boot but the request can land before this tab has ever been shown; the shop's close handler clears an abandoned one instead.
   - **`scrollCardIntoView` derives the offset from absolute positions, not a page index times a width.** A page is `COLUMNS_PER_PAGE / VISIBLE_CARD_COLUMNS` windows wide (item 7), so index arithmetic would have to restate `applyCanvas`'s numbers and then keep agreeing with them. It is deferred because `applyCanvas` re-derives the geometry on the very edge that consumes the request, leaving the page's `AbsolutePosition` a frame behind — and it bails on NaN, which is what that position reads before the first layout
