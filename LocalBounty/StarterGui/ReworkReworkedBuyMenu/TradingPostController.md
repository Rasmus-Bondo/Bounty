# TradingPostController

> **SUPERSEDED 2026-08-23.** The Trading Post is now `StarterGui.Shop` (ShopController + Shop.Modules.*). This ScreenGui is kept `Enabled = false` for one release as the rollback, and its LocalScripts are `Disabled = true` (they played purchase SFX and pulled state even while hidden). Nothing enables it; MenuHandlerScript, CurrencyHudController, BattlePassClient, ReworkedUIPlay and the Collection Shop module all point at `Shop` now. The text below describes the retired script as it still exists in Studio.

Main store UI controller for the reworked buy menu (Trading Post tabs).

## What it does
1. Manages tab navigation: Featured, Hunters (2), Skins (3), Bundles (4), Deals (5)
2. Opens/closes the store with slide-in reveal animation (tabsFrame, featuredFrame, topFrame)
3. **The currency chips are no longer in this ScreenGui.** They moved to [[CurrencyHudController]]'s `CurrencyHudGui`, which draws them on Bounty Pass and here (Home deliberately has none), owns their balances and owns the `+` buttons. This script keeps a handle for one reason: the vault view (11) re-lays them into its left-hand column. The HUD mirrors this canvas outright and its `TopFrame` is an exact copy, so canvas coordinates are interchangeable and the column math was left unchanged. Removed with them: `bindCash/TokenLeaderstat`, `playCash/TokenCountUp`, `set*HeaderValue`, `TOP_REVEAL_ROOTS`, `prepare/revealTopFrameSequence`, and the `topFrame` entry in `SECTION_ORDER` — the local `TopFrame` still exists but holds only an empty `LogoFrame`. **Behaviour change:** the shop's open sequence no longer staggers the chips in with a count-up, because they are now a persistent HUD that was already on screen before the shop opened
4. Featured tab (Fortuna card), driven by `refreshFortunaBundleState()` off player attributes (`OwnsFortuna`, `EquippedCharacter`, `EquippedSkin`): non-owners see two card buy buttons — Robux bundle (`BUY BUNDLE` / `INCLUDES 400 TOKENS`) and Cash (`$4,000`); owners see a single `EQUIP` / `EQUIPPED` button. The Robux frame shifts up to make room for the Cash frame when both show. The legacy center bundle button (`purchaseFrameRobux`) is kept hidden.
   - **A second panel shares the right-hand side: `FeaturedFrame.Canvas.LimitedItemFrame`,** a 70%-scale copy of the limited-run card from the SKINS tab, spanning canvas x `0.8257 – 0.9880` and vertically centred. `featuredBuyHunterFrame` was moved left from x-centre `0.7962` to `0.6996` to make room, with `0.012` gutters either side of the card. At full size the two would need `0.46` of the canvas while the podium hunter behind them occupies roughly `0.40 – 0.62`, leaving only ~`0.35` — scaling the card down is what keeps the pair mostly off her. At 70% the buy panel's left edge crosses her outer coat by ~`0.039`; the outer gutter is spent, so any further growth comes out of the hunter or out of the panel's width.
   - **This script only reveals that card; HuntersBuyController fills and drives it.** All of the state it needs — stock counts, gun-skin ownership, the memoized `GetProductInfoAsync` price — already lives over there for the SKINS copy, so the card is bound to a card-refs table on that side rather than duplicated here. This is a shared *instance*, not a code-level connection: no remote, bindable or `require()` runs between the two scripts, so there is no wikilink for it.
   - **`InfoFrame.EndTimer` is a live countdown (2026-07-31), not the authored string.** It was shipped as static text reading `ENDS IN 30D 12H 15M`; a `task.spawn` loop near the end of the file now ticks it down to `DEADLINE_UNIX = 1788566400` — Saturday 2026-09-05 00:00:00 UTC / 02:00 CEST, extended a week on 2026-08-29 from the original 1787961600 (2026-08-29 00:00 UTC), which had already elapsed. **Kept in step with `ShopFeaturedTab`'s copy of the constant**, which is the one live players actually see once the Shop rework publishes; this parked GUI carries it so a rollback does not land on a dead offer. Rotating the featured offer means moving that one constant. Past the deadline the label reads `OFFER ENDED` and the loop breaks for the session. **The authored `Text` is a placeholder only** — the loop overwrites it within its first frame, so no player ever sees it, but it was re-authored from `ENDS IN 30D 12H 15M` to `ENDS IN 28D 13H 15M` so that what Studio draws is consistent with the real deadline. It has the same character count as the original, so nothing about the authored layout moves (`TextScaled`, `AutomaticSize = None`). It goes stale by a day per day and is not worth chasing; re-author it when the deadline constant moves. Formatting drops leading units that have run out (`23H 59M`, `2M 5S`, `59S`) but keeps trailing zeroes once a larger unit is showing (`1D 0H 0M`), and the last hour switches to M/S so the final minutes visibly move.
     - **Clock is `workspace:GetServerTimeNow()`, not `os.time()`** — on a client the latter is just the device clock, so a player with a wrong system time would see a different number from everyone else. The `pcall` around it guards the window on a fresh client before its first server time sync; it resolves normally in edit mode, so the `os.time()` fallback is belt-and-braces rather than the usual path.
     - **The whole thing is wrapped in a `task.spawn` closure on purpose, not for style.** This chunk is at ~197 of Luau's 200 top-level local registers (the same ceiling that forced `vaultView` into a table and keeps `CONTENT_TOP`/`CONTENT_BOTTOM` function-scoped), so every name it introduces has to live in a function frame. A plain `do` block does not buy room — its locals stay live alongside the top-level ones while it runs. As written it adds **zero** top-level locals.
     - It sleeps to the next tick of the smallest unit actually on show (`remaining % 60` above an hour, 1 s inside it) rather than polling every second for the whole session. Nothing else writes this label, and the reveal owns its `Visible`/transparency, so the loop only ever touches `.Text`.
   - It is appended to `FEATURED_REVEAL_ORDER` **last**, so it pops in after the buy panel it sits beside. The append deliberately runs *after* the `includesFrame` insert, because that one splices itself in at `#FEATURED_REVEAL_ORDER` and would otherwise land behind the card instead of ahead of the buy panel. Since the reveal owns the frame's `Visible`, HuntersBuyController never writes it — a stock push landing mid-reveal would otherwise show the card early.
5. Fires `CharacterSelectEvent` and `EquipSkinEvent` remotes when equipping from the featured view
6. Robux purchase: fires `MarketplaceService:PromptProductPurchase` for the Fortuna **bundle** product (ProductId from [[StoreConfig]])
7. Cash purchase: fires `PurchaseHunterEvent` with `"Fortuna"`; the server validates ownership/balance and deducts $4,000 via Wallet
8. Listens to `ShopPurchaseSuccessEvent` to play a success sound
9. **Canvas fit (`updateCanvasAspect`, re-run on every `ViewportSize`/`CurrentCamera` change):** the canvas is grown until its **content band** exactly fills the usable box — the viewport minus `GuiService:GetGuiInset()` — with the band's top edge sitting flush on the Roblox topbar.

    **THE CANVAS BOX IS NOT THE PANEL.** Every pixel the shop draws lives in y `0.0349 .. 0.7576` of the canvas: `0 .. 0.0349` empty · `0.0349 .. 0.0823` `TopFrame`'s currency chips · `0.0991 .. 0.1707` TabsFrame · `0.1701 .. 0.7576` the selected tab's buy frame · `0.7576 .. 1` empty. `CONTENT_TOP` = the chips' **amount label**, the topmost hard-edged pixel; the `+` buttons' soft glow (`BuyMoreLabel`, 1.75× its button) reaches ~0.009 higher and is deliberately allowed to ride into the topbar inset — it is a faint halo, out at x 0.69 / 0.89 where the topbar has no buttons. **`CONTENT_BOTTOM` deliberately stays at `0.9603`** — a fifth of a canvas *below* the last drawn pixel — because tightening it to 0.7576 would grow the panel until the buy frame ran into the lobby's bottom nav bar, whose drawn top is screen y `0.7823` (`MainMenuGui.CanvasBottom`; the box is the bottom 25%, the diamonds start at 0.80, the NEW badge at 0.7823). **At 0.9603 the buy frame's bottom edge already lands within a few px of the nav bar, so the panel is at its vertical limit** — topbar above, nav bar below; the slack is clearance, not an oversight. Any further growth has to come from the *inside*: nothing under the canvas carries a `UIAspectRatioConstraint`, so widening past 16:9 to fill an ultrawide window would horizontally stretch every card. The two constants are function-scoped, not file constants — this chunk is at Luau's 200 top-level-local ceiling and two more names there stops it compiling. Re-derive `CONTENT_TOP` after re-authoring: min `AbsolutePosition` of every *drawn* descendant of TabsFrame + TopFrame, over the canvas height (a container's own box is not a safe proxy — the chip cells extend ~0.015 above their amount labels).

    **[[CurrencyHudController]] MIRRORS this canvas** — it copies the `Size`/`Position` written here rather than running its own copy of the fit, so this function is the single source of truth for both. It briefly did duplicate the math and that drifted in the real client: this script fits once at load, the HUD re-fitted later, and `GuiService:GetGuiInset()` returns `0` early and the real topbar inset afterwards, which put the two canvases ~36 px apart and dropped the chips onto the tab row. Note `CONTENT_TOP` still measures the **chips'** top edge even though they are no longer descendants of this canvas: do not "tighten" it to the TabsFrame at `0.0991` on the grounds that nothing is drawn up there any more, or the panel grows until the tabs slide up under the chips.

    This ScreenGui is `IgnoreGuiInset`, so nothing keeps the panel clear of the Roblox buttons on its own; aligning the band to the inset is what does it. **`AspectType` is forced to `FitWithinMaxSize`, not the authored `ScaleWithParentSize`** — only FitWithinMaxSize reads the element's own `Size`; ScaleWithParentSize measures the parent and discards it. `DominantAxis` is no longer set, being meaningless under FitWithinMaxSize. The 16:9 lock caps the growth on a window at or narrower than 16:9 (1080p fullscreen, 4:3 windowed), where the width runs out before the height does; the leftover vertical slack is then centred rather than all left at the bottom. The **lobby nav bar is what pins the bottom** — the panel cannot grow past `CONTENT_BOTTOM = 0.9603` without the buy frame reaching the HOME/COLLECTION/BOUNTY PASS/TRADING POST diamonds

    9b. ⚠ **Touch-only nav-bar cap (added 2026-07-31) — the `CONTENT_BOTTOM = 0.9603` clearance only survives at or under 16:9.** It is the *width* cap that holds the panel short of the screen bottom there; wider than 16:9 the *height* binds instead, the panel grows to fill the whole usable height and the buy frame's bottom edge lands **inside** the nav bar. Every modern phone in landscape is wider than 16:9 (iPhone 14 is 844×390 = 2.16:1), so on mobile the buy frame ran onto the bottom nav bar — level with the tab buttons' touch targets — while 1080p desktop kept its ~6 px of clearance. **Nothing could be won by moving the panel up:** `bandTop` is exactly `GuiInset.Y` in the height-bound case, so the currency chips' hard top edge is already flush on the Roblox topbar and any upward nudge puts them under it. The fix caps `canvasHeight` instead, so the *bottom* edge rises and the top never moves.

    - The cap is `canvasHeight ≤ (viewportY * (NAV_BAR_TOP - NAV_CLEARANCE) - inset.Y) / (DRAW_BOTTOM - CONTENT_TOP)` with `DRAW_BOTTOM = 0.7576`, `NAV_BAR_TOP = 0.8000`, `NAV_CLEARANCE = 0.0064`. **`DRAW_BOTTOM`, not `CONTENT_BOTTOM`** — the cap has to measure against the real last drawn pixel, since `CONTENT_BOTTOM` deliberately sits a fifth of a canvas below it. The whole thing collapses to `buyFrameBottom = viewportY × (NAV_BAR_TOP − NAV_CLEARANCE)`, which is the quickest way to re-tune it.
    - **`NAV_BAR_TOP` is a fraction of the VIEWPORT, not of this canvas.** Derive it from `MainMenuGui.CanvasBottom`: that frame is the bottom 25 % of the screen (its `4.5` aspect lock cannot bind in landscape, since 1.125·H < W always). It offers three candidate lines — `5TradingPostFrame.NewItemFrame` (the NEW pill) at `0.75 + 0.25 × 0.1294 = 0.7823`, the tab `Button` touch targets at 0.80, and the `Background` diamonds at 0.8125. This is a plain geometry constant read off another ScreenGui's authored layout, not a code-level connection — no wikilink.
    - ⚠ **We target 0.80, the buttons, and deliberately let the NEW pill be crossed by ~4 px.** Targeting 0.7823 is the strictly correct reading and was the first build of this cap, but it costs a **12 px** rise where **3 px** clears the buttons *and* the diamonds — and 12 px was a visibly larger gap than the overlap it fixed. The pill is a small badge on one tab and the last few px of the buy frame's box are empty, so it reads clean. **Do not "fix" this back to 0.7823.**
    - **`slack` must be pinned to 0 when the cap fires.** The centring branch exists for the width-bound case; left running here it would hand back half of the gap the cap just opened and re-cross the bar.
    - **It is a `math.min` that only fires where the overlap is real.** 4:3 and 16:9 touch devices are width-bound and already clear the bar, so tablets (iPad 4:3, iPad 10th) come out byte-identical. Measured on iPhone 14: canvas 382.5 → 378.4 px (−1.1 %), buy-frame bottom 312.5 → 309.5 (a 3 px rise), content top unchanged at 36. Across the phone range the rise is 2.3–3.3 px and the shrink 0.7–1.3 %. Chip sizes follow, because CurrencyHudGui mirrors this canvas.
    - **Gated on `UserInputService.TouchEnabled` by request — the bug is not mobile-only.** Ultrawide desktop (2560×1080) and a 1280×720 window are both height-bound and overlap by ~6 px and ~2 px for exactly the same reason; deleting the gate covers them. The service is resolved inline inside the function rather than as a file local, because this chunk is at Luau's 200 top-level-local ceiling
10. **SFX volume routing:** its sound helper clones the hover/click/purchase sounds from `ReplicatedStorage.SFX.ShopMenuSFX` and assigns `SoundGroup = SoundService.SFX` before playing, so they obey the player's SFX + Master volume settings (SettingsController drives `SoundService.SFX.Volume`)
11. **Currency vault (the `+` buttons on either chip).** `openCashVaultPage(mode)` runs a cinematic — black bars → `CameraPartVaultDoor` → the `VaultDoor` model's animation → a 0.62 s push through the doorway under a fade → `CameraPartVaultInside` — then reveals `Canvas.BuyCurrencyFrameNew` and drops physical coin/token stacks from `ReplicatedStorage.MoneyPhysical` onto `MoneySpawnPart`, one stack group per offer tier. Offers come from `StoreConfig.CashProducts` / `StoreConfig.TokenProducts`; `< / >` step `cashOfferIndex` and re-sync the stacks.
11b. ⚠ **`MoneySpawnPart` lives in `Workspace.PersistentMarkers`, a Persistent Model, and it has to.** It is the drop target for those coin stacks, and it used to be a **loose BasePart at Workspace root**. With `StreamingEnabled` a loose part does not replicate until it streams in, and the `WaitForChild` for it sits **near the top of this file** — so on a fresh join *everything below that line*, `openMenu` and the whole tab wiring included, did not exist yet. It recovered a few seconds later when the vault streamed in, which made it read as an F9 warning rather than as the Trading Post being inert straight after joining. Fixed 2026-07-30 by moving it (and the lootbox's `ChestShootPart`) into `PersistentMarkers`, the same device `CameraFolder` and `SkinMenu` already use.
    - **The `VaultDoor` wait two lines above HIDES this hazard instead of raising it.** A Model replicates as an **empty container**, so that wait returns instantly while the door's three BaseParts are still streamed out — which is exactly why `MoneySpawnPart` warned and `VaultDoor` never did. `VaultDoor` is still `ModelStreamingMode = Default`, so its parts are not guaranteed present when the vault cinematic starts.
12. **Vault "inside" view (`vaultView`).** While inside, the shop chrome is hidden and the currency chips move out of the top bar into a **left-hand column** — cash, tokens, then a `GO BACK` button — at canvas x `0.055 .. 0.255`, three rows centred on y `0.475`, clear of the centred offer panel (`0.17 .. 0.76`).

    - **The chips keep their authored pixel size exactly.** They have no `UIAspectRatioConstraint`, and the coin icon + `+` button are `SizeConstraint.RelativeYY` (tracking chip *height*) while the amount label tracks *width* — so changing the cell's **aspect** slides those three apart, and shrinking the height alone drags the `+` touch target under 44 px. The column is built by re-laying the grid (`CellSize` → full-width rows, alignments → Center), never by resizing the chips. `TopFrame` does not clip, which is what lets the column hang far below it.
    - `GO BACK` is `BuyCurrencyFrameNew.VaultBackFrame`, cloned from `HuntersBuyFrame`'s `GoBackHunterButton` for styling. It is a descendant of the vault frame, so it inherits that frame's visibility and staggered reveal for free. Its width is `0.79` of a chip cell — a **measured** constant matching the drawn run from the coin icon's left edge to the `+` button's right edge (175 of 222 px), which cannot be derived from the Size properties because of the RelativeYY sizing above. **It has two destinations.** If the `VaultReturnMenuFrame` attribute is set the player arrived via a `+` press on Home or the Bounty Pass, so it fires `MenuNavigateRequested` with that frame name — routed through `handleMainMenuClick`, which sees this ScreenGui is enabled and takes its black-bar leave path, disabling us and letting the `Enabled` handler tear the vault down. Otherwise it returns to the shop tab the player came from (captured into `vaultView.returnTab` before `openCashVaultPage` clears `selectedTab`) via `setSelectedTab`, which runs the black-bar wipe and camera restore itself. The attribute is cleared on read, and cleared again on any ordinary `openMenu`, so it can never steer a later visit.
    - **`vaultView.setLayout` no longer restores the chips' *layout* itself.** It writes `VaultLayout` on `CurrencyHudGui` and lets that GUI re-apply its own, because "authored" is the Row layout and that is the wrong answer on the Bounty Pass. The column values are still computed and applied here. Its `else` branch **does** restore the chips' *opacity* (below).
    - **`UIShadow` counts as a visual.** `rememberVisual` / `setVisualHidden` / `tweenVisualVisible` now treat it exactly like `UIStroke` (same plain `Transparency` property), and **`getObjectVisuals` collects it — `getSectionVisuals` deliberately does not**. This matters because *the chips' backdrop IS a UIShadow*: every Frame inside them is `BackgroundTransparency = 1`, so with shadows excluded the background snapped in at full strength while the text and icons faded up. The split keeps the change surgical — `cashVaultFrame` and `FeaturedFrame` contain **no** shadows, so `getObjectVisuals` gaining them affects only the chips, while `TabsFrame`'s five shadows keep popping in on shop open exactly as they always have rather than silently re-timing a shipped animation.
    - **The chips fade in with the page.** They are part of the left column but live outside `cashVaultFrame`, so `revealCashVaultPage`'s sweep missed them and they popped in at full opacity while everything around them faded. They are now prepended to that staggered reveal — first, so the column leads rather than trailing the whole panel (`GO BACK` is a child of `cashVaultFrame` and follows naturally). **They are hidden in the black-bar `onCovered` callback, NOT in `prepareCashVaultPage`**: that runs *before* the bars close, so hiding there blinks the chips out in front of the player. The matching restore lives in `setLayout`'s `else`, which is reached on all four exit paths — an entry aborted mid-cinematic never reaches `revealCashVaultPage`, and without it the chips would stay invisible on the Bounty Pass and in the shop for the rest of the session.
    - **Chrome hidden:** `Canvas.TabsFrame`, the lobby bottom nav bar and its gradient trim (`MainMenuGui.CanvasBottom` + `MainMenuGui.Fade`), the invite/multiplier chip (`InviteFriendsGui.Canvas`), and **`BattlepassGui.Canvas`**. The settings cog and the party tab stay reachable by design; the left sidebar is already handled by MenuHandlerScript's `SIDEBAR_VISIBLE_FRAMES`. `Visible` is **snapshotted and restored**, never forced back to `true` — several of these are driven false by their own owners. Layout + chrome are swapped while the black bars cover the screen, and restored on all four exit paths (`closeCashVaultForTab`, `openMenu`, the `Enabled → false` handler, and the `BlackBarMenuCovered` handler); the snapshot is consumed on the first restore, so the later ones are no-ops rather than clobbers.
    - **Why the Bounty Pass panel is on that list.** It is a whole page rather than chrome, but a `+` can be pressed while it is open, and BattlePassClient will not close it for us — it closes on `MenuCameraArrived` for another frame, on a real bottom-tab **button** click, or on `MainMenuGui.Enabled` going false, and the vault entry does none of those (it navigates programmatically and leaves the menu enabled). Left off the list it simply sat there behind the vault. This is a plain `Visible` write on a panel another script owns, not a code-level connection — no wikilink. Resolved with `FindFirstChild` at call time rather than in `initialise()`, because that GUI may not have replicated into PlayerGui yet when initialise runs; by the time a vault can open it always has. Restoring the **snapshot** rather than forcing `true` is what makes the already-dismissed-panel case behave.
    - **Switching currency while inside** does *not* replay the door: both `+` buttons route through `vaultView.request(mode)`, which swaps `vaultCurrencyMode`, resets to offer 1, tears the coins down instantly (the physical template differs per currency, so they must be gone before the stacks re-read it) and re-deals with a scale pop. Clicks during the cinematic (`cashVaultBusy`) are dropped.
    - **The offer panel sits below the coin pile, not over it.** `BuyCashFrame` (which holds the amount label *and* the whole `< / BUY / >` row — moving the frame keeps that row intact) is authored at `Position.Y = 0.85`, not its original `0.6`, putting the amount at canvas y `0.755` and the row at `0.841 .. 0.904`. The pile's bottom edge projects to canvas y **`0.7312` on every tier** — higher tiers only build upward and backward, and all tiers share the frontmost loose coins — so one offset clears all six offers. Verified against a spawned max-tier pile (117 coins), which still leaves the row on the platform. Note the UI is inset-aligned and the 3D pile is not, so a device with a *larger* topbar inset pushes the panel further down (safe direction); Studio's edit viewport has no topbar at all and so renders the panel ~8 px higher than the real game.
    - `cashVaultEntered` is cleared on **every** entry to the shop, not just in `closeCashVaultForTab` — leaving the shop straight from inside the vault never runs the close path, and a stale flag there deadens both `+` buttons for the rest of the session.
    - All of the above hangs off one `vaultView` table and is set up inside `vaultView.initialise()`. **This is forced, not stylistic:** the chunk sits at 197 of Luau's 200 top-level local registers, and a plain `do` block does not help — a block's locals stay live alongside every top-level local while it runs, so only a new *function* frame buys room.

13. **Deep link (`TradingPostRequestedTab`).** `openMenu` normally lands on `1Featured`; if that attribute is set on the ScreenGui it selects the named tab instead. Written by the Collection menu's Shop module when a locked item hands the player off, alongside `AccessoryModeRequest` which TitleBuyController reads to pick the EMOTES/TITLES half. **Cleared on read**, so it steers exactly one open and cannot hijack the next ordinary visit.
    - `revealSection` still runs in full for `FeaturedFrame` even when another tab was requested — it only forces `Visible` when Featured is the selected tab. **Do not "optimise" this into an early return:** that reveal's position tween is what brings the frame back from the offset `prepareSection` parked it at, and its visual tweens are what un-hide the contents, so skipping it leaves FEATURED shifted and blank for the rest of the session.

14. **Vault entry from outside the shop (`VaultOnOpen`).** The `+` buttons live on the shared HUD and fire `CurrencyVaultRequested`; this script answers only while `screenGui.Enabled`, routing to `vaultView.request`. When the shop is closed [[MenuHandlerScript]] takes the same event instead, sets `VaultOnOpen` (`"Cash"`/`"Tokens"`) plus `VaultReturnMenuFrame`, and enables us. `openMenu` reads `VaultOnOpen`, and if set skips the whole tab reveal and calls `openCashVaultPage` directly — the vault plays its own black bars, so nothing else transitions. **Cleared on read**, like `TradingPostRequestedTab`. The two listeners' guards (`Enabled` vs `not Enabled`) are mutually exclusive, so exactly one side responds to any press

15. **`workspace.VaultDoor` must stay `ModelStreamingMode = Persistent`** — set 2026-08-03, having been `Default`. The top-level loop at line 535 snapshots every BasePart `CFrame` and every Motor6D `C0` / `C1` / `Transform` into the two tables `resetVaultDoor()` restores from, and it runs **once, at load time**. If the parts have not streamed in by that instant the snapshot is simply empty, the door has no rest state to return to, and it drifts out of position after its first animation and stays wrong for the whole session. Nothing warns and nothing errors — this is the silent end of the streaming trap, findable only from a player screenshot. Only 3 parts, so Persistent costs essentially nothing here
