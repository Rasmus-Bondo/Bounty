# DailyLoginController

Drives the designer-built `StarterGui.DailyLoginGui` for the daily play-streak rewards in the Bounty lobby. Renders the 7-slot track from [[DailyRewardService]] state, lets the player claim each ready reward **individually**, and ticks a **live countdown** to the next daily reset on the tile that unlocks next. Replaces the old code-built DailyRewardClient panel (deleted).

## What it does
1. Renders the 7 `RewardN` tiles from `DailyRewardState`. Per tile: READY (gold gradient + CLAIM, claimable), CLAIMED (dark gradient, swapped from the `Template.ClaimedTemplate` look), NEXT, or LOCKED. `styleTile` records each tile's resolved `state`. Adds a per-tile `RewardLabel` in the empty middle band showing the reward amount ("50 Cash", "200 XP", "2 Boosts", "50 Tokens"…) read from [[DailyRewardConfig]]. The passive perk is rendered from `PASSIVE_PCT` with two wordings: `PASSIVE_UNLOCK` (Day 7 milestone) and `PASSIVE_MAINTAIN` (Day 7+ recurring)
2. **The "next" tile is smart** (Day 1 is free, so a new player's Day 1 shows READY immediately): the single tile in NEXT state shows either a **live countdown** `H:MM:SS` (when `advancedToday` — the player already advanced today, so they wait for the reset) or a **"PLAY"** prompt (when the reset has passed and the streak is alive — play a round in Redwater to earn it). Applies to the pre-7 next tile AND slot 7's milestone/recurring NEXT states
3. **Reset countdown ticker:** a `RunService.Heartbeat` loop (only while the panel is open) counts the next tile down using `os.clock()` + the server's `secondsUntilReset` (so it never trusts the client wall-clock); the label updates ~once/second. At zero it re-fires `RequestDailyReward` so the server re-evaluates `advancedToday` and the tile flips from the countdown to "PLAY"
4. **Per-day claim:** each tile's ClaimButton fires `ClaimDailyReward` with that tile's specific streak day number, so the server grants only that one day. The button optimistically locks until the fresh state re-renders. Each tile also carries an authored **`ClaimHitbox`** — an invisible TextButton pinned to the painted button's bottom edge with a `UISizeConstraint` `MinSize` of 44x44, wired to the same `onClaimPressed`. The painted button is sized in Scale only and resolved to ~19px tall on a 360px-tall phone, under half the touch minimum, on all seven tiles. Growing the button itself was the obvious fix and the wrong one — Reward3 and Reward4 are authored shorter than their neighbours, so a 44px button left their reward line 4px tall; expanding the hit area keeps every painted pixel as authored on every device. It sits at ZIndex 0 so the painted button still takes any press landing on it, and needs no `Active` bookkeeping because the guard is `claimReady`
5. **Slot 7 is dual-purpose:** shows the Day-7 milestone (50 Tokens + passive, label "DAY 7") until it is CLAIMED, then flips to the endless recurring 10 Tokens (label "DAY 7+"). The passive perk is shown on BOTH tiers — Day 7 "+10% Cash & XP Boost" (unlock), Day 7+ "Maintain +10% Cash & XP Boost". When multiple day ≥ 7 rewards are pending it shows "CLAIM x N" and claims the oldest first; once the milestone is claimed the recurring tier reads its countdown/"PLAY" (state `next`), never "CLAIMED"
6. Builds in code the affordances the finished GUI does not include: a full-screen dim in its OWN `DailyDimGui` ScreenGui (`IgnoreGuiInset` + `ScreenInsets.None`, DisplayOrder just under the panel) so it fills the raw screen incl. topbar inset / mobile notches, and a header close button. Open/close toggles `Canvas.Visible` (+ dim)
6b. **The close button and the header title are sized against each other.** The button's glyph is a plain ASCII `X` — GothamBold has no U+2715, so the typographic cross rendered as the missing-character box — inset by a 22% UIPadding so TextScaled does not blow one letter up to fill the whole tile. `fitHeaderTitle` then reserves the button's own footprint (`min(0.22 × headerW, 0.7 × headerH)` + margin) on **both** sides of the centred "DAILY PLAY REWARDS" label, re-run on the header's `AbsoluteSize`. Without it the title ran ~55px **under** the button on a phone: TextScaled tops out at 100px, so a desktop-height header caps the title long before it runs out of width, but a ~70px phone header makes it width-limited instead. Desktop is unaffected — the reservation is smaller than the slack it already had
6c. **The panel sinks its own presses so the dim only ever catches a real outside click.** Frames don't consume input unless `Active`, so a press that missed a CLAIM button fell through the tile, past the canvas, onto the dim and closed the panel — worst on the CLAIMED / LOCKED tiles, whose button is deliberately `Active = false` and so passed the press straight down. Marking the canvas alone is not enough: nothing in this panel clips and the art is authored to hang outside it (the reward tiles run to screen y 0.84 against a canvas ending at 0.75, and the mascot ViewportFrame hangs off its left edge), so `Active` is set on the canvas **and every direct child** — with one exception, and an authored backstop. A rect test like QuestClient's is deliberately NOT used here: the panel is `DeviceSafeInsets` while the dim's ScreenGui is `ScreenInsets.None`, so the two coordinate spaces drift apart on a notched phone
6d. **`AnimatedFrame` is the exception, and it cost Day 1 and Day 2 to find.** The mascot's ViewportFrame is a *transparent rectangle* spanning screen x 0.093-0.368, authored at ZIndex 5 against the reward tiles' 2, so its whole rect draws over the left column regardless of what the art inside it fills. Marking it `Active` turned that rect into an input sink covering **88% of the Reward1 and Reward2 CLAIM buttons** — an ~11px tappable sliver on a phone, on buttons that still looked entirely clickable. Days 3-7 are clear of it, which is exactly the shape the launch report described ("Day 2 impossible to claim, Day 1 difficult"). It is now set `Active = false` explicitly after the loop
6e. **`PressSink` replaces what that frame was sinking.** An authored transparent Frame at ZIndex 0, sized to the union of all the panel art including the mascot's overhang (screen x 0.093-0.750, y 0.083-0.899), so a press on the mascot lands either on the button it is drawn over or on the sink — never on the dim. Its left edge stops short of the menu's left nav column (art starts at x 0.093, the column ends at 0.0875), so a second press on DAILY still reaches the dim and closes, which is how the panel is expected to toggle
7. Updates the header `InfoText` to show the current streak + "+10% CASH & XP ACTIVE" while the passive is on (falls back to the designer's tagline at streak 0)
8. **Visibility gate:** enables the GUI only after `BountyIntroComplete` AND while on a tab that keeps the left sidebar up — **Home or Battle Pass** (matching MenuHandlerScript's `SIDEBAR_VISIBLE_FRAMES`). `onSidebarTab` is read from the `SelectedMenuFrame` attribute on `MainMenuGui`, which MenuHandlerScript publishes from `selectMenuFrame` — the one function every navigation route passes through. It previously hooked the `CanvasBottom.Frame` tab buttons, which only see navigation that *starts* on the bottom bar, so arriving back on a sidebar tab by any hand-off (the pass's X button, the currency vault's return hop) left the DAILY button visible but dead. Loot / Collection / Trading Post hide it. A 12s fallback reveals it if the intro flag is missed. Opened from the authored `CanvasLeft` `3Daily` button (whose click is a no-op while `gui.Enabled` is false, so the gate is also what makes the DAILY button live or dead); the red pending dot (`DailyNotiFrame`) is the only "reward waiting" cue. The panel sits at DisplayOrder 40 (dim 39) so it layers over the battle pass panel (8)
9. Requests state on load via `RequestDailyReward` (the server also pushes on join)
10. **BOUNTY+ reward numbers** (2026-09-06) — `describeReward` runs its Cash and XP lines through `BountyPlusConfig.apply` and leaves the Tokens line bare, matching what the server actually grants. The last pushed state is cached so the attribute's change signal can re-render when ownership resolves, rather than asking the server again

## Dependencies
- **Requires:** [[DailyRewardConfig]], [[BountyPlusConfig]]
- **Required by:** Nobody

## Connections
### RemoteEvents
| Remote | Direction | Other script |
|--------|-----------|-------------|
| `RequestDailyReward` | → Server | ask [[DailyRewardService]] for the current state (also re-fired when the countdown hits zero) |
| `DailyRewardState` | ← Server | full state `{ streak, pending, permaBoost, passivePercent, advancedToday, secondsUntilReset }` |
| `ClaimDailyReward` | → Server | claim ONE pending day (fires the specific day number) |

### Direct require()
| Target | Function | Purpose |
|--------|----------|---------|
| [[DailyRewardConfig]] | `getReward()`, `MAX_TRACK_DAY`, `PASSIVE_BOOST_PERCENT` | per-day reward labels + slot-7 recurring logic |
