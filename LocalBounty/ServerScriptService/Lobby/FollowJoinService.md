# FollowJoinService

Forwards a player who joined via the Roblox friends list ("Join" on a friend) into that friend's actual server.

## What it does
1. **Why it exists:** Roblox does **not** route a friends-list join into a non-start place. The joiner always lands in the start place (Bounty) and the Roblox client shows them *"<friend> has moved to a restricted location within this experience"* — which is just the client saying their friend is somewhere it didn't send them. Forwarding is the game's job. This is the documented "Following Another Player" flow from the TeleportService docs
1a. **Redwater servers ARE reserved as of 2026-08-03**, which changes the destination but not this flow — the app already routed follow-joins through Bounty, so nothing about the Join button moves. What does move is that `GetPlayerPlaceInstanceAsync` answers with a **jobId** while a reserved teleport needs an **access code**, and the directory is keyed on neither of those but on `privateServerId`. The chain is: jobId → [[MatchmakingService]] `getServerByJobId` (a scan, which is why Redwater publishes its jobId at all) → entry → `resolveAccessCode`
1b. **An empty directory lookup is not one situation, and treating it as one produced 29 identical warnings** (fixed 2026-08-13). It is a server that has not published yet, a match that genuinely ended, a friend in the onboarding **tutorial** — which never publishes, by design — or Roblox presence handing back a jobId that died a minute ago. All four told the player their friend's match had ended and all four warned. See items 4b, 4c and 6a for the three separate mechanisms that now split them apart
2. Reads `player.FollowUserId` on `PlayerAdded` — non-zero **only** for a follow-join, so nothing here can grab a player who joined normally and yank them into a match. A zero value returns immediately
3. Resolves the friend's server with `TeleportService:GetPlayerPlaceInstanceAsync(followId)`, wrapped in a `pcall` because it throws outright when the target user is offline. Note the result order: the raw call returns `(currentInstance, errorMessage, placeId, jobId)`, so through a `pcall` the values land one slot further along
4. `currentInstance == true` means Roblox already put them in the friend's server — fires `FollowJoinStatus` `"Arrived"` so the client overlay clears instead of hanging until its own timeout, and does nothing else
4a. Before every teleport attempt it asks [[FriendJoinService]] `evaluateTarget(placeId, jobId)` whether joining that server is allowed, and takes back the matched directory **entry** along with the verdict. A friend join deliberately **bypasses the 90-second join lock and both matchmaking caps** — Redwater holds seats 9-10 for exactly this — but it is refused when the target match is closing or already `Ended` (that server would bounce the arrival straight back to the lobby) or when it is at its 10-player hard cap. A lobby-to-lobby hop has no directory entry and always passes
4b. **`evaluateTarget`'s fourth return, the reason code, decides whether a refusal is retried.** `"missing"` is the one **transient** answer — the directory is a MemoryStore map on an 8-second heartbeat and a server reserved seconds ago has not booted or published yet — so it consumes `MAX_DIRECTORY_ATTEMPTS` (3) at `DIRECTORY_RETRY_DELAY` (4s) before giving up. That ladder is **separate from the teleport ladder** on purpose: a handful of "not published yet" answers must not eat the attempts needed to actually teleport once the entry does appear. `"full"` / `"closing"` / `"tutorial"` are real answers and give up at once — retrying only holds the player behind an overlay before telling them the same thing. The 12s ceiling is set by FollowJoinClient's `SAFETY_TIMEOUT` (20s), after which the overlay drops on its own
4c. **Every retry re-asks where the friend is** (`refreshTarget`), rather than re-teleporting at the jobId it opened with. `GetPlayerPlaceInstanceAsync` reads Roblox **presence**, which lags: a friend whose match ended is still reported at the dead jobId for a while, so the *first* answer is the one most likely to be wrong. Re-asking is what turns "their match has already ended" into an ordinary lobby hop once they are actually back in Bounty — the destination that was correct all along. A re-lookup that returns `currentInstance == true` means they landed in *this* server meanwhile, and fires `"Arrived"`; a re-lookup that fails keeps the previous target, since presence is flaky rather than authoritative
5. Otherwise teleports them into that exact server via `TeleportAsync` (`TeleportToPlaceInstance`, which the official doc sample still uses, is deprecated). **The destination differs per place:** a **match** place gets `TeleportOptions.ReservedServerAccessCode`, resolved off the entry `evaluateTarget` returned, and gives up cleanly if there is no reachable code; a lobby-to-lobby hop keeps `ServerInstanceId`, because Bounty is an ordinary public place and a jobId is exactly right for it. That branch — and the `"Match"` / `"Lobby"` session label above it — asks [[FriendJoinService]] `isMatchPlace(placeId)` rather than comparing against Redwater's id (2026-08-14): with a second map the comparison stopped being equivalent, and a Frostbite PlaceId falling to the else-branch would send a plain jobId at a reserved-only place. A fresh `TeleportOptions` is built per attempt, since one handed to `TeleportAsync` must not be reused
5a. **The match branch also stamps `TeleportData.friendUserId` with who they followed** (2026-08-29). `Player.FollowUserId` is a lobby-side fact that does not survive the teleport, so without it the match place cannot tell a follow-join from any other arrival — and a team gamemode seats an arrival with no preference on the **smaller** side, i.e. the enemy of the friend they pressed Join on, about half the time. Redwater reads it through RoundController's `friendTargetOf` accessor and TeamDeathmatch's `preferredTeamFor`; FFA ignores it. Deliberately **not** attached to the lobby-to-lobby hop: the lobby has no use for it, and a non-empty `TeleportData` is how TutorialDispatchService tells a teleport arrival from a fresh one
6. Retries up to `MAX_ATTEMPTS` (3). Both failure paths share one attempt budget: the synchronous `pcall` failure, and `TeleportService.TeleportInitFailed` — `TeleportAsync` returning cleanly is not proof the player left, and a follow-join targets one specific server instance that may have filled up or begun shutting down in the seconds since the lookup. `Flooded` / `GameFull` / `IsTeleporting` back off `BACKOFF_DELAY` (5s) instead of the normal `RETRY_DELAY` × attempt
7. The `TeleportInitFailed` handler only acts when the player has an entry in `pending`, which stops it stealing PartyService's Play-button teleports (a follow-joiner is gone long before they could press Play, so the two never overlap). PartyService now applies the mirror-image guard, ignoring any player it did not send — three modules connect to that one event
8. On giving up, fires `FollowJoinStatus` `"Failed"` with the friend's name and leaves the player in the lobby. The refusal's own **player-facing message** now travels with it, so the card can say "still in the training run" or "wrapping up" instead of one generic line; it is deliberately omitted for outcomes with nothing worth showing a player (a teleport ladder that ran out), and the client falls back to its own wording
8a. **Log level is chosen by the reason code, not by the fact that something failed.** `missing` / `closing` / `full` / `tutorial` / `offline` are how the world is and print; a warn out of this module should mean something is **broken** — a live match with no reachable access code, or Roblox refusing the teleport three times. 29 warnings in a row is what made this path look like an incident, and none of the 29 were bugs in the teleport
8b. **One `FollowJoin` [[Telemetry]] event per join, at the outcome and never before** — a partial emit per retry would make the outcome columns uncountable, and clearing the `session` entry is what enforces the "once". This is the measurement silencing the warns took away: value = seconds from join to verdict, CF02 = outcome (mapped from the reason code through `OUTCOME_BY_CODE`, which is a **separate** table from `EXPECTED_OUTCOMES` because "should a human look at this" and "which column does it land in" are different questions — `full` needs a column while deserving no warn), CF03 = `"<Match|Lobby|None>|R<directory retries>"`. **CF03 is the load-bearing half**: a `Forwarded` at `R1+` is a join the directory ladder rescued and a `Forwarded` to `Lobby` is one that re-asking presence rescued, so without it neither retry in 4b/4c is observable at all. `session` is deliberately not folded into `pending`, which `giveUp` clears and which never exists for a friend who turned out to be offline — both outcomes worth counting. `"Forwarded"` is booked on **`PlayerRemoving`**, not on a clean `TeleportAsync`: only the player actually leaving proves the teleport happened, and counting it earlier would book a success for joins that went on to fail at init and give up
9. Also fixes following a friend who is sitting **in the lobby**: Roblox can drop the joiner into a *different* Bounty server, where they can't party up. Same hop, same code path
10. `Players:GetNameFromUserIdAsync` resolves the friend's display name purely for the failure line — the client already has its overlay up from reading `FollowUserId` itself
11. Clears `pending` on `PlayerRemoving`, which makes any scheduled retry a no-op once the teleport succeeds
12. **Publishes its verdict so the onboarding tutorial can pick up whoever it drops.** `outcome[userId]` runs `"resolving"` → `"teleporting"` / `"arrived"` / `"failed"`, read through `waitForOutcome(player, timeout)`, which answers `"failed"` **only** once this module has actually given up and the player is staying in Bounty. Every other answer — including a timeout — means do not claim them, because a teleport may still be in flight and two services teleporting one player is exactly the collision the tutorial's old blanket refusal was avoiding. TutorialDispatchService is the only caller; before this it refused to invite *any* follow-joiner outright, which stranded a brand-new player whose friend was themselves mid-tutorial with no match, no lesson and a false error. `dismissOverlay(player)` is the companion: it clears the "Joining…" card without showing the failure card, so the hand-off into the tutorial reads as one flow. Writes to `outcome` are guarded on `player.Parent`, since terminal outcomes land after yields a player can leave during and `PlayerRemoving` has already run by then
