# FriendJoinService

Owns every rule about joining a friend who is already in a match, and is the only place those rules live.

## What it does
1. **Two callers:** FollowJoinService (someone used the Roblox friends list, landed in the lobby, and is being forwarded into their friend's server) and the friends-in-match panel [[FriendsInMatchClient]] (an explicit Join press)
2. **What makes a friend join different from pressing Play:** it targets one specific server, so it bypasses [[MatchmakingService]]'s *choice* entirely (it still reads the directory through it); it ignores the join lock, which is the whole point — you can join a friend even when the match has 40 seconds left and matchmaking stopped filling it long ago; and it is allowed into the friend slots above **both** matchmaking ceilings (`SOLO_PLAYER_CAP` 8 + `FRIEND_SLOTS` 2 in the Redwater Config, published as `hardCap` = 10 on the directory entry). Note the friend slots sit on top of the **solo** cap, not the party cap — see 9
3. **What it still refuses:** a match that is closing or already `Ended`. That server would bounce the arrival straight back to the lobby, so forwarding them means two loading screens to end up where they started. The friend is back in Bounty within ~30s anyway
4. `evaluateEntry(entry, groupSize)` is the single gate, returning `(ok, player-facing message, reason)`: no entry → "match has already ended" / `"missing"`, closing/`Ended` → "wrapping up" / `"closing"`, `players + groupSize > hardCap` → "match is full" / `"full"`, or "doesn't have room for your whole party" when more than one is arriving. The **reason code** exists because a refusal is not one thing to every caller — FollowJoinService retries `"missing"` and gives up on the rest — and it is a third return rather than a parsed message so the wording can change without breaking the logic. `groupSize` defaults to 1, leaving `evaluateTarget` and the banner unchanged (`players + 1 > hardCap` is the old `players >= hardCap`). It exists because **a party joins as a unit**: room for one is not room for four, and admitting a party that does not fit gets some in and refuses the rest, which is the split this path exists to prevent
4a. **A join is routed by the entry's own map, and refused only when that map does not resolve** (2026-08-14, spec §9.2 — this replaced the interim same-day rule that refused every non-Redwater entry outright). `destinationFor(entry)` asks [[MapCatalog]] `placeIdFor(entry.map)`; `joinFriend` resolves it once, stamps it on every member's `pending` entry, and both `TeleportAsync` calls use it — nothing in this module names a place outright any more. An entry whose map has no catalog row or no resolvable PlaceId in this environment answers `"othermap"` with its own message, tested before closing/full because it is not a worse version of them — those say *not right now*, this says *not from here*. [[MatchmakingService]] normalises an absent map to `"redwater"` on read, so an entry written before the field existed never trips it
5. `evaluateTarget(placeId, jobId)` wraps it for FollowJoinService, which knows a jobId but not whether joining it is a good idea. It resolves the jobId through [[MatchmakingService]] `getServerByJobId` and returns `(ok, message, entry, reason)` — the entry is handed back because the caller cannot teleport without it: the directory is keyed on `privateServerId`, a reserved teleport needs the access code, and all that path ever had was a jobId. A lobby-to-lobby hop (following a friend who is idling in another Bounty server) has no directory entry and always passes. **That early-out tests "is this any match place", not "is this Redwater"** (2026-08-14) — with a third place the old comparison made the else-branch wrong rather than merely incomplete, since every match place is reserved-only and a Frostbite PlaceId waved through as a lobby hop would get a plain jobId teleport into a place that refuses it. The set is exported as `isMatchPlace(placeId)` for FollowJoinService, which asks the same question to choose between an access code and a jobId
5a. **A `"missing"` verdict is re-checked against the tutorial map before it is returned** (2026-08-13). A friend in the onboarding training run and a friend whose match died produce the identical empty directory lookup, because a tutorial server never publishes an entry at all — so both were told the match had ended, which for the tutorial is simply false and was reported live on 2026-08-11. On a miss (and only on a miss, so the ordinary path pays nothing) it asks [[MatchmakingService]] `isTutorialServer(jobId)` and, on a hit, answers `"tutorial"` with its own message. That distinction is what lets the caller stop retrying a server that will never appear, and lets TutorialDispatchService pick the player up
6. `listFriendsInMatches(player)` powers the panel: pages `Players:GetFriendsAsync` and intersects the result with the `members` rosters already carried on the directory entries. No per-candidate `IsFriendsWith` calls. Results are age-corrected (the entry can be up to a heartbeat old) and sorted by most time left
6a. **`GetFriendsAsync` pages 20 at a time, not 50.** The ceiling was 6 pages on the assumption of 50, so the banner only ever saw a player's first **120** friends — and since the API does not promise a stable page order, *which* friends it could see changed between sessions. That was the main server-side reason a friend genuinely in a match did not show up. The ceiling is now 50 pages, the loop still stops on `IsFinished` (so it costs nothing for ordinary friend counts), and hitting the ceiling warns
6b. The list is cached for 240s rather than 60s — a friend list barely changes inside one lobby visit, and the banner's freshness comes from the match directory, which is re-read every refresh anyway. It is also **prefetched on `PlayerAdded`**, so the paging happens behind the loading screen instead of under the banner's first refresh. A failed read backs off for 20s (the endpoint is usually rate-limiting) and keeps serving the last list it managed to read; the cache write is skipped if the player left mid-paging
6c. **`getJoinableUsers` is friends PLUS recent party members**, and both the banner and the join gate read it. Party membership is *not* friendship — nothing in the invite flow checks `IsFriendsWith` — so on friends alone a party of non-friends split by a partial teleport left the stranded member with no route to the others: invisible in the banner and refused by `joinFriend` even if they found them. The roster comes from [[PartyService]] `getRecentCompanions`, **not** from live party state, because a member who reached a match has already left this server and `PlayerRemoving` removed them from the party — being in a match is precisely what makes live party state unable to answer the question
7. `joinFriend(player, friendUserId)` re-verifies the relationship server-side — the client can send any UserId, so the list handed to it is not trusted. Either relationship authorises: a Roblox friend, or someone in the recent-companion roster. The companion check runs first because it is a local table read where `IsFriendsWith` is a yielding web call, and party membership is server-side truth here (the client never asserts it), so it is no weaker a signal. Then a **fresh** directory read, the gate, and a teleport with `TeleportOptions.ReservedServerAccessCode`
7a. **A party joins as a party, in one call.** `joinFriend` resolves the roster through [[PartyService]] `prepareGroupTeleport`, resolves the access code **once** via [[MatchmakingService]] `resolveAccessCode`, gives every member their own `pending` entry naming that same code, and teleports the whole roster in a single `TeleportAsync`. Before this the banner teleported only whoever pressed Join and silently left the rest standing in the lobby (found live 2026-07-31), and then had to fan out one call per member because `ServerInstanceId` is rejected outright by a multi-player `TeleportAsync` (*"InstanceId is not currently supported for multiple players"*). `ReservedServerAccessCode` carries no such limit, so the window in which the match could fill or die between members is gone rather than merely narrowed. A rejected group call falls back to the per-member fan-out behind a loud warn — the twin of PartyService's safety valve, and deletable on the same evidence
7b. **The destination is pinned and never re-picked.** Each member retries independently through the per-player `pending` table, but always at the access code resolved in `joinFriend`, so a straggler can only ever end up where the rest of the party went, or nowhere. A match whose access code cannot be resolved at all (an orphaned server) is refused up front with a warn rather than teleported at. The pending entry carries the group `teleportData` so `attemptTeleport` can attach it — that is what reconstructs the party on the way back to the lobby; a join with no teleport data is an ordinary direct joiner that Redwater resolves off the persisted profile. The access code is also written into that payload as `redwaterAccessCode`, which heals a server that never learned its own, and **the target's user id as `friendUserId`** (2026-08-29), which is what makes a team gamemode seat the arrival on that player's side instead of the smaller one — without it the banner's promise was a coin flip. It is stamped on the payload the whole roster travels with, deliberately: a party joining a friend all want the same side, and the party rule keeps them together from the first member onward whatever the friend seat can take
8. Retries up to twice with its own `TeleportInitFailed` handler, backing off longer on `Flooded`/`GameFull`/`IsTeleporting`. Three modules now connect to that event (PartyService, FollowJoinService, this one) and each ignores players it did not send — this one keys on its own `pending` table
9. **The hard cap must equal the place's Maximum Visitor Count (10).** Redwater's Access settings are the real ceiling; if `SOLO_PLAYER_CAP + FRIEND_SLOTS` ever exceeds it this module admits a player Roblox then rejects with `GameFull` and the friend slots become fiction. Roblox's native **Social Slots** is now a **no-op** — Redwater runs on reserved servers, so Roblox's matchmaker never places anyone there and has nothing to reserve. No Creator Hub change is needed; leave Maximum Visitor Count at 10. The friend slots are real because *this* code is the only door and it counts
9a. **The `FALLBACK_HARD_CAP` constant, and why it is not `cap + 3`.** The malformed-entry fallback used to be written that way and landed on 10 by two cancelling errors: `cap` is the matchmade **party** ceiling (7), a seat below the solo ceiling the friend slots actually sit on, and `FRIEND_SLOTS` is 2, not 3. It is now stated as the one number it is — `SOLO_PLAYER_CAP + FRIEND_SLOTS` = 10 — next to that sentence, rather than rebuilt out of the wrong half of the pair
10. Clears its friend cache, failure backoff, refresh throttle, and pending entry on `PlayerRemoving`
