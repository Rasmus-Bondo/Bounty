# MatchmakingService

Chooses which match server a party is sent to — and, on a fresh reservation, which map. Roblox never chooses either.

## What it does
1. Reads the MemoryStore sorted map that every match server publishes itself into (`MatchDirectoryService`, carried byte-identical by Redwater and Frostbite) and hands PartyService a reserved-server **access code** for `TeleportOptions.ReservedServerAccessCode`. A Roblox server cannot refuse matchmaking, so every join rule is enforced here, at the sending end
2. **Reserved servers, since 2026-08-03.** The old scheme passed a jobId as `TeleportOptions.ServerInstanceId` and, when nothing was open, left it blank and let Roblox pick. That blank was a second entrance nobody controlled, and at launch population "nothing is open" was the common case — so Roblox filled matches that were seconds from shutting down, ignored a join lock it had never heard of, and ate the friend slots. Roblox's matchmaker cannot reach Redwater at all now; there is exactly one way in and this module is it
3. `chooseDestination(partySize)` returns `(accessCode, privateServerId, kind, placeId, mapId)`:
   - `code, id, "existing", placeId, mapId` — an open match with room; teleport straight into it
   - `code, id, "new", placeId, mapId` — nothing was open, so a fresh server was reserved
   - `code, id, "unavailable", placeId, mapId` — the directory could not be read; a fresh server was reserved anyway, since failing closed means nobody joins anything
   - `nil, nil, "failed", nil, nil` — `ReserveServer` itself failed. The caller retries or tells the player; there is no unmanaged destination left to use

   `placeId` is not a convenience (2026-08-14): an access code is only valid against the place it was reserved on, so a caller keeping its own destination constant would, the first time a party routed to a second map, teleport them at Redwater holding a Frostbite code — a bare teleport error naming nothing. It is returned rather than looked up because only this function knows whether the answer came from an entry's map or from the roll inside `reserveFreshServer`
4. **`ReserveServer` is called explicitly, never `ShouldReserveServer = true`.** They look equivalent and are not: the server Roblox would create has an access code known to *nobody*, and a reserved server cannot read its own — that match becomes a permanent one-party island no second player can ever join
5. **The access code round-trips, and losing it strands a whole server.** On reserving, the `privateServerId → accessCode` pair is written to the `RedwaterAccessCodes_v1` hash map and cached in-process; the match server publishes its entry under the same `privateServerId`; `resolveAccessCode(entry)` joins the two on read, preferring the entry's own copy and falling back to the map. A server that has neither is skipped with a loud warn — it is not broken from the inside, it simply never fills. **This write is duplicated in the match places' MatchDirectoryService `registerAccessCode`** (2026-08-14, spec §9.4): the map-vote move path reserves from inside a match, with no cross-place RPC to hand the write back here, so key, value shape and TTL must change in both copies together
6. **Solo players get a seat parties cannot have.** `ceilingFor(entry, partySize)` returns `entry.soloCap` (8) for a lone player and `entry.cap` (7) for a party. Parties are *seeds*: one turned away from a nearly-full match starts a new one, which is exactly the half-full match the next solo needs, and a denied party still has a fine game. A denied solo gets 1 human and 4 bots — the worst experience the game produces, and one that scores ~0 RP against a bot-padded field
7. Candidate filtering, all sourced from the entry itself so Redwater's Config stays the single source of truth: skip the wrong map (see 7a), skip stale entries (older than 25s), skip blocklisted, skip `closing`/not-`open`, and require `ceiling - players - pending >= partySize` since a party is never split
7a. **The map filter, and where "absent means redwater" is decided** (2026-08-14). Every match place publishes into this one directory, so an entry being open and this lobby being able to reach it stopped being the same question — without the filter a party is packed into a Frostbite match and then teleported to Redwater with a Frostbite access code. `isRoutableMap(entry.map)` asks [[MapCatalog]] for the row and requires `row.live` **and** a resolvable `placeIdFor` — a map can exist, be retired from rotation, or fail to resolve in this environment, and all three are "do not route there". The absent-map default (`LEGACY_MAP = "redwater"`) lives in **`readServers` and nowhere else** — normalising on read means `chooseDestination`, `listServers`, `getServerByJobId` and every FriendJoinService path through them see a real string, instead of four copies of the defaulting rule drifting apart. Absent can only mean Redwater, since no other match place had shipped before the field existed, and publishing does not update running servers
7b. **The map is rolled ONCE, on fresh reservation, and nowhere else** (2026-08-14 — a deliberate deviation from spec §9.2's literal wording, flagged and accepted). `reserveFreshServer` rolls `MapCatalog.randomLiveId()` and reserves on that map's place; `chooseDestination` never filters candidates against a fresh roll. Rolling first and then filtering to the roll would walk past a busy Redwater match to seed an empty Frostbite one — packing must win. The live population stays uniform anyway, because every server in the directory was created by this roll
7c. **The region filter, and why it is the one rule here that refuses to pack** (2026-08-15). `chooseDestination` takes the group's latency bucket from RegionService and `isRegionMatch` drops every candidate outside it. There is no cross-region fallback anywhere: "nothing local is open" ends at `reserveFreshServer`, never at a distant match. Every other rule in this module exists to pack players together; this one deliberately splits the pool, at the user's explicit instruction that a bot-padded local match beats a full one at 300ms. The cost is affordable only because it is a **seeding** cost rather than a per-player one — the server the first player in a region seeds is where the next one lands, and with `lockSeconds` at 0 and servers looping rounds it stays a valid destination for a long time. A region too thin to ever produce a second concurrent player plays bots forever, which is the accepted downside
7d. **Absent on either side means "no opinion" and routes freely.** Two ways that happens and both are permissive on purpose: an entry from a server generation predating the field (the same rollout window `map` has), and a player whose country lookup failed. The second is the load-bearing one — refusing there would spend a bot match, the exact cost the filter exists to justify, on an outage on our own side, and a global `GetCountryRegionForPlayerAsync` failure would turn the whole game into bot matches. Unlike `map`, the absent case is **not** normalised in `readServers`: there is no meaningful default for a region, only "unknown"
7e. **The region is written on reservation, to its own MemoryStore map.** `reserveFreshServer` writes `privateServerId → region` into `RedwaterServerRegions_v1` and stamps it on the provisional entry; the match server reads it at boot and republishes it on every entry. It is a **separate map** from `RedwaterAccessCodes_v1` deliberately — that map's value is a bare string on every normal reservation and `resolveAccessCode` type-tests for one, so widening it to a table would break access-code resolution on every lobby still running the previous build, i.e. friend joins into fresh matches for one lobby generation after every deploy. **The load-bearing assumption:** `ReserveServer` does not create the instance — Roblox allocates it near whoever joins first, which is the reserving party — so the reserving party's region *is* the server's region. That is standard observed behaviour, is not documented, and cannot be verified from Studio; the `MatchPing` telemetry exists to show whether it holds
7f. **A second copy of these predicates lives in the MATCH places** (2026-08-27, SERVER_CONSOLIDATION_SPEC §5). `MatchDirectoryService` duplicates `isRoutableMap`, `isFresh`, `isRegionMatch`, `acceptsMatchmaking`, `ceilingFor` and the pending / access-code readers, plus `ENTRY_MAX_AGE`, `PENDING_TTL`, `RANGE_COUNT`, `PENDING_PROBE_LIMIT` and `PROVISIONAL_TTL`, because the end of a round became a routing decision taken from inside the match — dissolve the roster into a fuller server, or rotate to a sibling place — and there is no cross-place RPC to hand that decision back here. Same precedent `registerAccessCode` set at item 5. **Both copies carry a comment naming the other; change one, change the other.** The **ceilings** are deliberately not duplicated: they ride on the published entry, so neither side holds a number that can drift from the match place's Config. Extracting a shared `MatchRouting` module was rejected — it is the right shape if a third caller appears, but it means refactoring this path to ship a behaviour change that does not need it. Nothing in this module's behaviour changed for it; the only edit here is that comment
8. **The join lock is off** (2026-08-12). `acceptsMatchmaking` only applies a time rule when the entry publishes `lockSeconds > 0`, and Redwater's `Config.JOIN_LOCK_SECONDS` is now 0, so the tail of a fight is a valid destination. When the lock *is* on, the rule is re-applied here against the entry's **age** — which is also why turning it back on turns away more servers than the number reads: an entry may be up to 25s stale, so its published `secondsLeft` can "run out" for a fight that has already looped into the next round. `DEFAULT_CAPS.lockSeconds` (0) applies only on a lobby that has never seen a live Redwater entry
9. Prefers the fullest match a party still fits into (tie-break: most time left), so players end up together rather than scattered across half-empty servers. Deliberately has **no floor on time remaining**: a 7-player match with seconds on the clock outranks a 3-player one with minutes, because servers loop rounds and landing in a busy lobby's intermission beats an empty match. `JOIN_LOCK_SECONDS` is 0, so the tail of a fight is a valid destination
9a. **QUICKPLAY (2026-08-27) — the one selection that does not narrow the candidate list.** `MatchmakingService.QUICKPLAY_ID` (`"quickplay"`) is the lobby's default and is **not a gamemode**: it is a routing instruction that says "pack me into the fullest open match on any live map in ANY mode, and roll something new only if nothing is open". It drops the mode test at item 7 and nothing else — map, region, freshness, blocklist and capacity all still apply, because those are about deliverability where the mode test is about preference. It exists because the picker splits the matchmaking pool three ways once Domination ships, and at low population three thirds of a small number is three matches nobody wants to be in
9b. **The sentinel never leaves this module.** Every value handed back names a real mode: an existing match answers with `entry.mode`, and a fresh reservation with the roll inside `reserveFreshServer`, which is where `quickplay` stops existing — the map roll, the access-code record the match server reads at boot and the provisional directory entry are all written with a real id. `freshDestination` and the directory-unreadable branch take the resolved mode off `reserveFreshServer`'s return rather than the argument they were handed, which is the whole reason that return value exists. Redwater's `setGamemode` would warn and fall back to deathmatch if the sentinel ever did arrive, so the failure mode is soft — but it would be a silent wrong mode, not an error
9c. **The fresh-server mode roll is weighted 20 deathmatch / 40 tdm / 40 domination**, per `QUICKPLAY_WEIGHTS`, and is the only place in the experience where a gamemode is chosen FOR a player. Not uniform, at the user's instruction: deathmatch is the mode a lone player still enjoys against a bot-padded field, so it needs the least help, while the team modes are only worth playing with a population and this roll is what decides whether that population ever forms. A weight row is dropped when its id is not a GamemodeConfig row **or** no live map runs it — either leaves it pointing at something no server can run — and an empty eligible set falls back to `LEGACY_MODE` with a warn. **The weights govern SEEDING only.** Packing ignores mode entirely under QuickPlay, so the live split drifts from 20/40/40 toward whatever is already busy; that is the intended behaviour, not a fault. Weights live here rather than on the GamemodeConfig row because that module is mirrored verbatim into the match places, which have no business knowing how the lobby seeds
10. Slot reservation: on selection it increments a per-`privateServerId` counter in a separate short-TTL hash map via `UpdateAsync`. Without it, every lobby server picking "the fullest match that fits" at the same moment would pile into the same one. `releaseSlots` hands them back when a teleport fails; otherwise they expire on their own after 25s
10a. Reservations are a per-server request and this runs on the **Play button**, so the candidate list is built first from arithmetic alone (no requests, however many servers are live), sorted, and only then probed for reservations in preference order — stopping at the first that still fits, and at most `PENDING_PROBE_LIMIT` (5) deep. If all five were claimed out from under it, it falls through to reserving a fresh server
11. **A just-reserved server is advertised on its behalf.** It does not appear in the directory until it boots and publishes, which is several seconds — and a burst of Play presses falls entirely inside that window, so without this every solo press with nothing open would reserve its *own* server. Under the old blank teleport Roblox packed those players; nothing does now unless we say the server exists. A provisional entry (`provisional = true`, `map` = the id `reserveFreshServer` rolled, `players = 0`, `jobId = ""`, 30s TTL, sortKey 0 so it sorts behind real matches) is written under the new `privateServerId` and its slots claimed. The match server overwrites it on the same key the moment it publishes for itself
11a. The provisional entry needs ceilings it has no server to ask, so `lastSeenCaps` is refreshed from every real entry read and `DEFAULT_CAPS` covers a lobby that has never seen a live Redwater server. **These constants are the module's one copy of Redwater's numbers** — everything else reads them off the entry
12. A 2s cache smooths bursts of Play presses and the friends-banner polling, and is invalidated the moment a reservation is made so this server's own claim is visible to its next lookup
12a. `reportBadServer(privateServerId)` blocklists a server for 60s. A server can die without withdrawing its entry (a crash leaves it in the directory until the TTL expires); PartyService's retry reports whatever it just aimed at, so the next pick cannot re-pick the same corpse
12b. **The blocklist is a matchmaking rule only** and is applied in `chooseDestination`, not in `isFresh`. It used to be folded into `isFresh`, which also hid those servers from `listServers` — so a `GameFull` or `Flooded` failure against a perfectly healthy match dropped it out of the friends banner for a minute and made a friend join answer *"your friend's match has already ended"*. Freshness is a property of the entry (its age); whether *we* just failed a teleport into it is not
13. `getServerByJobId(jobId)` linearly scans a fresh `listServers` read for a matching `jobId`. `GetPlayerPlaceInstanceAsync` — the only way to find the server a friend is in when someone taps Join in the Roblox app — answers with a *job* id, which is neither the directory key nor what a teleport uses. Without this scan every app-initiated friend join fails with "your friend's match has already ended", which is a lie
13a. **`isTutorialServer(jobId)` is the second answer for when that scan misses** (2026-08-13). A tutorial server is deliberately absent from the directory — Redwater's `writeEntry` fails closed on it — so a friend in the training run and a friend whose match had died produced the same empty lookup and the same wrong message. It reads `RedwaterTutorialServers_v1`, a hash map of `jobId → true` published by Redwater's MatchDirectoryService, and is called **only after `getServerByJobId` has already missed**: one keyed read, not a scan, on the one path that holds a jobId and nothing else. Deliberately **not** folded into `listServers` — every destination decision reads that, and a tutorial server has to stay unreachable to all of it. An unreadable map answers "no", which costs the old wrong message rather than inventing a tutorial that is not there
14. `listServers(fresh)` returns every live match, for the friends banner in FriendJoinService. **Deliberately not filtered by map**, unlike `chooseDestination`: "no entry" and "an entry we refuse" are different answers and only the second can be explained, so dropping other maps here would make `getServerByJobId` miss and reproduce the "your friend's match has already ended" lie the tutorial marker exists to prevent. The refusal belongs where it can be worded, in FriendJoinService `evaluateEntry`
15. Uses a `_studio` map-name suffix under `RunService:IsStudio()`, matching the Redwater side: Studio talks to the production MemoryStore, so the two pools must not mix
16. **`reserveTutorialServer()` (onboarding tutorial, 2026-08-09) — its own path, deliberately NOT `chooseDestination`.** Reserves a private Redwater server and writes a `{ code, tutorial = true }` **table** (not the normal bare string) into `RedwaterAccessCodes_v1` — the boot-time signal Redwater's MatchDirectoryService fails closed on — and, critically, publishes **no provisional directory entry** and claims no slots: a tutorial server must be invisible to matchmaking from before it boots. Returns `(accessCode, privateServerId)` or nil; the caller (TutorialDispatchService) keeps the player in the lobby on failure
