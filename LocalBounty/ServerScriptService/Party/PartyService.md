# PartyService

Server-side party system handling invites, membership, character selection, and teleportation to Redwater Canyon.

## What it does
1. Creates/manages RemoteEvents: PartyInviteEvent, PlayTeleportEvent, CharacterSelectEvent
2. Handles party actions: SendInvite, AcceptInvite, DeclineInvite, KickPlayer, LeaveParty, RequestPartyState
3. Enforces max party size of 4 and owner-only invite/kick permissions
4. Validates character selections against ReplicatedStorage.Characters folder structure
5. Syncs party state to all party members via FireClient "PartyUpdated"
6. Teleports party (or solo player) to the match place via TeleportService, attaching group ID, member list, and character selections via `TeleportOptions:SetTeleportData()` for groups of 2+. **The destination server — and since 2026-08-14 the destination PLACE — is chosen by [[MatchmakingService]], not by Roblox:** `chooseDestination(#playersToTeleport)` returns `(accessCode, privateServerId, kind, placeId, mapId)` — either an open match or a freshly reserved server, and the access code is set as `TeleportOptions.ReservedServerAccessCode`. The destination is no longer a constant: a reserved access code is only valid against the place it was reserved on, so every dispatch site uses the PlaceId of the choice it just made, every pinned/remembered destination stores it (`pinnedPlaceId`, `lastDispatch`, `initFailBatches`), and the `TeleportInitFailed` guard recognises its own teleports via `isMatchDestination(placeId)`, which walks the whole [[MapCatalog]] — a teleport in flight to a map taken out of rotation a moment ago is still ours. **There is no blank fallback any more** (2026-08-03): Redwater runs on reserved servers, so a blank destination is not "plain Roblox matchmaking", it is nowhere. `kind == "failed"` means even `ReserveServer` failed, and the press retries and then fails honestly. Every attempt re-picks and builds a **fresh** `TeleportOptions` via `buildTeleportOptions`, since an options instance handed to `TeleportAsync` must not be reused; a failed attempt calls `releaseSlots` to hand the reservation back early. `buildTeleportOptions` also copies the access code into the teleport data as `redwaterAccessCode`, because a reserved server cannot read its own and learns it from the first arrival. The routing decision is **warned** once per Play press — a warning rather than a print so it aggregates on the Creator Hub Errors page across every live server, where the `routed into an open match` vs `no open match` ratio measures whether the join gate is actually holding. The warning text is a **fixed string per outcome**, since that page groups by exact message and an interpolated jobId would produce one row per server; the variable detail goes to a `print` alongside it for the F9 console
6a. Fires `TeleportQueued` to all party members just before TeleportAsync, and `TeleportFailed` via PlayTeleportEvent on final failure or early-exit (non-owner, empty party). `TeleportAsync` is retried up to 3 times (2s apart, dropping players who left between attempts) before giving up. A `TeleportService.TeleportInitFailed` handler additionally retries up to 2 more times (5s backoff on `Flooded`, 2s on `Failure`/`GameFull`), covering teleports that were accepted but failed to initiate. Retry counters live in `teleportRetryAttempts`, reset on each Play press and cleared on PlayerRemoving; a **nil** counter is the ownership guard that makes this handler ignore teleports it did not start, since FollowJoinService and FriendJoinService also send players to Redwater and re-routing those would drop someone into a random match instead of the friend they were joining
6d. **`dispatchTeleport` sends the whole party in ONE call.** It used to be one `TeleportAsync` per member, and the split was not a style choice: `TeleportOptions.ServerInstanceId` is **rejected outright when TeleportAsync is handed more than one player** — the call throws *"InstanceId is not currently supported for multiple players"*. Nothing in the TeleportAsync or TeleportOptions reference documents this; their only stated group limits are "same experience" and "50 players". So from the day routing shipped, **every** party of 2+ matched into a live server failed all three attempts on it, silently, while solo presses and friend joins — one player at a time — worked fine, which is exactly the shape the reports had. `ReservedServerAccessCode` carries no such limit (it is the standard "send my party to a private server" pattern), so the fan-out is retired and a party **cannot be split by a partial dispatch** at all. That is what removed the `forceDestination` latch and the `partyDestinations` `sent` bookkeeping with it
6d-i. **The safety valve.** Multi-player `TeleportAsync` accepting an access code is the one unverified assumption in the reserved-server switch — it cannot be tested from Studio, so the first live party-of-2 Play press is the test, and this API surface has already lied once undocumented and silently. So a rejected group call falls back to the old per-member fan-out (spawned in parallel, joined on a completion count with a `PARALLEL_DISPATCH_TIMEOUT` (20s) ceiling so one wedged call cannot hold the press open) and **warns loudly** rather than swallowing it. `dispatchTeleport` returns `(ok, err, failedPlayers, usedValve)`; `usedValve` is the caller's signal to pin. Marked for deletion once verified live
6g. **A party is never split by a retry.** A group teleport is all-or-nothing, so an ordinary failed attempt means *nobody* got in and re-picking cannot split anyone — that is why the loop is free to call `chooseDestination` fresh every attempt, and why `reportBadServer` on a total failure is safe. **Only the safety valve can produce a partial dispatch**, and when it does the destination is latched into `pinnedAccessCode` and every remaining attempt goes back to that same match, with no re-pick and no blocklist call. `lastDispatch[groupId] = { accessCode, privateServerId, kind, valve }` carries the same knowledge to the `TeleportInitFailed` retry, which otherwise sees only a Player and a `TeleportOptions` — the options hold the access code, while the blocklist and the slot reservations are keyed on the `privateServerId`. **Deliberate trade, unchanged:** a straggler who cannot reach their party's match exhausts its retries and gets "Teleport failed. Please try again." rather than being silently placed in a different one
6j. **`prepareGroupTeleport(player)` is how a caller outside this module sends a whole party somewhere.** Returns `(players, teleportData)` or `(nil, nil, message)`, resolving the roster under the **same owner-only rule the Play button uses** — a non-owner dragging everyone else into a match is exactly what that rule prevents — and recording the companions on the way through. FriendJoinService uses it so the friends-in-match banner takes the party along instead of teleporting only whoever pressed Join. It mints **no** MatchLoop funnel ids: those belong to the Play button's funnel and folding friend joins in would change what that metric measures. It does carry `groupId`/`members`, which is the point — without them a party that joined this way returns to the lobby as unrelated strangers
6i. **`getRecentCompanions(player)` is the public record of who someone last pressed Play with**, `{ [userId] = name }`, written once per press from the full roster (parties of 2+ only) and expiring after `RECENT_COMPANION_SECONDS` (900s, longer than a Redwater round). It exists because `PlayerRemoving` calls `removeUserIdFromAnyParty`, so the instant a party teleports out the party is gone from this server — live party state can *never* answer "is someone from my party in a match", since being in a match is what removes them from it. FriendJoinService reads it to authorise a join and to list party members in the banner, which matters because nothing in the invite flow requires friendship
6h. **`GameEnded` and `GameNotFound` are retryable.** Both are only reachable by naming a specific instance, so they mean "that jobId is stale", not "teleporting is impossible" — yet they used to fall through to the give-up branch, ahead of the whole fallback ladder. 11 live *"Giving up on teleport for &lt;Player&gt; - Could not find requested game instance"* on 25 Jul came through exactly there
6f. **Every retry path now ends on a freshly reserved server rather than on a blank teleport.** A routed teleport can still die because the match filled (`GameFull`) or because it no longer names a live server (*"Could not find requested game instance (GameEnded)"*, seen live on 25 Jul), and the old ladder's last rung was a blank `ServerInstanceId` — the one destination Roblox cannot refuse. That rung is gone with reserved servers, and its replacement is `ReserveServer`: `chooseDestination` reserves rather than returning nil, including when the directory is unreadable, because failing closed means nobody joins anything. Both paths still report the refusing server to [[MatchmakingService]] `reportBadServer` (60s blocklist) before re-picking; the Play-press loop previously called it **only** from the init-failed handler, so its own retries re-ran `chooseDestination`, got the same unblocked server back, and burned all three attempts on one dead match
6e. **A failed party teleport is retried as a party.** `TeleportInitFailed` fires once per **player**, so one failed teleport still arrives as one event per member even though it went out as a single call; retrying each separately re-runs the destination lookup per player and scatters the party across whatever server each lookup happens to pick. Members are collected into `initFailBatches`, keyed on the `groupId` every member was sent with, debounced by the backoff itself (re-armed to the longest any member asked for) and re-teleported together. A solo Play press has `groupId == its own UserId`, so it forms a batch of one and behaves as before. `retryGroupTeleport` re-picks when the group went out as one call (nobody got in) and **pins** when `lastDispatch.valve` says the safety valve fanned them out. There is no `forceBlank` rung left. `buildTeleportOptions` also skips `SetTeleportData` when the carried-over data is nil, which `GetTeleportData()` can return and which the setter rejects
6c. `buildTeleportData` also attaches `weaponSkinSelections[userId] = { [hunter] = equippedGunSkin }`, read off the `EquippedWeaponSkin_<Hunter>` attributes [[DataService]] mirrors from the profile. Driven by a local `DEFAULT_WEAPON_SKINS` table covering **all four** hunters (`DefaultRevolver`/`DefaultCard`/`DefaultSniper`/`Grudgekeeper`, a mirror of DataService's profile-template defaults) — it used to hardcode Dust and Fortuna only, so Vesper's and Bram's gun skins could never physically reach Redwater. Redwater now re-reads the same fields from the shared profile on every spawn (`HunterSelectionService.RefreshWeaponSkinsFromProfile`), so a gap here is a redundancy loss rather than a bug — but the payload is still expected to be complete
6b. Right after validation passes (non-owner/empty-party early-exits cleared) and before the teleport attempt, logs step 3 "Clicked Play" of the onboarding funnel for every player about to be teleported via [[DataService]] `tryLogFunnelStep(partyPlayer, 3, ...)` — fires `AnalyticsService:LogOnboardingFunnelStepEvent` **at most once per player, ever** (persisted de-dup)
6l. **QUICKPLAY is admitted alongside the GamemodeConfig rows (2026-08-27), and it changes where the mode is decided.** `tryStartPartyTeleport` validates the picker's id against the registry and collapses anything unrecognised to the default; `MatchmakingService.QUICKPLAY_ID` has to be named explicitly in that test or the lobby's **default** selection folds into deathmatch and the feature is silently gone. Because the real mode is then chosen inside `chooseDestination`, `teleportData.gamemode` is no longer written once before the retry loop — it is **re-stamped per attempt** from the resolved mode the call returns (its 6th value, previously discarded). That field is the backup a fresh server reads when its reservation record write was lost, so a stale one boots that server as the wrong mode. The pinned/valve rejoin branch deliberately leaves it alone: that destination resolved its own mode on an earlier attempt and part of the party is already standing in it
6m. **The retry paths carry what the party ASKED for, not what it got.** `lastDispatch[groupId].requestedMode` is the original picker id, and `retryGroupTeleport` re-picks off it — falling back to `teleportData.gamemode` only when the dispatch record is gone, which is right but narrower than the press. Without it a QuickPlay party that hits `TeleportInitFailed` would be pinned to whichever mode the dead server happened to be running, and would seed a fresh server of that mode rather than pack into an open one. `retryGroupTeleport` writes `requestedMode` back into `lastDispatch` for the same reason: a **second** bounce would otherwise lose it. Safe on this branch because a group teleport is all-or-nothing — nobody got in, so there is no partial party a mode change could split. The retry also re-stamps `batch.teleportData.gamemode` from its own re-pick, but only when the batch already carries data; with none, the server reads its reservation record, which is the primary source anyway
6k. **`isInParty(player)` is the read-only membership export**, added 2026-08-17 for services outside this module that have to refuse an action a party cannot take. TutorialReplayService is the only caller: a tutorial server is reserved solo and its TeleportData carries no `groupId` and no `members`, so there is no shape of that teleport that brings a party along, and the honest answer is to refuse rather than strand the rest of the party in the lobby. It delegates to the same private resolver `isPartyOwner` and the invite rules use, so a **reconstructed** party — one rebuilt from TeleportData by item 7 rather than assembled by invite — counts exactly the same
7. On PlayerAdded, reads `player:GetJoinData().TeleportData` to reconstruct groups returning from a gamemode — restores party membership, character selections, and promotes a new owner if the original owner disconnected. Reconstruction is resilient to staggered arrivals (players who left Redwater early at different times): whenever a returning player creates a reconstructed party, `reattachPresentGroupMembers` immediately pulls in any group members already on the server who are party-less; and if a returning member finds the original owner on the server after the pending window expired, they join the owner's current party directly (or recreate it if the owner is party-less — but never if the owner joined someone else's party). Party state syncs to clients immediately on every reconstruction change, not just at window expiry
8. Uses a 10-second restartable sync timer (`PENDING_GROUP_SYNC_SECONDS`) to close out group reconstruction; at expiry it clears all pending entries for the group, syncs parties, and **disbands any reconstructed party that still has 0 members** — previously such "ghost" solo parties lived forever and blocked invites to that player ("already in a party")
9. Cleans up invites, party membership, and pending group data on PlayerRemoving
10. Defaults all players to Dust/Default/DustDefault character selection
11. Fires `PartyInfo` (neutral) events for: invite sent confirmation, member left/disbanded notifications to remaining members, kicked-member name visible to remaining members
12. Fires `PartyMessage` (error) events for: party full, target already in party, non-owner invite attempt

## NewPlayer funnel (step 5)
Fires `Telemetry.logJourneyStep(player, 5)` — "Queued For Match" — immediately alongside onboarding step 3 "Clicked Play", and again in `prepareGroupTeleport` so a friend join counts as queuing too. That second site is a change from the funnel this replaced: `MatchLoop` measured the Play button specifically and deliberately excluded friend joins, whereas `NewPlayer` measures whether a new player reaches a match **at all**, and a first-timer who finishes the lesson and then taps a friend rather than PLAY would otherwise stall at step 4 having actually played. Over-firing is safe by construction — Telemetry's gate refuses any step whose predecessor did not fire.

**`buildTeleportData` no longer carries funnel ids.** `MatchLoop`'s per-player `matchFunnelIds` map (`{ [tostring(userId)] = guid }`) existed only so Redwater could continue the same recurring funnel session across the teleport; `NewPlayer` keeps its session id on the profile, which both places read through the same `PlayerData_v2` key, so nothing rides in `TeleportData` and the `TeleportInitFailed` retry path has nothing to preserve. Its old step 2 "Teleport Started" is gone with it: the drop it exposed — a clean `TeleportAsync` return that still dies on `TeleportInitFailed`, indistinguishable from lost interest without a step in between — is now the gap between step 5 here and step 6 on arrival in Redwater.
