# DataService

Manages player data loading, saving, and leaderstats using ProfileService. Also handles server-authoritative skin purchases and equip persistence.

## What it does
1. Defines a profile template with Cash, Tokens, Level, XP, LifetimeKills, LifetimeDeaths, TotalPlaytime, OwnedSkins/Characters/WeaponSkins, EquippedCharacter/Skin, `EquippedTitles` (equipped cosmetic title **id per hunter** — `{ Dust, Vesper, Bram, Fortuna }`, `""` = none; read/written by CollectionService) + `OwnedTitles` (`{[titleId]=true}` — titles the player BOUGHT with Cash/Tokens; battle-pass titles are recorded in `Cosmetics.Titles` instead and CollectionService treats both as owned), `EquippedEmote` (single account-wide emote id, defaults to `electro_swing`; legacy `""` migrated to the default on join by CollectionService) + `OwnedEmotes` (`{[emoteId]=true}` beyond the EmoteConfig defaults) — both read/written by CollectionService and read by Redwater's RoundController, Quests, Settings (empty sub-table backfilled by `:Reconcile()` so PlayerSettingsService can read/write it)
2. Profile template also includes battle-pass fields backfilled via `:Reconcile()`: `BattlePass` (seasonId/xp/level/ownsFullPass/claimed/quests — season-scoped, managed by BattlePassService), `Cosmetics` (Titles/Emotes/Charms/KillEffects/HunterSkins/GunSkins — persistent inventory), and `Boosts` (`{ Inventory = {[boostId]=count}, Active = {xp=…, cash=…} }` — boost consumables plus the currently-running boost per kind; catalog in BoostConfig, activated/ticked by Redwater's BoostService). Also the daily play-streak fields `DailyStreak` / `DailyLastPlayDay` / `DailyPending` (unclaimed reward queue) / `DailyPermaBoost` (passive +10% flag) — advanced in Redwater on round finish and **claimed here** by DailyRewardService
2a. Profile template also carries `Settings.AbilityDescriptions` (`"On"` / `"Default"` / `"Off"`, default `"Default"`) — how Redwater's hunter ability tags behave. The lobby has no ability HUD of its own, so nothing here reads it, but it **is** writable from this place's settings panel via PlayerSettingsService, and the key lives in this template so both templates of the shared `PlayerData_v2` profile stay aligned. This replaced a `SeenHunterIntro` set; `:Reconcile()` only ADDS keys, so older profiles keep a dead table that nothing reads
3. Store name is `PlayerData_` .. `DATA_VERSION` (currently "v2"); **bumping `DATA_VERSION` wipes ALL player data universe-wide** — the release-reset lever. Must match Redwater's DataService
4. Loads player profiles via ProfileService on join, kicks on failure
3. Creates leaderstats (Cash, Level) and PlayerStats (XP) folders on the player
4. Fires `SkinDataEvent` to client after profile loads so the Collection screen can populate owned/equipped state
4b. Handles `RequestSkinData` — the **pull half** of the skin-data handshake. `fireSkinData` is a one-shot `FireClient` sent the instant the profile loads, and a RemoteEvent fire that lands before the client has connected `OnClientEvent` is dropped for good. The Collection menu was once a single ~3500-line chunk that connected its handler at the very bottom, and [[HuntersBuyController]] is ~2200, so on a live server the join push routinely beat their handlers (the Collection side now connects in [[State]], ahead of all grid construction, precisely for this), leaving `ownedSkins` empty for the whole session: **owned skins rendered LOCKED while the equipped hunter/skin still read correctly**, because those come from replicated player attributes (state) rather than from this remote (a transient message). Hunter ownership was masked by the `Owns<Hunter>` attribute fallback; skins have no such fallback. The handler **waits up to `SKIN_DATA_REQUEST_TIMEOUT` (20s) for the profile to load** rather than replying empty — a request arriving before the profile is the normal case, not the exception. It also debounces per player (`SKIN_DATA_REQUEST_COOLDOWN`, 0.5s), but **the debounce suppresses only the second 20s waiter, never the payload**: a rate-limited request still gets a `fireSkinData` whenever the profile is already loaded. Withholding it was a second, distinct instance of the same lost-ownership bug — **THREE** independent client scripts pull this remote on startup ([[State]], [[HuntersBuyController]], [[CollectionClient]]) and the debounce is keyed per *player*, so the server cannot tell them apart. `State` is always the last to connect, because the Collection menu's `Refs` blocks on the boost/emote/title remotes ahead of it. An earlier script's request was therefore answered while `State` was still deaf (a push with no listener is dropped for good), and then `State`'s own request landed inside the 0.5s window and was discarded — nothing ever arrived, ownership stayed empty for the whole session, and every owned hunter skin **and** gun skin rendered as PURCHASE (both `EquipButton` labels short-circuit on the same `isHunterOwned(...) and isSkinOwned(...)` test). When the profile genuinely is not ready, the in-flight waiter sends as soon as it lands, and whoever was turned away is connected by definition. The companion fix is the start-order change in `Main`, which stops `Refs` being blocked for most of server boot in the first place. Every other join-time state push in Bounty already had a `Request*` companion (`RequestQuestDataEvent`, `RequestBoostState`, `RequestTitleState`, `RequestEmoteState`, `RequestDailyReward`, `RequestMultiplierState`, `RequestBattlePassDataEvent`, `PlayerSettingsRequest`); `SkinDataEvent` was the only one without
5. Handles `PurchaseSkinEvent`: validates cash against server-authoritative `SKIN_PRICES`, deducts cost, writes to `OwnedSkins`, fires `SkinDataEvent` back to client
5b. On profile load (`onPlayerAdded`, between `sanitizeEquippedSelection` and `fireSkinData`), `grantGroupSkins` checks `player:IsInGroup(GroupPerkConfig.GroupId)` — `647193849`, the Outlaw Syndicate creator group (`game.CreatorId`). Members get every skin in `GroupPerkConfig.Skins` written into `OwnedSkins` — currently **Dust `Wraith`** — as a **permanent** free unlock: it persists even if the player later leaves the group, and the check re-runs each join (idempotent) so joining the group later still grants it. No Wallet/economy event (free grant, not a currency transaction); the existing `fireSkinData` push then surfaces it as owned in the Collection / Trading Post UI. `IsInGroup` is wrapped in `pcall` so a group-service hiccup never blocks data load — it now `warn`s on that branch (2026-08-12), because a silent return made "the service failed" indistinguishable from "not a member" and left a real member seeing the skin locked all session with nothing in the log
5c. **Group-perk skins are not for sale in any currency** — membership is the only way in. `isGroupUnlockSkin(characterName, skinName)` delegates to [[GroupPerkConfig]] (one source of truth, now client-readable too) and both purchase handlers reject a match: `PurchaseSkinWithTokensEvent` and `PurchaseSkinEvent`. `Wraith` was removed from `TOKEN_SKIN_PRICES` (it used to cost 400 Tokens), which alone blocks the token path — but the cash path needed the explicit guard, because `PurchaseSkinEvent` treats "absent from `TOKEN_SKIN_PRICES`" as "cash-purchasable" and would otherwise have fallen through to its 1000-Cash default price
5d. **Free skin grants for earned rewards.** `GrantHunterSkin(player, characterName, skinName)` and `GrantWeaponSkin(player, characterName, skinName)` unlock a skin without charging, then re-fire `SkinDataEvent` — both the Collection menu and the Trading Post read ownership from that payload rather than polling, so a grant that skips the resend leaves the tile LOCKED until the player rejoins. Idempotent. Used by BattlePassService `grantReward` for the season's skin rewards, by CodeRedemptionService for a code carrying a `weaponSkin` reward, and by BundleService for a Token bundle's cosmetics. `SkinGrantExists(kind, character, skinName)` (2026-08-29) exposes the same catalog predicates so a caller assembling several grants can check them all *before* it takes any money, instead of discovering a typo half way through and having to unwind a spend. `GrantHunterSkin` deliberately does **not** check hunter ownership: a player can earn a skin for a hunter they haven't bought (Fortuna's pass skin), and it waits in their inventory until they own her. `GrantWeaponSkin` re-guards the per-hunter sub-table because `normalizeWeaponSkinData` only seeds hunters listed in `DEFAULT_WEAPON_SKINS`
5e. **Battle-pass skins are not for sale either.** `PurchaseSkinEvent` rejects any skin matching [[BattlePassConfig]] `isExclusiveSkin(character, skin, "hunterSkin")` — same trap as the group perk above: absent from `TOKEN_SKIN_PRICES` reads as "cash-purchasable" and would fall through to the 1000-Cash default, selling the season's showpiece skins to anyone who fired the remote. The gun-skin path needs no equivalent guard because `PurchaseWeaponSkinWithTokensEvent` requires an explicit entry in `TOKEN_WEAPON_SKIN_PRICES`
5f. **Robux bundle cosmetics are not for sale either.** `PurchaseSkinEvent` rejects any skin matching [[StoreConfig]] `isBundleExclusive(character, skin, "HunterSkin")` — third instance of the same trap: a bundle skin lives in the ordinary catalog folder and is absent from `TOKEN_SKIN_PRICES`, so without the guard it reaches the 1000-Cash default and undercuts the Robux bundle. The check derives from the bundles' own `Grants` lists, so registering a new bundle covers it automatically — minus any grant flagged `SoldSeparately`, which is deliberately still for sale on its own (both LET THE HUNT BEGIN grants, 2026-08-29; the Cash sale of `FrostveilVesper` is refused anyway by its `TOKEN_SKIN_PRICES` entry). The weapon-skin half needs no guard, for the same reason as 5e
6. Handles `EquipSkinEvent`: validates the skin is owned (or is Default), writes to `EquippedCharacter`/`EquippedSkin`, fires `SkinDataEvent` back, then logs step 2 "Selected Hunter" of the onboarding funnel via `tryLogFunnelStep(player, 2, ...)` (only reachable from a genuine client equip action, not the on-join skin-restore path)
6a. Handles `EquipWeaponSkinEvent`: validates the gun skin exists in `ReplicatedStorage.WeaponSkins.<Hunter>`, the hunter is owned, and the skin is in `OwnedWeaponSkins`; writes `EquippedWeaponSkins[hunter]`, mirrors it onto the replicated `EquippedWeaponSkin_<Hunter>` player attribute, fires `SkinDataEvent` back. `DEFAULT_WEAPON_SKINS` seeds one default gun per hunter (Dust `DefaultRevolver`, Fortuna `DefaultCard`, Vesper `DefaultSniper`, Bram `Grudgekeeper`); `normalizeWeaponSkinData` grants **only the default gun** per hunter as owned. Non-default gun skins must be purchased and are **not** auto-granted; players keep any skin already saved in their `OwnedWeaponSkins` (existing free grants persist)
6b. Handles `PurchaseWeaponSkinWithTokensEvent`: validates the gun skin exists, is non-default, and has a price in server-authoritative `TOKEN_WEAPON_SKIN_PRICES` (Vesper's `Frostpiercer` at 400 since 2026-08-14; Dust's `Icefang`, Fortuna's `FrozenHand` and Bram's `FrostbiteGrudgekeeper` at 600 since 2026-08-21; Dust's `BetaRevolver` sat in that group until 2026-08-27, when it became code-only and came off the table entirely — the shop label alone does not stop a sale; Fortuna's `PrestigeCard` moved out of it when it became a limited Robux run governed by `ReplicatedStorage.LimitedStockConfig`, which DataService does not require; this table is the entire authorization check for the remote, so any entry is buyable by a client firing it directly with **no stock check**, and re-adding the card would let players mint it past the cap); requires the hunter owned; if already owned just resyncs; otherwise spends Tokens via [[Wallet]] (`weapon_skin_tokens` **Sink**), writes `OwnedWeaponSkins[hunter][skin]`, updates leaderstats, fires `SkinDataEvent` back and `ShopPurchaseSuccessEvent` to the buyer
7. Tracks playtime via `os.clock()` join timestamps and accumulates on leave
8. Releases profiles on PlayerRemoving to free session locks
9. Exposes `getPlayerData()` and `updateLeaderstats()` for other modules
9b. Exposes `getLevelFromXP(totalXP)` — account level derived from total XP using the same curve as Redwater (`xpToNext(L) = 250 + 100L + 0.5L^2`, mirrored from `RoundSystem.Config`). `data.Level` is only a cache of this, so any lobby code that writes `data.XP` must re-derive it: QuestService does on both claim paths, and DailyRewardService keeps its own equivalent local copy
10. All Cash/Token balance changes route through [[Wallet]] so each one logs a Roblox economy event: `PurchaseHunterEvent` and `PurchaseSkinEvent` spend Cash (**Sinks**, reasons `hunter_cash` / `skin_cash`), `PurchaseSkinWithTokensEvent` spends Tokens (`skin_tokens`), `PurchaseWeaponSkinWithTokensEvent` spends Tokens for gun/card skins (`weapon_skin_tokens`), and `AddTokens` / `AddCash(player, amount, reason, itemSku)` award Tokens/Cash (IAP **Sources** driven by StoreService). Every skin/hunter Sink carries a readable itemSku — a `Hunter` name for `hunter_cash`, `Hunter:Skin` for the skin/gun Sinks. If a hunter grant fails **after** the Cash has been debited (the exceptional grant-failure / rollback path), the price routes back through [[Wallet]] `award` (reason `refund`, a Source that cancels the `hunter_cash` Sink) instead of a raw `data.Cash` write, so the ledger stays balanced in analytics
11a. **Offline currency gifts** via ProfileService **GlobalUpdates**. `QueueCurrencyGrant(userId, currency, amount, reason, message)` writes a pending gift (`{ kind = "currency_gift", currency, amount, reason, message }`) to a player's profile with `ProfileStore:GlobalUpdateProfileAsync` — works whether or not they're online. On profile load (`onPlayerAdded`, after `fireSkinData`), a handler applies each pending `currency_gift` **immediately** — no waiting on a datastore save round-trip, so the popup isn't delayed: it grants through [[Wallet]] `award` (economy Source still logs; default reason `admin_grant`) + `updateLeaderstats`, then fires `GiftNotice` to the client for the one-time thank-you popup. Exactly-once is guaranteed by a **persisted `ClaimedGiftIds`** set (update id → true) in the profile template, so the follow-up locked-listener and any crash-then-rejoin can't double-grant; `LockActiveUpdate` / `ClearLockedUpdate` (+ a background `profile:Save()`) are just cleanup to drop the update from the GlobalUpdates list. Used for developer thank-you token grants to specific players.
12. `tryLogFunnelStep(player, step, name)` is the **onboarding funnel chokepoint**: it fires `AnalyticsService:LogOnboardingFunnelStepEvent` only the first time a player reaches each step, recording completed steps in the persisted `OnboardingFunnel` set (`{ [tostring(step)] = true }`, added to the profile template). Shared with Redwater via the same `PlayerData_v2` key, so a step never re-fires across rejoins/teleports/places. All 8 funnel call sites (steps 1-7 across both places) route through this — previously step 5 "Shot the Gun" fired on every shot and tripped AnalyticsService's per-server event cap ("sent too many events")
13. Profile template includes the onboarding `Tutorial` sub-table (`Completed`, `Skipped`, `BonusPaid`, `Attempts`, `StartedAt`, `CompletedAt`, `Screened`, `JourneyId`, `JourneyStep`), backfilled via `:Reconcile()` and byte-aligned with Redwater's template. `onPlayerAdded` applies the **grandfather rule** right after Reconcile: a not-Completed profile with `Attempts == 0` and any veteran signal (`MatchesPlayed`, `TotalPlaytime`, `Level > 1`, or `XP`) is silently marked Completed so the live player base is never dispatched into a tutorial; profiles with `Attempts > 0` are already in the tutorial flow and are governed by TutorialDispatchService's `Attempts < 2` rule instead. Read by TutorialDispatchService for the dispatch conditions and the Skipped/Attempts writes
13a. **The grandfather rule is a one-time migration decision, not a standing rule** (`Screened`, 2026-08-11). It used to re-run on every profile load, which meant the four veteran signals kept growing under a player who simply had not been dispatched yet — and reclassified them as a veteran the moment they played anything. Two ways in, both real: a brand-new player who arrives by **following a friend** is deliberately not dispatched (TutorialDispatchService's `shouldInvite` treats `FollowUserId` as an arrival with an intent) and plays the match they were invited to, which would have grandfathered them out of onboarding forever on their next solo join; and `refundAttempt`, which exists so a player whose dispatch failed "gets a full set again on a later join", was worth nothing the moment they played a round in between. `Screened` is stamped on the first load a profile ever gets, whichever way the screen decides, and the block is skipped entirely afterwards — the question it answers is "was this account here before onboarding existed?", a fact about the past that cannot change. The `Attempts == 0` guard stays **alongside** it rather than being replaced: a profile mid-lesson when this shipped has `Screened` false and playtime from the lesson itself, and its one screening must not eat the run it is in the middle of. Redwater's copy is identical and matters as much — a follow-joiner's first load can happen there, and whichever place loads the profile first seals the screen
13b. **The screen's un-grandfathered branch mints `Tutorial.JourneyId`** (2026-08-15), a GUID that is the session id for Telemetry's `NewPlayer` journey funnel, alongside `JourneyStep = 0`. This branch is the only moment in the codebase that knows an account is genuinely new, and Telemetry treats an empty id as "not in the cohort" and drops every step — which is what keeps the entire existing player base out of a funnel they could never finish. It is deliberately **not** a `tryLogFunnelStep`-style call: the data layer carries no dependency on analytics, so this writes a profile field and Telemetry reads it. Redwater's copy carries the identical branch for the same reason its copy of the screen does — minting in Bounty alone left a follow-joiner (whose first load happens there) permanently invisible to the funnel while still being dispatched into the lesson on their next ordinary join. One-way, like `Screened` itself: an account gets at most one journey
14. **Lootbox chests** (2026-09-03, LOOTBOX_SPEC.md). Profile template gained `Lootboxes` (`Unopened`, `LevelClaimed`, `Opened`, `PityEpic`, `PityLegendary`, `SuperUnopened`, `TutorialChestPaid`) and the `LootboxLaunchV1` stamp, byte-identical in Redwater / Frostbite and backfilled by `:Reconcile()`. LootboxService owns every write except Redwater's TutorialDirector banking the tutorial super chest. `onPlayerAdded` runs the **launch migration** right after the grandfather screen (so the screen still sees the real Level / XP signals) and before `updateLeaderstats`: every account's Level / XP resets to 1 / 0, a veteran (the screen's four signals, read before zeroing) is paid 5 chests + 3 `xp_25_30` potions + 200 Tokens via [[Wallet]] (`lootbox_launch_grant`), `LevelClaimed` is pinned to 1 so level 1 never pays a chest, and the stamp seals it. **Data-affecting and one-way** — reverting a place does not restore it. In both places for the same reason the screen is: a follow-joiner's first load can happen in a match. **`LOOTBOX_LAUNCH_ARMED = GameEnvironment.env == "Dev"`** gates it — the DEV universe (separate stores) runs it so the reset can be tested, live stays off until the launch publish flips it to `true` in all three places in one pass, because Studio loads the live data store and one Studio session would reset the tester's real account (this is the module's only use of [[GameEnvironment]]); LootboxService keys its free-chest accrual off the stamp, so nothing pays chests before the reset that defines them
14a. `getLevelProgress(totalXP)` — the same curve walk as `getLevelFromXP` returning `level, xpInto, xpNeeded`, for the chest menu's next-free-chest bar

## Analytics fields (added with [[Telemetry]])
Profile template gained four fields, backfilled via the existing `:Reconcile()` and byte-identical to Redwater's copy (same shared `PlayerData_v2` key): `MatchesPlayed` (matches STARTED, not finished — counting only finishers would compute completion rate against a denominator that drops the very people it measures), `LastMatchAt` + `SittingMatchIndex` (the same-sitting replay counter; a Redwater server hosts one match then closes and the lobby a player returns to may be a different server instance, so this can be held neither in-server nor in memory), and `LastPlatform` (written by [[Telemetry]] `setPlatform`, persisted so a server can attribute events before the client has booted). All four are **written in Redwater** — Bounty only mirrors them to keep the shared template in sync, apart from `LastPlatform`, which is written in both places whenever a client reports in.
