# Telemetry

The single choke point for `AnalyticsService:LogCustomEvent` and the `NewPlayer` / `Tutorial` custom funnels, mirrored VERBATIM in Redwater Canyon and Frostbite Claim.

## What it does
1. **Third analytics choke point** alongside Wallet (economy events) and [[DataService]] `tryLogFunnelStep` (onboarding funnel). Mirrored byte-for-byte in Redwater Canyon and Frostbite Claim — custom event names, funnel names and the 8,000-unique-custom-field-combination budget are all per-EXPERIENCE, not per-place, so every copy must share one taxonomy. Edit them together and verify with a byte-length + checksum compare
2. `EVENTS` registry gates every emit by name. Roblox caps distinct event names per experience and a typo silently mints a new one rather than erroring, so an unregistered name warns and drops instead of quietly polluting the dashboard
3. **Field contract, uniform across all 13 events:** CustomField01 = plain Platform, CustomField02 = the event's primary dimension, CustomField03 = its secondary dimension or nil
4. `hunterField(player, hunterName)` returns the COMPOSITE `"Platform|Hunter"`, which is what every hunter-bearing field carries. Plain platform is already in CF01 so the composite costs nothing, and it is what makes "Vesper on phones" readable off a single field if the dashboard turns out not to cross-filter two custom fields at once
5. `setPlatform` / `getPlatform` — platform is client-resolved (the server cannot see input devices at all), arrives over the `ReportPlatform` remote from [[TelemetryClient]], is whitelisted to Phone/Tablet/Desktop/Console/Unknown, published as the `Platform` player attribute, and persisted to `LastPlatform` so a server can attribute events before the client has booted. `getPlatform` falls back to the persisted value, then to "Unknown". Client-reported and so spoofable — acceptable, since platform drives no gameplay
6. `log(player, eventName, value, field02, field03)` — pcall-wrapped, non-yielding, warns on failure. **Never call from a hot path**; aggregate first and emit once. That path is what tripped the per-server event cap the last time this game logged from combat code
7. `logJourneyStep(player, step)` (2026-08-15) — the 7-step `NewPlayer` journey funnel: First Join → Tutorial Started → Tutorial Completed → Returned To Lobby → Queued For Match → Joined Match → Finished Match. Steps 1 and 4 fire here in Bounty (`Start()`'s join handler and TutorialDispatchService's return check), step 5 in PartyService, steps 2-3 and 6-7 in Redwater. One funnel per ACCOUNT, spanning both places and any number of sittings, so unlike the other two it carries **no session id argument**: the id lives on the profile (`Tutorial.JourneyId`) and is read here. **The gate is the whole design.** Every other funnel stays honest because each step is strictly implied by the ones after it; this one cannot be — "played a real match" does not imply "completed the tutorial" for a grandfathered veteran, a follow-join forwarded into a friend's match, an exhausted dispatch ladder or an abandoner at `Attempts >= 2` — and Roblox backfills skipped steps, so logged naively the chart would read *better* the more players skipped the lesson. So `Tutorial.JourneyStep` records the highest step actually reached and a step is refused unless it is exactly its successor. Nothing can be skipped, nothing can re-fire, and callers are free to be dumb. `JourneyStep` advances **before** the emit, so a failed `LogFunnelStepEvent` cannot retire an account from the funnel; the path is deliberately exempt from `takeToken` for the same reason (7 events per account per lifetime cannot be a hot path). Non-yielding for the caller — the profile wait (20s, for the ProfileService handoff after a teleport) and the platform wait (10s, so step 1's breakdown is not permanently "Unknown" for accounts that have no persisted `LastPlatform` yet) both run on a spawned thread. It replaced the 5-step recurring `MatchLoop` funnel, whose steps 1-4 had settled at a 1.6% total loss and whose step 5 was already readable off `MatchEnd`'s Completed/LeftEarly split
7a. `logTutorialFunnelStep(player, step, funnelSessionId)` (2026-08-09) — the onboarding tutorial's own 11-step `Tutorial` funnel (12 until the same-day Look/Move merge dropped "Look Around"). Each funnel gets its own entry point with its name and step table hardcoded, rather than one function taking them as parameters. The session id is minted here in Bounty by TutorialDispatchService and carried in TeleportData; every step is fired in Redwater (TutorialDirector). Step 8's number (Alt) is only meaningful filtered to PC (touch players skip it and backfill through it); step 11 fires only on genuine completion — four alternative terminals would be corrupted by backfill, so the non-completion outcomes ride the `TutorialRun` aggregate (one per run: value = seconds, CF02 = outcome, CF03 = `T<timeouts>|S<exitStep>`)
8. `logSessionEnd(player, seconds)` resolves its own exit context so the module stays identical in both places: no `RoundActive` instance in ReplicatedStorage means this is the lobby, so Bounty always reports the "Lobby" context. Session length is timed inside this module (own `PlayerAdded` clock) rather than read off DataService's TotalPlaytime bookkeeping, so the data layer carries no dependency on analytics
9. **Per-player (30/min) and per-server (400/min) sliding-window budgets**, far above expected traffic, so a future caller wired into a hot path degrades into dropped events instead of tripping the experience-wide cap and taking the economy and funnel events down with it
10. **Studio gate** — `ENABLED = DEBUG_FORCE or not RunService:IsStudio()`. Studio API access is ON in both places, so without this a Studio playtest writes straight into live analytics
11. Shared `bucket*` helpers (match index, kills, player count, FPS) live here rather than at the call sites, because a bucket boundary that differs between the two places produces two silently incompatible sets of chart values. **`bucketKills` was re-cut on 2026-07-31** from `0 / 1-2 / 3-5 / 6+` to `0 / 1-4 / 5-9 / 10-19 / 20-29 / 30+`: at the rate players actually kill, the old ceiling swallowed nearly every completed match into the single `6+` cell. The *average* value on `MatchKills` was never affected — what was invisible was the **distribution**, which is what the streak-shaped battle-pass quests (`killStreak5`, `deadMansHand`) are calibrated against. Re-cutting boundaries is only free before data exists; afterwards it makes the before and after charts incomparable
12. **`MatchAssists`, `MatchBounties` and `MatchBountyKills`** (added 2026-07-31) are registered here but emitted only in Redwater, where the round-end block lives. They close the gap between what the battle pass pays and what the dashboard could see: `BattlePassConfig.XP_SOURCES` awards BP XP for `assist` (2), `becomeBounty` (20) and `killBounty` (10), and none of the three had an event — together roughly half of a match's BP XP was unmeasured. The registry is per-EXPERIENCE, which is why this copy carries names it never fires
12a. **`FollowJoin`** (added 2026-08-13) is fired from **this** place only — FollowJoinService owns the app-side friends-list join — though the registry entry is mirrored into Redwater like every other name. One event per follow-join at the outcome: value = seconds from join to verdict, CF02 = outcome (`Forwarded`/`Arrived`/`Tutorial`/`Full`/`Ended`/`Closing`/`Offline`/`TeleportFailed`/`NoAccessCode`, plus `Failed` as the catch-all), CF03 = `"<Match|Lobby|None>|R<directory retries>"`. It exists because that path's only previous instrument was a warn, and the 2026-08-13 fix quite deliberately silenced the warn for every *expected* outcome — leaving nothing to judge it by. CF03 is the load-bearing half: a `Forwarded` at `R1+` is a join the directory retry ladder rescued, and a `Forwarded` to `Lobby` is one that re-asking Roblox presence rescued. Cardinality is ~540 combinations against the 8,000 budget
12b. **`MatchPing`** (added 2026-08-15) is registered here but emitted only in a **match place**, from RoundController's `emitMatchStart` — the mirror-parity rule again, like `MatchAssists` above. One row per player per match: value = measured ping in ms, CF02 = the *server's* region bucket (`NA`/`SA`/`EU`/`AS`/`OC`, or `Unknown`), CF03 = `bucketPing`. It audits the region gate **this** place applies in MatchmakingService — a gate that deliberately fragments the matchmaking pool, so a thin region seeds its own server and plays bots, on the strength of an assumption Studio cannot test: that Roblox allocates a reserved server near its first joiner. Same-region rows above ~100ms say the country buckets are wrong or that assumption is; `Unknown` rows are servers that lost their region write and accept players from every continent. `bucketPing`'s boundaries (`0-49`/`50-99`/`100-149`/`150-249`/`250+`) are cut around the two numbers the gate was argued over: ~100ms is what same-datacenter play should come in under, 150 is where an FPS starts feeling wrong, 250+ is the unplayable band the gate exists to eliminate
12c. **`LootboxOpen`** (added 2026-09-03) is registered here and emitted only in **Bounty**, from LootboxService on every chest opened — one row per open: value = 1, CF02 = the tier the box landed on (`Common`..`Legendary`), CF03 = how it got there (`Standard` for the base roll, `PityEpic` / `PityLegendary` when a guarantee fired, `Super` for the fixed tutorial chest). Purchases are deliberately **not** a custom event: Wallet's economy Sink (reason `lootbox_tokens`) already records them. Cardinality is 5 × 4 × platforms against the 8,000 budget
13. `Start()` wires the `ReportPlatform` and `ReportClientPerf` remotes, tracks join clocks, fires `NewPlayer` step 1 on join (gated on `GameEnvironment.place == "Bounty"` so this file stays byte-identical everywhere — it lives here rather than at a lobby call site because it must not lose a race with TutorialDispatchService: a first-time player can be reserved and teleported into the lesson before their lobby character has ever spawned, and a step 2 whose step 1 never fired is refused by the gate, emptying the funnel for exactly the players it exists to measure), and fires `SessionEnd` on `PlayerRemoving`. Platform cache cleanup is deferred so any other `PlayerRemoving` handler still sees the platform on the way out. The `ReportClientPerf` handler is present in both copies to keep them identical, but Bounty's client never fires it — a ClientPerf chart mixing lobby and combat framerate would be misleading

## Dependencies
- **Requires:** [[GameEnvironment]]; [[DataService]] — resolved lazily inside a pcall'd getter rather than at the top, so analytics can never break a spawn and the module stays loadable if DataService ever grew a require back into it
- **Required by:** Main, PartyService, TutorialDispatchService, FollowJoinService, LootboxService
