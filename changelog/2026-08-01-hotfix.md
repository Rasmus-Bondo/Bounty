# Hotfix — 2026-08-01

**Summary:** First post-launch patch — bot FX dropping on loading clients, 3D invite buttons
streaming in late, and the Vesper grapple getting its own caster kicked by the movement anti-cheat.

## Fixed

- **Bot muzzle flashes, tracers and rig movement no longer break up while a client is still loading.**
  Reported from the live error dashboard as 35 dropped client events on
  `Hunters.Shared.Remotes.BotShotFX` and `BotTransformUpdate`. Both are `UnreliableRemoteEvent`s,
  which have no invocation queue at all — unlike a reliable `RemoteEvent`, which buffers ~256
  events before complaining, an unreliable one discards immediately when the receiving client has
  no `OnClientEvent` handler yet. `BotVisualClient` resolves `BotShotFX` early but does not connect
  its handler until it has finished resolving ~10 VFX assets and modules, so the remote sat
  unlistened for that whole window while bots were already shooting.

  `ReplicatedFirst.EarlyShotRemoteDrain` existed for exactly this and covered the four *player*
  shot remotes; the bot pair was never added. Both are now drained. The guard that decides whether
  to attach the no-op also had to change from `IsA("RemoteEvent")` to `IsA("BaseRemoteEvent")` —
  `UnreliableRemoteEvent` does **not** inherit from `RemoteEvent`, so adding the remotes without
  that change would have been a silent no-op.

  `HunterSharedRemoteSetup` gained a comment (no behaviour change) recording why `BotUltimateFX`
  and `BotFortunaCardFX` stay **reliable** and must never be drained: they carry paired state
  transitions (ultimate `Start`/`End`, card `Stick`/`Remove`/`Recall`/`Clear`), unreliable delivery
  is lossy *and* unordered, and a reliable remote hands its queued events to whichever handler
  connects first — so a no-op drain would swallow a `Start` the real handler never sees. A lost
  `End` leaves the highlight, looping sound and dust ring running on every client indefinitely.

- **The lobby's three 3D party-invite buttons can no longer fail to appear.**
  From the same dashboard, as an infinite-yield warning on
  `Workspace.InviteButtons:WaitForChild("InvitePartyPart2")`. `InviteButtons` was a plain Folder,
  so its parts streamed by distance like ordinary geometry. Bounty has no `SpawnLocation`, so the
  character spawns at the origin while the invite parts sit ~850 studs away, and `ReworkedPartyClient`
  resolves all three through a no-timeout `WaitForChild` chain at the top of the script — meaning a
  slow stream-in stalls not just the buttons but every one of the ~840 lines below it, the whole
  party panel included. `InviteButtons` is now a Model with `ModelStreamingMode = Persistent`, the
  same treatment `CameraFolder` already had, so the parts replicate on join regardless of where the
  player is standing. `Mobile3DClickHandler` resolves the container by name without a class check
  and is unaffected.

  *Player-facing:* "fixed the party invite buttons sometimes not showing up in the lobby."

- **Vesper's Grapple Hook no longer gets the caster kicked by the movement anti-cheat.**
  `GrappleGraceUntil` was a fixed `TravelTime + GraceBuffer` (1.35s) window opened when the
  server validated the hook — but the client's pull only starts a round-trip later and itself
  runs up to `TravelTime * 2` (0.7s), the landing `HopVelocity` of 60 adds ~0.61s of flight at
  gravity 196.2, and the character's position replicates back a further latency late. A clean
  grapple therefore needed ~1.5s of cover at 100ms ping, and ~1.9s on a 200ms mobile
  connection. Overshooting the platform is far worse: striking it at `distance / TravelTime`
  (357 studs/s on a max-range hook) means the pull never reaches the anchor, grinds out its
  full deadline against geometry, and flings for seconds.

  `MovementChecker` then sampled the residual velocity — 25% of pull speed, ~89 studs/s — and
  charged **weight 3** for it. With a kick threshold of 5 and decay only while grounded, two
  such samples ended the player's match. Reported by a player and reproduced in-house.

  `GrappleHookService:_beginGrappleGrace` now holds the window open until the caster lands:
  it polls every `GracePollInterval` (0.2s), extends the grace past `MovementChecker`'s 0.5s
  sample while `Humanoid.FloorMaterial == Air`, and closes `LandingSettle` (0.4s) after
  touchdown so arrival velocity bleeds off first. `MaxGraceTime` (4s) is a hard ceiling, so a
  validated hook can never buy unbounded immunity — the abuse budget is at most 4s per 8s
  cooldown. A per-character token retires the previous watcher when a second grapple starts,
  and `CleanupPlayer` retires it on disconnect. New dials live in `VesperConfig.GrappleHook`.

- **Movement anti-cheat no longer false-flags the first sample after *any* grace window closes.**
  Separate latent bug, not Vesper-specific. The graced branch refreshes `lastPosition` and
  returns, but up to a full `CHECK_INTERVAL` (0.5s) of graced travel happens between that
  sample and the next — so the position-delta check measured movement the server itself had
  authorised. At weight 3 that is most of the kick threshold. It applied equally to Fortuna's
  dash (`FortunaDashGraceUntil`), Bram's knockback (`KnockbackGraceUntil`) and the spawn/round
  teleport immunities. Now gated on a `gracedLastCheck` flag; the speed checks still run on
  that sample, so the window is not a free teleport.

**Player-facing wording:** these are anti-cheat internals — do not describe the checks, weights
or thresholds anywhere a player reads. The kick was genuinely player-affecting, so it earns a
note, but only as *"fixed a bug that could disconnect you while using Vesper's Grapple Hook"*.
Everything else here is *"backend improvements"*.
