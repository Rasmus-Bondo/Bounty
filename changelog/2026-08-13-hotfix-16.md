# Hotfix 16 — 2026-08-13

**Summary:** Corpses stop healing themselves and dying a second time, joining a friend from the Roblox app stops answering "their match already ended" for four situations that were not that, and passive healing now pauses for five seconds after you take damage — plus completely silent movement, a second knocked off the respawn, and a ranked leaderboard season reset landing 14 August.

- **Profile schema:** v2 (unchanged)
- **Data-affecting:** **yes**, on two counts, neither undone by reverting a place.
  **A ranked season boundary lands 2026-08-14 18:00 UTC**, inside this release's life: every profile's
  `RankPoints` zeroes on its first award past it and the board moves to `RankPoints_v3`. Deleting the
  season row restores the season 2 board intact, but never RP already zeroed — so the revert stops
  being clean the moment the first player earns past the boundary.
  Separately, a follow-joiner whose forward fails can now be dispatched into the tutorial, which spends
  a `Tutorial.Attempts` (ceiling 2, refunded for failures observed in Bounty). Reverting stops the
  dispatch but does not return a spent attempt.
- **Cross-place contract:** two, both requiring the places to go out together. The friend-join fix
  spans them — Bounty alone leaves the tutorial-server lookup permanently answering "no" (silently the
  old behaviour), Redwater alone writes a map nobody reads. And the ranked boundary lives in a mirrored
  module, so a half-published experience would run two different season numbers against two different
  leaderboard stores.

## Added

- **`FollowJoin` telemetry event — one per app-initiated friend join, emitted at the outcome.**
  value = seconds from join to verdict, CF02 = outcome, CF03 = `"<Match|Lobby|None>|R<retries>"`.

  It exists because the fix below deliberately silenced the warnings for every *expected* outcome,
  which left that path with no instrument at all — and the absence of warnings is not evidence the
  retries work. CF03 is the half that earns it: a `Forwarded` at `R1+` is a join the directory
  ladder rescued, a `Forwarded` to `Lobby` is one that re-asking presence rescued.

  Registry entry mirrored into Redwater like every other name; fired only from Bounty. ~540 field
  combinations against the 8,000-per-experience budget. Reverting loses the measurement and nothing
  else. Verified: mirrors byte-identical, both copies recompile.

## Changed

- **The ranked leaderboard resets to a fresh season on 2026-08-14 at 20:00 CEST (18:00 UTC).** One
  epoch appended to `GameEnvironment.RANK_SEASONS`: season 3 serves an empty `RankPoints_v3`, and
  each profile zeroes its own RP the first time it earns past the boundary.

  **This must publish before the boundary, not after.** Servers resolve the season from `os.time()`
  per call and roll over unattended — but only servers already running this build, so publish and
  then *Shut Down All Servers*. Deliberately **not** aligned to the battle-pass boundary this time:
  `BattlePassConfig.SEASON_START` is untouched and that season runs to Aug 21 17:00 UTC, so ranked
  and the pass run on separate cycles from here on. The first reset shared one instant with it.

  Deleting the row restores the season 2 board intact — `RankPoints_v2` is never written to or
  deleted — but does not restore RP on any profile already zeroed past the boundary, so a revert
  stops being clean the moment the first player earns. Verified: mirrors byte-identical, both
  recompile, and the rollover was exercised against the live source under a shimmed clock —
  `17:59:59 → RankPoints_v2`, `18:00:00 → RankPoints_v3`.

- **Vesper's first-person sprint pose plays 25% slower** — the authored 0.650s loop now runs at
  `SPRINT_ANIMATION_SPEED = 0.75` in `VesperViewModelAnimationClient`, a ~0.87s cycle. Its shared
  `setHeldLoop` helper gained an optional speed argument to carry it; the Starfall ultimate pose,
  the other user of that helper, still plays at 1x.

  Cosmetic — no timing, input or hit logic reads the track. Redwater only, no mirrored module
  touched; reverting restores the fast loop. Verified: recompiles. The number was chosen by eye
  after a 0.7 pass read as too slow.

- **`StarterPlayerScripts.DisableDefaultHealth` renamed to `DisableDefaultHealthBar`.** It only ever
  hid the CoreGui element, but next to the new `StarterCharacterScripts.Health` the old name read as
  if it disabled regeneration. Matches its sibling `DisableDefaultLeaderboard`. Nothing references
  the name — verified across both places — so the rename is inert and reverting it changes nothing.

- **Footstep audio removed from Redwater — characters are now completely silent when moving.**
  `StarterPlayerScripts.FootstepClient` (475 lines) is deleted. `DefaultFootStepRemover` was
  deliberately kept, so Roblox's stock "Running" sound stays muted rather than filling the gap —
  silence is the intended result, chosen over falling back to the default sound.
  `ReplicatedStorage.SFX.Footsteps` (9 material folders) is left in place but dormant; nothing
  references it, and re-sourcing the asset ids later would be painful. Reverting the place restores
  the script and the audio in one step. Verified: no dangling references place-wide, Bounty never
  had footstep code.

- **`RoundSystem.DestructibleService` removed** along with its three lines in `RoundController`
  (require, `Initialize()`, `resetDestructibles()`). It was already dead — `breakWindow()` had no
  callers anywhere, and the only Part named `Window` is `Workspace.Assets.Window`, an unplaced asset
  template — so no behaviour changes and nothing in the map is affected. Reverting restores a module
  that does nothing. Verified: `RoundController` recompiles (2053 lines) and the place greps clean.

  Both removals also struck two Frostbite bring-up blockers from `FROSTBITE_CLAIM_SPEC.md` (§3b-ii
  item 2, §3c). Re-measuring §2 for that edit surfaced an unrelated **13-script drop since
  2026-08-11 of which only these 2 are explained** — flagged in the spec, not chased here.

- **Unused assets moved out of Redwater's `ReplicatedStorage` into `ServerStorage.Unused`** — 21
  items, 1,571 instances, about 20% of the folder, including ~18 minutes of music. Everything under
  `ReplicatedStorage` replicates to every client and is fetched at join whether or not any code
  touches it, so this is a direct cut to join-time download. The set: `Characters.Iris` (unfinished
  fifth hunter, absent from the `HunterSwitchService` roster), four dead viewmodel sets sitting as
  siblings of live templates (`RevolverDefaultViewmodel.Backup`, `SniperDefaultViewmodel.Backup`,
  `Grudgekeeper.ArmsViewModelMCP`, `Grudgekeeper.BackupDefaultBram`), the duplicate
  `Hunters.Dust.Viewmodel.Skin` and `BackupHellFire`, `BotRig`, `CharacterScripts`,
  `BackupViewmodel`, `RevolverModel`, eight full-length music tracks nothing plays, and the dormant
  `SFX.Footsteps` + `Footstep`. Each parked node mirrors its original path under
  `ServerStorage.Unused` and carries an `OriginalPath` attribute, so restoring one is a reparent.

  **This supersedes the note above** that `SFX.Footsteps` stays in `ReplicatedStorage` — the asset
  ids are equally recoverable from `ServerStorage`, and there they cost no client a download.

  Reverting the place restores all of it. Verified against the live data model: all four hunters'
  viewmodel templates still resolve by walking their manifest segment lists, and every live sibling
  that sat next to a dead one is intact (`RevolverDefaultViewmodel.Skins.HellFire`,
  `Grudgekeeper.WorldShotgun` and `WorldModel`, `BotAnimate`, the four real `Characters` folders).
  **Confirmed in a playtest on 2026-08-13.** `Grudgekeeper.Skin.FrostbiteGrudgekeeper` was
  deliberately left in place: it is
  unreachable twice over and probably wants wiring up rather than parking.

- **A player on a bad connection can no longer be kicked by two position-delta flags.**
  `AntiCheat.MovementChecker`'s delta flag was a flat weight 3 against a threshold of 5, so two of
  them in one life was a silent kick. It is now conditional on the horizontal-speed check firing on
  the same sample: weight 3 when the velocity read corroborates the jump, weight 1 when it does not,
  with `(uncorroborated)` appended to the reason. The kick context also gained a `ping` field.

  A large delta at `hSpeed` ~0 is equally the signature of a CFrame teleport and of a stalled client
  snapping in, and nothing in the check could separate them — which is why the ping goes in the same
  pass. A cheat that keeps repeating still reaches the threshold, a few seconds later.

  Reverting restores the flat weight 3 and the two-strike kick; nothing is stored, so it is clean.
  Verified: recompiles (471 lines), both new format paths and the weight selection exercised.
  **Not playtested** — the confirmation is the shape of the next kick batch on the Creator Hub, where
  an `(uncorroborated)` flag now carries the connection state that would decide it.

  Prompted by review of three live kicks on 2026-08-13 (two accounts); all three were judged genuine
  exploits and none would have been prevented by this. **Anti-cheat — not for the public note.**

- **Respawn delay cut from 6s to 5s — players are back in the fight a second sooner, and the kill
  cam is a second shorter with it.** `RoundSystem.Config.RESPAWN_DELAY` is the only number involved:
  the kill cam carries no duration of its own and ends when the character respawns. Tutorial mode
  still respawns instantly (`TUTORIAL_RESPAWN_DELAY = 0`), unchanged.

  Reverting restores 6s; nothing is stored, so it is clean. Redwater only, no mirrored module
  touched. Verified: `Config` recompiles and returns 5. **Playtested 2026-08-13.**

## Fixed

- **Round-start and respawn teleports no longer yank players backwards, and the
  `[SpawnService] Teleport ... did not take` warnings are gone.** Two teleports issued closer
  together than the 0.35 s verify window each repaired the player back to its *own* stale target —
  undoing the unique-spawn assignment `teleportAllToRoundSpawns` had just made and flipping network
  ownership twice. Round start issues exactly that pair, 0.25 s apart. Every teleport now carries a
  per-player ticket, and a verify whose ticket has been superseded does nothing.

  `RoundController`'s post-settle placement check now measures the root against the spawn it aimed
  at, instead of asking `ZoneService.isPositionInSafeZone` — which accepts the world origin for most
  of a round, so a discarded write (Redwater has no `SpawnLocation`) fell through to the 0.35 s
  verify rather than being repaired at ~0.15 s. `teleportPlayerToSpawn` returns the target CFrame as
  a second value to make that comparison possible; every existing caller reads only the boolean.

  Reverting restores the double-repair and the warnings; nothing is stored, so it is clean.
  Verified: both scripts recompile, all six call sites audited, and **a playtest on 2026-08-13
  produced no warnings.**

- **Corpses were healing themselves and could be killed a second time (launch issue #10, cause
  found and closed).** Roblox inserts its own `Health` script into every player character and it has
  no dead check: its regen loop sleeps in one-second steps, so a loop already in flight when the
  killing blow lands wakes up and writes ~1% of MaxHealth onto a body that has already died.
  Everything in the game that asked only `Health > 0` then read that corpse as a live target.

  `HunterCharacterUtil.IsAlive` (new) tests `GetState() ~= Dead` alongside health and is now used by
  that module's own three checks, `RevolverModule`'s current-raycast branch and three `BotCombat`
  entry points; the four damage services (`Revolver` / `Sunspike` / `Grudgekeeper` / `HighNoon`) and
  `SpawnService.ensureAllPlayersAlive` test the same rule inline because they require nothing. The
  `Died` handler in `HunterCharacterUtil` also pins the corpse at zero, which covers every remaining
  `Health > 0` predicate — bot targeting, aim assist, the respawn sweep — without editing them.

  Three knock-on bugs go with it: a second kill-feed row per death (the `KillFeedGate` warnings that
  reported this), bots and aim assist tracking corpses, and `ensureAllPlayersAlive` skipping a
  regenerated corpse at round start so that player began the round dead.

  **The reviver itself is now replaced too** — see the balance note below. `IsAlive` and the corpse
  pin stay regardless: they are the guarantee against the *next* thing that heals a body, not the
  fix for this one. Reverting restores the corpse behaviour; nothing is stored, so a revert is
  clean. Verified: all nine edited scripts recompile, playtested 2026-08-13. **The playtest does not
  confirm the kill-feed fix** — the gate only speaks when it blocks a row, so a quiet session is not
  evidence either way (this is the trap open item #57 recorded against the first #10 sample). The
  standing check is still that `[KillFeedGate] duplicate row refused` stops appearing in live logs
  across real player-vs-player deaths.

- **Redwater has its own health-regen script, and passive healing now pauses for 5s after you take
  damage.** `StarterPlayer.StarterCharacterScripts.Health` (new, 106 lines) claims the `Health` name,
  which is how the engine's default character script is replaced. It keeps the engine's numbers —
  1% of MaxHealth per second — and differs in exactly two ways: it stops at death, and it holds off
  for 5 seconds since the last damage taken.

  **This is a balance change, deliberately.** Regen used to run uninterrupted at 1%/s, which made a
  health pack a faster version of standing still; it is now the only way to heal during a fight.
  Duels are more lethal. Only a *decrease* in health arms the delay, so a pack's instant heal does
  not push it out, and the fire zone suppresses regen for free by re-arming it every tick.

  The docs describe the replacement as a **LocalScript** while the engine's own version is a server
  **Script**, which edit mode could not settle. **A server Script does claim the slot** — the
  playtest fired no `DefaultHealthScriptSeen` warning. That check stays as a regression guard: if the
  engine ever starts inserting its own alongside this one, the warning is how that surfaces instead
  of the corpse bug returning.

  Reverting the place restores Roblox's default script, its uninterrupted regen, and the corpse bug.
  Verified: compiles, `RunContext` is `Legacy`, only `Health` in the container, and **playtested
  2026-08-13** — regen behaves and no warning fires.

- **Joining a friend from the Roblox app no longer answers "your friend's match has already ended"
  for four situations that were not that.** An empty match-directory lookup was the single answer
  for: a friend in the onboarding tutorial (those servers never publish, by design), a server that
  had not published yet, Roblox presence handing back a jobId that had already died, and a match
  that genuinely ended. All four warned identically, which is where a report of 29 warnings in
  Bounty came from — none of them a bug in the teleport.

  Redwater now publishes a tutorial marker (`RedwaterTutorialServers_v1`, jobId → true, read only
  once the directory has already missed) so that case gets its own message; a directory miss retries
  on its own ladder, kept separate from the teleport budget; every retry re-asks where the friend
  is, which turns a stale "match ended" into a plain lobby hop; the refusal's player-facing message
  now reaches the card instead of being computed and discarded; and log level is chosen by reason
  code, so a warn from this path again means something is broken.

  **Both places must publish together** — Bounty alone leaves the tutorial lookup permanently
  answering "no" (silently the old behaviour), Redwater alone writes a map nobody reads. Reverting
  restores the one wrong message and the give-up-on-first-miss; the new map is harmless if orphaned
  (30s TTL). Verified: all touched scripts recompile. **Not runtime-tested** — the MemoryStore
  round-trip needs two accounts on live.

- **A brand-new player who joins a friend that is themselves in the tutorial is no longer left with
  neither.** `TutorialDispatchService` refused to invite *any* follow-joiner, on the reasonable
  assumption that the forward would succeed. When it could not, that player landed cold in the full
  lobby menu with a false error and no onboarding — the exact drop the tutorial exists to prevent,
  and two new friends inviting each other is an ordinary way to start this game. It now waits for
  `FollowJoinService`'s verdict and claims them only on a real give-up.

  A timeout is deliberately not a failure, so the double-teleport collision the old guard prevented
  is still impossible. Reverting returns those players to the lobby with nothing; see the
  data-affecting note above for the spent tutorial attempt. Verified: recompiles, no require cycle.
  **Not runtime-tested.**

- **Fortuna's double jump and the shared dash roll no longer leak an AnimationTrack per use.**
  Both loaded a fresh track onto the character's Animator on every press and never released it, so a
  long life walked the Animator to its 64-track ceiling; past the ceiling it refuses *every* later
  load, including the default `Animate` script's own jump clip. That is the shape the bug reported
  in — a client warning naming the stock R15 jump asset, 44 occurrences, nothing pointing at either
  script. `CardsClient` now caches one track per life (released in `stopCharacterState`);
  `RevolverDashService` keeps one per character in `DashTracks`, dropped by each humanoid's
  `Destroying` hook. Both load through `AnimationLoader.loadCached`, so a dead clip now reports
  instead of silently posing.

  Affects Fortuna (both paths) and Dust (dash only); Bram opts out of the roll and was never
  exposed. Reverting restores the leak, not a behaviour change — the animations look identical.
  Verified: both scripts recompile, no raw `LoadAnimation` remains in either. **Not playtested** —
  the real confirmation is the warning count on the Creator Hub after the next publish.

- **Redwater's bounty and round-ending music no longer fails silently.** `BountyMusicClient`
  preloads its five cues at boot, retries the failures once after 10s, then warns naming whatever
  never arrived. Before this a failed asset fetch produced a clone with no audio data and no log
  line at all — the round-ending track's own `TimeLength <= 0` guard just returned.

  Prompted by a live client error listing eight sound fetches as `HttpError`. All eight ids resolve
  through `GetProductInfo`, are public-domain Roblox library audio, and preload clean from Studio,
  so the failure was the client's network and not permissions or moderation. Six of the eight were
  music nothing plays, which is what turned up the cleanup entry above.

  Reverting removes only the diagnostic; playback behaviour is unchanged. Playtested 2026-08-13 —
  but that proves absence of harm, not that the guard works: a CDN failure cannot be induced on
  demand, so the retry-and-warn path is unexercised by construction.

- **Redwater's bounty cards never appeared for some players — the panel's snapshot handler crashed
  on an attribute that came back as *no value* instead of `nil`.** `BountyListClient.applySnapshot`
  threw `missing argument #1` before dressing a single card, and repeated once per snapshot for as
  long as a bounty was up (19 client errors on r2518). Reading the attribute into a local before
  converting it truncates the result to exactly one value and closes it.

  Fixed as a class rather than at the crash site: **18 call sites across 9 scripts** in both places —
  Redwater `BountyListClient` (2), `KillFeedClient`, `KillCamClient`, `VictoryShowcaseClient`,
  `RoundStatusClient`, `ZoneService`, `MatchDirectoryService`; Bounty `LobbySpawn` and
  `HuntersBuyController` (9, all in one deep-link diagnostic that would otherwise have thrown
  instead of reporting). `AntiCheat.MovementChecker` matches the same grep and was deliberately left
  alone — it is already safe.

  Reverting restores the crash on affected clients; nothing else changes, since every site produces
  the same value it did before. Verified: all nine scripts recompile and both places grep clean.
  **Not playtested** — Studio's engine returns `nil` and cannot reproduce the failure, so the
  confirmation is the error count on the Creator Hub after the next publish.

- **Roblox's native death sound no longer plays when another player dies near you.** The two
  removers in `StarterCharacterScripts` could only ever reach the local character, while the core
  sound system builds its Sound set inside *every* player's HumanoidRootPart on each client — so
  your own death was silent and nobody else's was. `DefaultDeathSoundRemover` and
  `DefaultFootStepRemover` are deleted and replaced by an empty
  `StarterPlayerScripts.RbxCharacterSounds`, whose name alone stops the core script from loading;
  none of the nine default sounds are created at all now.

  **This supersedes the footstep note above** — `DefaultFootStepRemover` is gone, and stock
  "Running" is suppressed at the source instead, so movement is still completely silent.

  Jump, landing, splash, swim and climb audio go with it and nothing replaces them (accepted —
  `ManuelJumpClient` and `LandingImpactClient` drive motion only, neither plays audio). Reverting
  the place brings all nine back, as does deleting that empty script as apparent scaffolding.
  `FROSTBITE_CLAIM_SPEC.md` §2, §3b-ii and §7.1 are corrected accordingly — the second map must
  copy it. Redwater only, no mirrored module touched. **Verified in a two-client playtest on
  2026-08-13:** killed the other player, no death sound.
