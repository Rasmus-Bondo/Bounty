  Each deletion is backed up separately to `backups/*_deadui_2026-08-03.rbxm` so any one can be

  With the Roblox chat window open it sat directly behind the chat panel and was unreadable —
  which is exactly the moment a player is most likely to be screenshotting a bug, and the whole
  reason the tag is permanently on screen. The top-left corner belongs to the engine and can be
  taken away at any time, so it is no longer used.

  It now sits 8px to the left of whatever is actually pinned in the top-right, resolved at
  runtime rather than authored in scale, because those buttons are pixel-pinned and so eat a
  larger fraction of a narrow screen. That is **62px in from the right edge everywhere except
  Redwater on touch**, which is 130px in to clear the mobile Stats button — Bounty has no Stats
  button, so keying the wide offset on `TouchEnabled` alone left the lobby tag floating 68px
  from its gear on a phone. The second gate is `GameEnvironment.place ~= "Bounty"`, resolved
  from `game.PlaceId` at load rather than by probing for the button, which `StatMenuScript`
  creates with a runtime `Instance.new` — a probe would either race it or visibly jump the tag
  once it appeared. An unrecognised place takes the wide offset: a needless gap is cosmetic,
  sitting under a button is not.

  Vertically centred on the 44px button row. Directly *under* the gear was rejected — that band
  is the kill feed's, whose top edge is only 60px down on a phone and which grows upward into
  the corner.

  The label is anchored by its **right** edge, so the text grows leftward. That matters beyond
  tidiness: `PlaceVersion` is 0 in Studio, so the tag reads `Hotfix 4` in edit mode and
  `Hotfix 4 r2286` on a real server, and the gap to the gear has to survive that.

  `VersionTagGui` changes inset space to `ScreenInsets.None` to match the buttons it now aligns
  to. This is the third time that enum has been set on this GUI and the first time it is
  correct: the two 2026-07-30 attempts failed because the *top-left* placement had to re-derive
  a topbar offset from a number that measures 0 in Studio. Nothing is derived now — y = 32 and
  the right offsets are copied from buttons living in the same space. See the comment block in
  the script before changing it back.

  Verified in the device simulator at 1658×678 desktop, iPhone 16 Pro Max landscape and a
  640×480 windowed PC: 8px gap to the cluster in all three, clear of the kill feed in all
  three, and the right edge holding steady across build strings from `Hotfix 4` to
  `Update 12 Hotfix 3 r1234567`. Mirror re-verified after the edit — 13474 bytes, identical
  checksum in both places, and `GameEnvironment.place` confirmed live as `Bounty` / `Redwater`
  so the two copies take different branches from the same bytes.

- **Both "win" quests now say they mean 1st place** (launch issue #7). The battle pass's week 1
  capstone read `VICTORY — Win 3 matches`, which does not distinguish finishing **1st** from
  finishing **top 3** — a live question given the pass's own week 3 quest says "Finish top 3 in 6
  matches" a screen away.

  The code was never ambiguous. `win` and `podium` are separate quest types fed by two separate
  calls in `RoundController`: `placement == 1` fires `win`, `placement <= 3` fires `podium`. Only
  the copy was unclear, so this is a wording change and **no tracking behaviour moved**.

  Both `win` quests were reworded onto the phrasing the podium quests already used, so the two
  placement objectives now explain each other: the pass capstone becomes **"Finish 1st in 3
  matches"** and the daily **"Finish 1st in a Match"**. The daily was not in the report but carried
  the identical ambiguity under the identical `VICTORY` heading, and a daily is seen far more often
  than a once-a-season pass quest.

  Quest **ids** were deliberately left alone (`w1_laststand`, `d_win_1`). Ids are persisted in
  player profile buckets and the quest engine drops slots whose id no longer exists, so renaming
  them for tidiness would churn every live bucket.

  Worth knowing for the next copy change in this area: a quest card's text comes from **two files,
  only one of which is mirrored**. The label is in the config (mirrored, two copies); the category
  heading above it — `VICTORY`, `PLACEMENT`, `MOST WANTED` — is a `type` → title map in Bounty's
  `QuestClient` alone. Retitling a category is a one-place edit; changing a label is a two-place
  edit.

- **The lobby's hunter and weapon-skin displays stop re-resolving the camera on every item**
  (Bounty). `HuntersBuyController` cached `workspace.CameraFolder` at load and then ignored it,
  re-walking `workspace:WaitForChild("CameraFolder"):WaitForChild("CameraPartFeatured")` from
  scratch each time it placed a model on the display stand. Both sites now read a part resolved
  once at load beside the two closeup parts already cached there.

  The ordering was the odd part: both calls sat two lines below a `getStandTopPosition()` nil-check
  that bails when the stand is not ready, so the function already had a "world is not loaded, give
  up" path — and then blocked unboundedly right after declining to take it. Bounty's `CameraFolder`
  lookups drop 8 → 6, and all six that remain are single load-time resolutions held in a local.

- **Three lobby panels now report a missing remote instead of hanging on it** (Bounty).
  `FriendsInMatchClient`, `SettingsController` and `GiftPopupClient` each opened with an unbounded
  wait on `ReplicatedStorage.Events`, so if that folder never arrived the script parked forever
  with nothing on screen and nothing in the log. Each is now capped at 10 seconds — the same
  timeout the server-side callers already used — and warns before disabling itself.

  This buys a **diagnostic, not resilience**: the failure path was silent and inert either way, and
  the only difference now is that it says which panel gave up. The caps had been on the wrong side
  of the wire — the three server callers already passed a 10s timeout despite facing no replication
  at all, while the client callers, which face both replication and streaming, were bare.

  **`LoadingScreen` was deliberately left unbounded and should stay that way.** Its settings gate is
  capped from the outside — `MAX_HOLD_TIME` holds the reveal loop to 6 seconds and a `task.delay`
  failsafe lifts the veil regardless — so a timeout there would add nothing and contradict the
  comment block explaining why the inner gates are open-ended.

- **Movement kick logs now record vertical velocity, position, and why the player's speed is what it
  is** (Redwater). Every sample `MovementChecker` flags now carries `vY` and `pos`, and each of its
  `warn()` lines carries a `move{...}` dump resolved from `HunterMovement`'s live modifier set.

  This is a diagnostic, not a behaviour change — nothing new is read back into any check, and no
  threshold moved. It exists because a real kick report could not be diagnosed from the old context.
  The airborne checks deliberately suppress themselves while a player is descending, so a long fall
  and a stuck hover produced **identical-looking logs**; there was no way to tell where the character
  had ended up; and the context reported `walkSpeed=0.0` with nothing able to say what had set it.
  `HunterMovement` owns `WalkSpeed` outright and its rogue-writer warning is gated to
  `RunService:IsStudio()`, so on a live server a stuck modifier is completely silent.

  **The two new field groups are placed differently on purpose.** `vY` / `pos` are per-sample,
  because they change between samples and the trajectory across the history is the whole point.
  `move{...}` is emitted **once per warn** instead — the modifier set does not meaningfully change
  across flags half a second apart, and repeating it six times took a worst-case kick line from
  ~1.1 KB to ~2.2 KB, spending the headroom `FLAG_HISTORY_LIMIT` was cut from 12 to 6 to protect.
  Once-per-warn measures ~1.4 KB. That margin matters because a truncated line would drop the very
  field this was added for.

  `Explain` is `pcall`'d because this runs on the kick path — a throw in the logger would take the
  kick record with it — and its newlines are flattened to `; ` so each warn stays one row, which is
  what keeps the error dashboard aggregating rather than treating every kick as unique. The stable
  first kick line is untouched, so the existing per-player tally stays continuous across the publish.

  **Player-facing wording for this release should say "backend improvements" and nothing more.**
  Anti-cheat detail stays internal.

## Fixed

- **The featured-item pedestal no longer turns up empty, and every remaining lobby prop has been
  hardened against the same cause** (Bounty). Same root cause as the lobby weapons below: workspace
  Models sitting hundreds of studs from the player, left on `Default` streaming mode, replicating to
  the client as **empty containers** while client code reads their parts.

  The reported symptom was `Stand model needs a PrimaryPart set.` from `FeaturedSequence:656`. The
  Stand's PrimaryPart *is* authored — `Model.PrimaryPart` is a reference to a descendant BasePart, so
  it reads nil whenever the Model has arrived without its parts. `workspace.FeaturedItems.Stand`,
  `Card` and `Rocks` are now Persistent. That fixes three consumers at once, because
  `getStandTopPosition` returning nil made `FeaturedSequence:802` bail and made
  `HuntersBuyController:583` / `:1149` **destroy the display model outright** — and that second
  script's copy of the helper returns nil *without warning*, so one log line could mean two blank
  stands.

  A sweep of every name any script resolves under `workspace` then found two more Default-mode
  Models whose parts are read, both now Persistent before anyone reported them:

  - **`VaultDoor`** (3 parts) — `TradingPostController:535` snapshots every BasePart CFrame and
    Motor6D `C0`/`C1`/`Transform` into the tables `resetVaultDoor()` restores from, **once, at load
    time**. An empty snapshot leaves the door with no rest state, so it drifts out of position after
    its first animation and stays wrong for the session. No warning, no error — the silent end of
    this trap, and the reason the sweep was worth running rather than waiting for reports.
  - **`PlayModel`** (100 parts) — `ReworkedUIPlay:18-30` opens with eight consecutive **unbounded**
    `WaitForChild` calls at the top level of the file, so losing the race doesn't degrade the PLAY
    button, it stalls every line below and the button never wires up. 100 always-replicated parts is
    the only real cost in this pass and was taken deliberately: a dead PLAY button is the worst
    failure available in the lobby, and timeouts would only make it warn, not work.

  All 15 workspace Models that client scripts read are now Persistent — 243 parts total. `Terrain`
  and `JailSpawn` were confirmed as the two standing false positives (a singleton that never streams,
  and a part read only by a server module). Nothing sets `ReplicationFocus`, so focus is the default.

  **Not playtest-verified** — streaming cannot be reproduced in an edit-only session. Verified by
  read-back that all 15 are Persistent and by tracing each consumer. No mirrored shared modules
  involved; not data-affecting; no script source changed, these are instance properties only.

- **Lobby character displays no longer turn up empty-handed** (Bounty). Intermittently — on some
  joins and not others — a hunter on the lobby stand would stand there with no weapon, leaving one
  `Lobby weapon missing <Hunter> <Skin> offset` warning per affected dummy. Seen live for Dust
  `DefaultRevolver` and `HellFire`, Vesper `DefaultSniper` and Bram `Grudgekeeper`; all four hunters
  were affected.

  The grips are not hardcoded CFrames. `LobbySpawn` *measures* each one at runtime, taking the
  `RightHand` of a poser rig parked in the workspace (`DustWire` / `FortunaWire` / `VesperWire` /
  `BramWire`) and comparing the weapon pivot against it — which is what lets a grip be re-tuned by
  dragging the rig in Studio instead of editing numbers. Those four rigs sit **460–480 studs from
  the lobby slots** and were in `Default` streaming mode, so under `StreamingEnabled` the Model
  replicated as an empty container: `FindFirstChild("DustWire")` succeeded while its parts were
  still streamed out, `RightHand` came back nil, and the offset with it. All four are now
  `ModelStreamingMode = Persistent`, which takes distance out of the equation — they replicate at
  join and never stream out.

  Two things had disguised this as a harmless log line. The failure is **not cached** — a nil offset
  writes nothing, so any later rebuild re-measures and succeeds — and the
  `task.delay(1.5, rebuildLobbyDummies)` on the respawn path usually re-ran late enough to catch it.
  That is why it self-healed and why it appeared only now and then.

  `warmWeaponOffsetCache` was also **wired up**; it had been defined and never called. It now
  resolves all ten hunter/skin offset pairs in one pass at init instead of lazily during the first
  dummy build. It is a backstop rather than the fix — it reads the same rigs, so it only helps
  because they are Persistent now.

  Worth knowing for next time: the warning's **last word is a discriminator**, and the two cases are
  unrelated bugs. `offset` is this streaming race. `source` would mean the hunter folder never
  resolved — impossible from streaming, since `ReplicatedStorage` replicates in full — and would
  instead point at `getHunterNameFromSelection` returning something that is not one of the four
  hunters. Every warning observed live ended in `offset`.

  **Not playtest-verified** — `start_playtest` hangs the plugin connection, so a cold join with real
  streaming cannot be reproduced here. Verified instead by mechanism plus recomputing all ten
  offset pairs post-fix, every one resolving. The proof is whether these warnings stop appearing in
  the Creator Hub log after publish. No mirrored shared modules involved; not data-affecting.

- **A legacy Robux product that charged players and granted nothing has been retired** (Bounty).
  Developer Product `3601170442` matched a branch in `StoreService` that fired the purchase-success
  FX announcing 20,000 Cash and returned `PurchaseGranted` — **without ever calling `AddCash`**.
  `PurchaseGranted` consumes the receipt permanently, so a buyer paid, saw the confirmation, and
  received nothing, with no retry and no way for the grant to be reattempted. It also bypassed
  `Wallet`, so the transaction never reached economy analytics.

  It was reachable, not dead code: the id appears nowhere in `StoreConfig`, so the generic
  cash-bundle path above it never caught the product first. The branch had lost its `AddCash`
  somewhere in the shop rework — both client ends were already gone along with the old `ShopMenuGui`
  (the LocalScript that prompted the product, and the `PlayCurrencyCounter` remote it listened on,
  removed in the same pass as this). That is why nothing in-game had offered it for some time, and
  why the fault went unnoticed: a Developer Product stays purchasable by direct link whether or not
  any UI offers it.

  The branch and both `LEGACY_CASH_*` constants are gone; `StoreService` is 163 → 151 lines and an
  unrecognised product id now falls through to `NotProcessedYet`. **The product was deactivated on
  the Creator Hub on 2026-08-03, before this shipped** — that ordering was mandatory and is now
  satisfied; see the metadata bullet at the top of this file. Found by analysis while purging dead
  lobby UI, not from a player report, so it is not known whether anyone ever bought it.

- **High Noon no longer locks onto players who are still inside their spawn shield** (Redwater,
  launch issue #12). A freshly spawned player could be acquired, tracked with a lock-on reticle and
  shot at while their 3-second invincibility bubble was up.

  It was never a damage bug — spawn protection is a native `ForceField` and both High Noon damage
  paths go through `Humanoid:TakeDamage`, which a ForceField absorbs, so the shielded player was
  already taking zero. The whole cost was in **target acquisition**: the untouchable target occupied
  one of the six lock slots and could be the caster's only lock, wasting the entire ultimate, while
  from the victim's side an execute shot appeared to land on an invincible character. That mismatch
  is what made it P1 rather than cosmetic.

  Fixed in both acquisition paths — the player's cone scan and the Dust **bot's** ultimate, which
  reimplements its own targeting — beside the existing invisible-Fortuna check that already had
  exactly this shape. One filter covers both the live 0.08s cone loop and the fire-time rescan.
  Shielded players are still excluded from the line-of-sight ignore list, so being unlockable does
  not also turn them into a wall other enemies can hide behind.

  Fortuna's ultimate ring and Bram's proximity gate deliberately still see shielded players: their
  damage is simply absorbed, and filtering there would change *who the ability sees* rather than who
  it can lock.

  **Verified in a multi-client playtest 2026-08-03.** No mirrored shared modules involved.

  One maintenance note for whoever is next in this area: both sites read the `SpawnProtected`
  attribute **by name** rather than requiring `SpawnProtectionService`, because the targeting module
  lives in `ReplicatedStorage` and cannot reach `ServerScriptService`. Renaming that attribute
  silently reintroduces the bug — nothing errors, the ult just starts locking shielded players
  again. It is called out in the `SpawnProtectionService` vault entry too.

- **Sun glare no longer washes out players standing on high ground** (Redwater, launch issue #16).
  Looking up at a ridge from the canyon floor put the sun almost directly behind whoever was
  standing on it, and players had started using those spots deliberately because they were very
  hard to pick out from below. `SunRaysEffect` is now disabled in Redwater's `Lighting`.

  **One property changed — `Lighting.SunRays.Enabled` → `false`.** Every other lighting value is
  still at its authored baseline, confirmed by diffing all 18 relevant properties against the
  values recorded before the investigation. Redwater only; `Lighting` is not a mirrored module, so
  Bounty is untouched and cannot drift from this.

  **"Turn the sun down" was the wrong lever and `Brightness` was deliberately left at 3.5.** It
  scales the directional light landing on surfaces, not the sun disc or the glare around it.
  Dropping it 3.5 → 2.5 visibly darkened the canyon rock while the sun disc stayed pixel-for-pixel
  identical — it dims the *player on the platform* without touching what is blinding the *viewer*,
  which makes the silhouette harder to see, not easier. Anyone revisiting this should not reach for
  `Brightness` first.

  Two hypotheses were tested and rejected, recorded so they are not re-run. **`Bloom` had no
  observable effect** despite looking like the obvious culprit on paper (`Intensity` 1.0 against
  Roblox's 0.4 default, `Size` 24, `Threshold` 2 — a wide additive kernel that should smear a bright
  sky across a thin silhouette); it is still at 1. And **`Sky.SunAngularSize` 11 → 5 appeared in an
  edit-mode A/B to fix it almost entirely**, which did not survive contact with the running game —
  this effect only resolves with the game playing, so edit-mode lighting comparisons in this place
  are indicative at best. Left at 11.

  What does carry over, because it is geometry rather than shading: at the reported framing the sun
  sits **15° off the camera axis inside a 35° half-FOV, at 46.7° elevation** with `ClockTime` 14.5.
  Players looking up at platform height are looking straight into it. If the residual glare is ever
  revisited, raising `ClockTime` toward 12 to lift the sun out of that sightline, and raising
  `OutdoorAmbient` from 0.275 grey so a backlit player's underside is not crushed to black, are the
  two untried levers — both change the map's warm late-afternoon grade, which is why neither was
  taken here.

  **Verified in playtest by the owner 2026-08-03**, who reported the improvement as partial and
  elected to close the item on that basis. If players are still reported disappearing against the
  sun, reopen #16 rather than starting a fresh diagnosis. Player-facing wording for this should stay
  neutral — a lighting adjustment, not a description of the spots it was being used from.

- **Vesper's grapple no longer throws her off the far side of the platform she hooked** (Redwater,
  launch issue #17). A long, flat hook — across the canyon rather than up onto a ledge — released her
  with enough speed to sail clean over the perch she had just reached.

  **The bug was in the release, not the pull.** The grapple ended by handing the player 25% of the
  pull speed, and pull speed is `distance / TravelTime` — so the leftover velocity was **0.714 ×
  hook length with no ceiling**, 89 studs/s off a max-range hook. The little upward hop that lets a
  ground-level grapple clear a platform lip is a *floor*, not an addition, so a flat hook with almost
  no natural lift was handed 60 anyway, buying that horizontal speed 0.61 seconds of hang time to run
  in. A 125-stud flat hook carried **54.6 studs** past the target; every one of the map's 33 authored
  perches is narrower than that, mean width 20.

  That is why it was intermittent rather than constant. The common grapple — standing on the ground,
  hooking a ledge above you — is steep, so the leftover speed points mostly *upward* and she pops up
  and lands. Only a long flat hook dumps it sideways. It correlates with hook length and flatness,
  **not with ping**: the pull is client-owned and the client recomputes distance from its own
  position, so latency shifts when the pull starts and never where it goes.

  Fixed by capping the **horizontal** release speed at a new `MaxLandingSpeed` of 40, direction
  preserved. Maximum travel past the target drops 54.6 → 24.5 studs.

  **The cap is deliberately horizontal-only, because the hook must not change how it feels.** The
  hop, the vertical carry, and therefore the moment the player lands and regains control are
  arithmetically untouched — 0.61s before and after, at every distance. Any hook whose leftover speed
  was already under the cap, roughly **56 studs and shorter**, runs identical arithmetic to before,
  so the only hooks that behave differently are the ones that were broken.

  Three tempting changes were rejected on the same grounds. Copying the **bot** grapple's arrival,
  which zeroes horizontal velocity outright — the bot code's own comment says that suits something
  which cannot course-correct on landing, and on a player it would read as the hook stopping dead.
  Dropping the hop when the pull times out — the hop is doing real work there, lifting the player
  over a lip the pull failed to clear. And adding the bot's overshoot check, which is worth doing on
  its own terms but barely moves this symptom once the cap is in.

  Worth knowing: **the bot path already carried the fix and the player path never got it.** The bot
  separates its success and failure endings, zeroes horizontal on success and clamps the vertical to
  12 rather than 60 on failure, with a comment describing this exact symptom.

  **Not playtest-verified** — MCP playtesting is unavailable. Verified by mechanism plus arithmetic:
  both scripts compile, and the flight distance and time-to-landing were recomputed across the full
  distance and angle range. What to check on a real run is in `OPEN-ITEMS.md` #17. No mirrored shared
  modules involved; not data-affecting.
