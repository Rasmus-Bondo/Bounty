## Fixed

- **Lobby dummies stop warning about a missing weapon grip on every join** (Bounty,
  `StarterPlayerScripts.LobbySpawn`). Hotfix 5 attributed one
  `Lobby weapon missing <Hunter> <Skin> offset` per join to the four grip poser rigs
  (`DustWire` / `FortunaWire` / `VesperWire` / `BramWire`) streaming out at 460–480 studs, and made
  them `ModelStreamingMode = Persistent`. That was a real bug and the rigs should stay Persistent,
  but it was **the wrong half** — and fixing it made the remaining half deterministic, turning an
  occasional warning into exactly one per login. Reported live after Hotfix 6.

  `Persistent` promises a Model is sent at join and never evicted. It does **not** promise the Model
  has arrived before a `StarterPlayerScripts` LocalScript runs its first line — the proof was
  already in this file, where `LobbySpawns` and `CameraFolder` are Persistent *and* still need
  30-second `WaitForChild` gates. Those gates release the moment their two models replicate, and the
  script's last line then calls `rebuildLobbyDummies()` **synchronously**, resolving each rig with a
  bare `workspace:FindFirstChild`. The rigs land later in the same replication batch, so
  `RightHand` came back nil and the grip with it. Removing the distance-based eviction stabilised
  that ordering, which is why the race went from flipping both ways to losing every time.

  `resolveWireRigs` now does a bounded `WaitForChild` for each rig and its `RightHand` before any
  grip is measured, inside a `task.spawn` that **does not yield at all** when the rigs are already
  present — so the common case warms the offset cache before the first build and nothing is rebuilt
  twice. Until it completes, `attachLobbyWeapon` treats a missing offset as a deferral (a
  `weaponAttachDeferred` flag) rather than an error, and the resolver re-runs the build the moment
  the rigs land instead of leaving it to the 1.5 s respawn retry.

  The warning is **suppressed, not deleted**: the resolved flag is set even when a rig times out, so
  a rig that is genuinely renamed or deleted still warns — once, naming the rig — and a `source`
  failure (the other half of that message, an unrecognised hunter name) is untouched.

  This also explains why Hotfix 5's `warmWeaponOffsetCache` backstop changed nothing.
  Wiring it up was correct, but it ran at the same instant as the first build, resolved none of the
  ten hunter/skin pairs, and stored none of the failures — `cachedWeaponOffsets[key] = nil` is a
  no-op in Lua, which is what keeps failures from being cached. It was a complete no-op from
  2026-08-03 until now; it does its job only now that it is gated behind the rigs arriving.

  **The fix is hunter-agnostic.** `resolveWireRigs` iterates all four entries of
  `LOBBY_WEAPON_WIRES`, and the deferral in `attachLobbyWeapon` names no hunter — the warning read
  `Dust` only because the local player's dummy is the sole one built before party data arrives, so
  whichever hunter is equipped is the one that reports. Hotfix 5 had already seen all four live
  (Dust `DefaultRevolver` and `HellFire`, Vesper `DefaultSniper`, Bram `Grudgekeeper`). All 10
  hunter/skin offset pairs were re-measured against the live rigs and resolve.

  **A second, related hole closed in the same pass: the `CharacterAdded` handler now also runs for
  a character that already exists.** It was an anonymous connect with no fallback, and
  `CharacterAdded` does not fire retroactively — so if the character won the race against this
  script (which the bounded `WaitForChild` gates at the top of the file make easy), the initial life
  got no camera lock and *neither* of its two rebuilds. A dummy built before its grip rig replicated
  then stayed empty-handed for the **whole session**, well past the loading screen. That is almost
  certainly the visible "standing there with no weapon" half of the Hotfix 5 report, as against the
  log-only half the 1.5 s retry always healed; it would have been far likelier before Hotfix 5, when
  `LobbySpawns` still streamed by distance and could delay this script for seconds. The handler is
  now a named `onCharacterSpawned`, connected *and* invoked directly when `localPlayer.Character` is
  already set, deduped on the character instance so the fallback racing a real `CharacterAdded`
  cannot run it twice for one life — a respawn is a new instance and still runs.

  Worth recording, since it is why this was only ever log noise in the normal case: **none of this
  is sequenced against the loading screen, and never was.** The initial `rebuildLobbyDummies()` is
  called flat at the bottom of the file; only `startCamera` waits on `BountyIntroComplete`.
  `ReplicatedFirst.LoadingScreen` covers the window incidentally — `DisplayOrder = 1000`,
  `IgnoreGuiInset`, a `MIN_HOLD_TIME` 1.5 s floor measured from before StarterPlayerScripts run,
  plus a `MIN_SKY_TIME` 1.2 s floor and the camera pan, over a camera it holds with a RenderStep
  bind. Do not rely on that cover when adding lobby work: it is a coincidence of timing, not a gate.

  Also tidied a two-statements-on-one-line run in the same file (`GetAttributeChangedSignal
  ("EquippedSkin"):Connect(...)` butted against the `for` loop that wires the per-hunter weapon-skin
  listeners). Valid Lua, behaved correctly, purely a readability fix.

  Verified by `loadstring` compile of the edited source (1023 lines) and read-back of all six
  edits; the rigs were confirmed present, Persistent, and each carrying a `RightHand` MeshPart, and
  no other script in the place references them. **Not playtest-verified** — replication ordering
  cannot be reproduced in an edit-only session, so the check is a join to Bounty with no
  `Lobby weapon missing` line and a weapon in the dummy's hand on the first build. Client-only
  script; no mirrored shared modules; not data-affecting.

- Vesper's scope no longer logs a warning claiming mobile look sensitivity is undamped. The
  condition it reported — the camera controller's pending look input being momentarily absent —
  is a normal one-or-two-frame gap while the PlayerModule swaps controllers around scope-in, and
  it recovers on the next frame. Every one of the 22 warnings seen in the launch window was that
  transient, none a session where damping was actually lost, so the warning and its grace-frame
  counter are gone. Scoped look damping itself is unchanged: those frames were already being
  skipped, and only the log line was removed. Note that there is now no signal at all if scoped
  touch look ever genuinely does run undamped — it would have to be caught by feel.
