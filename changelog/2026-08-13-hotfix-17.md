## Added

### `ReplicatedStorage.MapConfig` — per-place map declaration (Frostbite spec Phase 1)

New root-level ModuleScript in Redwater declaring `Id`, `DisplayName`, `Gamemodes`, `Zone`
(shape/axis/start/end plus the tutorial centre offset) and `Instances` (`SpawnPoints`,
`JailSpawn`, `FinishSpawns`). It is the one file per match place that is deliberately
excluded from the cross-place mirror, so shared code stops assuming Redwater's coordinates.

**Pure refactor — no behaviour change intended.** Verified by recompiling all six touched
scripts and re-deriving the constants: `FIRE_WALL_SPEED` 1.875, `SPAWN_ZONE_MARGIN` 27,
zone span 900, match centre -250, tutorial centre -257.437 — every one bit-identical to
before. `Config.ROUND_TIME` confirmed 360.

**Rollback risk:** reverting Redwater alone is safe (no data shape touched, Bounty
untouched, no mirrored module changed). But `RoundSystem.Config` no longer defines
`ZONE_START_Z` / `ZONE_END_Z` / `TUTORIAL_ZONE_CENTER_OFFSET`, so reverting *only* MapConfig
while keeping the consumers leaves four scripts reading a nil zone — revert the whole set or
none of it.

**PLAYTESTED 2026-08-13 — verified.** Three full rounds at compressed timings (`ROUND_TIME`
80, `ZONE_PHASE_DURATION` 20), which is 12 phase transitions at a **4x** fire-wall speed and a
**72-stud** spawn margin against production's 27 — worst-case Final-phase eligible spawns 6
instead of 13. Strictly harder than production, and it held. A separate tutorial run confirmed
the compressed zone. Config restored to 360 / 80 afterwards and re-verified.

The tutorial centre was additionally confirmed *statically*, because observation cannot catch
it: a missing `TutorialCenterOffset` falls back to 0 and shifts the zone only 7.4 studs, which
is invisible in play. `ZoneService` reads the field, MapConfig supplies -7.437, centre resolves
to -257.437 = TutorialSpawn's Z. The `or 0` fallback never fired.

## Changed

### Zone geometry moved out of `RoundSystem.Config`

`ZONE_START_Z` / `ZONE_END_Z` and `TUTORIAL_ZONE_CENTER_OFFSET` deleted from Config and now
read from `MapConfig.Zone`. Config keeps the closing *schedule* (phase duration, damage ramp,
fire fractions, jitter range), which is the same on every map. Consumers rewritten:
`ZoneService` (8 sites), `SpawnService` (margin derivation + `SpawnPoints` + `JailSpawn`),
`RoundController` (`FinishSpawns` x2), `BotPathing` (`SpawnPoints`).

`SPAWN_ZONE_MARGIN` stays **derived** rather than inlined — a map with a different-sized zone
now re-derives its own margin instead of inheriting Redwater's 27.

**Two deviations from `FROSTBITE_CLAIM_SPEC.md` §5, both deliberate:**

- **`WallMap` is not in `MapConfig.Instances`.** The spec's example lists it, but it is
  resolved by a string literal in **15** scripts (13 of them sharing a
  `{ "VesperHookSpotsBot", "WallMap" }` raycast-filter idiom across combat code). Wiring the
  2 sites the spec names would leave 13 ignoring the table — a config that is authoritative
  for some callers and not others is worse than no config. Left for a follow-up that extracts
  the shared idiom into one helper.
- **`CorpseFolder` is not in `MapConfig.Instances`.** It has **zero** references anywhere in
  the 290 scripts; its last consumer is gone. It was still listed in the spec's §3a map
  contract, so Frostbite would have been authored a folder nothing reads.

### Dead assets parked out of the client download path, both places

Redwater: `ReplicatedStorage.SFX."Recall complete"` and `"purchase complete"` — two Sounds no
script references by id or by name, and the only two in that folder carrying no `SoundGroup`.
Bounty: `Workspace.WorkingChest`, a 45-part leftover prop parked 341 studs off the lobby whose
server Script played two third-party animations at every server start. Its client driver
(`LootboxMenu…ChestController`) is `Disabled` and named by no script, so the chest minigame was
already dead code. Bounty had no `ServerStorage.Unused` before this; it does now.

Everything under `ReplicatedStorage` and every streamed-in `Workspace` model is fetched by clients
whether or not code touches it, so this is a straight cut to join-time download. Each parked node
carries an `OriginalPath` attribute; restoring one is a reparent, and reverting either place
restores all of it.

Prompted by a live client-error sweep that named both chest animation ids and an `HTTP 429` on the
`Recall complete` id. **The 429 row is unlikely to disappear.** The same second carries fetch
failures from three unrelated subsystems, so it is join-time request volume being throttled rather
than anything about that asset — this reduces volume, it does not target the row.

Verified: both places grep clean for the parked names, and the six Sounds left in
`ReplicatedStorage.SFX` all carry a SoundGroup. **Not playtested.**

## Fixed

### Frostbite Claim: sealed a walk-through gap in the arena boundary

**Frostbite is unpublished and NOT part of this release** — recorded because it is a real geometry
change to a place and this is the only history. It ships whenever Frostbite first ships.

One of `workspace.WallMap`'s 16 parts had its base at Y 62.7 while the other 14 sat at Y 4.0, and the
terrain beneath falls to Y 8.4 — roughly 54 studs of open gap across ~18.5 degrees of arc, about 99
studs of walkable opening on the west side. Corrected to `Size.Y` 312.1 / `Position.Y` 160.0 to match
its siblings; X/Z position and footprint untouched. `CastShadow` also cleared on all 16 (they are
`Transparency 1`).

**Verified:** a 720-bearing scan went from 37 breaching bearings to 0, tightest clearance now 216.6
studs of wall above ground. Angular coverage was already 100% — the hole was purely vertical.

### A player leaving at round start no longer costs everyone behind them their fresh character

`SpawnService.respawnAllPlayers` walked `Players:GetPlayers()` calling `SkinService.loadCharacter`
with no pcall, and `loadCharacter`'s last-resort branch called `player:LoadCharacter()` unguarded.
That throws for a player who has already left, and the throw escaped the loop — so every player
behind the leaver began the round on last round's character, at whatever health they finished on.
`loadCharacter` now routes its three fallback spawns through a presence-checked helper, and
`respawnAllPlayers` pcalls per player.

Logged once on r2545, but the count understates it: one line in the log is one aborted loop, not
one affected player.

Reverting restores the abort; nothing is stored, so it is clean. Redwater only, no mirrored module
touched. Verified: both scripts recompile. **Not playtested** — the confirmation is the
`LoadCharacter can only be called when Player is in the world` row not returning.

### The end-of-match showcase no longer crashes when the podium streams in empty

`VictoryShowcaseClient.getFinishSpawns` checked its three podium slots with `pairs()` over a table built from
`WaitForChild(name, 10)` — and a key assigned nil is absent from the table, so `pairs` skipped
exactly the missing entries the check existed to catch. An empty podium passed validation, the
`if not slots` guard downstream saw a truthy table, and `computePodiumFraming` threw on
`slots.Player1.Position` with the showcase already committed — costing that player the entire
end-of-match sequence. That loop and the identical one over `scene.Spotlights` now walk fixed name
lists. `Workspace.FinishSpawns.BoxPlayerSpawns` is additionally set to
`ModelStreamingMode = Persistent` (18 instances) so the podium stops arriving empty at all.

`FinishSpawns.VictoryScreenRigSpawn` is a bare Part in a Folder and cannot take that property. It
already fails safely rather than crashing, which now makes it the **only** remaining producer of
the `Victory cinematic scene is incomplete` warning — a clean prediction to check after publishing.

Reverting restores both the crash and the streaming default. Redwater only, no mirrored module
touched. Verified: recompiles, and the `pairs` hole was demonstrated on a simulated streamed-out
slot rather than asserted. **Not playtested.**
