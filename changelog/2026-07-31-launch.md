**Summary:** First public release. Two places under one experience — **Bounty** (lobby) and
**Redwater Canyon** (free-for-all deathmatch).

- **Published:** `Bounty r2255 · Redwater r2041` — published 2026-07-31 for the 20:00 CEST launch. **This is the rollback target for the initial release.**

  Read these off **Creator Hub or the in-game version tag**, never from Studio.
  `game.PlaceVersion` in an edit session reports the version the file was *opened* at and goes
  stale as you publish — Studio read `2094` for Bounty while the live server was already on
  `r2099`.
- **Shared modules:** all 16 — mirror verified ✅ (byte length **and** checksum, both places), re-verified at publish time on the eight touched during launch day: `TitleRenderer` 56,830 B, `TitleStyles` 23,531 B, `BattlePassConfig` 21,856 B, `QuestConfig` 16,870 B, `VersionTagController` 10,760 B, `GameEnvironment` 6,132 B, `Wallet` 5,736 B, `FriendBonusConfig` 1,942 B.

  Two traps this release proved, both worth carrying into every `/preflight` run:

  - **A ✅ is only good until the next edit.** `BattlePassConfig`, `QuestConfig` and `GameEnvironment` were each verified and then edited again hours later. The compare belongs at publish time and nowhere earlier.
  - **A length-only compare is not enough.** Bumping `SEASON_ID` from `"S5"` to `"S6"` left the file byte-identical in *length*, the two strings being the same width. Only the checksum caught it.

  `CodeRedemptionService` is a **partial** mirror and deliberately *not* one of the 16: its `CODES` table and `resolveCode` gate are identical by intent, while the award plumbing around them differs per place by design. A whole-file compare therefore always fails and tells you nothing — this one has to be checked by eye. Drift in the shared half is silent and *player-visible*: a code present in only one place reads as invalid in the other while still burning its one-shot-per-profile redemption.
- **Profile schema:** v1 (baseline; not yet version-tracked in code — see [Open items](OPEN-ITEMS.md)). Additive fields only: quest buckets carry a `cycle` field back-derived from `assignedAt` on first load, and profiles gain `RankSeason`, `LastSeasonRankPoints` and `BattlePass.questProgressToken` via `:Reconcile()`.
- **Data-affecting:** **yes** — unusual for an initial release, but four independent groups of stored-data effects ship *inside* this build rather than arriving in a later update. Reverting a place restores code and undoes none of them.
  1. **The battle pass resets on first join.** `SEASON_ID = "S6"` wipes level, XP, quest state and reward-track claims; Tokens and unlocked cosmetics survive. It **also revokes the Full Pass** — `BattlePassService` sets `bp.ownsFullPass = false` in the same block and nothing refunds the 800 Tokens. Correct for a genuine season boundary, and the one part of a `SEASON_ID` bump that is easy to fire by accident, since the module header promises only that Tokens and cosmetics are kept and says nothing about the entitlement. `QUEST_PROGRESS_TOKEN = "2026-07-31-weekly-retune"` separately clears `bp.quests` once. Neither is scheduled — both are token compares in `ensureData`, so they land on each player's next join after publish rather than at a wall-clock instant, and running servers keep the old value until they empty.
  2. **Ranked season 2 begins at epoch `1785517200`** (17:00 UTC / 19:00 CEST). Each profile's `RankPoints` zeroes the first time it is awarded on the new season, and the lobby board moves to a fresh, empty `RankPoints_v2` OrderedDataStore. **Recoverable**, unusually for this list: `RankPoints_v1` is never written to or deleted and each profile keeps its previous total in `LastSeasonRankPoints`, so deleting the season 2 row from `RANK_SEASONS` restores the old board intact.
  3. **The limited-stock run** writes a new DataStore key (`{ sold, pending }`, one per item) and grants `OwnedWeaponSkins` on receipt. Not applied on load — nothing happens to a profile until someone buys — but the least reversible entry here, because units sell for **real Robux**. Reverting un-sells nothing, and lowering `Cap` below the number already sold does not undo a sale, it just pins the item at sold out.
  4. **Redemption codes** grant Cash/Tokens and set `RedeemedCodes` permanently. No migration was needed — reason `code` was already in Wallet's map and `RedeemedCodes` already in both profile templates — but it is one-way in the direction that matters: a code cannot be un-redeemed to give a player another attempt. A wrong Token figure published for `SOPU` or `RELEASE` is permanent for everyone who redeems it before the correction ships.

  **Studio playtests write the live data store** (see [Open items](OPEN-ITEMS.md)), so developer profiles took all of the above during testing — and a Studio purchase burns a real unit out of the 100, permanently.

First public release. Two places under one experience: **Bounty** (lobby) and
**Redwater Canyon** (free-for-all deathmatch).

## Combat
- Server-authoritative hitscan gunplay with lag compensation and position history
- Bullet penetration — shoot through cover, 50% falloff per wall, per-hunter tuning
- Four hunters, data-driven off a per-hunter `Manifest`: **Dust**, **Fortuna**,
  **Vesper**, **Bram**
- Mid-match hunter switching from the kill-cam card row
- **Ability intro tags** — three 2-4 word action phrases resting on a hunter's ability icons for
  the first 30 seconds of *live round time* on that hunter, with the clock stopped while dead and
  between rounds so the window is never spent on a respawn screen. The phrases say what the button
  does rather than what it is called (`DASH + RELOAD`, not `QUICK DRAW`), since the name only helps
  someone who already knows the ability. Copy lives in each hunter's `Manifest`; settings offer
  Default / On / Off.
- Bots with full ability kits for all four hunters. **Always at least 4 in a match**, at
  every player count — the bots are deliberately weak, so this guarantees every player
  (especially a new one on a phone) always has something they can reliably kill. A skill
  floor, not an empty-server measure, which is why it does not taper as population grows.

## Rounds
- Timed FFA rounds with intermission, stats and map reset
- Post-game summary, victory showcase, kill cam
- Round XP and Cash banked during play, paid out at the buzzer

## Progression & economy
- Account XP and levels; Cash and Tokens routed through the `Wallet` chokepoint
- **Battle pass** — *Season 1: Dead Man's Hand*. Two linked tracks, paid 1–30 plus 12 free
  levels, 800-Token Upgrade Pass. Three themed, non-repeating weeks — W1 *Ride In* (breadth),
  W2 *Dead Eye* (precision and pressure), W3 *Legend of Redwater* (mastery) — 7 slots and
  21,500 XP each. Internally `SEASON_ID = "S6"`; the id is a reset counter, not the season
  number players see.
- **Daily quests** — 24 across 10 groups: kills, headshots, kill streaks, damage, assists,
  placement, bounties, bounty time, ultimates and hunter variety. A draw takes three *distinct*
  groups, so a day can never serve a pair like "5 kills" and "10 kills" where the smaller one
  completes itself.
- **Weekly quests**, manually claimed, one page per unlocked week. The pass and the WEEKLY tab
  point at each other — a live banner on the pass reads how much XP is waiting to be claimed,
  and the tab carries a VIEW PASS button back.
- **Daily play-streak rewards** — earned in Redwater, claimed in the lobby
- **Ranked RP** with a top-100 lobby leaderboard and **scheduled season resets**. `RANK_SEASONS`
  holds season-start epochs; the season number doubles as the leaderboard store suffix, and each
  profile zeroes itself lazily on the first award of a season it has not seen. Season state
  resolves from `os.time()` on every call, so a server already running at the boundary rolls
  over on its own — no republish, no restart. Scheduling the next reset is one appended row.
- **Limited-run items** — globally capped and sold for Robux, with the unit reserved *before* the
  purchase prompt opens so the run cannot oversell into a refund that Roblox cannot give.
  First item: the **Prestige Card** Fortuna weapon skin, capped at 100 units.
- **Redemption codes** — per-code Cash and/or Tokens, with an optional `active` flag and a
  `startsAt`/`expiresAt` window stored in UTC. Live at launch: `SOPU` (200 Tokens) and
  `RELEASE` (100 Tokens), both closing 2026-08-08 00:00 CEST. Four like-milestone codes are
  authored and switched on by flipping one field. A code that is off or not yet open reports as
  **not found**, never "coming soon" — the milestone codes are trivially guessable, and a
  distinct response would confirm to anyone typing `500LIKES` that it exists and is worth
  retrying later.
- **Friend-group bonus** — +5% Cash & XP per friend on the server, capped at +50%
- **Boost potions** — +25% XP or Cash for a match, activated lobby-side

## Social & routing
- Parties, matchmaking, and a MemoryStore match directory with a 3-minute soft lock
- Redwater holds **10 humans** (`MATCH_PLAYER_CAP` 7 + `FRIEND_SLOTS` 3) plus 4 bots, for a
  ceiling of 14 fighters. Bots are Models in `workspace.ArenaBots`, not Players, so they never
  consumed player slots — the human cap was set to hold the *total* at 14. Creator Hub
  Maximum Visitor Count and Social Slots (Customize = 3) must match these numbers.
- Friend bonus caps at 9 friends (+45%), since 9 is the most that can share a 10-human server
- Friends-list joins forwarded from the lobby into the friend's live match
- Offline gift grants applied on next lobby join

## Release infrastructure
- **`ProfileService.ForceLoadMaxSteps` had diverged: 8 in Bounty, 4 in Redwater.** It controls
  how many steps ProfileService waits before *stealing* a session lock from another server
  (~7s each, so 56s vs 28s). Both are now 8, the upstream default, and the two copies are
  byte-identical. The 4 was set to work around Studio playtests locking a profile — but
  Studio uses the **live** data store (no `IsStudio` branch on `GetProfileStore`), so a
  development annoyance was being treated with a production-wide data-safety setting. It
  matters more now that `SoftShutdown` deliberately mass-evacuates servers: that is exactly
  when the steal timer is reached, and a stolen live session loses the buzzer payout the old
  server had not saved yet. **Open item:** scope the profile store on `IsStudio()` the way
  `MatchDirectoryService` scopes its MemoryStore map, so this never has to be a compromise.
- `GameEnvironment` (mirrored) — resolves environment, sibling place IDs, version string
  and `isLive` from `game.PlaceId`. All 7 previously hardcoded place ID sites now resolve
  through it: Bounty `PartyService`, `FriendJoinService`, `Wallet`, `Telemetry`; Redwater
  `Config`, `Wallet`, `Telemetry`. Behavioural no-op on Live — identical values, one source.
  Makes a DEV universe safe to add later without per-environment constant edits.
- Always-visible build tag, top-left in both places, so a bug screenshot carries the exact
  version without the player opening a menu. Built in code rather than authored, so it can
  be checksum-compared against its mirror. Text size scales off viewport height (clamped
  7–15): phone viewports are 360–440 studs tall against 720–1080 for desktop, so a fixed
  size rendered ~3× larger in the hand than on a monitor. Tuned twice against real
  handsets; every phone and tablet now sits between 1.79% and 1.94% of screen height.
- `SoftShutdown` (mirrored) — evacuates players to the lobby on server close, so
  *Shut Down All Servers* retires stale code instead of disconnecting everyone.
- MemoryStore match-directory and pending-join maps carry a `_studio` suffix, so a Studio session
  gets its own pool and can never route a live player into a Studio server, or the reverse.
- Telemetry now gates on `GameEnvironment.isLive` as well as the existing Studio check,
  so a DEV server (which is *not* Studio) cannot write into live dashboards.

  *Deviation from plan:* the intent was to stamp the version onto every event, but
  `CustomField01/02/03` are all already spoken for and the 8,000-unique-combination budget
  is per-experience — a field whose cardinality grows with every release would consume it
  for no benefit. Release timing is date-bounded and recorded here, which serves the same
  analytical purpose for free.

## Design notes worth keeping
- **Ultimate kills are a time window**, not Ultimate-sourced damage. Fortuna's ult is a vanish that
  deals no damage *and blocks her own attacks*, and Bram's Last Call is a self-buff — a strict rule
  is uncompletable for both. A kill counts while `UltimateActive` is set or within 10s of
  activation.
- **No generic "ability" quest.** Only Bram and Fortuna have a damaging ability; Dust's dash and
  Vesper's grapple/scope deal none, so half the roster could never finish one.
- **"Hold a bounty" counts seconds marked**, not "bounties survived" — `awardBountySurvival` fires
  both when a bounty holder dies and when one reaches the buzzer, so a survival quest hung off it
  would count dying as surviving.
- **A 3-kill streak is exactly the bounty trigger** (`BOUNTY_KILL_THRESHOLD = 3`), so no
  killStreak3 quest exists anywhere — it would be "Become a Bounty" wearing a different label.
- The hunter-swap quest's *how* lives in the card's title slot (`SWAP ON DEATH`) because the
  objective slot is physically too small to hold it.
