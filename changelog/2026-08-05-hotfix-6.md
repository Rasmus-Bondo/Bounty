# Hotfix 6 — 2026-08-05

**Summary:** The largest launch-issue sweep yet — Bram's charge clash and cooldown, duplicate and
truncated kill-feed lines, bots vanishing mid-fight, and anti-cheat kicks during the end-of-match
summary — plus bots carrying bounties, per-tab quest dots in the lobby, and a leave-match popup
rebuilt in the game's own style.

## Added

- **The DAILY and WEEKLY quest tabs now carry a red dot when something is waiting to be claimed**
  (Bounty; verified by the owner 2026-08-05). The QUESTS button on the left of the menu has always
  shown a badge when a reward is ready, but it could not say *where*. A player who opened the panel
  onto DAILY, saw nothing claimable and closed it again had no reason to look at WEEKLY, where a
  finished battle-pass quest might have been sitting since their last match — the pass only marks
  those quests complete, it never pays them, so they wait to be collected by hand and can sit
  unclaimed for the rest of the season. Each tab now answers for itself: the dot appears on DAILY
  for a completed daily quest or the complete-all bonus, on WEEKLY for any finished battle-pass
  quest in an unlocked week, and clears as soon as the last one on that tab is claimed. The
  left-hand badge is unchanged in meaning and still stands for the panel as a whole. Both are now
  computed from the same two counts in one place, so the badge and the dots cannot disagree. EVENT
  has no dot; that tab is still deliberately empty.

  Nothing new drives the clearing. Both claim paths already echo fresh state back from the server —
  which is what redraws the cards — so the dots ride the refresh that was there. One incidental fix
  came with it: the badge's visibility check used to give up early whenever the left-hand menu had
  not finished loading, and since that menu lives in a separate screen and resolves late, it would
  have left the new tab dots stale. Each is now checked on its own.

  **The dot sits centred on its button's top-right corner, and keeping it there took a second
  pass.** It half-overhangs into the gap between tabs, and that gap scales with the *width* of the
  screen while the dot scales with the button's *height* — so on a squarer screen the overhang
  outgrew the gap and ran into the next tab, by roughly 1.5 pixels on a phone and 3.8 on a 4:3
  tablet. Shrinking the dot enough to survive the worst case made it weak everywhere, and pinning
  it inside the corner instead was visibly not the placement asked for. So the position is
  corrected rather than the size: the dot is pulled in by exactly the amount that would have
  overlapped and no more, which is **zero on any screen with room for it**. Measured at 0.0px pull
  on a 2.45:1 desktop, 2.0px on an iPhone 7 and 4.0px on a 4:3 iPad, each leaving daylight to the
  next tab.

  Worth knowing for anyone adding a corner badge later: this is a *positioning* problem and not a
  sizing one, and 4:3 is the aspect that exposes it — a phone alone will not. The dot is authored as
  a real instance on each tab button, like the rest of this panel, and the recentring runs when the
  panel is resized and once on first open, because nothing here has a measurable size until the
  panel has been shown once.

  **What was checked, and what was not.** Geometry was measured at the three aspects above and the
  panel screenshotted at each; the script compiles. The dots were confirmed appearing correctly in
  a live playtest driven by real claimable quest data — but that run covered the earlier tucked-in
  placement, because the playtest ended before the corner-centring landed, so **the final placement
  has been seen only in edit mode**. Clearing-on-claim follows a refresh path that was already in
  use and was traced end to end in both services, but was not watched happening in a running match.

## Changed

- **The "leave the match?" popup has been rebuilt in the game's own style** (Redwater). Pressing
  *Return to Bounty* in the settings panel used to raise a plain grey box in a different typeface to
  everything around it — the only piece of UI in either place that looked like it came from a
  different game. It was also mispositioned: its top-left corner was pinned to the centre of the
  screen rather than the box itself, so it hung down and to the right, overlapping the settings panel
  it had just been opened from and covering the crosshair colour swatches. It is now a dark-brown
  panel with the same gold outline, edge-straddling title plaque and gold rule the settings panel
  behind it uses, centred properly, with an amber **STAY** and a deep-red **LEAVE**.

  It is also **modal** now. Previously the settings panel stayed live underneath, so a press that
  landed outside the popup could still drag a volume slider or hit a toggle while the game waited for
  an answer. The popup now sits on a dimming full-screen layer that absorbs those presses.

  Three things behind it are worth recording, because each is a trap that will be hit again:

  - **Button labels have to be the same length.** Text that scales to its box shrinks the *longer* of
    two labels, so the first draft's `STAY IN MATCH` / `RETURN TO BOUNTY` pair rendered at two
    visibly different sizes and the long one wrapped onto two lines on a phone. `STAY` / `LEAVE`
    render identically at every size; the sentence above them carries the detail.
  - **A minimum touch size on a button pushes its neighbours around.** The button row keeps a 44px
    floor for phones, and on a 360px-tall screen that floor grew the row upward *into* the body text
    — a measured 4px overlap. The popup itself now has a minimum height, so the row's normal
    proportion is already above 44px and the floor never has to engage.
  - **Capping text size breaks large screens.** Caps tuned on a phone left small labels stranded
    inside big buttons at 1080p. Every text box is now a fraction of the popup and the popup a
    fraction of screen height, so the type scale is identical everywhere with no caps at all.

  Bounty has no equivalent popup — this flow is Redwater-only — so nothing was mirrored. Verified by
  screenshot at 1920×1080, 1024×768, 640×480 and an 800×360 phone, with the geometry measured rather
  than eyeballed at both extremes: no overlap, buttons at or above 44px, both labels at matching
  size, and the popup fully on-screen. The controlling script compiles and every instance it looks up
  still resolves. **Not checked in a live match** — the popup was verified against the real authored
  panel in edit mode, so what remains unseen is the button actually firing the teleport, which was
  not touched.

  **The design language it was rebuilt against is now written down**, in `UI_STYLE_GUIDE.md` in the
  project root, derived by scanning every screen in both places rather than from anyone's intent —
  colour tokens, the three legitimate fonts and the banned ones, corner and stroke rules, component
  recipes, motion timings, the `DisplayOrder` registry, and a build-and-verify order. `CLAUDE.md`
  points at it as required reading before any UI work, and it is a living document agents may edit.
  It exists because this popup was not an isolated lapse: three panels had drifted to plain grey
  boxes in a different typeface, and each one drifted because the style was only ever recorded in the
  instance tree. The remaining three are listed in its "known style debt" section — including the
  "Returning to main menu…" screen above — so they get fixed rather than copied.

  It also corrects two pieces of received wisdom that were costing time. `UIStroke.Thickness` on a
  **newly created** stroke is plain pixels and anything below 1 is invisible; the sub-pixel values
  all over the authored files render only because those instances carry it through `:Clone()`, so
  copying such a number into a new stroke silently produces nothing. And a `UIGradient` on a
  `TextButton` tints the **text** as well as the fill, which is why every gradient button in the
  lobby uses black text — white text on a red gradient disappears entirely. Both read back from the
  properties as perfectly correct, which is the general lesson the guide now leads with: only a
  screenshot verifies UI.

  The screen that follows it — the "Returning to main menu…" line — is still in the old typeface and
  now looks out of place directly after this. It is logged as the top item of style debt rather than
  changed here.

## Fixed

- **Skin prices in the Trading Post sit centred again** (Bounty; verified by the owner 2026-08-05).
  On the SKINS panel the token
  price, and the OWNED / GROUP PERK / BOUNTY PASS / LOCKED lines that share the same slot, were all
  drawn about ten pixels right of where they belong — a fifth of the way off centre in a panel that
  narrow, and visible as the price and the BUY NOW button beneath it not lining up. Everything on
  that panel is centred, so the one line that was not read as a mistake.

  The cause is worth recording because it is an easy one to reintroduce: the coin and the number are
  a single centred pair, which means the number has to be nudged right of centre to leave the coin
  room on its left. That nudge is **already built into the position the panel is authored with** —
  it matches the calculated value to sixteen figures — and the code was adding it a second time on
  top. The word states then inherited the coin's spacing while showing no coin. Prices now stay
  exactly where the panel is drawn in Studio, and the word states subtract the coin's allowance
  instead. The sibling Cash price on the HUNTERS panel already worked this way; the skin price is
  now the same.

  **What was checked:** the script compiles; every state re-measured against the panel's centre —
  0.00px on all four word states, and 0.25px or better on prices of three and four digits (that
  residual is a known approximation in how digit widths are estimated, documented in place and
  unchanged by this fix). Confirmed by screenshot with a centre guide drawn on the panel, before and
  after. **Confirmed in a live playtest by the owner 2026-08-05**, which closes the one gap those
  edit-mode measurements left.

  Found while fixing the entry below, not reported from play, so it has presumably been off since
  the coin was introduced.

- **Emote and title prices in the Trading Post now show the coin instead of spelling out the
  currency** (Bounty; verified by the owner 2026-08-05). Selecting a title or an emote on the
  ACCESSORIES tab filled the panel on the
  right with the words "600 CASH" or "250 TOKENS" — the last place in the shop that wrote the
  currency out in text. Everywhere else already shows the art: the currency bar along the top of the
  menu, the price tag on every card in the grid behind that very panel, and the HUNTERS and SKINS
  panels in the same shop. So the one spot a player looks at *after* deciding what they want was
  also the one spot that read differently from everything around it. It now reads as the gold coin
  or the purple token followed by the number, formatted the same way the card behind it is —
  `1.500`, not `1500`.

  A pass-exclusive emote is unchanged and deliberately so: its line says **BOUNTY PASS** with no
  coin, because that is a route to the item rather than a price, and hanging a currency icon off it
  would imply one.

  Worth knowing for anyone touching this panel later: the coin and the number are **one centred
  pair**, so both move when a price gains a digit — the number is centred in a full-width label, so
  its left edge, which is exactly where the coin has to sit, travels with the price's width. The
  font's digits are not all the same width here (a `1` is roughly three-quarters of a `0`, and the
  thousands separator is narrower still), so the width is measured per price rather than counted in
  digits, and the whole calculation is expressed as fractions of the label — the shop is aspect-
  locked, so those hold at every screen size and none of it depends on measuring the panel after it
  has been drawn. The icon itself is an authored instance copied from the skin panel's, so it
  carries the same art and shadow rather than a hand-built lookalike.

  **What was checked:** all three affected scripts compile; the pair lands within half a pixel of
  the panel's centre at 600, 1.500 and 250 Tokens; the label does not creep across repeated
  selections; the token icon swaps in for a token-priced title; and the panel was screenshotted at
  2x in each state. That was done against the real authored panel in edit mode, and the panel was
  then **confirmed in a live playtest by the owner 2026-08-05** — nothing outstanding.

- **The SWAP HUNTER button now appears every time you go down** (Redwater; launch issue #20). The
  mid-match hunter swap is offered only while you are dead, and sometimes it simply was not there —
  no button, no cards, nothing to pick from, so that death was spent as whichever hunter you were
  already playing. The panel waits for the server to confirm you are down before it offers itself,
  which is deliberate: it is what stops you tapping a hunter a fraction of a second before the
  server will accept the choice. But that confirmation could arrive fractionally *before* your own
  character finished registering the death, and when it did, the panel checked once, saw a player
  who was still alive, and never looked again for the rest of that life. It now takes a second look
  the moment your own character dies. The server still decides when the offer opens — nothing was
  loosened, and the panel still cannot be opened while you are alive — it just stops being possible
  to miss the one moment it was listening. A related gap is closed alongside: the hook that noticed
  your death could be dropped entirely if two respawns landed in quick succession, which is what
  made this worse near a round boundary and on a slow connection.

  Fixed in the same pass, and a different bug with the same appearance: **the four hunter portraits
  could come up as empty boxes.** The panel asked for each hunter's model without waiting for it to
  finish arriving, and on a slow join it had not. There was no second attempt, so the cards showed
  as blank tiles with names underneath for the rest of that session — which reads as the menu being
  broken rather than the pictures being late. It now waits for them, and a portrait that arrives
  late fills itself in rather than staying empty.

  Worth knowing for testing: **the cause is a timing race, so it will not reproduce on demand.** It
  needs real latency, and it was never the kill cam or the swap teardown, which is where the
  original notes pointed. The fix also writes a line to the log each time it catches the race, so
  the next match played on a live server will say how often it was actually happening.

- **Cosmetic titles now fade in with the nameplate instead of appearing ahead of it** (both places;
  launch issue #18). Seven of the 28 titles — DEADEYE, DRIFTER, EAGLE EYE, IRON BUCK, THE DEALER,
  BREACHER and GUNHAND — drew their outline and glow at full strength the moment the title was set,
  whether or not the panel carrying it was visible yet. On the overhead nameplate, which spends most
  of its life hidden and re-reads a player's equipped title whenever it arrives late, that showed as
  the title hanging in the air above a player with no name and no health bar under it, until the next
  hit faded the rest of the plate in around it.

  **The other 21 titles were never affected, which is why this read as a problem with one title
  rather than with titles generally.** Every title's decoration is meant to follow the transparency of
  the text it belongs to, and the animated styles genuinely do — they recompute it every frame, so
  they correct themselves on the next one. The seven above use styles that draw nothing moving and
  therefore have no per-frame pass to correct anything, and nothing else revisited the decoration once
  it had been built. Those styles now check the same signal when a title is first applied and again
  whenever they re-measure, so they hide with the panel and return with it.

  Closed by the same change: those styles could also quietly re-light themselves on an already-hidden
  nameplate, because the pass that re-measures a title as the camera moves rewrote the glow's strength
  from its authored value without checking whether the plate was visible — and an overhead nameplate
  re-measures continuously, since its text scales with distance. Decoration is now restored from its
  own recorded strength on the way back in rather than relying on the panel's fade to sweep it, so a
  surface that shows titles without a fade of its own cannot end up with the decoration stuck off.

- **Two Brams charging into each other now cancel out instead of locking together** (Redwater;
  launch issue #23). The charge grabs whoever it catches and carries them along, and nothing stopped
  it grabbing another Bram who happened to be charging at the same moment — so the two grabbed each
  other. A carried player is held in place by their own device, which meant each player's position
  was being set by the other's, a frame out of date, and the pair snapped back and forth several
  studs every frame. It could not resolve itself: a victim is only released once they get far enough
  away, and these two never separated far enough to trigger it, so both players sat in a violent
  jitter for the best part of four seconds, unable to shoot, reload, use an ability, or cancel the
  charge that had caused it. Head-on charges now cancel each other: both charges end, both Brams are
  stunned briefly, and neither is carried. Anyone *else* either Bram was carrying is dropped exactly
  as a charge ending without a wall has always dropped them, and both pay the full cooldown.

  The stun is deliberately shorter than the one a wall slam inflicts. A slam is a fight someone
  lost and costs them health on top; a clash is symmetrical, nobody misplayed it, and both players
  have already forfeited the ability and its cooldown. It matters too that in a free-for-all, two
  players stunned in the open together are an easy double kill for whoever else is watching — that
  is the thing to weigh if the length ever needs adjusting, and it is a single tuning value.

  Deliberately **not** done: knocking the two apart with an impact effect. It is the flashier
  version and it was considered, but it is a new mechanic — knockback distance, stun length and new
  impact FX all needing tuning and art — for a bug whose entire cost is that the two charges fail to
  resolve. **Bot Brams are not part of this and did not need to be:** a bot's charge is a separate
  implementation, and a bot is driven by the server rather than by its own device, so a player
  charging into a charging bot could never produce the deadlock. That still grabs the bot as before.

  This was found by analysis rather than reported, and had been deferred with the diagnosis written
  up but no code changed, pending the decision on how a clash should resolve.

  **A second bug came out of the first: after a clash, Bram could not jump again for the rest of
  that life.** It was reported immediately on testing the above, and it is older than the clash fix
  rather than caused by it. The charge switches jumping off for its duration and switches it back on
  when it ends — except when the player is stunned at that moment, where it deliberately stood aside
  on the grounds that the stun owns the same lock and would hand jumping back itself. It does not.
  The stun runs on the server, and that particular switch is one each machine keeps its own copy of,
  so the server flipped its copy back and the player's own copy — the only one their jump input
  actually consults — stayed off. Nothing else ever turned it on again. Standing aside is still the
  right call while a stun is running, so the charge now genuinely waits and hands jumping back the
  moment the stun lifts, with a deadline as a backstop so a stun that somehow never clears costs a
  few seconds rather than the rest of the round. Switching hunters mid-match also hands it back
  unconditionally, since a Bram who has been swapped away is not around to finish the job.

  **This was reachable before today** — it needed Bram to be stunned at the instant his own charge
  ended, which until now meant being slammed into a wall by a second Bram mid-charge. Rare enough to
  have gone unreported, and common enough to be worth knowing it was never specific to the clash.

- **Dust's High Noon keeps its narrowed view for the whole ultimate** (Redwater; launch issue #24,
  verified by the owner 2026-08-04). The ultimate zooms the camera in as it locks on, and that zoom
  was being thrown away the instant it finished — about 2.7 seconds into an ultimate that can run
  for five. It did not fade, it cut, which is what made it read as the ultimate having expired while
  targeting was plainly still live. Nothing was ending early: the zoom simply stopped being held,
  and Dust's sprint camera — which was quietly writing the field of view every frame whether it had
  anything to show or not — took the camera back the moment the ultimate's own camera control let
  go. The sprint camera now releases the view whenever it has nothing to do, so the ultimate holds
  its zoom until it genuinely ends and then eases back out over about a second. Ordinary play is
  untouched: the sprint widen, the shot and dash kicks all behave exactly as before, and when the
  sprint camera does pick the view back up it picks up from wherever the camera actually is rather
  than snapping from a stale value.

  This was the same class of problem as a swap between two hunters snapping the view, and the
  internal hunter guide has been corrected to match: owning the field of view is not enough on its
  own, an owner also has to let go of it when idle, or it silently outlives every other camera
  effect in the game. **One thing to watch** — starting a sprint in the instant the ultimate is
  easing back out is the single handoff that could not be checked without playing it.

- **Being killed by Dust's High Noon is no longer silent** (Redwater; launch issue #3, verified by
  the owner 2026-08-04). The victim heard nothing at all — not even the ordinary bullet impact every
  other weapon in the game plays on them. High Noon is the one attack that does not run through the shared post-hit chain; it keeps its
  own copy of that bookkeeping, and the copy had simply never made the audio call. A Dust *bot's*
  ultimate has always played it correctly, so the bug only ever affected being shot by a real player.
  The same fix passes along the flag that tells a victim's client a shot connected, which lets it stop
  playing a near-miss whizz for a bullet that actually hit them. Deliberately **not** done in this
  pass: folding High Noon back onto the shared chain outright, which is the standing recommendation
  and would delete the duplicate for good — it re-routes kill feed, kill cam, ultimate charge and
  stats on a live ultimate, which is far more risk than an audio fix should carry. That remains worth
  doing on its own.

- **Vesper's first shot after her ultimate has its rifle report back** (Redwater; launch issue #4,
  verified by the owner 2026-08-04). Starfall shots are supposed to play their own layered report
  instead of the ordinary one, and the viewmodel muted the normal sound for a single shot to make
  room. But it was waiting for an
  ammo-spend to tell it when that shot had happened, and Starfall runs on its own pool of rounds with
  the magazine frozen — so the moment never arrived, the mute survived the whole ultimate, and it
  landed on the player's next *ordinary* shot instead. Exactly one shot, right after the ultimate,
  which is what made it look like the ultimate had caused it. The ultimate shot now drives the
  viewmodel directly rather than waiting to be told. That fixes a second half nobody reported: the
  ultimate's shots had no shoot-or-cycle animation at all, for the same reason. **One thing to listen
  for** — the bolt-cycle layer belongs to that animation and so is now audible during Starfall, under
  the ultimate's own report. It has never been heard there before, and muting it too is a one-line
  change if it reads as cluttered.

- **Bots now leave when they next die instead of vanishing the moment a player joins** (Redwater;
  launch issue #19). The arena keeps a target headcount, so every join displaced a bot — and it did
  so by destroying that bot where it stood, taking the character with it. Anyone mid-fight with it
  watched their opponent blink out. The bot being displaced is now flagged rather than deleted: it
  keeps playing, keeps shooting back, and is removed after its next death, which is a moment nobody
  is looking at. Because it leaves through the ordinary death path, a player who kills a departing
  bot still gets the kill, the assists still resolve, and a Bram bot that dies mid-charge still hands
  its victim back rather than stranding them locked in place. A player *leaving* now cancels a
  pending departure instead of spawning a fresh bot, so the same fighters stay in the match across a
  join and a leave, and the guarantee of at least four bots at every player count is unchanged.
  Departure flags never survive a round: the next round clears the roster and rebuilds it against
  the current player count.

  One consequence worth knowing: a flagged bot that stays alive through a run of joins means the
  arena briefly runs above its headcount target, up to a worst case of 8 bots alongside 10 players
  where the old behaviour capped out at 4 alongside 10. It is transient — every flagged bot leaves
  on its next death, and a round boundary resets it regardless — and the bot count itself never
  exceeds the existing maximum of 8. Deliberately **not** given a timeout that removes a
  long-surviving flagged bot anyway: that just reintroduces the disappearing-bot symptom on a delay,
  and the round boundary already bounds how long it can last.

- **Players are no longer kicked during the end-of-match summary** (Redwater; launch issue #25).
  The victory freeze anchors the player and drops their walk speed to zero for the whole 30-second
  showcase, but the movement checks did not know that: their only cover was the 8-second window the
  jail teleport grants, leaving ~22 seconds in which a body the server itself had pinned was judged
  as if it were moving under its own power. Anyone frozen somewhere with no ground beneath them —
  under the terrain, over a gap, mid-void — accrued flags they could neither move off nor decay, and
  was removed from the match roughly 14 seconds into the summary. **Do not describe this one in
  player-facing wording** beyond "backend improvements": it is an anti-cheat change. Immunity now
  starts with the freeze and is cleared when it lifts, and the closing lobby teleport re-grants it
  after the unfreeze rather than before, where the unfreeze immediately dropped it again. Anchored
  bodies also have their velocity zeroed, so a frozen player no longer reports the speed they
  carried into the buzzer for the rest of the showcase. Deliberately **not** done: exempting
  anchored characters inside the checker itself — clients can anchor their own character parts and
  have it replicate, so that would be a free bypass. Diagnosed from a live export; the extra
  context fields added on 2026-08-03 for exactly this purpose identified the cause in one pass.

- **A spawn teleport that the client refused is now detected and repaired** (Redwater). Moving a
  player is a server write against physics the *player* owns, and a client asserting its own
  position could win — with no error and no failed return, so nothing downstream could tell. At the
  end of a match this merely left someone frozen in the wrong place; at the **start** of one it cost
  them the entire match, stranding them at the jail spawn 59 studs below the map, and the existing
  retry for slow-loading clients could not see it because a discarded write still reported success.
  Spawn teleports now re-check the player a third of a second later and correct them only if they
  are more than 30 studs from where they were sent. The tolerance is loose on purpose: players are
  dropped four studs above a spawn point and are still falling during that window, while the real
  failure measured 119 studs off. The correction takes ownership of the character for the rewrite
  and hands it straight back, retrying the handback if the body is anchored at that moment, because
  a player left server-simulated feels like permanent lag. Missed jail teleports also warn now
  instead of passing silently.

- **Bram's Breach Charge cooldown now starts when the charge ends, not when Q is pressed**
  (Redwater; launch issue #5, verified by the owner 2026-08-04). The charge previously ran *inside*
  its own cooldown, so the ability came back roughly 3 seconds after a full charge finished rather
  than the 6 the number implies — and a charge cut short on a wall came back sooner still. The
  cooldown value is deliberately unchanged at 6s; moving where it starts lengthens the real gap on
  its own. Applied to all three implementations of the charge: the server, the player's client
  (which owns its own input gate and cooldown meter), and the bot Bram, which gated on the same
  number and would otherwise ram more often than a player can. Two behaviours were deliberately
  preserved: Last Call still refreshes the charge and each landed blast during it still shaves the
  cooldown, including when either lands mid-charge, and the Q meter still stays occupied for the
  duration of the charge rather than reading ready while a press would cancel it. Dying mid-charge
  now starts the cooldown the same way every other ending does, so the meter can no longer clear
  ahead of the server and offer a charge the server refuses.

- **Bram's Breach Charge is now committed for its first second and cannot be thrown away on the
  press** (Redwater; launch issue #6, verified by the owner 2026-08-04). Tapping Q a second time
  used to abort the charge instantly, so a fumbled double-tap spent the ability and the full
  cooldown for no distance and no pin. The charge now ignores a cancel for its first second and
  cancels normally after that; an early press is discarded rather than remembered, so it cannot end
  the charge a moment later when the player has forgotten making it. This completes the commitment
  rule the charge already followed elsewhere — firing during a charge does not cancel it, and
  jumping is locked for its duration — leaving Q-again as the only deliberate way out. The mobile Q
  button follows the same rule. Everything that ends a charge for you is unaffected and still ends
  it immediately: ramming a wall, leaving the ground, dying, or the server calling it. The one-second
  window is a tuning value rather than a constant in the logic, so it can be adjusted after more
  play without touching the ability.

- **A kill can no longer show up twice in the kill feed** (Redwater; launch issue #10). One death now
  posts one line, whichever weapon or ability landed it and whether the killer was a player or a bot.
  **Nothing was ever double-paid for it** — that was checked before anything was changed rather than
  assumed. Kills, Cash, XP and quest progress are all credited once per death from the death itself,
  on a path deliberately kept separate from the feed so that deaths the weapons never see (the closing
  fire, a fall, a bot's killing blow) still credit properly. The duplicate cost a line and nothing
  else. The one place the two were coupled was a bot's own kill tally, which is booked in the same
  breath as its feed line; that is now covered by the same guard, so a bot's scoreboard count cannot
  drift from what the feed showed.

  **The cause is still unknown, and the fix is built to say so.** Every path that announces a kill was
  audited and every one of them already tested correctly for having landed the killing blow — a second
  hit into a body that is already down reports nothing, and the paths that could plausibly strike one
  victim twice each turned out to be closed. The duplicate is therefore something that only happens
  under live timing, and it could not be reproduced by reading. Rather than guess, the game now
  refuses a second announcement for a death it has already announced, on the reasoning that a
  character can only die once — which holds no matter what the cause turns out to be — and **writes a
  detailed warning to the server log whenever it actually catches one**, naming both announcements and
  where each came from. The next log export from a live match will identify the root cause without
  anyone needing to reproduce it. Seeing those warnings appear is the good outcome, not a bad one:
  it means the guard is catching a real duplicate that players would otherwise have seen.

  Deliberately **not** done: suppressing on "same killer and victim within a few seconds", which would
  also have swallowed a legitimate second kill after a fast respawn and would have needed a guessed
  time window to tune. And an announcement that cannot be identified is let through rather than
  refused, on the principle that a missing kill feed line is a worse failure than a repeated one.

- **Kill feed names no longer get cut off with "…", and the feed's text is smaller on phones**
  (Redwater; launch issue #14). Each name sat in a fixed-width slot that fitted about 13 characters
  on a phone, while Roblox names run to 20 — so anything longer was chopped. The slot could not lend
  space either, so a long name was truncated even when the name opposite it was two letters and most
  of the row was empty. The two names now size themselves to their text and **share** the row between
  them, so a long name uses whatever room the short one beside it is not. Phone text also drops a
  size, which is the other half of what was asked for. Between them, a phone now fits roughly 32–36
  characters across both names instead of about 13 in each — an 18-character name beside a
  19-character one renders in full where previously both were cut. Desktop keeps its current text
  size and gets the shared-row change only; long names fit there now too. An ellipsis is still
  possible if two players with maximum-length names in the widest letters kill each other, where
  nothing short of unreadable text would fit — but it is no longer the everyday case.

  Worth knowing for testing: **bots cannot show this bug.** The longest bot name is 11 characters, so
  a match against bots always looked fine no matter how long it ran; it takes a real player with a
  long display name to see it.

- **The kill feed now sits flush against the right of the screen** (Redwater). The feed itself was
  always pinned correctly, but the text inside each line was centred within it, so every line ended
  at a different distance from the edge — on a phone, a short name finished nearly 103 pixels from
  the edge and a long one 38, which made the whole feed look like it was floating rather than tucked
  into the corner. Lines are now aligned to the right, so every one of them ends at the same place
  and the feed reads as anchored. The uneven edge moves to the left-hand side, where there is nothing
  for it to line up against and it simply looks like a kill feed. Desktop gets the same change for
  the same reason. This was a long-standing issue rather than a new one — the previous fixed-width
  layout put a short name marginally *further* from the edge than the current one does; it only
  became easy to see once the names stopped being padded out to a fixed width.

  A related possibility was checked and deliberately left alone: the feed keeps clear of device
  "safe areas" — the notch and rounded corners on modern phones — and that reserved strip can add a
  further gap on such a handset. It cannot be reproduced or measured in Studio, which models no
  notch, and removing it risks the feed sliding under one. **If the feed still looks inset on a real
  phone, that is the cause and not the alignment.** Also no longer done in this pass, and now much
  less pressing: making each line shrink to fit its contents. Short lines still draw a wider
  translucent bar than they need, but with the text correctly aligned the bar is the only thing left
  out of place, and the empty part of it now sits on the left where nothing lines up anyway.

- **Bots on a killing spree now get a bounty on their head, the same as players** (Redwater; launch
  issue #21, verified by the owner 2026-08-04). Three kills without dying has always marked a
  *player*: a gold outline visible through terrain, a row on the bounty board carrying a cash value
  that climbs the longer they stay alive, and a payout to whoever brings them down. Bots were never
  eligible, so in a match that is mostly bots the whole mechanic sat idle. They are now marked at
  exactly the same threshold, share one board with players ranked against them by the same climbing
  reward, and pay out the same when killed — including credit toward the "Kill the Bounty Target"
  daily. A bot's bounty ends with its life, and a bot finished off by another bot simply loses the
  mark with nobody paid. Bots earn nothing themselves: the survival bonus a marked player collects
  for staying alive has no meaning for one.

  **The glow needed a second pass, and it is worth knowing about before anything visual is ever
  added to a bot again.** What a player actually sees of a bot is a smoothed copy the game draws
  locally, not the body the server moves around — so the outline has to be drawn on the copy. Put on
  the server's body, which is the obvious place and exactly where the player version lives, it
  attaches to something nobody is looking at, and the first version of this shipped invisible for
  precisely that reason. The outline is now driven off the bounty board's own broadcast, which
  republishes the whole list about once a second, so it corrects itself if a player joins
  mid-spree, wanders far enough for the bot to be rebuilt, or misses the moment the bounty was
  placed.

  One thing to watch: **more bounty targets means more bounty payouts.** Bots backfill against the
  player count, so the quietest servers have the most of them, and the "Kill the Bounty Target"
  daily in particular is now much easier to finish. Nothing about the reward itself changed — there
  are simply more heads carrying one, which is a balance question worth a look once it has been
  played.

  For anyone reading the internal match stats: **bounty *kills* per match now include bots, so that
  figure no longer moves with the human headcount the way it used to** and cannot be compared
  directly against matches before this release. Bounties *held* is still players only. Two comments
  in the code asserting the opposite have been corrected, since they were the reason the split
  existed.
